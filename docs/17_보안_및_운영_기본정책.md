# 보안 및 운영 기본 정책

이 문서는 `boilerplate-turborepo`를 기반으로 서비스를 개발하고 운영할 때 기본적으로 지켜야 할 보안 및 운영 원칙을 설명합니다.

이 문서의 목적은 특정 Cloud Provider나 배포 서비스의 설정 방법을 정의하는 것이 아닙니다.

다음과 같은 공통 원칙을 정의합니다.

```txt
Server / Client Boundary

Secret 관리

인증과 인가

외부 입력 Validation

Error 처리

Logging

Rate Limiting

Security Header

외부 서비스 연동

Database 보호

파일 업로드

운영 환경 검증
```

실제 프로젝트에서는 사용하는 배포 환경과 Infrastructure에 맞게 이 원칙을 구체적인 설정으로 구현합니다.

기본 방향:

```txt
Client는 신뢰하지 않는다.

외부 입력은 신뢰하지 않는다.

인증과 인가를 구분한다.

Secret은 Server에만 존재한다.

Business Permission은 Domain에서 판단한다.

민감정보를 Error와 Log에 남기지 않는다.

비용을 발생시키는 요청에는 남용 방지 수단을 검토한다.

보안 설정은 Application과 Infrastructure 양쪽에서 방어한다.

특정 Provider에만 의존하는 보안 구조를 만들지 않는다.
```

---

## 1. 보안은 여러 경계에서 적용한다

하나의 보안 기능만으로 Application 전체를 보호하려 하지 않습니다.

기본적으로 다음 경계를 각각 고려합니다.

```txt
Browser
  ↓
Network / Edge
  ↓
Application
  ↓
Authentication
  ↓
Authorization
  ↓
Domain
  ↓
Repository
  ↓
Database
  ↓
External Infrastructure
```

예를 들어 Rate Limiting이 존재한다고 해서 Server Action의 권한 검사가 없어도 되는 것이 아닙니다.

마찬가지로 관리자 Page가 UI에서 숨겨져 있다고 해서 관리자 권한 검사를 생략하지 않습니다.

각 경계는 서로 다른 책임을 가집니다.

---

# 2. Server / Client Boundary

보안상 가장 중요한 기본 원칙은 **Server에 있어야 할 값을 Client로 보내지 않는 것**입니다.

Client에 전달된 값은 사용자가 볼 수 있다고 가정합니다.

다음 위치의 코드는 Browser Bundle에 포함될 가능성이 있습니다.

```txt
Client Component

"use client" Module

Client에서 Import되는 Module

NEXT_PUBLIC_* 환경변수
```

따라서 Client 코드에는 다음 정보를 포함하지 않습니다.

```txt
Database Credential

Authentication Secret

OAuth Client Secret

Private API Key

Webhook Secret

Storage Secret

SMTP Credential

Encryption Key

Service Account Credential

Internal Admin Secret
```

---

## 3. Server-only 코드

Server에서만 실행되어야 하는 Module은 Server Boundary를 명확하게 유지합니다.

Domain의 Server Public API는 다음과 같이 구성할 수 있습니다.

```ts
import "server-only";
```

대표적인 Server-only 대상:

```txt
Domain Service

Repository

Database Client

Server Environment

Authentication Session 처리

Private Infrastructure Adapter

Secret을 사용하는 API Client
```

Client Component에서 Server-only Module을 직접 Import하지 않습니다.

---

# 4. Client에 전달하는 데이터 최소화

Server에서 조회한 객체 전체를 그대로 Client Component로 전달하지 않습니다.

필요한 값만 DTO 또는 명시적인 Props 형태로 전달합니다.

지양:

```txt
Database Row 전체
  ↓
Client Component
```

권장:

```txt
Database Row
  ↓
Domain Mapper
  ↓
Response DTO
  ↓
필요한 데이터만 Client
```

특히 다음 값은 UI에서 실제로 필요하지 않다면 전달하지 않습니다.

```txt
Password Hash

Token Hash

Internal Identifier

Private Metadata

IP Address

User Agent

Provider Secret

Internal Error Detail

Audit Metadata
```

---

# 5. 환경변수와 Secret

환경변수 관리 기준은 `06_환경변수.md`를 따릅니다.

보안상 핵심 원칙은 다음과 같습니다.

```txt
Secret은 Server Environment에 둔다.

Client에서 필요하지 않은 값에는 NEXT_PUBLIC_*를 사용하지 않는다.

Secret을 Source Code에 직접 작성하지 않는다.

실제 Secret을 Git에 Commit하지 않는다.

Example Env에는 실제 Secret을 넣지 않는다.
```

예:

```env
DATABASE_URL=
AUTH_SECRET=
STORAGE_API_TOKEN=
MAILER_API_KEY=
```

Example 파일에는 값의 형식이나 설명만 제공합니다.

---

# 6. `NEXT_PUBLIC_*`

`NEXT_PUBLIC_*` 환경변수는 Browser에 공개되는 값으로 취급합니다.

따라서:

```env
NEXT_PUBLIC_SOMETHING=
```

이라는 이름을 사용하는 순간 해당 값은 Secret이 아니어야 합니다.

다음과 같은 값을 넣지 않습니다.

```txt
API Secret

Private Token

Database URL

OAuth Client Secret

Webhook Secret

Encryption Key
```

Client에 공개할 필요가 없다면 Server Environment로 유지합니다.

---

# 7. Secret Rotation

운영 서비스에서는 Secret이 영구적인 값이라고 가정하지 않습니다.

다음과 같은 상황에서 Secret Rotation을 고려합니다.

```txt
Credential 노출 의심

퇴사자 또는 외부 작업자 접근 종료

외부 Provider Security Incident

Repository 또는 Log에 Secret 노출

정기적인 보안 정책
```

Secret을 변경했을 때 Application 전체를 수정해야 하는 구조보다 Environment 설정만 교체할 수 있는 구조를 유지합니다.

---

# 8. Secret을 Log에 출력하지 않는다

다음과 같은 코드를 작성하지 않습니다.

```ts
console.info(process.env);

console.info({
  databaseUrl,
  authSecret,
});
```

외부 API 요청 실패 시에도 Request Header 전체를 그대로 기록하지 않습니다.

특히:

```txt
Authorization

Cookie

Set-Cookie

API Key

Access Token

Refresh Token

Session Token

Webhook Secret
```

등이 Log에 포함되지 않도록 주의합니다.

---

# 9. 인증과 인가를 구분한다

Authentication과 Authorization은 서로 다른 문제입니다.

```txt
Authentication
  누구인가?

Authorization
  이 사용자가 이 행위를 할 수 있는가?
```

사용자가 로그인되어 있다는 사실만으로 특정 행위를 허용하지 않습니다.

예:

```txt
로그인됨
  ≠
관리자 권한 있음

주문 소유자임
  ≠
모든 주문 수정 가능

관리자임
  ≠
모든 Domain Rule 무시 가능
```

---

# 10. Authentication

Authentication은 사용자 또는 시스템의 Identity를 확인합니다.

대표적인 대상:

```txt
Session

OAuth

API Token

Webhook Signature

Internal Service Credential
```

인증 관련 공통 기능은 `@repo/auth`의 책임으로 유지합니다.

Application에서는 가능한 한 공통 Auth API를 사용합니다.

예:

```txt
requireUser

requireAdmin

Session Validation
```

실제 함수 이름은 현재 Auth Package의 Public API를 따릅니다.

---

# 11. Authorization

Business Authorization은 Domain 규칙으로 판단합니다.

예:

```txt
누가 이 주문을 취소할 수 있는가?

누가 이 콘텐츠를 수정할 수 있는가?

누가 이 문의에 답변할 수 있는가?

누가 이 환불을 승인할 수 있는가?
```

이 판단은 UI Visibility만으로 처리하지 않습니다.

예:

```txt
UI
  관리자에게만 버튼 표시

Domain
  실제 관리자 권한 다시 검증
```

두 단계 모두 필요할 수 있습니다.

UI는 사용자 경험을 위한 것이고 Domain Authorization은 보안을 위한 것입니다.

---

# 12. Client의 권한 값을 신뢰하지 않는다

다음과 같은 Client 입력을 신뢰하지 않습니다.

```txt
role=ADMIN

isAdmin=true

userId=<다른 사용자>

ownerId=<다른 사용자>

paymentProvider=TOSS
```

현재 사용자 Identity와 권한은 Server Session과 Server-side State에서 결정합니다.

예:

```txt
Client
  userId 전송

Server
  해당 userId를 현재 사용자 Identity로 신뢰
```

와 같은 구조를 만들지 않습니다.

가능하면 현재 사용자 ID 자체도 Session에서 결정합니다.

---

# 13. Object Ownership 검증

사용자가 특정 Resource ID를 알고 있다는 이유만으로 접근을 허용하지 않습니다.

예:

```txt
/orders/<orderId>

/questions/<questionId>

/addresses/<addressId>
```

Server에서는 다음을 함께 검증합니다.

```txt
Resource 존재 여부

현재 사용자 Identity

Resource Owner

현재 상태

필요한 Permission
```

단순히 ID로 조회한 뒤 반환하지 않습니다.

---

# 14. 관리자 권한

관리자 Route가 별도의 App이나 Route Group에 존재하더라도 Server에서 관리자 권한을 다시 확인합니다.

다음만으로 관리자 권한을 보장할 수 없습니다.

```txt
Admin Navigation에서만 링크 제공

Admin URL을 숨김

Client에서 role 확인

관리자 Component 조건부 Rendering
```

Server Boundary에서 Admin Authentication / Authorization을 수행합니다.

---

# 15. 외부 입력은 모두 신뢰하지 않는다

Application 외부에서 들어오는 모든 값은 Untrusted Input으로 취급합니다.

대표적인 입력:

```txt
FormData

JSON Request Body

Search Params

Route Params

Cookie

HTTP Header

Webhook Payload

File Upload

External API Response

Environment Variable

Database 외부에서 유입된 기존 데이터
```

입력 Source가 내부 UI라고 해서 신뢰하지 않습니다.

Browser Request는 사용자가 임의로 수정할 수 있습니다.

---

# 16. Validation 경계

구조적인 입력 Validation에는 Zod Schema를 사용합니다.

대표적인 대상:

```txt
Route Params

Search Params

Form Input

Request Payload

Configuration Input
```

예:

```ts
const result = UpdateUserProfileRequest.safeParse(input);
```

Validation 실패를 정상적인 입력 실패로 처리하고 Runtime Exception과 구분합니다.

---

# 17. Structural Validation과 Business Validation

두 종류의 Validation을 구분합니다.

Structural Validation:

```txt
UUID 형식인가?

문자열 길이가 맞는가?

Enum 값인가?

필수 필드가 존재하는가?

숫자 범위가 맞는가?
```

Domain Validation:

```txt
현재 주문 상태에서 취소할 수 있는가?

이미 사용된 Coupon인가?

현재 사용자가 수정할 권한이 있는가?

환불 가능한 수량이 남아 있는가?
```

구조:

```txt
Zod Schema
  Structural Validation

Domain Service / Permission / Rule
  Business Validation
```

Business Rule을 Zod Refinement 안에 과도하게 넣지 않습니다.

---

# 18. Validation은 Client에서 끝나지 않는다

Client Validation은 사용자 경험 개선을 위한 것입니다.

보안 Boundary가 아닙니다.

따라서:

```txt
Client Validation
  ↓
Server Validation
```

을 모두 사용할 수 있습니다.

Client에서 Schema Validation을 수행했다고 하더라도 Server에서 동일한 요청을 다시 검증합니다.

---

# 19. Search Params도 Validation한다

Search Params는 URL에 있으므로 안전한 값이라고 생각하지 않습니다.

예:

```txt
?page=-100

?limit=9999999

?sortKey=UNKNOWN

?userId=<arbitrary>
```

같은 요청이 들어올 수 있습니다.

Query Schema로:

```txt
Page

Limit

Sort Key

Sort Direction

Filter

Keyword
```

를 검증하고 정규화합니다.

---

# 20. ID Validation

Route 또는 Form에서 전달되는 Identifier는 형식을 검증합니다.

예:

```ts
UserIdParam;
OrderIdParam;
QuestionIdParam;
```

형식 검증 이후에도 Resource 존재 여부와 접근 권한은 별도로 확인합니다.

```txt
UUID가 유효함
  ≠
해당 Resource에 접근할 수 있음
```

---

# 21. SQL Injection

Database Query는 Prisma와 같은 Parameterized Query API를 기본으로 사용합니다.

사용자 입력을 직접 SQL 문자열에 연결하지 않습니다.

지양:

```txt
"... WHERE email = '" + email + "'"
```

Raw Query가 반드시 필요한 경우에도 Parameter Binding을 사용합니다.

Raw SQL 사용은 일반 Repository Query보다 더 엄격하게 검토합니다.

---

# 22. XSS

사용자 입력이나 외부 Content를 HTML로 Rendering할 때 주의합니다.

React의 일반적인 문자열 Rendering은 Escaping을 제공하지만 다음과 같은 기능은 별도 위험을 가집니다.

```txt
dangerouslySetInnerHTML

HTML Editor Output

Markdown의 Raw HTML

외부 HTML

사용자 작성 Rich Text
```

Raw HTML이 필요한 경우 Sanitization 정책을 별도로 적용합니다.

---

# 23. URL 입력

사용자 또는 외부 시스템이 URL을 입력할 수 있는 경우 형식을 검증합니다.

특히 Server가 해당 URL로 직접 요청을 수행한다면 SSRF를 고려해야 합니다.

다음과 같은 Target으로 Server Request가 전달되지 않도록 검토합니다.

```txt
localhost

127.0.0.1

Private Network

Cloud Metadata Endpoint

Internal Admin Service
```

단순 URL 형식 Validation만으로 SSRF를 막을 수 있다고 가정하지 않습니다.

---

# 24. Error 처리

예상 가능한 Business Failure와 예상하지 못한 Runtime Error를 구분합니다.

예:

```txt
NOT_FOUND

FORBIDDEN

INVALID_STATE

ALREADY_EXISTS

OUT_OF_STOCK
```

등은 Domain에서 예상 가능한 실패입니다.

반면:

```txt
Database Connection Failure

Provider Timeout

Programming Error

Unexpected Exception
```

등은 운영 Error입니다.

두 종류를 동일한 메시지로 Client에 노출하지 않습니다.

---

# 25. Client Error Message

Client에는 사용자가 행동을 결정하는 데 필요한 정보만 전달합니다.

예:

```txt
주문을 찾을 수 없습니다.

현재 상태에서는 주문을 취소할 수 없습니다.

입력한 정보를 다시 확인해 주세요.
```

다음과 같은 내부 정보는 노출하지 않습니다.

```txt
SQL

Stack Trace

Database Host

Table Name

Internal File Path

Environment Variable

Provider Credential

Detailed Infrastructure Error
```

---

# 26. Production Stack Trace

Production Response에 Stack Trace를 그대로 반환하지 않습니다.

Stack Trace는 운영 진단용 Log나 Error Tracking System에서 확인하고 Client에는 일반화된 메시지를 제공합니다.

예:

```txt
서버 처리 중 문제가 발생했습니다.
```

사용자에게 내부 구현 정보를 제공하지 않습니다.

---

# 27. Error Cause

내부적으로 Error Cause를 보존하는 것은 디버깅에 유용할 수 있습니다.

하지만 Error Object 전체를 Client Response나 Log에 그대로 Serialization하지 않습니다.

Error에 다음 데이터가 포함될 가능성을 고려합니다.

```txt
SQL Query

Credential

Request Payload

Header

File Path

Provider Response

Personal Information
```

---

# 28. Logging 기본 원칙

Log의 목적은 운영 상태를 파악하고 장애를 진단하는 것입니다.

Log 자체가 새로운 정보 유출 경로가 되어서는 안 됩니다.

권장:

```txt
이벤트 이름

관련 Resource ID

상태

오류 코드

소요 시간

필요한 최소 Context
```

예:

```ts
logger.error("order.cancel.failed", {
  orderId,
  errorCode,
});
```

---

# 29. Log에 기록하지 않는 정보

원칙적으로 다음 값은 그대로 기록하지 않습니다.

```txt
Password

Password Hash

Session Token

Access Token

Refresh Token

Authorization Header

Cookie 전체

API Secret

Database URL

OAuth Secret

Webhook Secret

Payment Credential
```

개인정보 역시 운영상 꼭 필요한 범위로 제한합니다.

예:

```txt
실명

이메일

전화번호

주소

IP Address

User Agent
```

운영상 필요하여 저장하는 경우에는 목적과 보관 정책을 별도로 검토합니다.

---

# 30. Request 전체 Logging

다음처럼 Request Object 전체를 무조건 Log에 남기지 않습니다.

```ts
logger.info("request", request);
```

Request에는 다음이 포함될 수 있습니다.

```txt
Cookie

Authorization

Form Input

Personal Information

File Metadata

Internal Header
```

필요한 값만 선택적으로 추출합니다.

---

# 31. FormData Logging

Server Action 오류를 확인하기 위해 `FormData` 전체를 Log에 출력하지 않습니다.

FormData에는 다음이 포함될 수 있습니다.

```txt
Password

Address

Phone Number

Personal Information

Private Message

File
```

가능하면:

```txt
Action Name
Resource ID
Error Code
```

등의 최소 Context만 남깁니다.

---

# 32. Rate Limiting

운영 환경에서는 요청 남용과 비용 증가를 방지하기 위해 Rate Limiting을 검토합니다.

특히 다음 Endpoint는 우선순위가 높습니다.

```txt
로그인

회원가입

비밀번호 또는 인증 관련 요청

Email 전송

SMS 전송

파일 업로드

결제 시작

주문 생성

문의 등록

검색 API

외부 Provider 호출

AI API

비용이 발생하는 API
```

모든 요청에 동일한 Rate Limit을 기계적으로 적용하지 않습니다.

---

# 33. Rate Limit 기준

Endpoint 성격에 따라 서로 다른 제한을 사용할 수 있습니다.

예:

```txt
일반 조회
  비교적 완화

인증
  엄격

결제
  엄격

파일 업로드
  엄격

외부 유료 API
  매우 엄격
```

Rate Limit 값은 실제 Traffic과 서비스 특성을 기준으로 조정합니다.

Boilerplate에서 임의의 숫자를 운영 정답으로 간주하지 않습니다.

---

# 34. Rate Limit Key

Rate Limiting의 식별 기준으로 다음을 검토할 수 있습니다.

```txt
User ID

Session ID

IP Address

API Key

Resource ID

User + Endpoint

IP + Endpoint
```

로그인 전 Request에는 User ID가 없을 수 있으므로 IP 등을 사용할 수 있습니다.

로그인 후에는 User Identity와 IP를 함께 고려할 수도 있습니다.

---

# 35. IP Address 신뢰

Proxy나 CDN 뒤에서 실행되는 Application에서는 Request Header의 IP 값을 무조건 신뢰하지 않습니다.

예:

```txt
X-Forwarded-For
```

는 Infrastructure 구성에 따라 Client가 조작할 가능성이 있습니다.

Trusted Proxy가 어떤 Header를 보장하는지 확인한 뒤 사용합니다.

---

# 36. In-memory Rate Limiter

다음과 같은 Process-local 구현:

```ts
const store = new Map();
```

은 개발 환경이나 단일 Process에서의 간단한 방어에 사용할 수 있습니다.

하지만 다중 Instance / Serverless 운영 환경에서는 Global Rate Limit을 보장하지 않습니다.

```txt
Instance A
  Map A

Instance B
  Map B

Instance C
  Map C
```

이므로 각각 별도의 Count를 가집니다.

따라서 운영 환경에서 정확한 분산 Rate Limiting이 필요하면 다음 중 하나를 검토합니다.

```txt
Shared Data Store

Distributed Rate Limiter

API Gateway

CDN / Edge Rate Limiting

WAF
```

특정 Provider의 기능을 Boilerplate의 필수 전제로 만들지는 않습니다.

---

# 37. Application Rate Limit과 Infrastructure Rate Limit

두 계층을 함께 사용할 수 있습니다.

```txt
Edge / WAF
  대량 Traffic 차단
  Bot / Abuse 완화

Application
  User / Resource / Use Case 단위 제한
```

Infrastructure Rate Limiting만으로 Business-specific 제한을 모두 해결하려 하지 않습니다.

반대로 Application Rate Limiter만으로 대규모 DDoS를 처리하려 하지 않습니다.

---

# 38. Rate Limit Response

Rate Limit에 걸린 요청은 일관된 Error Response를 제공합니다.

예:

```txt
TOO_MANY_REQUESTS
```

가능하다면 HTTP `429`를 사용합니다.

재시도 시점을 제공하는 경우 `Retry-After`와 같은 표준 Header도 검토할 수 있습니다.

---

# 39. 비용 보호

Serverless 또는 Usage-based Infrastructure에서는 보안과 비용 보호를 함께 고려합니다.

다음과 같은 요청은 공격이 아니더라도 비용을 증가시킬 수 있습니다.

```txt
과도한 Crawling

무한 Retry

검색 반복

Image Processing 반복

파일 업로드 반복

Email 반복

External API 반복

DB-intensive Query 반복
```

다음 수단을 조합합니다.

```txt
Rate Limiting

Caching

Pagination

Maximum Limit

Request Size Limit

Timeout

Queue

Idempotency

Infrastructure Protection
```

---

# 40. Pagination Limit

목록 API에서 Client가 무제한 크기를 요청하지 못하도록 합니다.

예:

```txt
limit=1000000
```

같은 요청을 허용하지 않습니다.

Schema 수준에서 최대값을 제한합니다.

예:

```ts
z.coerce.number().int().min(1).max(100);
```

실제 최대값은 Use Case에 맞게 결정합니다.

---

# 41. Request Body Size

큰 Request Body는 Memory와 Network 비용을 증가시킬 수 있습니다.

특히 다음 요청은 크기 제한을 검토합니다.

```txt
JSON Payload

File Upload

Rich Text

Image

CSV

Import File
```

Application과 Reverse Proxy / Platform의 제한을 함께 확인합니다.

---

# 42. Security Header

운영 환경에서는 Browser Security Header를 검토합니다.

대표적인 항목:

```txt
Content-Security-Policy

Strict-Transport-Security

X-Content-Type-Options

Referrer-Policy

Permissions-Policy
```

Frame Embedding 정책이 필요하다면:

```txt
Content-Security-Policy: frame-ancestors
```

또는 호환성을 고려한 관련 Header를 검토할 수 있습니다.

---

# 43. Content Security Policy

CSP는 XSS 및 외부 Resource 실행 위험을 줄이는 중요한 Browser 정책입니다.

다음 Source를 검토합니다.

```txt
script-src

style-src

img-src

font-src

connect-src

frame-src

frame-ancestors
```

단순히 모든 Source에:

```txt
*
```

를 허용하는 방식은 피합니다.

하지만 CSP는 사용하는 Analytics, OAuth, Payment, Image CDN 등에 따라 달라질 수 있으므로 Boilerplate에서 특정 Policy를 모든 프로젝트의 정답으로 고정하지 않습니다.

---

# 44. HSTS

HTTPS 운영 환경에서는 HSTS 적용을 검토합니다.

```txt
Strict-Transport-Security
```

다만 HSTS는 Browser에 장기간 영향을 주는 정책이므로 HTTPS 구성이 완전히 준비된 운영 Domain에서 적용합니다.

개발 환경에 무조건 적용하지 않습니다.

---

# 45. MIME Sniffing 방지

다음을 검토합니다.

```txt
X-Content-Type-Options: nosniff
```

Browser가 선언된 Content-Type을 임의로 다른 형식으로 해석하는 위험을 줄입니다.

---

# 46. Referrer Policy

외부 사이트로 이동할 때 URL 정보가 과도하게 전달되지 않도록 Referrer Policy를 검토합니다.

예:

```txt
strict-origin-when-cross-origin
```

실제 정책은 서비스 요구사항에 맞게 결정합니다.

---

# 47. Permissions Policy

사용하지 않는 Browser 기능을 제한할 수 있습니다.

예:

```txt
camera

microphone

geolocation
```

서비스에서 사용하지 않는 기능은 허용 범위를 최소화하는 것을 검토합니다.

---

# 48. Header 적용 위치

Security Header는 다음 중 적절한 계층에서 적용할 수 있습니다.

```txt
Application Config

Reverse Proxy

CDN

Load Balancer

Edge Network

WAF
```

어느 한 Provider의 설정만을 Architecture 필수 조건으로 만들지 않습니다.

Application에서 관리하는 것이 일관적인 Header는 Application Config에 둘 수 있고, Infrastructure 전체에 적용해야 하는 정책은 외부 Layer에서 관리할 수 있습니다.

---

# 49. CORS

CORS는 필요한 Endpoint에만 명시적으로 설정합니다.

특별한 요구가 없다면 외부 Origin에 API 접근을 넓게 허용하지 않습니다.

지양:

```txt
Access-Control-Allow-Origin: *
```

특히 Credential을 사용하는 Endpoint에서는 허용 Origin을 명확하게 관리합니다.

CORS를 Authorization 수단으로 사용하지 않습니다.

CORS는 Browser 정책이며 Server-side Request를 차단하는 보안 경계가 아닙니다.

---

# 50. CSRF

Cookie 기반 Authentication을 사용하는 State-changing Request에서는 CSRF 위험을 검토합니다.

Framework가 제공하는 보호 장치가 있더라도 다음 요소를 함께 확인합니다.

```txt
Cookie SameSite

Secure Cookie

Origin 검증

Request Method

Framework의 Server Action 보호 방식
```

특히 직접 구현한 Route Handler나 외부 API Endpoint가 있다면 별도로 검토합니다.

---

# 51. Cookie

Authentication Cookie에는 가능한 한 다음 속성을 검토합니다.

```txt
HttpOnly

Secure

SameSite

Path

Expires / Max-Age
```

Session Token을 JavaScript에서 읽을 필요가 없다면 `HttpOnly`를 사용합니다.

Production HTTPS 환경에서는 `Secure`를 사용합니다.

Cookie 범위를 불필요하게 넓히지 않습니다.

---

# 52. Session

Session은 다음 특성을 고려합니다.

```txt
충분한 Entropy

만료 시간

Server-side Validation

Revocation

Rotation

탈취 대응
```

Session Identifier 자체를 Database에 평문으로 영구 저장하는 것보다 필요한 경우 Hash 형태로 관리하는 방식을 검토합니다.

---

# 53. OAuth

OAuth 로그인에서는 Provider가 반환한 사용자 정보만으로 Business Authorization을 결정하지 않습니다.

예:

```txt
Google 인증 성공
  ≠
Admin 권한
```

OAuth는 Identity 확인 수단이며 Application Role과 Permission은 서비스 내부 정책으로 관리합니다.

---

# 54. Webhook

Webhook Endpoint는 인터넷에 공개되는 경우가 많으므로 일반 Client API와 동일하게 신뢰하지 않습니다.

가능하면 Provider가 제공하는 다음 검증을 사용합니다.

```txt
Signature

Secret

Timestamp

Event ID
```

Webhook Payload만 보고 이벤트를 신뢰하지 않습니다.

---

# 55. Webhook 멱등성

외부 Provider는 같은 Webhook을 여러 번 전송할 수 있습니다.

따라서 중요한 상태 변경에서는 Idempotency를 고려합니다.

예:

```txt
Payment Webhook Event ID

Provider Event ID

Unique Constraint

Processed Event Record
```

같은 Event가 여러 번 도착해도 상태가 중복 변경되지 않도록 합니다.

---

# 56. 외부 API

외부 API Response 역시 완전히 신뢰하지 않습니다.

다음 항목을 고려합니다.

```txt
Response Validation

Timeout

Retry

Rate Limit

Error Mapping

Unexpected Response

Provider Outage
```

외부 Provider Error를 그대로 Domain Error나 Client Response로 노출하지 않습니다.

---

# 57. Timeout

외부 Network Request는 무한히 기다리지 않도록 Timeout을 검토합니다.

대상:

```txt
Payment

Email

Storage

Analytics

External REST API

AI API
```

Provider 장애가 Application 전체 Request를 장시간 점유하지 않도록 합니다.

---

# 58. Retry

Retry는 모든 Error에 무조건 적용하지 않습니다.

Retry가 적합한 경우:

```txt
일시적 Network Failure

일부 5xx

일시적 Provider Unavailable
```

Retry가 위험한 경우:

```txt
Payment 생성

주문 생성

Email 발송

중복 Side Effect가 가능한 요청
```

Side Effect가 있는 작업은 Idempotency와 함께 설계합니다.

---

# 59. 파일 업로드

파일 업로드는 다음을 검증합니다.

```txt
File Size

MIME Type

Extension

허용 Format

업로드 개수

사용자 권한
```

Client가 보내는 MIME Type만으로 파일을 완전히 신뢰하지 않습니다.

가능하면 Storage 또는 Image Provider의 검증 기능도 함께 사용합니다.

---

# 60. Upload Credential

Client Direct Upload를 사용하는 경우 Client에 Storage Master Credential을 전달하지 않습니다.

일반적인 구조:

```txt
Client
  ↓
Server에서 제한된 Upload Authorization 발급
  ↓
Client가 Storage Provider로 직접 Upload
```

Upload Token에는 가능한 한:

```txt
짧은 만료 시간

업로드 범위 제한

파일 크기 제한

허용 Format
```

등을 적용합니다.

---

# 61. 업로드 파일명

사용자가 제공한 파일명을 Server Path에 그대로 사용하지 않습니다.

파일명에는 다음과 같은 위험이 있을 수 있습니다.

```txt
Path Traversal

Control Character

Unexpected Extension

충돌
```

Storage Key는 Server에서 안전하게 생성하는 것을 권장합니다.

---

# 62. Database Credential

Database Credential은 Server에서만 사용합니다.

Client에 Database Connection String을 전달하지 않습니다.

Database User도 가능한 한 필요한 권한만 가집니다.

운영 환경에서는 개발용 또는 관리자 Credential을 Application Runtime Credential로 그대로 사용하지 않는 방식을 검토합니다.

---

# 63. Database Query

Application에서 무제한 Query를 만들지 않습니다.

다음 항목을 검토합니다.

```txt
Pagination

Index

Maximum Result Size

N+1

Expensive Sort

Unbounded Search

Transaction 범위
```

보안 공격이 아니더라도 과도한 Query는 운영 비용과 장애를 발생시킬 수 있습니다.

---

# 64. Transaction

여러 Persistence 변경이 하나의 Business Operation을 구성한다면 Transaction을 검토합니다.

예:

```txt
Order 생성
+
Inventory 차감
+
Payment Record 생성
```

중간 상태가 남아서는 안 되는 작업은 Transaction Boundary를 Domain Service 수준에서 결정합니다.

Database Transaction 정책은 `07_데이터베이스.md`를 따릅니다.

---

# 65. Sensitive Data 최소 수집

서비스에 필요하지 않은 개인정보는 수집하지 않습니다.

수집 여부를 판단할 때 다음을 고려합니다.

```txt
실제 Business Requirement가 있는가?

운영에 반드시 필요한가?

보관 기간은 얼마인가?

삭제가 가능한가?

누가 접근할 수 있는가?
```

필요하지 않은 개인정보를 "나중에 쓸 수도 있다"는 이유로 저장하지 않습니다.

---

# 66. Sensitive Data 보관

개인정보나 중요한 운영 정보에는 다음 정책을 검토합니다.

```txt
보관 기간

삭제 정책

접근 권한

Audit

Backup

Encryption
```

구체적인 개인정보 처리 정책은 실제 서비스와 법률 요구사항에 따라 별도로 정의합니다.

Boilerplate는 특정 서비스의 법적 보관 기간을 고정하지 않습니다.

---

# 67. Audit Log

관리자나 시스템의 중요한 상태 변경은 Audit Log 대상이 될 수 있습니다.

예:

```txt
회원 차단

권한 변경

주문 상태 강제 변경

환불 승인

약관 발행

중요 설정 변경
```

Audit Log에는 다음과 같은 Context를 고려합니다.

```txt
누가

언제

무엇을

어떤 Resource에

어떤 행위를 했는가
```

그러나 Audit Log에도 Secret 자체를 저장하지 않습니다.

---

# 68. 운영 Logging과 Audit Log를 구분한다

두 로그의 목적은 다릅니다.

```txt
Operational Log
  장애와 시스템 상태 진단

Audit Log
  중요한 행위 이력 추적
```

일반 Error Log를 Audit Log 대용으로 사용하지 않습니다.

반대로 모든 Application Event를 Audit Log로 저장하지 않습니다.

---

# 69. Dependency 보안

외부 Package는 Application의 Supply Chain 일부입니다.

다음을 검토합니다.

```txt
불필요한 Dependency 제거

신뢰할 수 없는 Package 사용 최소화

Lockfile 유지

Dependency Update

Security Advisory 확인
```

기능 하나를 위해 지나치게 큰 Dependency를 추가하지 않습니다.

---

# 70. Build Script 보안

Package 설치 과정에서 실행되는 Build Script는 임의 Code Execution 가능성이 있습니다.

pnpm의 Build Dependency 허용 정책을 사용하는 경우 실제 필요한 Package만 허용합니다.

새로운 Dependency가 Postinstall 또는 Build Script 실행을 요구한다면 이유를 확인한 뒤 허용합니다.

---

# 71. Production Environment

Production Environment는 개발 환경과 분리합니다.

다음 값이 동일하지 않도록 검토합니다.

```txt
Database

Storage

OAuth Redirect URL

Application URL

API Credential

Mailer

External Provider
```

개발 환경의 테스트 Credential을 Production에서 사용하지 않습니다.

---

# 72. Test Environment

Test에서는 Production Database나 Production Provider를 사용하지 않습니다.

특히 Integration / E2E Test는 데이터를 생성하거나 삭제할 수 있으므로 별도 환경을 사용합니다.

```txt
Development

Test

E2E

Production
```

환경을 가능한 한 분리합니다.

---

# 73. Seed

Development / Test Seed가 Production에서 실수로 실행되지 않도록 환경을 구분합니다.

Seed Script에는 다음 데이터가 포함될 수 있습니다.

```txt
Test User

Admin User

Fixture

Fake Product

Test Order
```

운영 환경에 들어가면 안 되는 데이터가 무엇인지 검토합니다.

---

# 74. Backup과 Recovery

운영 Database나 Storage를 사용하는 프로젝트에서는 Backup 여부만 확인하는 것으로 끝내지 않습니다.

다음을 함께 고려합니다.

```txt
Backup 존재

Backup 주기

보관 기간

Restore 가능 여부

복구 절차
```

Backup이 존재하더라도 실제 Restore 방법을 모르면 운영상 충분하지 않습니다.

이 부분은 사용하는 Infrastructure Provider에 맞게 구성합니다.

---

# 75. Monitoring

운영 환경에서는 최소한 다음 상태를 관찰할 수 있어야 합니다.

```txt
Application Error

HTTP Error Rate

Latency
```

```txt
Request Count

Database Usage

Bandwidth

Storage

External API Usage
```

특정 Observability Provider를 Boilerplate 필수 조건으로 두지 않습니다.

# 76. Alert

Monitoring 데이터가 존재하는 것만으로 충분하지 않을 수 있습니다.

심각한 상태에 대해서는 Alert를 검토합니다.

예:

```txt
Error Rate 급증

Database Connection Failure

Payment Failure 급증

Webhook 처리 실패

Storage Failure

비정상 Traffic 증가

비용 급증
```

모든 Warning을 Alert로 만들면 Noise가 증가하므로 운영에 실제 대응이 필요한 항목을 선택합니다.

# 77. Health Check

Infrastructure가 필요로 하는 경우 Application Health Check를 제공할 수 있습니다.

Health Check에서는 Secret이나 내부 상세 정보를 노출하지 않습니다.

예:

```json
{
  "status": "ok"
}
```

정도의 최소 응답을 사용할 수 있습니다.

Database나 외부 Provider 상태까지 확인하는 Deep Health Check가 필요한지는 운영 환경에 따라 결정합니다.

```txt
Secret

Signature

허용 Method

Logging
```

URL이 알려지지 않을 것이라는 사실을 인증 수단으로 사용하지 않습니다.

# 80. Search Engine 및 Crawler


```txt
WAF

Bot Management

Authentication

Pagination
```

단순 User-Agent 차단만으로 신뢰할 수 있는 Bot 방어가 된다고 가정하지 않습니다.

다음은 보안 수단으로 간주하지 않습니다.

# 83. Fail Closed

권한이나 보안 판단이 불확실할 때 기본적으로 허용하는 구조를 피합니다.

예:

```txt
Permission 정보 없음
  → 허용
```

보다:

```txt
Permission 확인 성공
  → 허용

확인 실패
  → 거부
```

를 기본으로 합니다.

# 84. 최소 권한

사용자, Application, Database, 외부 API Credential 모두 필요한 권한만 부여하는 것을 원칙으로 합니다.

예:

```txt

  → Write 권한을 주지 않음

Storage Upload만 필요
  → 전체 Storage 관리 권한을 주지 않음

Application DB User
  → Infrastructure Admin 권한을 주지 않음
```

# 95. 핵심 원칙

```txt
Client는 신뢰하지 않는다.

외부 입력은 신뢰하지 않는다.

Secret은 Server에만 둔다.

NEXT_PUBLIC_* 값은 공개 정보로 취급한다.

Client에 필요하지 않은 데이터를 전달하지 않는다.

Server-only Module의 Boundary를 명확하게 유지한다.

Authentication과 Authorization을 구분한다.

로그인 여부만으로 Business Permission을 판단하지 않는다.

현재 사용자 Identity는 Server에서 결정한다.

Resource ID를 알고 있다는 이유만으로 접근을 허용하지 않는다.

UI에서 버튼을 숨기는 것을 Authorization으로 간주하지 않는다.

외부 입력은 Server에서 다시 Validation한다.

Structural Validation과 Business Validation을 구분한다.

Business Rule은 Domain에서 판단한다.

Search Params와 Route Params도 외부 입력이다.

Error Response에 내부 구현 정보를 노출하지 않는다.

Production Stack Trace를 Client에 반환하지 않는다.

Log에 Secret, Token, Cookie를 기록하지 않는다.

Request나 FormData 전체를 무조건 Logging하지 않는다.

Rate Limiting은 Endpoint의 비용과 위험에 따라 적용한다.

Process-local In-memory Rate Limiter를 분산 운영용 Rate Limiter로 간주하지 않는다.

대규모 Traffic 방어는 Infrastructure Layer와 함께 처리한다.

목록 Query에는 적절한 최대 Limit을 둔다.

Security Header는 운영 환경에서 검토한다.

CORS를 Authorization으로 사용하지 않는다.

Cookie 기반 Mutation에서는 CSRF 위험을 검토한다.

Webhook은 Signature와 Idempotency를 검토한다.

외부 API에는 Validation, Timeout, Error Mapping을 적용한다.

Side Effect Retry에는 Idempotency를 고려한다.

파일 업로드에는 크기, 형식, 권한 제한을 적용한다.

Storage Master Credential을 Client에 전달하지 않는다.

Database Credential은 Server에서만 사용한다.

운영 Database와 Test Database를 분리한다.

개인정보는 필요한 범위만 수집한다.

Audit Log와 Operational Log의 목적을 구분한다.

Application Credential에는 최소 권한을 부여한다.

Production 환경에서는 Backup과 Restore 가능성을 확인한다.

운영 서비스에는 Error와 주요 Resource 상태를 관찰할 수 있는 수단을 마련한다.

보안 기능을 특정 Hosting Provider 하나에 종속시키지 않는다.

Application Security와 Infrastructure Security를 함께 적용한다.

Boilerplate는 보안의 최종 완성본이 아니라 안전한 기본 구조와 검토 기준을 제공한다.
```
