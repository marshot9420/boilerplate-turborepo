# 보안 및 운영 기본 정책

이 문서는 `boilerplate-turborepo`를 기반으로 서비스를 개발하고 운영할 때 기본적으로 지켜야 하는 보안 및 운영 원칙을 설명합니다.

특정 Cloud Provider나 Hosting Platform의 설정 방법을 정의하는 문서가 아닙니다.

Boilerplate 수준에서는 다음과 같은 공통 기준을 제공합니다.

```txt
Server / Client Boundary

Secret 관리

Authentication / Authorization

외부 입력 Validation

Error / Logging

Rate Limiting과 비용 보호

Security Header와 Browser Security

외부 서비스 연동

파일 업로드

Database와 운영 환경

Monitoring / Backup / Audit
```

실제 프로젝트에서는 서비스의 데이터, 사용자 규모, 비용 구조, 외부 Provider, 운영 국가와 법적 요구사항에 따라 정책을 강화합니다.

기본 원칙:

```txt
Client는 신뢰하지 않는다.

외부 입력은 신뢰하지 않는다.

Secret은 Server에만 둔다.

Authentication과 Authorization을 구분한다.

Business Permission은 Domain에서 판단한다.

민감정보를 Client Response나 Log에 노출하지 않는다.

비용을 발생시키는 요청에는 남용 방지 수단을 검토한다.

Application과 Infrastructure 양쪽에서 보안을 적용한다.

특정 Provider 하나에 의존하는 보안 구조를 만들지 않는다.
```

---

## 1. 여러 경계에서 방어한다

Application Security를 하나의 기능에 의존하지 않습니다.

기본적으로 다음 경계를 각각 고려합니다.

```txt
Browser
  ↓
Network / Edge
  ↓
Application
  ↓
Authentication
  ↓
Authorization
  ↓
Domain
  ↓
Repository
  ↓
Database
  ↓
External Infrastructure
```

예:

```txt
Rate Limiting이 있다.
  ≠
Authorization을 생략해도 된다.

Admin UI에서 버튼을 숨긴다.
  ≠
Admin Permission이 보장된다.

CORS를 설정했다.
  ≠
Server Authorization이 된다.
```

각 보안 기능은 서로 다른 책임을 가집니다.

---

## 2. Server / Client Boundary

Client에 전달된 값은 사용자가 볼 수 있다고 가정합니다.

다음과 같은 값은 Client에 포함하지 않습니다.

```txt
Database Credential

Authentication Secret

OAuth Client Secret

Private API Key

Webhook Secret

Storage Secret

SMTP Credential

Encryption Key

Service Account Credential
```

다음 영역은 Browser에 포함될 가능성이 있습니다.

```txt
Client Component

"use client" Module

Client에서 Import되는 Module

NEXT_PUBLIC_* 환경변수
```

Server 전용 Module은 Server Boundary를 명확하게 유지합니다.

예:

```ts
import "server-only";
```

대표적인 Server-only 대상:

```txt
Domain Service

Repository

Database Client

Server Environment

Session 처리

Private Infrastructure Adapter

Secret을 사용하는 API Client
```

Client Component에서 Server-only Module을 Import하지 않습니다.

---

## 3. Client에 필요한 데이터만 전달한다

Server에서 조회한 Database Row 전체를 그대로 Client에 전달하지 않습니다.

권장 흐름:

```txt
Database
  ↓
Repository
  ↓
Domain Mapper
  ↓
Response DTO
  ↓
필요한 데이터만 Client
```

특히 UI에서 필요하지 않다면 다음과 같은 정보는 전달하지 않습니다.

```txt
Password Hash

Token Hash

Private Metadata

IP Address

User Agent

Provider Secret

Internal Error Detail

Audit Metadata
```

Client / Server 구조의 일반 기준은 `10_앱_구조.md`를 따릅니다.

---

## 4. Environment와 Secret

환경변수 관리 기준은 `06_환경변수.md`를 따릅니다.

보안상 핵심 원칙:

```txt
Secret은 Server Environment에 둔다.

Secret을 Source Code에 작성하지 않는다.

실제 Secret을 Git에 Commit하지 않는다.

Example Env에는 실제 Secret을 넣지 않는다.

NEXT_PUBLIC_* 값은 공개 정보로 취급한다.
```

따라서 다음 값에 `NEXT_PUBLIC_*`를 사용하지 않습니다.

```txt
Private Token

Database URL

OAuth Client Secret

Webhook Secret

Encryption Key

Private API Key
```

Secret이 노출되었거나 접근 권한이 변경된 경우 Rotation 가능성을 고려합니다.

Log에도 Secret을 남기지 않습니다.

---

## 5. Authentication과 Authorization

두 개념을 구분합니다.

```txt
Authentication
  누구인가?

Authorization
  이 사용자가 이 행위를 할 수 있는가?
```

로그인되어 있다는 사실만으로 특정 Business Action을 허용하지 않습니다.

예:

```txt
로그인됨
  ≠
관리자임

관리자임
  ≠
모든 Domain Rule을 무시할 수 있음

Resource ID를 알고 있음
  ≠
해당 Resource에 접근할 수 있음
```

인증 관련 공통 기능은 `@repo/auth`의 책임으로 유지합니다.

Business Authorization은 Domain의 Permission / Rule에서 판단합니다.

구체적인 역할은 `08_도메인_레이어.md`를 따릅니다.

---

## 6. Client가 전달한 Identity나 Permission을 신뢰하지 않는다

다음과 같은 Client 입력을 권한 판단의 근거로 사용하지 않습니다.

```txt
role=ADMIN

isAdmin=true

userId=<arbitrary>

ownerId=<arbitrary>

paymentProvider=<arbitrary>
```

현재 사용자 Identity와 권한은 Server Session과 Server-side State에서 결정합니다.

가능하면 현재 사용자 ID 역시 Client Input이 아니라 Session에서 가져옵니다.

Resource 접근 시 다음을 함께 확인합니다.

```txt
Resource 존재 여부

현재 사용자

Resource Owner

현재 Resource 상태

필요한 Permission
```

UI에서 버튼이나 Route를 숨기는 것은 사용자 경험을 위한 것이며 보안 Boundary가 아닙니다.

---

## 7. 외부 입력 Validation

Application 외부에서 들어오는 값은 모두 신뢰하지 않습니다.

대표적인 입력:

```txt
FormData

JSON Body

Search Params

Route Params

Cookie

HTTP Header

Webhook Payload

File Upload

External API Response

Environment Variable
```

구조적 Validation에는 Zod Schema를 사용합니다.

```txt
UUID 형식

문자열 길이

Enum

필수 필드

숫자 범위

Pagination Limit
```

Business Validation은 Domain에서 처리합니다.

```txt
Zod Schema
  Structural Validation

Domain Service / Permission / Rule
  Business Validation
```

Client Validation은 사용자 경험을 위한 것이므로 Server Validation을 대체하지 않습니다.

Server Action 기준은 `09_Server_Actions.md`를 따릅니다.

---

## 8. 일반적인 입력 공격을 고려한다

Boilerplate에서 특정 보안 Library나 구현을 강제하지는 않지만 다음 위험을 고려합니다.

```txt
SQL Injection
  사용자 입력을 SQL 문자열에 직접 연결하지 않는다.
  Raw SQL이 필요하면 Parameter Binding을 사용한다.

XSS
  Raw HTML Rendering은 별도 Sanitization을 검토한다.

SSRF
  Server가 사용자 제공 URL로 요청하는 경우
  Private Network나 Metadata Endpoint 접근을 검토한다.

Path Traversal
  사용자 파일명을 Server Path나 Storage Key로 그대로 사용하지 않는다.
```

Framework나 ORM이 기본 보호를 제공하더라도 보호 범위를 이해하고 사용합니다.

---

## 9. Error Response

예상 가능한 Business Failure와 예상하지 못한 Runtime Error를 구분합니다.

예상 가능한 실패:

```txt
NOT_FOUND
FORBIDDEN
INVALID_STATE
ALREADY_EXISTS
OUT_OF_STOCK
```

운영 오류:

```txt
Database Connection Failure

Provider Timeout

Unexpected Exception

Programming Error
```

Client에는 사용자가 행동을 결정하는 데 필요한 정보만 전달합니다.

다음과 같은 내부 정보는 Production Response에 노출하지 않습니다.

```txt
Stack Trace

SQL

Database Host

Table Name

Internal File Path

Environment Variable

Provider Credential

Infrastructure Error Detail
```

Error 처리 구조는 Domain의 Result / Error 정책과 함께 사용합니다.

---

## 10. Logging

Log는 운영 상태와 장애를 확인하기 위한 수단이며 새로운 정보 유출 경로가 되어서는 안 됩니다.

권장 Context:

```txt
Event Name

Resource ID

Error Code

Status

Latency

필요한 최소 Context
```

다음 정보는 그대로 기록하지 않습니다.

```txt
Password

Password Hash

Session Token

Access Token

Refresh Token

Authorization Header

Cookie 전체

API Secret

Database URL

OAuth Secret

Webhook Secret

Payment Credential
```

개인정보도 운영상 필요한 최소 범위로 제한합니다.

Request, Error Object, FormData 전체를 무조건 Logging하지 않습니다.

필요한 값만 선택적으로 추출합니다.

---

## 11. Rate Limiting과 비용 보호

운영 환경에서는 요청 남용과 비용 증가 가능성을 검토합니다.

우선적으로 고려할 수 있는 대상:

```txt
인증 요청

Email / SMS

파일 업로드

결제

주문 생성

검색

외부 API 호출

AI API

비용이 발생하는 작업
```

모든 Endpoint에 동일한 Limit을 적용하지 않습니다.

Rate Limit은 다음과 같은 기준을 조합할 수 있습니다.

```txt
User ID

Session

IP

API Key

Endpoint

Resource
```

실제 Limit 값은 서비스 Traffic과 비용 구조에 따라 결정합니다.

---

## 12. In-memory Rate Limiter의 한계

Process-local 구현:

```ts
const store = new Map();
```

은 개발 환경이나 단일 Process에서는 사용할 수 있지만 다중 Instance 또는 Serverless 환경의 Global Rate Limit을 보장하지 않습니다.

```txt
Instance A
  Store A

Instance B
  Store B
```

정확한 분산 Rate Limit이 필요하다면 다음 Capability를 검토합니다.

```txt
Shared Store

Distributed Rate Limiter

API Gateway

CDN / Edge Rate Limiting

WAF
```

특정 Provider를 Boilerplate 필수 조건으로 두지 않습니다.

Application과 Infrastructure의 Rate Limiting은 서로 보완적으로 사용할 수 있습니다.

```txt
Infrastructure
  대량 Traffic / Bot / Abuse 완화

Application
  User / Resource / Use Case 단위 정책
```

---

## 13. Resource 사용량을 제한한다

보안 공격이 아니더라도 과도한 요청은 운영 비용과 장애를 발생시킬 수 있습니다.

다음을 검토합니다.

```txt
Pagination Maximum

Request Body Size

File Size

Upload Count

Timeout

Caching

Query Cost

Retry 횟수

Idempotency
```

예를 들어 목록 요청에서 Client가 무제한 결과를 요청하지 못하도록 Query Schema에 최대값을 둡니다.

구체적인 값은 Use Case에 따라 결정합니다.

## 14. Browser Security

운영 환경에서는 다음 Security Header를 검토합니다.

```txt
Content-Security-Policy

Strict-Transport-Security

X-Content-Type-Options

Referrer-Policy

Permissions-Policy
```

CSP는 서비스에서 실제 사용하는:

```txt
Script

Style

Image

Font

API

Frame
```

Source를 기준으로 구성합니다.

특정 CSP 값을 Boilerplate의 고정 정답으로 두지 않습니다.

Header는 다음 위치 중 적절한 계층에서 적용할 수 있습니다.

```txt
Application

Reverse Proxy

CDN

Load Balancer

Edge

WAF
```

---

## 15. CORS, CSRF, Cookie

CORS를 Authorization 수단으로 사용하지 않습니다.

Credential을 사용하는 외부 요청이 필요한 경우 허용 Origin을 명확하게 관리합니다.

Cookie 기반 Authentication에서 State-changing Request를 처리한다면 CSRF 위험을 검토합니다.

주요 확인 대상:

```txt
SameSite

Secure

HttpOnly

Origin

Request Method
```

Authentication Cookie는 가능한 한 필요한 범위만 가집니다.

```txt
HttpOnly

Secure

SameSite

Path

Expires / Max-Age
```

Session 정책은 `@repo/auth`와 실제 프로젝트 인증 요구사항에 맞게 구성합니다.

---

## 16. 외부 서비스 연동

외부 Provider의 Request와 Response를 신뢰하지 않습니다.

다음을 검토합니다.

```txt
Secret 관리

Response Validation

Timeout

Retry

Error Mapping

Rate Limit

Provider 장애
```

Provider Error를 그대로 Client Response에 노출하지 않습니다.

Retry는 중복 Side Effect 가능성을 고려합니다.

특히:

```txt
Payment

Order

Email

외부 Mutation
```

같은 작업은 Idempotency와 함께 설계합니다.

---

## 17. Webhook과 Scheduled Job

외부 Webhook은 가능한 경우 Provider가 제공하는 검증 기능을 사용합니다.

```txt
Signature

Secret

Timestamp

Event ID
```

중요한 상태 변경은 중복 Event를 고려하여 Idempotency를 적용합니다.

예:

```txt
Provider Event ID

Unique Constraint

Processed Event Record
```

Cron이나 Scheduled Job이 HTTP Endpoint 형태로 공개된다면 일반 Public URL이라고 가정하지 않습니다.

다음을 검토합니다.

```txt
Authorization

Secret / Signature

Method 제한

Rate Limit

Idempotency

Logging
```

URL을 숨기는 것을 Authentication으로 사용하지 않습니다.

---

## 18. 파일 업로드

파일 업로드에서는 다음을 검증합니다.

```txt
File Size

MIME Type

Extension

허용 Format

업로드 개수

사용자 권한
```

Client가 전달하는 MIME Type만으로 파일을 완전히 신뢰하지 않습니다.

Direct Upload를 사용하는 경우 Storage의 Master Credential을 Client에 전달하지 않습니다.

일반적인 구조:

```txt
Client
  ↓
Server에서 제한된 Upload Authorization 발급
  ↓
Storage Provider에 직접 Upload
```

Upload Authorization은 가능한 한 다음 범위를 제한합니다.

```txt
만료 시간

Upload Scope

File Size

Format
```

Storage Key는 Server에서 안전하게 생성하는 것을 권장합니다.

---

## 19. Database와 환경 분리

Database Credential은 Server에서만 사용합니다.

Application Runtime Credential에는 가능한 한 필요한 권한만 부여합니다.

Database Query에서는 다음을 고려합니다.

```txt
Pagination

Maximum Result Size

Index

N+1

Expensive Sort

Unbounded Search
```

Transaction 기준은 `07_데이터베이스.md`를 따릅니다.

운영 환경과 개발 / Test 환경도 분리합니다.

```txt
Development

Test

E2E

Production
```

Integration 또는 E2E Test에서 Production Database나 Production Credential을 사용하지 않습니다.

개발용 Seed가 Production에서 실수로 실행되지 않도록 환경을 구분합니다.

---

## 20. 개인정보와 민감정보

서비스에 필요하지 않은 개인정보를 미리 수집하지 않습니다.

수집하거나 보관할 때 다음을 검토합니다.

```txt
Business Requirement

접근 권한

보관 기간

삭제 정책

Encryption

Audit

Backup
```

구체적인 개인정보 처리와 법적 보관 기준은 실제 서비스의 운영 국가와 법률 요구사항에 따라 별도로 정의합니다.

Boilerplate에서 특정 법적 기준을 고정하지 않습니다.

---

## 21. Operational Log와 Audit Log

두 Log의 목적을 구분합니다.

```txt
Operational Log
  Application 상태와 장애 진단

Audit Log
  중요한 사용자 / 관리자 / 시스템 행위 추적
```

Audit 대상이 될 수 있는 예:

```txt
권한 변경

회원 차단

주문 상태 강제 변경

환불 승인

약관 발행

중요 운영 설정 변경
```

Audit Log에도 Secret을 저장하지 않습니다.

---

## 22. Dependency와 Supply Chain

외부 Package 역시 보안 Boundary의 일부입니다.

다음을 검토합니다.

```txt
불필요한 Dependency 제거

신뢰할 수 있는 Package 사용

Lockfile 유지

Dependency Update

Security Advisory
```

Package 설치 과정에서 실행되는 Build / Postinstall Script도 Code Execution 가능성이 있으므로 실제 필요한 Dependency만 허용합니다.

Dependency 관리 기준은 `02_기본설정.md`를 따릅니다.

---

## 23. 운영 환경

Production에서는 다음 항목을 검토합니다.

```txt
Environment 분리

TLS / HTTPS

Secret 관리

Backup

Restore 가능 여부

Monitoring

Alert

Error Tracking

Resource Usage

External Provider Failure
```

Backup은 존재 여부뿐 아니라 실제 Restore 가능 여부도 중요합니다.

Monitoring에서는 최소한 다음 상태를 관찰할 수 있어야 합니다.

```txt
Application Error

HTTP Error Rate

Latency

Database Error

External Provider Failure

Scheduled Job Failure

Resource / Cost Usage
```

특정 Observability, WAF, CDN, Secret Manager를 Boilerplate 필수 조건으로 두지 않습니다.

---

## 24. Admin과 비공개 Application

관리자 Application은 일반 사용자 Application보다 높은 권한을 가지므로 다음 항목을 우선적으로 검토합니다.

```txt
Authentication

Admin Authorization

중요 Mutation Permission

Session 만료

Audit

민감정보 표시 범위

Rate Limit
```

관리자 Route가 별도 App이나 Domain에 존재한다는 사실만으로 접근이 보호되지는 않습니다.

`robots.txt`나 `noindex` 역시 Search Engine 노출을 줄이는 정책이지 접근 통제 수단이 아닙니다.

## 25. Application과 Infrastructure의 책임

보안을 어느 한 계층에 모두 맡기지 않습니다.

Application에서 주로 다루는 책임:

```txt
Authentication

Authorization

Input Validation

Business Permission

DTO 제한

Use Case별 Rate Limit

Sensitive Logging 방지
```

Infrastructure에서 주로 다루는 책임:

```txt
TLS

DDoS 완화

WAF

Network Policy

Distributed Rate Limiting

Secret Storage

Backup

Infrastructure Monitoring
```

일부 책임은 양쪽에서 중첩될 수 있습니다.

중요한 것은 특정 Provider의 기능이 아니라 필요한 Security Capability를 명확하게 정의하는 것입니다.

## 26. 배포 전 기본 확인

Production 배포 전 최소한 다음을 확인합니다.

```txt
필수 Environment Variable이 설정되어 있는가?

Client에 Secret이 노출되지 않는가?

Authentication이 Server에서 검증되는가?

Authorization과 Ownership을 검증하는가?

외부 입력을 Server에서 Validation하는가?

Production Error에 내부 정보가 노출되지 않는가?

Log에 Secret이나 민감정보가 남지 않는가?

Database Schema / Migration이 준비되어 있는가?

Rate Limiting이 필요한 Endpoint를 검토했는가?

Security Header를 검토했는가?

외부 Provider의 Timeout / Failure를 처리하는가?

Backup과 Monitoring이 필요한 수준으로 준비되어 있는가?
```

실제 프로젝트의 위험도에 따라 별도의 배포 Checklist를 추가할 수 있습니다.

## 27. 기능 구현 시 보안 확인

새로운 기능을 구현할 때 모든 보안 항목을 기계적으로 적용하지는 않지만 해당되는 항목을 확인합니다.

### 조회

```txt
인증이 필요한가?

누가 어떤 데이터를 볼 수 있는가?

Ownership을 확인하는가?

민감정보가 Response에 포함되지 않는가?

Query Input이 Validation되는가?

조회량에 상한이 있는가?
```

### Mutation

```txt
누가 호출할 수 있는가?

Identity를 Server에서 결정하는가?

현재 상태에서 가능한 행위인가?

Input Schema가 존재하는가?

Business Rule을 Domain에서 검증하는가?

중복 호출에 안전한가?

Rate Limit이나 Audit가 필요한가?
```

### 외부 연동

```txt
Secret은 Server에 있는가?

Response를 검증하는가?

Timeout이 있는가?

Retry가 안전한가?

Webhook 검증이 필요한가?

Idempotency가 필요한가?

Provider Error를 그대로 노출하지 않는가?

비용 보호가 필요한가?
```

## 29. 핵심 원칙

```txt
Client는 신뢰하지 않는다.

외부 입력은 신뢰하지 않는다.

Secret은 Server에만 둔다.

NEXT_PUBLIC_* 값은 공개 정보로 취급한다.

Client에는 필요한 데이터만 전달한다.

Authentication과 Authorization을 구분한다.

현재 사용자 Identity와 권한은 Server에서 판단한다.

UI Visibility를 Authorization으로 간주하지 않는다.

외부 입력은 Server에서 다시 Validation한다.

Structural Validation과 Business Validation을 구분한다.

Business Permission과 Rule은 Domain에서 판단한다.

Production Error에 내부 구현 정보를 노출하지 않는다.

Log에 Secret, Token, Cookie를 기록하지 않는다.

Rate Limiting은 요청의 위험과 비용에 따라 적용한다.

Process-local Rate Limiter를 분산 운영용으로 간주하지 않는다.

대규모 Traffic 방어는 Infrastructure와 함께 처리한다.

외부 Provider에는 Validation, Timeout, Error Mapping을 적용한다.

Side Effect와 Webhook에는 Idempotency를 고려한다.

파일 업로드는 크기, 형식, 권한을 검증한다.

운영 환경과 Development / Test / E2E 환경을 분리한다.

개인정보는 필요한 범위만 수집한다.

Application Credential에는 최소 권한을 부여한다.

Backup은 Restore 가능 여부까지 확인한다.

운영 서비스는 Error와 주요 Resource 상태를 관찰할 수 있어야 한다.

Application Security와 Infrastructure Security를 함께 적용한다.

특정 Hosting Provider를 보안 Architecture의 필수 전제로 만들지 않는다.

Boilerplate는 보안의 최종 완성본이 아니라 안전한 기본 구조와 검토 기준을 제공한다.
```
