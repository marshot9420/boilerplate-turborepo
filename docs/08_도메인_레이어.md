# 도메인 레이어

이 문서는 `boilerplate-turborepo`에서 Domain Layer가 담당하는 책임과 구성 기준을 설명합니다.

Domain Layer의 목적은 파일 종류를 일정하게 맞추는 것이 아니라 **비즈니스 규칙과 Use Case를 앱, UI, Database 구현으로부터 분리하는 것**입니다.

기본 흐름은 다음과 같습니다.

```txt
App
 ↓
Domain Service
 ↓
Repository
 ↓
Database
```

Domain 내부에는 필요에 따라 다음 역할을 둘 수 있습니다.

```txt
constant
schema
DTO
error
mapper
permission
rule
service
client export
server export
```

이 목록은 모든 Domain이 반드시 구현해야 하는 고정 Template이 아닙니다.

```txt
역할이 필요할 때 추가한다.

작은 Domain은 작게 유지한다.

책임이 분화될 때 구조도 함께 분리한다.
```

Database Layer의 Persistence 책임은 `07_데이터베이스.md`, Server Action에서 Domain을 호출하는 방식은 `09_서버_액션.md`에서 설명합니다.

---

# 1. Domain의 역할

Domain Layer는 서비스가 무엇을 할 수 있고, 어떤 조건에서 허용되며, 어떤 결과를 반환하는지를 정의합니다.

대표적인 책임:

```txt
비즈니스 규칙

Use Case

입력 계약

출력 계약

도메인 오류

권한 판단

상태 전이 판단

비즈니스 계산

Persistence 결과와 외부 응답 사이의 변환
```

Domain은 다음 질문에 답합니다.

```txt
이 작업을 수행할 수 있는가?

현재 상태에서 이 변경이 허용되는가?

이 사용자가 이 Resource를 조작할 권한이 있는가?

입력 값의 의미가 비즈니스 규칙에 맞는가?

여러 Database 작업을 하나의 Transaction으로 묶어야 하는가?

성공하면 어떤 데이터를 반환하는가?

실패하면 어떤 Domain Error를 반환하는가?
```

---

# 2. Domain이 담당하지 않는 것

Domain은 다음 책임을 가지지 않습니다.

```txt
React Rendering

Toast

Dialog

FormData Parsing

URL Search Params 직접 처리

redirect

revalidatePath

Next.js Request / Response

Prisma Query 직접 작성

OAuth Provider SDK 호출

Mailer Provider 구현

Storage Provider 구현
```

예를 들어:

```txt
사용자 차단 가능 여부
→ Domain

차단 버튼 표시
→ App Entity / Feature

FormData에서 userId 읽기
→ Server Action

User Row Update
→ Repository

Prisma Query
→ Database
```

처럼 책임을 나눕니다.

---

# 3. Domain 구조는 고정 Template이 아니다

Domain을 추가했다고 다음 파일을 모두 생성하지 않습니다.

```txt
example.constant.ts
example.schema.ts
example.dto.ts
example.error.ts
example.mapper.ts
example.permission.ts
example.service.ts
```

각 파일은 **필요한 책임이 생겼을 때만** 추가합니다.

작은 Domain:

```txt
content/
├─ content.schema.ts
├─ content.dto.ts
├─ content.service.ts
├─ client.ts
└─ server.ts
```

조금 더 복잡한 Domain:

```txt
content/
├─ content.constant.ts
├─ content.schema.ts
├─ content.dto.ts
├─ content.error.ts
├─ content.mapper.ts
├─ content.permission.ts
├─ content.service.ts
├─ client.ts
└─ server.ts
```

Use Case와 Rule이 많아진 Domain:

```txt
content/
├─ content.constant.ts
├─ content.schema.ts
├─ content.dto.ts
├─ content.error.ts
├─ content.mapper.ts
├─ content.permission.ts
│
├─ rules/
│  ├─ can-publish-content.rule.ts
│  └─ can-edit-content.rule.ts
│
├─ services/
│  ├─ get-content.service.ts
│  ├─ create-content.service.ts
│  ├─ update-content.service.ts
│  └─ publish-content.service.ts
│
├─ client.ts
└─ server.ts
```

가장 복잡한 구조를 처음부터 만드는 것은 피합니다.

---

# 4. Domain 구조의 성장 원칙

Domain은 가능한 한 단순한 구조에서 시작합니다.

```txt
단일 파일
   ↓
책임 증가
   ↓
역할별 파일
   ↓
Use Case 증가
   ↓
services/
   ↓
복잡한 순수 규칙 증가
   ↓
rules/
```

구조를 분리하는 기준은 줄 수 자체가 아닙니다.

다음을 기준으로 판단합니다.

```txt
서로 다른 변경 이유를 가지는가?

독립적으로 이름 붙일 수 있는 책임인가?

여러 Use Case에서 재사용되는가?

한 파일을 이해하기 위해 관련 없는 코드를 많이 읽어야 하는가?

특정 기능을 수정하기 위해 거대한 Service 전체를 확인해야 하는가?
```

---

# 5. `constant`

Domain Constant는 비즈니스 규칙에서 반복적으로 사용하는 상수나 제한값을 정의합니다.

예:

```ts
export const USER = {
  DISPLAY_NAME: {
    MIN_LENGTH: 2,
    MAX_LENGTH: 50,
  },
} as const;
```

적합한 대상:

```txt
최소 / 최대 길이

비즈니스 제한값

공통 Label

상태별 고정 설정

Domain에서 반복 사용하는 값
```

단순히 값 하나가 존재한다는 이유로 반드시 별도 `constant.ts`를 만들 필요는 없습니다.

해당 값이 한 파일에서만 사용되고 그 의미도 해당 코드에 국한된다면 Colocation을 유지할 수 있습니다.

---

# 6. `schema`

Schema는 주로 Zod를 사용하여 Domain에 들어오는 데이터의 구조와 형식을 검증합니다.

대표적인 대상:

```txt
Create Request

Update Request

Search Query

List Query

ID Param

Filter
```

예:

```ts
export const UpdateUserRequestSchema = z.object({
  userId: z.uuid(),
  displayName: z.string().trim().min(2).max(50),
});
```

Schema는 다음과 같은 **구조적 Validation**을 담당합니다.

```txt
required / optional

string / number / boolean

UUID

URL

Enum

문자열 길이

숫자 범위

객체 구조
```

---

# 7. Zod Validation과 Business Validation

두 종류의 Validation을 구분합니다.

## Zod Validation

질문:

```txt
입력 데이터의 형태가 유효한가?
```

예:

```txt
UUID인가?

필수 문자열인가?

허용된 Enum인가?

길이 제한을 만족하는가?

숫자가 양수인가?
```

이러한 검증은 Schema에서 처리합니다.

---

## Business Validation

질문:

```txt
현재 비즈니스 상태에서 이 작업이 허용되는가?
```

예:

```txt
사용자가 존재하는가?

이미 차단된 사용자인가?

현재 상태에서 발행할 수 있는가?

자기 자신을 차단하려 하는가?

취소 가능한 주문 상태인가?

요청 수량이 남은 수량보다 많은가?
```

이러한 판단은:

```txt
Service

Permission

Rule
```

등의 Domain Logic에서 처리합니다.

Mutation의 Business Validation은 UI나 이전 조회 결과가 아니라 실행 시점의 Server State를 기준으로 수행합니다. 같은 Resource가 동시에 변경될 수 있다면 Business Rule이 올바른 것과 그 판단이 Update 시점까지 유효한지는 별도로 검토합니다.

State Transition, Stale State, 동시 요청에서의 Business Rule 검토 기준은 `22_구현_안전성.md`를 따릅니다.

---

## 구분 예

```txt
orderId가 UUID인가?
→ Zod

해당 주문이 존재하는가?
→ Business

quantity가 1 이상의 정수인가?
→ Zod

quantity가 실제 환불 가능 수량 이하인가?
→ Business
```

Zod Schema에 Database 조회가 필요한 검증을 넣지 않습니다.

---

# 8. DTO

DTO는 Domain 경계를 오가는 명시적인 데이터 계약입니다.

대표적인 유형:

```txt
Request DTO

Response DTO

List Item Response

Detail Response

Summary Response
```

예:

```ts
export interface UserDetailResponse {
  id: string;
  email: string;
  displayName: string | null;
  status: UserStatus;
}
```

DTO의 중요한 목적 중 하나는 Persistence Model과 App 계약을 분리하는 것입니다.

```txt
Prisma Model
    ↓
Mapper
    ↓
Domain DTO
    ↓
App
```

다음 구조를 피합니다.

```txt
Prisma User
   ↓ 그대로
Server Action
   ↓
React UI
```

---

# 9. DTO를 과도하게 만들지 않는다

내부 함수에서 한 번만 사용하는 작은 객체까지 모두 DTO로 만들 필요는 없습니다.

DTO 분리를 우선 검토하는 경우:

```txt
Domain 외부로 반환되는 데이터

여러 Service에서 공유되는 계약

Client와 Server 사이에 의미 있는 계약

Persistence Model과 다른 구조를 가져야 하는 응답

명시적인 이름이 이해를 돕는 데이터 구조
```

내부 구현 세부사항만을 위한 Type은 필요한 위치에 Colocate할 수 있습니다.

---

# 10. `error`

Domain Error는 비즈니스적으로 구분해야 하는 실패 상태를 표현합니다.

예:

```txt
USER_NOT_FOUND

USER_BLOCKED

CANNOT_BLOCK_SELF

CONTENT_NOT_FOUND

CONTENT_ALREADY_PUBLISHED
```

Domain Error는 다음과 같은 의미를 가져야 합니다.

```txt
무엇이 실패했는가?

호출자가 실패 종류를 구분할 필요가 있는가?
```

일반 JavaScript Error Message만으로 비즈니스 실패를 구분하지 않습니다.

---

# 11. Error 파일을 만드는 기준

모든 Domain에 반드시 `domain.error.ts`를 만들지는 않습니다.

다음 상황에서 분리를 검토합니다.

```txt
구분해야 할 Domain Error Code가 여러 개 있음

여러 Service가 같은 Error를 사용함

Action Layer가 Error Code를 기반으로 결과를 변환해야 함

테스트에서 실패 종류를 명확하게 검증해야 함
```

실제 Domain Error가 없는 단순 조회 기능이라면 빈 Error 파일을 만들 필요가 없습니다.

---

# 12. `mapper`

Mapper는 Persistence Data나 내부 Domain Data를 외부 계약으로 변환합니다.

예:

```txt
Database Record
      ↓
Mapper
      ↓
Response DTO
```

대표적인 책임:

```txt
필요한 Field만 선택

nullable 처리

날짜 표현 정리

Relation 구조 변환

Persistence Field 숨김

Response DTO 구성
```

Mapper는 비즈니스 권한을 판단하지 않습니다.

---

# 13. Mapper 분리 기준

다음 상황에서 별도 Mapper가 유용합니다.

```txt
같은 변환을 여러 Service에서 사용

Persistence Model과 Response DTO 차이가 큼

Nested Relation 변환이 복잡함

변환 자체를 독립적으로 테스트할 가치가 있음
```

반대로 한 Service에서 단 한 번 사용하는 단순한 객체 변환이라면 Service 내부에 Colocate할 수도 있습니다.

```ts
return ok({
  id: user.id,
  displayName: user.displayName,
});
```

이 정도만을 위해 반드시 Mapper 파일을 만들 필요는 없습니다.

---

# 14. `permission`

Permission은 Actor와 Resource 사이의 **인가 규칙**을 담당합니다.

질문:

```txt
누가 이 작업을 할 수 있는가?
```

예:

```txt
현재 사용자가 이 콘텐츠를 수정할 수 있는가?

관리자가 이 사용자를 차단할 수 있는가?

현재 사용자가 이 주문을 볼 수 있는가?
```

Permission은 인증 자체와 다릅니다.

```txt
Auth
  누구인가?

Permission
  이 사람이 이것을 할 수 있는가?
```

인증은 `@repo/auth`, 비즈니스 인가는 Domain의 Permission에서 처리합니다.

---

# 15. `rule`

`rule`은 Permission으로 표현하기 어려운 순수 비즈니스 규칙을 분리할 때 사용합니다.

질문:

```txt
현재 상태에서 무엇이 가능한가?

어떤 값이 계산되는가?

어떤 상태 전이가 허용되는가?
```

예:

```txt
주문이 취소 가능한 상태인가?

콘텐츠가 발행 가능한 상태인가?

환불 가능한 수량은 얼마인가?

다음 상태로 전환할 수 있는가?
```

Rule은 가능한 한:

```txt
Pure Function

Side Effect 없음

Database 직접 접근 없음

입력 → 판단 또는 계산
```

형태로 유지합니다.

Rule이 상태 전이 가능 여부를 올바르게 판단하더라도 동시에 실행되는 다른 요청까지 제어하는 것은 아닙니다. 기대 상태를 Mutation 조건에 포함하거나 Conflict를 감지해야 하는 경우 Domain은 Business 의미를 정의하고 Repository / Database의 Concurrency 수단과 조합합니다.

---

# 16. Permission과 Rule의 차이

개념적으로 Permission도 Business Rule의 한 종류지만, 인가 경계를 명확하게 하기 위해 별도로 구분합니다.

```txt
permission
  누가 할 수 있는가?

rule
  무엇이 가능한가?
```

예:

```txt
canUserEditContent(...)
  → Permission

canPublishContent(...)
  → Rule
```

하나의 Use Case에서는 두 판단이 모두 필요할 수 있습니다.

```txt
현재 사용자가 수정 권한이 있는가?
       ↓
Permission

현재 콘텐츠 상태가 수정 가능한가?
       ↓
Rule
```

---

# 17. `service`

Domain Service는 하나의 Use Case를 실행하는 중심 Orchestrator입니다.

대표적인 흐름:

```txt
입력
 ↓
Repository 조회
 ↓
Permission 확인
 ↓
Rule 확인
 ↓
필요한 Transaction 시작
 ↓
Repository 변경
 ↓
Mapper
 ↓
Result 반환
```

Service의 핵심 책임은 여러 Domain 구성 요소와 Persistence Operation을 **Use Case 단위로 조합하는 것**입니다.

---

# 18. Service에 들어가는 것

대표적으로 다음 코드를 Service에서 조합합니다.

```txt
Repository 호출

Domain 존재 여부 판단

Permission 호출

Rule 호출

Transaction 조합

여러 Repository Operation 순서 결정

동일 Business Operation과 중복 처리 정책 결정

Mapper 호출

Domain Result 반환
```

예:

```ts
export async function blockUserService(
  actor: UserActor,
  targetUserId: string,
): Promise<Result<UserDetailResponse, UserError>> {
  const targetUser = await findUserById(targetUserId);

  if (!targetUser) {
    return err(USER_ERROR.NOT_FOUND);
  }

  if (!canBlockUser(actor, targetUser)) {
    return err(USER_ERROR.CANNOT_BLOCK);
  }

  const updatedUser = await updateUserStatus(targetUserId, "BLOCKED");

  return ok(mapUserDetail(updatedUser));
}
```

---

# 19. Service에 넣지 않는 것

다음 책임을 Service에 넣지 않습니다.

```txt
FormData Parsing

Toast

redirect

revalidatePath

React State

Prisma Query

HTTP Response 구성

Provider SDK 세부 구현
```

또한 Service가 다음과 같이 지나치게 비대해지는 것도 피합니다.

```txt
수백 줄의 상태 판단

복잡한 계산

반복되는 Mapping

서로 관련 없는 여러 Use Case

서로 다른 이유로 변경되는 기능
```

이 경우 Permission, Rule, Mapper 또는 Use Case별 Service로 분리합니다.

---

# 20. Service 분리 기준

작은 Domain은 단일 Service 파일로 시작할 수 있습니다.

```txt
content/
└─ content.service.ts
```

Use Case가 많아져 탐색이 어려워지면:

```txt
content/
└─ services/
   ├─ get-content.service.ts
   ├─ create-content.service.ts
   ├─ update-content.service.ts
   └─ publish-content.service.ts
```

처럼 Use Case 단위로 분리합니다.

분리 판단 기준:

```txt
서로 독립적인 Use Case인가?

각 함수의 변경 이유가 다른가?

특정 Service를 수정하기 위해 거대한 파일 전체를 읽어야 하는가?

개별 Use Case의 의존성이 명확하게 분리되는가?

테스트 파일도 지나치게 비대해졌는가?
```

---

# 21. 줄 수를 기준으로 강제 분리하지 않는다

다음과 같은 규칙은 두지 않습니다.

```txt
300줄 이상이면 무조건 분리

함수 5개 이상이면 services/ 생성
```

줄 수보다 응집도와 책임을 우선합니다.

```txt
200줄이어도 하나의 응집된 책임
→ 유지 가능

80줄이어도 서로 다른 Use Case가 섞임
→ 분리 검토
```

---

# 22. Service와 Repository의 경계

Domain Service는 **무엇을 해야 하는지**를 결정합니다.

Repository는 **어떻게 저장하고 조회할지**를 담당합니다.

```txt
Domain Service
  ↓
Business Decision

Repository
  ↓
Persistence Operation
```

예:

```txt
Service
  사용자를 차단할 수 있는지 확인
  차단 상태로 변경하기로 결정

Repository
  User Status Column Update
```

---

## Service 책임

```txt
Use Case

Business Validation

Permission

Rule

Transaction Scope

Error 의미

반환 결과
```

## Repository 책임

```txt
find

create

update

delete

count

exists

Query Condition

Select / Include

Persistence Error 정규화
```

---

# 23. Domain에서 Prisma를 직접 사용하지 않는다

Domain Service에서는 Prisma Client나 Prisma Model에 직접 의존하지 않는 것을 기본 원칙으로 합니다.

지양:

```ts
import { prisma } from "@repo/database/client";

export async function getUserService(userId: string) {
  return prisma.user.findUnique({
    where: {
      id: userId,
    },
  });
}
```

권장:

```ts
import { findUserById } from "@repo/database/user";

export async function getUserService(userId: string) {
  const user = await findUserById(userId);

  // Domain 판단...
}
```

Prisma와 Repository의 세부 기준은 `07_데이터베이스.md`에서 설명합니다.

---

# 24. Result Pattern

예상 가능한 비즈니스 성공과 실패는 Result Pattern을 사용하여 표현합니다.

개념:

```txt
Result
├─ Ok
└─ Err
```

예:

```ts
Promise<Result<UserDetailResponse, UserError>>;
```

호출자는 Exception Message를 분석하지 않고 결과의 성공 여부와 Error Code를 명시적으로 처리할 수 있습니다.

---

# 25. Result를 사용하는 경우

다음과 같은 **예상 가능한 Domain 실패**에 사용합니다.

```txt
Resource가 존재하지 않음

현재 상태에서 작업 불가

권한 없음

이미 처리됨

Business Rule 위반

중복 상태
```

예:

```txt
User Not Found
→ Err

Cannot Block Self
→ Err

Already Published
→ Err
```

이들은 Application이 정상적으로 처리해야 하는 비즈니스 결과입니다.

---

# 26. Result와 Exception

모든 오류를 Result로 바꾸지는 않습니다.

Result:

```txt
예측 가능한 비즈니스 실패
```

Exception:

```txt
예측하지 못한 시스템 실패

Database Connection 장애

프로그램 버그

불변식 붕괴

Infrastructure의 예기치 않은 실패
```

개념:

```txt
"이 주문은 이미 취소되었습니다."
→ Result Err

"PostgreSQL Connection을 열 수 없습니다."
→ Exception / Infrastructure Error
```

Infrastructure Error를 어느 수준에서 Domain Error로 정규화할지는 오류의 의미와 복구 가능성을 기준으로 판단합니다.

---

# 27. Result의 목적

Result Pattern을 사용하는 이유는 다음과 같습니다.

```txt
성공과 실패 계약을 Type으로 표현

예상 가능한 실패를 Exception과 분리

Service 호출자가 처리해야 할 Error를 명확화

Server Action에서 ActionResult로 변환하기 쉬움

Test에서 실패 종류를 명확하게 검증
```

기본 흐름:

```txt
Domain Result
      ↓
Server Action
      ↓
ActionResult
      ↓
UI
```

`ActionResult` 변환 기준은 `09_서버_액션.md`에서 설명합니다.

---

# 28. Transaction과 Domain Service

Transaction은 Persistence 기술이지만 **어떤 작업이 하나의 Atomic Unit인가**는 Use Case가 결정합니다.

따라서 Transaction Scope는 Domain Service에서 조합합니다.

예:

```txt
회원 생성
 +
OAuth Account 생성
```

두 작업이 반드시 함께 성공해야 한다면:

```txt
Domain Service
     ↓
transaction
     ↓
User Repository
OAuth Account Repository
```

형태로 구성합니다.

---

# 29. Transaction이 필요한 경우

여러 Persistence 변경 중 일부만 성공하면 Domain 상태가 불완전해지는 경우 사용합니다.

```txt
A 성공
B 실패
→ 허용할 수 없음
```

예:

```txt
Order 생성
+
Order Item 생성

User 생성
+
OAuth Account 생성

재고 차감
+
주문 상태 변경
```

필요한 결과:

```txt
전부 성공
→ Commit

하나라도 실패
→ Rollback
```

---

# 30. Transaction이 필요하지 않은 경우

다음 작업을 습관적으로 Transaction으로 감싸지 않습니다.

```txt
단일 조회

독립적인 단일 Insert

독립적인 단일 Update

서로 Atomicity가 필요 없는 작업
```

Transaction은 실제 비즈니스 불변식을 보호해야 할 때 사용합니다.

Transaction은 Atomicity를 제공하지만 모든 Race Condition이나 중복 실행을 자동으로 해결하지 않습니다.

같은 Resource에 대한 동시 요청, Read-Modify-Write, State Transition 충돌, Idempotency가 중요한 Use Case라면 Transaction과 별도로 필요한 Concurrency Control을 검토합니다. 공통 판단 기준은 `22_구현_안전성.md`를 따릅니다.

---

# 31. Repository가 Transaction Scope를 결정하지 않는다

다음 구조를 피합니다.

```txt
Repository A
  내부에서 임의로 Transaction 시작
  Repository B까지 호출
```

이렇게 되면 Repository가 Use Case를 알게 됩니다.

대신:

```txt
Domain Service
      ↓
transaction(...)
      ↓
Repository A
Repository B
```

형태를 사용합니다.

Repository는 필요한 경우 Transaction Client를 받아 동일한 Persistence Operation을 수행할 수 있게 합니다.

---

# 32. Transaction 내부의 Business Logic

Transaction Callback에는 필요한 Database Operation과 즉시 필요한 판단만 둡니다.

가능하면 Transaction 시간을 불필요하게 늘리는 작업은 밖에서 수행합니다.

예:

```txt
외부 Mail API 호출

외부 Storage 업로드

느린 HTTP Request
```

이런 작업을 Database Transaction 내부에서 수행하면 Connection을 오래 점유하고 실패 경계도 복잡해집니다.

일반적으로:

```txt
비즈니스 검증
 ↓
필요한 DB Transaction
 ↓
Commit
 ↓
외부 Side Effect
```

순서를 검토합니다.

단, 외부 Side Effect와 Database 상태의 일관성이 강하게 요구되는 경우에는 별도 설계가 필요합니다.

---

# 33. Infrastructure와 Domain

Domain은 가능한 한 Mailer, Storage 등 구체적인 Infrastructure 구현을 직접 알지 않습니다.

예:

```txt
회원 가입
+
환영 메일
```

이라고 해서 자동으로:

```txt
domain → mailer
```

Dependency를 추가하지 않습니다.

먼저 상위 조립 계층에서:

```txt
Use Case / App
├─→ Domain
└─→ Mailer
```

형태로 해결 가능한지 검토합니다.

Domain Dependency의 전체 기준은 `05_의존성_경계.md`를 따릅니다.

---

# 34. Client Export

`client.ts`는 Browser에서도 안전하게 import할 수 있는 Domain API를 노출합니다.

대표적인 대상:

```txt
상수

Enum

공개 Type

Request Schema

Request Type

Response DTO Type

Client에서도 필요한 Label / Formatter용 데이터
```

Client Export에는 Server Runtime Dependency가 섞이지 않아야 합니다.

금지 대상:

```txt
Repository

Domain Service

Database

server-only

Secret

Node.js 전용 구현
```

---

# 35. Server Export

`server.ts`는 Server에서만 사용해야 하는 Domain API를 노출합니다.

대표적인 대상:

```txt
Domain Service

Permission

Server-only Mapper

Repository를 사용하는 기능

Transaction을 사용하는 Use Case

Server 전용 Helper
```

예:

```ts
import { getUserService } from "@repo/domain/user/server";
```

App의 Server Component나 Server Action에서는 Server Public API를 사용합니다.

---

# 36. Client / Server Export를 나누는 이유

다음 문제를 방지합니다.

```txt
Server Code가 Client Bundle에 포함됨

Database Dependency가 Browser Graph에 진입

server-only 오류

Secret을 사용하는 코드가 Client에서 import됨
```

개념:

```txt
client.ts
  Browser-safe API

server.ts
  Server-only API
```

Client에서 필요하다는 이유만으로 Server API 전체를 Client Entry에 다시 export하지 않습니다.

---

# 37. Public API

Domain 외부에서는 가능한 한 명시적인 Public API를 사용합니다.

권장:

```ts
import type { UserDetailResponse } from "@repo/domain/user/client";

import { getUserService } from "@repo/domain/user/server";
```

지양:

```ts
import { getUserService } from "@repo/domain/src/user/services/get-user.service";
```

Internal Directory 구조는 Package 외부 Contract가 아닙니다.

Public API 원칙은 `04_패키지_구조.md`를 따릅니다.

---

# 38. `index.ts`

`index.ts`는 해당 Directory의 모든 파일을 자동으로 노출하기 위한 Barrel이 아닙니다.

필요한 Public API만 명시적으로 export합니다.

예:

```ts
export { getUserService } from "./services/get-user.service";
export { updateUserService } from "./services/update-user.service";
```

내부 구현까지 무분별하게 export하지 않습니다.

---

# 39. Domain 간 의존성

한 Domain이 다른 Domain의 내부 구현을 깊게 참조하지 않습니다.

필요하다면 해당 Domain의 Public API를 사용합니다.

하지만 Domain 간 Dependency가 지속적으로 늘어난다면 다음을 검토합니다.

```txt
책임이 잘못 나뉘었는가?

상위 Use Case에서 조립해야 하는가?

공통된 더 낮은 개념이 있는가?

실제로 하나의 Domain으로 보는 것이 맞는가?
```

양방향 Domain Dependency는 만들지 않습니다.

전체 Workspace Boundary는 `05_의존성_경계.md`에서 설명합니다.

---

# 40. Directory 승격 기준

처음에는 다음처럼 평평하게 유지합니다.

```txt
order/
├─ order.schema.ts
├─ order.dto.ts
├─ order.service.ts
├─ client.ts
└─ server.ts
```

Service가 많아지면:

```txt
order/
├─ services/
│  ├─ get-order.service.ts
│  ├─ create-order.service.ts
│  └─ cancel-order.service.ts
```

Schema가 많아지면:

```txt
order/
├─ schemas/
│  ├─ create-order.schema.ts
│  ├─ cancel-order.schema.ts
│  └─ order-list-query.schema.ts
```

DTO가 많아지면:

```txt
order/
├─ dto/
│  ├─ order-detail.dto.ts
│  └─ order-list-item.dto.ts
```

비즈니스 Rule이 늘어나면:

```txt
order/
├─ rules/
│  ├─ can-cancel-order.rule.ts
│  └─ calculate-refundable-quantity.rule.ts
```

처럼 필요한 책임만 승격합니다.

---

# 41. 불필요한 추상화를 피한다

다음과 같은 이유만으로 파일이나 계층을 만들지 않습니다.

```txt
다른 Domain에도 있으니까

나중에 필요할 것 같아서

Architecture Diagram이 대칭적이어야 해서

Generator가 만들어주니까
```

좋은 기준:

```txt
실제 책임이 존재하는가?

분리했을 때 이해하기 쉬워지는가?

독립적인 변경 이유가 있는가?

재사용 또는 테스트 가치가 있는가?
```

---

# 42. Domain Generator와의 관계

Domain Generator는 Domain의 최대 구조를 강제해서는 안 됩니다.

기본 생성 결과는 가능한 한 작은 시작점을 제공합니다.

이후 실제 요구사항에 따라:

```txt
constant

error

mapper

permission

rules/

services/
```

등을 추가합니다.

Generator의 실제 생성 구조와 옵션은 `14_코드_생성기.md`에서 문서화하며, Domain 구조 원칙과 어긋나지 않도록 유지합니다.

---

# 43. AI와 작업하기 위한 경계

하나의 거대한 Domain Service 파일은 사람뿐 아니라 AI와 작업할 때도 Context 범위를 불필요하게 키웁니다.

예:

```txt
user.service.ts
  모든 User Use Case
```

보다:

```txt
services/
├─ block-user.service.ts
├─ unblock-user.service.ts
├─ update-user.service.ts
└─ withdraw-user.service.ts
```

처럼 책임이 분리되어 있으면 수정 범위가 명확합니다.

Domain 구조는 다음 목적도 가집니다.

```txt
관련 Context만 전달 가능

변경 영향 범위 파악 용이

Test 대상 명확화

Code Review 범위 축소
```

다만 AI 사용을 위해 필요 이상의 작은 파일로 쪼개지는 것은 피하고, 항상 Domain 응집도를 우선합니다.

---

# 44. 테스트 관점

Domain Service는 비즈니스 Use Case를 중심으로 테스트합니다.

대표적인 대상:

```txt
성공 경로

Resource 없음

Permission 실패

Rule 실패

상태 전이

Transaction 성공 / 실패

동시 요청에서의 State Transition과 Idempotency

Domain Error
```

Pure Rule과 Permission은 독립적으로 테스트할 가치가 있을 때 별도 Unit Test를 작성할 수 있습니다.

Mapper 역시 변환 로직이 복잡하다면 독립적으로 테스트합니다.

Repository 자체의 Persistence 동작은 `07_데이터베이스.md`의 Integration Test 책임입니다.

전체 테스트 전략은 `12_테스트_전략.md`에서 설명합니다.

---

# 45. 새로운 Use Case 추가 흐름

새로운 Use Case를 추가할 때 일반적으로 다음 순서로 판단합니다.

```txt
1. Request 계약이 필요한가?

2. Zod Schema가 필요한가?

3. 새로운 Business Error가 있는가?

4. 새로운 Permission 판단이 필요한가?

5. 재사용 가능한 Rule이 필요한가?

6. 기존 Repository API로 충분한가?

7. 새로운 Repository Operation이 필요한가?

8. 여러 DB 변경을 Transaction으로 묶어야 하는가?

9. Response DTO가 필요한가?

10. Mapper 분리가 필요한가?

11. 기존 service.ts에 유지할 수 있는가?

12. 독립 Service 파일로 분리하는 것이 더 명확한가?

13. Client / Server Export에 무엇을 노출할 것인가?

14. 같은 Use Case가 동시에 또는 중복 실행될 수 있는가?

15. State Transition 충돌, Idempotency, Partial Failure를 별도로 설계해야 하는가?
```

필요하지 않은 단계는 생략합니다.

---

# 46. 예시: 단순 조회 Use Case

단순한 조회라면 구조가 매우 작을 수 있습니다.

```txt
content/
├─ content.dto.ts
├─ content.service.ts
├─ client.ts
└─ server.ts
```

흐름:

```txt
getContentService
      ↓
findContentById
      ↓
Response DTO
```

별도 Permission, Rule, Error, Mapper가 필요 없다면 만들지 않습니다.

---

# 47. 예시: 복잡한 상태 변경 Use Case

반대로 복잡한 변경은 여러 역할을 사용할 수 있습니다.

```txt
cancelOrderService
      ↓
Order 조회
      ↓
Permission 확인
      ↓
canCancelOrder Rule
      ↓
Transaction
  ├─ Order 상태 변경
  └─ 관련 Persistence 변경
      ↓
Mapper
      ↓
Result
```

이 경우:

```txt
order.permission.ts

rules/can-cancel-order.rule.ts

services/cancel-order.service.ts

order.error.ts
```

등의 분리가 실제 책임을 표현하므로 의미가 있습니다.

# 50. 핵심 원칙

```txt
Domain은 비즈니스 규칙과 Use Case를 담당한다.

Domain 구조는 고정된 파일 Template이 아니다.

constant, schema, DTO, error, mapper, permission은 필요한 역할만 추가한다.

작은 Domain은 평평하게 유지한다.

책임이 분화될 때 Directory와 파일을 승격한다.

Zod는 데이터 구조를 검증한다.

Business Validation은 Domain이 판단한다.

Permission은 누가 할 수 있는지를 판단한다.

Rule은 무엇이 가능한지와 어떻게 계산되는지를 판단한다.

Service는 Use Case를 조립한다.

Service가 비대해지면 Use Case 단위로 분리한다.

줄 수가 아니라 책임과 응집도를 기준으로 분리한다.

Repository는 Persistence만 담당한다.

Domain Service는 Prisma를 직접 사용하지 않는다.

예상 가능한 Business Failure는 Result로 표현한다.

예기치 않은 System Failure와 Domain Failure를 구분한다.

Transaction Scope는 Domain Use Case가 결정한다.

Business Rule은 최신 Server State를 기준으로 최종 검증한다.

동시 요청과 중복 실행에서 필요한 Idempotency 의미는 Domain Use Case가 정의한다.

Client Export에는 Browser-safe API만 노출한다.

Server Export에는 Service와 Server-only API를 노출한다.

미래를 예상해 빈 계층과 파일을 미리 만들지 않는다.

책임이 생기면 구조가 따라온다.
```
