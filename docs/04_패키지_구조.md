# 패키지 구조

이 문서는 `packages/` 아래에 존재하는 공통 Package의 책임과 경계를 정의합니다.

목표는 다음 질문에 일관된 기준을 제공하는 것입니다.

```txt
이 코드는 어느 Package에 두어야 하는가?

어떤 코드는 해당 Package에 두면 안 되는가?

Package끼리는 어떤 책임을 나누는가?

외부에 무엇을 export해야 하는가?

새로운 Package를 만들 필요가 있는가?
```

세부적인 Package 간 의존 허용 관계는 `05_의존성_경계.md`에서 다룹니다.

---

## 1. 기본 원칙

`packages/*`는 단순히 여러 앱에서 사용할 것 같은 코드를 모아 두는 공간이 아닙니다.

하나의 Package는 명확한 책임과 독립적인 경계를 가져야 합니다.

기본 원칙:

```txt
앱은 Package를 조립한다.

Package는 자신의 책임만 가진다.

하위 Package는 자신을 사용하는 앱을 알지 않는다.

공유 가능성만으로 코드를 Package로 승격하지 않는다.

실제 공유 또는 독립적인 책임이 발생했을 때 분리한다.

Package 내부 구현보다 Public API를 통해 사용한다.
```

특정 앱에서만 사용하는 코드는 기본적으로 해당 앱에 colocate합니다.

```txt
하나의 앱에서만 사용
→ apps/*

여러 앱에서 공유하는 비즈니스 규칙
→ packages/domain

여러 앱에서 공유하는 UI 기반
→ packages/design-system

외부 시스템과의 공통 연결
→ Infrastructure Package

개발 Tool 설정
→ Config Package
```

# 2. Runtime Package

현재 Runtime Package는 다음과 같습니다.

```txt
@repo/auth
@repo/core
@repo/database
@repo/design-system
@repo/domain
@repo/env
@repo/mailer
@repo/storage
```

이 Package들은 애플리케이션의 Runtime 코드에서 직접 또는 간접적으로 사용됩니다.

## 3. `@repo/core`

`@repo/core`는 가장 아래에 위치하는 순수 공통 기반 Package입니다.

### 책임

다른 도메인이나 Infrastructure에 종속되지 않는 범용 코드를 제공합니다.

대표적인 책임:

```txt
Result
AppError
ActionResult
공통 Error 기반
Validation Helper
Pagination
Search Params Helper
Normalizer
Logger 기반
공통 Type
범용 Utility
```

### 넣어야 하는 코드

다음 조건을 만족하는 코드가 적합합니다.

```txt
특정 비즈니스 도메인을 몰라도 된다.

Database가 없어도 동작한다.

Next.js가 없어도 동작한다.

React가 없어도 동작한다.

특정 외부 Provider가 없어도 동작한다.

여러 Package에서 자연스럽게 재사용할 수 있다.
```

예:

```txt
Result<T, E>

AppError

PaginationResult<T>

문자열 Normalizer

일반적인 Date / Number Helper

범용 Validation Helper
```

### 넣지 말아야 하는 코드

```txt
사용자, 주문, 콘텐츠 같은 도메인 규칙

Prisma Model 또는 Repository

OAuth 처리

Storage Provider

메일 전송

React Component

Next.js 전용 코드

특정 앱 URL이나 Route
```

### 핵심 원칙

```txt
core는 다른 도메인을 모른다.

core는 database를 모른다.

core는 auth를 모른다.

core는 design-system을 모른다.

core는 특정 앱을 모른다.
```

`core`가 비대해져 사실상의 잡동사니 Package가 되지 않도록 주의합니다.

## 4. `@repo/domain`

`@repo/domain`은 비즈니스 규칙의 중심입니다.

### 책임

대표적으로 다음을 담당합니다.

```txt
Domain Constant
Zod Schema
Request Input
Response DTO
Domain Service
Mapper
Permission
Domain Error Code
Business Rule
```

도메인별 구조는 일반적으로 다음 형태를 가질 수 있습니다.

```txt
src/
└─ [domain]/
   ├─ [domain].constant.ts
   ├─ [domain].dto.ts
   ├─ [domain].error.ts
   ├─ [domain].mapper.ts
   ├─ [domain].permission.ts
   ├─ [domain].schema.ts
   ├─ [domain].service.ts
   ├─ client.ts
   └─ server.ts
```

실제 필요한 파일만 생성합니다.

### 넣어야 하는 코드

```txt
사용자 상태 변경 가능 여부

콘텐츠 공개 조건

도메인 입력 Validation

도메인 Request / Response 계약

권한 판단

Database Model을 Response DTO로 변환하는 Mapper

여러 Repository를 조합하는 Use Case

Transaction이 필요한 비즈니스 흐름
```

### 넣지 말아야 하는 코드

```txt
React Component

Toast

Dialog

Next.js Route

Server Action

FormData 직접 처리

Prisma Client 직접 호출

OAuth SDK 직접 호출

메일 Provider 구현

파일 Storage Provider 구현
```

### Domain Service

Domain Service는 다음을 판단합니다.

```txt
무엇이 가능한가?

누가 할 수 있는가?

어떤 상태에서 가능한가?

어떤 데이터가 유효한가?

어떤 Repository 작업이 필요한가?
```

예:

```txt
사용자를 차단할 수 있는가?

게시물을 공개할 수 있는가?

현재 사용자가 해당 리소스를 수정할 권한이 있는가?
```

앱의 Presentation 상태는 판단하지 않습니다.

## 5. `@repo/database`

`@repo/database`는 데이터 영속성 계층입니다.

### 책임

```txt

Transaction
Repository

```

일반적인 흐름:

```txt
Domain Service
  ↓
Repository
  ↓
Prisma
  ↓
Database
```

### 넣어야 하는 코드

```txt
Prisma Client 생성

Repository 구현

Database Query

Transaction Helper

Prisma Error 변환

Migration

Schema

Database Seed를 위한 저수준 접근 기반
```

### 넣지 말아야 하는 코드

```txt
비즈니스 상태 전이 판단

사용자 권한 정책

Server Action

React Component

Toast

메일 발송

Storage Upload

OAuth 처리
```

Repository는 데이터를 어떻게 저장하고 조회할지는 알지만, 해당 작업이 비즈니스적으로 허용되는지는 판단하지 않습니다.

예:

```txt
좋음

updateUserStatus(userId, status)

좋지 않음

blockUserIfCurrentAdminCanBlockTarget(...)
```

두 번째 판단은 Domain Service의 책임입니다.

## 6. `@repo/auth`

`@repo/auth`는 인증과 Session Infrastructure를 담당합니다.

### 책임

현재 구조에서는 다음 범위를 담당할 수 있습니다.

```txt
OAuth Provider 추상화
Google OAuth
Kakao OAuth
Naver OAuth
Session 생성 / 조회 / 폐기
Session Cookie
Token
Authentication Guard
인증 관련 Server API
```

### 넣어야 하는 코드

```txt
OAuth 인증 URL 생성

OAuth Callback 처리 기반

Provider별 사용자 Profile 정규화

Session Token 생성

Session Cookie 처리

현재 Session 조회

requireUser

requireAdmin과 같은 인증 Guard 기반
```

Guard가 특정 Role을 검사하는 경우에도 실제 비즈니스 도메인의 복잡한 권한 정책까지 가져오지는 않습니다.

### 넣지 말아야 하는 코드

```txt
회원 Profile UI

로그인 Button

특정 앱 로그인 화면

회원 차단 비즈니스 규칙

콘텐츠 접근 권한 정책

주문 소유권 판단

메일 발송

Database Schema 정의
```

인증은 다음 질문을 담당합니다.

```txt
누구인가?

로그인되어 있는가?

어떤 기본 인증 정보를 가지고 있는가?
```

도메인은 다음 질문을 담당합니다.

```txt
그 사용자가 이 작업을 할 수 있는가?
```

## 7. `@repo/design-system`

`@repo/design-system`은 도메인에 독립적인 공통 UI 기반을 제공합니다.

```txt
@repo/design-system/form
@repo/design-system/toast
@repo/design-system/utils
@repo/design-system/web
@repo/design-system/admin
```

### 넣어야 하는 코드

여러 도메인에서 의미가 변하지 않는 UI가 적합합니다.

```txt
Button

Input

Textarea

Select

Dialog

Alert Dialog

Tabs
```

```txt

CreateProductForm

QuestionAnswerDialog

회원 관리 Navigation

특정 Domain DTO를 직접 사용하는 Component
```

이런 코드는 앱의 `entities`, `features`, `views`에 위치합니다.

### 판단 기준

다음 질문을 사용합니다.

```txt
이 Component가 사용자 도메인을 몰라도 의미가 있는가?

다른 서비스에서도 동일한 의미로 사용할 수 있는가?

특정 Business DTO 없이 props만으로 동작할 수 있는가?
```

그렇다면 Design System 후보입니다.

---

### 7.1 Primitive와 App Wrapper

Design System 내부에서도 범위를 구분할 수 있습니다.

```txt

  가장 범용적인 UI Primitive

  web 앱 Theme 또는 Composition

  admin 앱 Theme 또는 Composition
```

`web`, `admin` 영역이 존재하더라도 비즈니스 도메인 Component를 넣는 공간으로 사용하지 않습니다.

```txt
가능

AdminPageShell
WebThemeProvider
AdminThemeStyle

부적절

AdminUserTable
AdminOrderRefundDialog
```

## 10. `@repo/storage`

`@repo/storage`는 파일 Storage Infrastructure를 추상화합니다.

### 책임

```txt
Storage Provider Interface

Upload

Delete

Storage Config

Storage Error

Testing Provider
```

현재 실제 외부 Provider가 없더라도 Provider 교체가 가능한 경계를 유지합니다.

예:

```txt
In-memory Provider
향후 S3
향후 R2
향후 Supabase Storage
```

### 넣어야 하는 코드

```txt
파일 업로드

파일 삭제

Provider Adapter

Storage Key 처리

Storage Error 변환

테스트용 In-memory Storage
```

### 넣지 말아야 하는 코드

```txt
Product Image라는 비즈니스 의미

User Avatar 변경 정책

Database Metadata 저장

Server Action

React Upload Component

특정 앱 Form
```

Storage와 Database 저장이 동시에 필요하다면 App 또는 Domain Use Case에서 두 책임을 조립합니다.

예:

```txt
App / Use Case
├─ Storage Service
│    └─ File Upload
│
└─ Domain Service
     └─ Repository
          └─ Metadata 저장
```

Storage Package가 Domain Repository를 직접 호출하여 비즈니스 데이터를 저장하지 않습니다.

```txt

특정 앱 설정을 공통 Package에 넣지 않는다.

소비 Workspace가 필요한 차이는 로컬에서 확장한다.
```

```txt
공통 Addon

Framework 선택

공통 Story Pattern

공통 Preview Parameter

Accessibility 기본 설정

React Storybook의 공통 Vite Plugin
```

### 넣지 말아야 하는 코드

```txt
특정 앱 Server Action Mock

특정 앱 Alias

특정 앱 Global CSS

Design System Theme Wrapper

특정 앱 Navigation State
```

이런 설정은 각 Workspace의 `.storybook`에서 공통 Config를 확장하여 추가합니다.

Story 작성 규칙은 `13_스토리북.md`에서 설명합니다.

# 17. Package 내부 구조

Package 내부 구조는 책임에 따라 다르게 구성할 수 있습니다.

모든 Package에 동일한 Directory Template을 강제하지 않습니다.

예를 들어 Domain과 Database는 구조적 요구가 다릅니다.

```txt
domain
  비즈니스 도메인 중심

database
  Repository와 Prisma 중심

design-system
  UI 분류 중심

auth
  Provider / Session 중심

storage
  Provider / Service 중심
```

구조보다 책임을 우선합니다.

```txt
먼저 책임을 정한다.
↓
그 책임을 표현하기 위한 구조를 만든다.
```

반대로 디렉터리 Template을 먼저 만든 뒤 코드를 억지로 맞추지 않습니다.

---

# 18. Public API

Package 외부에서는 가능한 한 명시적인 Public API를 통해 접근합니다.

예:

```ts
import { Result } from "@repo/core";

import { getUserService } from "@repo/domain/server";

import { Button } from "@repo/design-system/primitives";

import { sendMail } from "@repo/mailer/server";
```

Package 내부 파일 경로에 직접 의존하는 Deep Import는 기본적으로 허용하지 않습니다.

예:

```ts
// 지양
import { Result } from "@repo/core/src/result/result";

import { getUserService } from "@repo/domain/src/user/user.service";
```

Public API는 Package의 구현 구조와 소비자를 분리하기 위한 경계입니다.

```txt
Package 내부 구조 변경
       ↓
Public API가 유지됨
       ↓
소비 Workspace 수정 최소화
```

---

## 19. `package.json`의 `exports`

외부에 공개할 진입점은 `package.json`의 `exports`에서 명시적으로 관리합니다.

예:

```json
{
  "exports": {
    ".": "./src/index.ts",
    "./server": "./src/server.ts",
    "./client": "./src/client.ts"
  }
}
```

모든 내부 파일을 export하지 않습니다.

기본 원칙:

```txt
실제 소비자가 필요한 진입점만 공개한다.

내부 구현 파일은 숨긴다.

Client와 Server 경계가 있다면 Export를 분리한다.

환경별 API가 다르면 명시적인 Subpath를 사용한다.
```

---

## 20. Root Export와 Subpath Export

Package의 성격에 따라 Root와 Subpath를 함께 사용할 수 있습니다.

예:

```txt
@repo/design-system
@repo/design-system/primitives
@repo/design-system/form
@repo/design-system/toast
@repo/design-system/web
@repo/design-system/admin
```

이런 Subpath는 단순히 디렉터리 구조를 노출하기 위해 만드는 것이 아닙니다.

다음과 같은 의미 있는 소비 경계가 있을 때 사용합니다.

```txt
실행 환경이 다르다.

의존성 특성이 다르다.

API 범주가 명확히 다르다.

소비자가 불필요한 API까지 의존하지 않게 할 필요가 있다.
```

---

## 21. `index.ts`

`index.ts`는 Public API를 구성하는 용도로 사용합니다.

예:

```ts
export { Button } from "./button";
export { Input } from "./input";
export { Select } from "./select";
```

모든 파일을 자동으로 다시 export하는 Barrel로 만들지 않습니다.

좋은 기준:

```txt
외부에서 사용할 API
→ export

Package 내부 구현
→ export하지 않음
```

`index.ts` 자체를 Repository 구조를 숨기기 위한 목적으로 과도하게 중첩하지 않습니다.

---

## 22. Client / Server Export

Server 전용 코드가 존재하는 Package는 Client 코드와 진입점을 분리합니다.

예:

```txt
@repo/domain/client
@repo/domain/server

@repo/auth/client
@repo/auth/server
```

목적:

```txt
Server-only 코드가 Client Bundle로 넘어가는 것을 방지한다.

사용 가능한 API의 실행 환경을 명확하게 한다.

Secret이나 Node.js 전용 Dependency의 잘못된 Import를 줄인다.
```

Client에서 Server 전용 Public API를 import하지 않습니다.

---

## 23. Package Dependency 추가 기준

새로운 Package Dependency를 추가하기 전 다음을 확인합니다.

```txt
이 Dependency가 정말 해당 Package의 책임에 필요한가?

상위 계층의 책임을 하위 Package로 끌고 내려오지는 않는가?

더 낮은 공통 Package에 이미 같은 기능이 있는가?

Dependency 추가로 순환 의존성이 생기지 않는가?

Runtime Dependency인가 Dev Dependency인가?
```

정확한 Package 간 허용 관계는 `05_의존성_경계.md`에서 정의합니다.

---

## 24. `dependencies`, `peerDependencies`, `devDependencies`

Package는 Dependency의 성격도 구분합니다.

### `dependencies`

Package의 Runtime 구현에 직접 필요한 Dependency입니다.

```txt
Package 코드가 실제 실행 중 import한다.
```

### `peerDependencies`

소비 애플리케이션과 동일 Instance 또는 Version Contract를 공유해야 하는 Dependency에 사용합니다.

대표적인 예:

```txt
react
react-dom
```

Design System처럼 React Runtime을 소비 앱과 공유해야 하는 Package에서 활용할 수 있습니다.

### `devDependencies`

Package 자체의 개발, 테스트, Lint, Build에만 필요한 Dependency입니다.

예:

```txt
eslint
typescript
vitest
storybook
Testing Library
```

Runtime에서 필요한 Dependency를 편의상 `devDependencies`에 숨기지 않습니다.

---

## 25. Workspace Package 참조

Repository 내부 Package 간 의존성은 `workspace:*`를 사용합니다.

예:

```json
{
  "dependencies": {
    "@repo/core": "workspace:*",
    "@repo/domain": "workspace:*"
  }
}
```

외부 공통 Dependency는 `pnpm-workspace.yaml`의 Catalog를 우선 사용합니다.

```json
{
  "dependencies": {
    "zod": "catalog:"
  }
}
```

즉 기본 구분은 다음과 같습니다.

```txt
Repository 내부 Package
→ workspace:*

공통 외부 Dependency
→ catalog:

해당 Workspace에서만 사용하는 외부 Dependency
→ 필요에 따라 직접 Version 또는 Catalog 검토
```

# 26. 새로운 Package를 만들 기준

새로운 기능이 생겼다고 바로 Package를 추가하지 않습니다.

우선 해당 코드를 사용하는 곳 가까이에 둡니다.

다음 조건이 생겼을 때 Package 분리를 검토합니다.

```txt
여러 앱에서 실제로 공유한다.

독립적인 책임을 가진다.

별도의 외부 시스템 경계가 존재한다.

독립적인 테스트 전략이 필요하다.

의존성 경계를 분리할 필요가 있다.

Provider를 교체할 가능성이 있다.

Package로 분리했을 때 유지보수 비용이 실제로 줄어든다.
```

잘못된 이유:

```txt
나중에 쓸 것 같아서

구조가 더 멋있어 보여서

파일 수가 많아져서

일단 공통처럼 보여서
```

좋은 이유:

```txt
두 앱이 동일한 책임을 실제로 공유한다.

외부 시스템을 독립적으로 교체할 필요가 있다.

하위 계층에서 독립된 계약으로 관리할 가치가 있다.
```

# 30. 핵심 원칙

```txt
core는 가장 순수한 공통 기반이다.

domain은 비즈니스 규칙을 판단한다.

database는 데이터를 저장하고 조회한다.

auth는 인증과 Session을 담당한다.

design-system은 도메인 독립적인 UI 기반을 제공한다.

env는 환경변수를 검증하고 노출한다.

mailer는 메일 전송 방식을 추상화한다.

storage는 파일 저장 방식을 추상화한다.

Config Package는 개발 Tool 설정을 재사용하게 한다.

Package는 자신의 책임을 넘어서는 코드를 소유하지 않는다.

Public API는 의도적으로 제한한다.

내부 구현보다 Package Export를 통해 사용한다.

Server와 Client API는 필요할 경우 명시적으로 분리한다.

Repository 내부 Dependency는 workspace:*를 사용한다.

공통 외부 Dependency는 Catalog를 사용한다.

공유 가능성이 아니라 실제 공유와 책임을 기준으로 Package를 만든다.
```
