# 패키지 구조

이 문서는 `packages/` 아래에 존재하는 공통 Package의 책임과 경계를 정의합니다.

목표는 다음 질문에 일관된 기준을 제공하는 것입니다.

```txt
이 코드는 어느 Package에 두어야 하는가?

어떤 코드는 해당 Package에 두면 안 되는가?

Package끼리는 어떤 책임을 나누는가?

외부에 무엇을 export해야 하는가?

새로운 Package를 만들 필요가 있는가?
```

세부적인 Package 간 의존 허용 관계는 `05_의존성_경계.md`에서 다룹니다.

---

## 1. 기본 원칙

`packages/*`는 단순히 여러 앱에서 사용할 것 같은 코드를 모아 두는 공간이 아닙니다.

하나의 Package는 명확한 책임과 독립적인 경계를 가져야 합니다.

기본 원칙:

```txt
앱은 Package를 조립한다.

Package는 자신의 책임만 가진다.

하위 Package는 자신을 사용하는 앱을 알지 않는다.

공유 가능성만으로 코드를 Package로 승격하지 않는다.

실제 공유 또는 독립적인 책임이 발생했을 때 분리한다.

Package 내부 구현보다 Public API를 통해 사용한다.
```

특정 앱에서만 사용하는 코드는 기본적으로 해당 앱에 colocate합니다.

```txt
하나의 앱에서만 사용
→ apps/*

여러 앱에서 공유하는 비즈니스 규칙
→ packages/domain

여러 앱에서 공유하는 도메인 독립 UI 기반
→ packages/design-system

외부 시스템과의 공통 연결
→ Infrastructure Package

개발 Tool 설정
→ Config Package
```

## 2. Runtime Package

현재 Runtime Package는 다음과 같습니다.

```txt
@repo/auth
@repo/core
@repo/database
@repo/design-system
@repo/domain
@repo/env
@repo/mailer
@repo/storage
```

이 Package들은 애플리케이션 Runtime에서 직접 또는 간접적으로 사용됩니다.

## 3. `@repo/core`

`@repo/core`는 가장 아래에 위치하는 순수 공통 기반 Package입니다.

### 책임

다른 Domain이나 Infrastructure에 종속되지 않는 범용 코드를 제공합니다.

대표적인 책임:

```txt
Result
AppError
ActionResult
공통 Error 기반
Validation Helper
Pagination
Search Params Helper
Normalizer
Logger 기반
공통 Type
범용 Utility
```

### 넣어야 하는 코드

다음 조건을 만족하는 코드가 적합합니다.

```txt
특정 비즈니스 Domain을 몰라도 된다.

Database가 없어도 동작한다.

Next.js가 없어도 동작한다.

React가 없어도 동작한다.

특정 외부 Provider가 없어도 동작한다.

여러 Package에서 자연스럽게 재사용할 수 있다.
```

예:

```txt
Result<T, E>
AppError
PaginationResult<T>
문자열 Normalizer
일반적인 Date / Number Helper
범용 Validation Helper
```

### 넣지 말아야 하는 코드

```txt
사용자, 주문, 콘텐츠 같은 Domain Rule

Prisma Model 또는 Repository

OAuth 처리

Storage Provider

메일 전송

React Component

Next.js 전용 코드

특정 앱 URL이나 Route
```

### 핵심 원칙

```txt
core는 다른 Domain을 모른다.

core는 database를 모른다.

core는 auth를 모른다.

core는 design-system을 모른다.

core는 특정 앱을 모른다.
```

`core`가 사실상의 잡동사니 Package가 되지 않도록 주의합니다.

## 4. `@repo/domain`

`@repo/domain`은 비즈니스 규칙의 중심입니다.

### 책임

대표적으로 다음을 담당합니다.

```txt
Domain Constant

Zod Schema

Request Input

Response DTO

Domain Service

Mapper

Permission

Rule

Domain Error Code
```

Domain 내부에는 책임에 따라 다음과 같은 역할이 존재할 수 있습니다.

```txt
constant
schema
DTO
error
mapper
permission
rule
service
client export
server export
```

모든 Domain이 이 역할을 전부 가져야 하는 것은 아닙니다.

실제 필요한 책임만 유지합니다.

### 넣어야 하는 코드

```txt
사용자 상태 변경 가능 여부

콘텐츠 공개 조건

Domain Input Validation

Domain Request / Response 계약

권한 판단

Persistence Data를 Response DTO로 변환하는 Mapper

여러 Repository를 조합하는 Use Case

Transaction이 필요한 Business Flow
```

### 넣지 말아야 하는 코드

```txt
React Component

Toast

Dialog

Next.js Route

Server Action

FormData 직접 처리

Prisma Client 직접 호출

OAuth SDK 직접 호출

메일 Provider 구현

파일 Storage Provider 구현
```

### Domain Service

Domain Service는 다음을 판단합니다.

```txt
무엇이 가능한가?

누가 할 수 있는가?

어떤 상태에서 가능한가?

어떤 데이터가 비즈니스적으로 유효한가?

어떤 Repository 작업이 필요한가?
```

예:

```txt
사용자를 차단할 수 있는가?

게시물을 공개할 수 있는가?

현재 사용자가 해당 Resource를 수정할 권한이 있는가?
```

App의 Presentation 상태는 판단하지 않습니다.

Domain 내부 구조와 각 역할의 세부 기준은 `08_도메인_레이어.md`를 따릅니다.

### 넣어야 하는 코드

```txt

Migration

```

### 넣지 말아야 하는 코드

```txt

Server Action

React Component

Toast
```

## 6. `@repo/auth`

`@repo/auth`는 인증과 Session Infrastructure를 담당합니다.

### 책임

현재 구조에서는 다음과 같은 범위를 담당할 수 있습니다.

```txt
OAuth Provider 연결

Session 생성 / 조회 / 폐기

Session Cookie

Token

Authentication Guard

인증 관련 Server API
```

현재 Repository에 구성된 OAuth Provider 구현도 이 Package에서 관리합니다.

### 넣어야 하는 코드

```txt
OAuth 인증 URL 생성

OAuth Callback 처리 기반

Provider별 사용자 Profile 정규화

Session Token 생성

Session Cookie 처리

현재 Session 조회

requireUser

requireAdmin과 같은 Authentication Guard
```

Guard가 기본적인 Role을 검사할 수 있더라도 복잡한 Business Permission까지 `auth`로 가져오지 않습니다.

### 넣지 말아야 하는 코드

```txt
회원 Profile UI

로그인 Button

특정 앱 로그인 화면

회원 차단 Business Rule

콘텐츠 접근 정책

주문 소유권 판단

메일 발송

Database Schema 정의
```

인증은 다음 질문을 담당합니다.

```txt
누구인가?

로그인되어 있는가?

어떤 기본 인증 정보를 가지고 있는가?
```

Domain은 다음 질문을 담당합니다.

```txt
그 사용자가 이 작업을 할 수 있는가?
```

## 7. `@repo/design-system`

`@repo/design-system`은 도메인에 독립적인 공통 UI 기반과 UI Interaction Infrastructure를 제공합니다.

### 책임

현재 주요 책임은 다음과 같습니다.

```txt
Web 공통 UI

Admin 공통 UI

Form Interaction Infrastructure

Toast

Style

UI Utility
```

현재 주요 Public 영역은 다음과 같습니다.

```txt
@repo/design-system

@repo/design-system/form

@repo/design-system/toast

@repo/design-system/utils

@repo/design-system/web

@repo/design-system/admin
```

`primitives`라는 별도의 중간 계층은 사용하지 않습니다.

구체적인 Public Export는 실제 `package.json`의 `exports`를 기준으로 하며, Design System 내부 구조와 세부 책임은 `11_디자인_시스템.md`에서 정의합니다.

### 넣어야 하는 코드

특정 Business Domain을 몰라도 사용할 수 있는 UI와 UI Infrastructure가 적합합니다.

예:

```txt
Button

Input

Textarea

Select

Dialog

Table 기반 공통 UI

Feedback UI

Navigation UI

Layout UI

Form Interaction Utility

Toast

공통 UI Utility
```

실제로 필요한 Component만 추가합니다.

특정 UI Library나 별도의 Primitive Layer를 Architecture의 전제로 두지 않습니다.

### 넣지 말아야 하는 코드

```txt
UserProfileCard

OrderStatusBadge

ContentTable

CreateProductForm

QuestionAnswerDialog

회원 관리 Navigation

특정 Domain DTO를 직접 사용하는 Component

특정 Server Action을 호출하는 Component

특정 Permission을 판단하는 Component
```

이러한 코드는 앱의 `entities`, `features`, `views`에 위치합니다.

### 판단 기준

다음 질문을 사용합니다.

```txt
특정 Domain 이름을 제거해도 의미가 유지되는가?

Domain DTO 없이 사용할 수 있는가?

특정 Server Action 없이 독립적으로 사용할 수 있는가?

특정 Permission을 알 필요가 없는가?

특정 URL 구조를 알 필요가 없는가?

여러 UI에서 동일한 Presentation 책임을 가지는가?
```

대부분 `예`라면 Design System 후보입니다.

---

### 7.1 `web`과 `admin`

Design System은 현재 `web`과 `admin`의 UI 요구를 독립적으로 표현할 수 있습니다.

```txt
@repo/design-system/web

  Web Application에서 반복되는
  도메인 독립 UI

@repo/design-system/admin

  Admin Application에서 반복되는
  도메인 독립 UI
```

Web과 Admin에서 비슷한 Component가 존재하더라도 별도의 Primitive Layer로 즉시 추출하지 않습니다.

다음 기준을 먼저 확인합니다.

```txt
실제로 같은 책임인가?

Public API도 동일한가?

변경 이유도 동일한가?

공통화했을 때 구조가 더 단순해지는가?
```

`web`, `admin`은 비즈니스 Domain Component를 두는 공간이 아닙니다.

```txt
적절

공통 Button

공통 Dialog

공통 Table UI

Page Layout UI


부적절

AdminUserTable

AdminOrderRefundDialog

WebProductCard
```

후자의 UI는 앱의 Entity 또는 Feature에서 관리합니다.

## 8. `@repo/env`

`@repo/env`는 Repository 공통 환경변수의 접근과 검증 경계를 담당합니다.

### 책임

```txt
공통 Environment Schema

Server Environment Validation

Client-safe Environment Validation

Shared Environment Validation

Environment Parsing

Typed Environment API
```

### 넣어야 하는 코드

```txt
여러 App과 Package가 공유하는 Database Environment 계약

여러 App과 Package가 공유하는 Authentication Environment 계약

공통 OAuth Environment 계약

공통 Mailer Environment 계약

공통 Server-only Secret Schema

공통 Client-safe Environment Schema
```

### 넣지 말아야 하는 코드

```txt
특정 앱에서만 사용하는 Environment 계약

특정 앱 Base URL

환경변수를 사용하는 실제 Business 기능

OAuth Flow

Database Client

Storage Provider

Mailer Provider

UI Config

특정 Page Logic
```

예를 들어 앱별 URL은 다음과 같이 각 App Config에서 관리합니다.

```txt
apps/web/src/config
  WEB_APP_URL

apps/admin/src/config
  ADMIN_APP_URL
```

반면 여러 Workspace가 공유하는 OAuth Credential 계약은 `@repo/env`에서 관리할 수 있습니다.

```txt
@repo/env
  GOOGLE_CLIENT_ID 검증

@repo/auth
  GOOGLE_CLIENT_ID를 사용하여 OAuth Provider 구성
```

환경변수 전체 관리 정책은 `06_환경변수.md`를 따릅니다.

## 11. Config Package

다음 Package는 Runtime 기능이 아니라 개발 환경의 공통 설정을 제공합니다.

```txt
@repo/eslint-config

@repo/typescript-config

@repo/vitest-config

@repo/playwright-config

@repo/storybook-config
```

공통 원칙:

```txt
설정 중복을 줄인다.

새 Workspace가 같은 기준을 쉽게 적용할 수 있게 한다.

특정 앱 설정을 공통 Package에 넣지 않는다.

소비 Workspace가 필요한 차이는 Local Config에서 확장한다.

Runtime이 다른 Workspace를 억지로 하나의 설정으로 묶지 않는다.
```

## 17. Package 내부 구조

Package 내부 구조는 책임에 따라 다르게 구성합니다.

모든 Package에 동일한 Directory Template을 강제하지 않습니다.

예:

```txt
domain
  Business Domain 중심

database
  Repository와 Prisma 중심

design-system
  UI 책임 중심

auth
  Provider / Session 중심

storage
  Provider / Service 중심
```

구조보다 책임을 우선합니다.

```txt
먼저 책임을 정한다.
  ↓
그 책임을 표현하기 위한 구조를 만든다.
```

Directory Template을 먼저 만든 뒤 코드를 억지로 맞추지 않습니다.

## 18. Public API

Package 외부에서는 명시적인 Public API를 통해 접근합니다.

예:

```ts
import { Result } from "@repo/core";

import { getUserService } from "@repo/domain/server";

import { Button } from "@repo/design-system/web";

import { sendMail } from "@repo/mailer/server";
```

실제 Export 경로는 각 Package의 `package.json`을 기준으로 합니다.

Package 내부 경로에 직접 의존하는 Deep Import는 사용하지 않습니다.

```ts
// 지양
import { Result } from "@repo/core/src/result/result";

import { getUserService } from "@repo/domain/src/user/user.service";
```

Public API는 Package 내부 구조와 소비 Workspace를 분리하기 위한 경계입니다.

```txt
Package 내부 구조 변경
       ↓
Public API 유지
       ↓
소비 Workspace 수정 최소화
```

---

## 19. `package.json`의 `exports`

외부에 공개할 진입점은 `package.json`의 `exports`에서 명시적으로 관리합니다.

예:

```json
{
  "exports": {
    ".": "./src/index.ts",
    "./server": "./src/server.ts",
    "./client": "./src/client.ts"
  }
}
```

모든 내부 파일을 Export하지 않습니다.

기본 원칙:

```txt
실제 소비자가 필요한 진입점만 공개한다.

내부 구현 파일은 숨긴다.

Client와 Server 경계가 있다면 Export를 분리한다.

의미 있는 API 범주가 있다면 명시적인 Subpath를 사용한다.
```

---

## 20. Root Export와 Subpath Export

Package의 책임에 따라 Root Export와 Subpath Export를 함께 사용할 수 있습니다.

예:

```txt
@repo/design-system

@repo/design-system/form

@repo/design-system/toast

@repo/design-system/utils

@repo/design-system/web

@repo/design-system/admin
```

Subpath는 단순히 Directory 구조를 외부에 노출하기 위해 만들지 않습니다.

다음과 같은 의미 있는 소비 경계가 있을 때 사용합니다.

```txt
실행 환경이 다르다.

Dependency 특성이 다르다.

API 범주가 명확히 다르다.

소비자가 불필요한 API까지 의존하지 않게 할 필요가 있다.
```

---

## 21. `index.ts`

`index.ts`는 Public API를 구성하는 용도로 사용합니다.

예:

```ts
export { Button } from "./button";
export { Input } from "./input";
export { Select } from "./select";
```

모든 파일을 자동으로 다시 Export하는 Barrel로 만들지 않습니다.

기본 기준:

```txt
외부에서 사용할 API
→ export

Package 내부 구현
→ export하지 않음
```

`index.ts`를 Directory 구조를 숨기기 위한 목적으로 과도하게 중첩하지 않습니다.

Export의 세부 Convention은 `18_컨벤션.md`를 따릅니다.

## 22. Client / Server Export

Server 전용 코드가 존재하는 Package는 필요한 경우 Client와 Server 진입점을 분리합니다.

예:

```txt
@repo/domain/client

@repo/domain/server

@repo/auth/client

@repo/auth/server
```

목적:

```txt
Server-only 코드가 Client Bundle로 넘어가는 것을 방지한다.

사용 가능한 API의 Runtime을 명확하게 한다.

Secret이나 Node.js 전용 Dependency의 잘못된 Import를 줄인다.
```

Client에서 Server 전용 Public API를 Import하지 않습니다.

## 23. Package Dependency 추가 기준

새로운 Package Dependency를 추가하기 전에 다음을 확인합니다.

```txt
이 Dependency가 정말 해당 Package의 책임에 필요한가?

상위 계층의 책임을 하위 Package로 끌고 내려오지는 않는가?

더 낮은 공통 Package에 이미 같은 기능이 있는가?

Dependency 추가로 순환 의존성이 생기지 않는가?

Runtime Dependency인가 Dev Dependency인가?
```

정확한 Package 간 허용 관계는 `05_의존성_경계.md`에서 정의합니다.

## 24. `dependencies`, `peerDependencies`, `devDependencies`

Package는 Dependency의 성격을 구분합니다.

### `dependencies`

Package의 Runtime 구현에 직접 필요한 Dependency입니다.

```txt
Package 코드가 실제 Runtime에서 Import한다.
```

### `peerDependencies`

소비 Application과 동일 Instance 또는 Version Contract를 공유해야 하는 Dependency에 사용합니다.

대표적인 예:

```txt
react

react-dom
```

Design System처럼 React Runtime을 소비 App과 공유해야 하는 Package에서 사용할 수 있습니다.

### `devDependencies`

Package 자체의 개발, Test, Lint 등에만 필요한 Dependency입니다.

예:

```txt
eslint

typescript

vitest

storybook

Testing Library
```

Runtime에 필요한 Dependency를 편의상 `devDependencies`에 숨기지 않습니다.

## 25. Workspace Package 참조

Repository 내부 Package 간 의존성은 `workspace:*`를 사용합니다.

예:

```json
{
  "dependencies": {
    "@repo/core": "workspace:*",
    "@repo/domain": "workspace:*"
  }
}
```

여러 Workspace가 공유하는 외부 Dependency Version은 `pnpm-workspace.yaml`의 Catalog를 사용할 수 있습니다.

```json
{
  "dependencies": {
    "zod": "catalog:"
  }
}
```

기본 구분:

```txt
Repository 내부 Package
→ workspace:*

공통 Version으로 관리하는 외부 Dependency
→ catalog:

특정 Workspace에서만 사용하는 외부 Dependency
→ 해당 Workspace에서 관리
```

Package Manager와 Catalog 정책은 `02_기본설정.md`를 따릅니다.

## 26. 새로운 Package를 만들 기준

새 기능이 생겼다는 이유만으로 바로 Package를 추가하지 않습니다.

우선 실제 사용하는 위치 가까이에 둡니다.

다음과 같은 조건이 생겼을 때 Package 분리를 검토합니다.

```txt
여러 Workspace에서 실제로 공유한다.

독립적인 책임을 가진다.

별도의 외부 시스템 경계가 존재한다.

독립적인 Public API를 정의할 수 있다.

의존성 경계를 별도로 관리할 가치가 있다.

Package로 분리했을 때 변경 경계가 더 명확해진다.
```

잘못된 이유:

```txt
나중에 쓸 것 같아서

구조가 더 멋있어 보여서

파일 수가 많아져서

일단 공통처럼 보여서
```

좋은 이유:

```txt
두 App이 동일한 책임과 정책을 실제로 공유한다.

외부 시스템 연결을 독립적인 책임으로 관리해야 한다.

App Context와 분리 가능한 Public API가 존재한다.
```

구체적인 승격과 확장 판단은 `19_확장_가이드.md`를 따릅니다.

## 30. 핵심 원칙

```txt
core는 가장 순수한 공통 기반이다.

domain은 비즈니스 규칙을 판단한다.

database는 데이터를 저장하고 조회한다.

auth는 인증과 Session을 담당한다.

design-system은 도메인 독립적인 UI 기반과 UI Infrastructure를 제공한다.

env는 Repository 공통 환경변수 계약을 관리한다.

앱 전용 환경변수 계약은 각 App에서 관리한다.

mailer는 메일 전송 메커니즘을 담당한다.

storage는 파일 저장 메커니즘을 담당한다.

Config Package는 개발 Tool 설정을 재사용하게 한다.

Package는 자신의 책임을 넘어서는 코드를 소유하지 않는다.

Public API는 의도적으로 제한한다.

내부 구현보다 Package Export를 통해 사용한다.

Server와 Client API는 필요한 경우 명시적으로 분리한다.

Repository 내부 Package Dependency는 workspace:*를 사용한다.

공통 외부 Dependency Version은 필요한 경우 Catalog로 관리한다.

공유 가능성이 아니라 실제 공유와 책임을 기준으로 Package를 만든다.

Package의 세부 구조는 해당 책임을 소유한 전문 문서를 따른다.
```
