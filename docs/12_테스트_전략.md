# 테스트 전략

이 문서는 `boilerplate-turborepo`에서 테스트 종류별 책임과 실행 환경, Mock 기준, Integration Test와 E2E Test의 사용 기준을 정의합니다.

테스트의 목적은 모든 코드를 가능한 한 많이 테스트하는 것이 아닙니다.

각 계층의 책임에 맞는 테스트를 배치하여 다음을 달성하는 것이 목적입니다.

```txt
Business Rule의 안정성

Persistence 동작의 신뢰성

Application Boundary 검증

UI Interaction 검증

실제 사용자 흐름 검증

변경 시 Regression 조기 발견
```

기본적으로 테스트는 다음 네 종류로 구분합니다.

```txt
Unit Test

Component Test

Integration Test

E2E Test
```

각 테스트는 서로 다른 책임을 가지며 동일한 동작을 모든 계층에서 반복해서 검증하지 않습니다.

현재 공통 Vitest와 Playwright 설정 역시 이 구분을 기준으로 구성되어 있습니다.

---

# 1. 기본 원칙

테스트의 기본 원칙은 다음과 같습니다.

```txt
테스트 종류보다 검증하려는 책임을 먼저 결정한다.

Pure Logic은 가능한 한 Unit Test로 검증한다.

React Interaction은 Component Test로 검증한다.

실제 Database 동작이 중요하면 Integration Test를 사용한다.

전체 사용자 흐름은 E2E Test로 검증한다.

하위 계층의 책임을 상위 테스트에서 반복해서 검증하지 않는다.

Mock은 테스트 경계를 만들기 위해 사용한다.

실제 동작이 중요한 Infrastructure는 Mock보다 실제 의존성을 우선한다.

구현 세부사항보다 외부에서 관찰 가능한 결과를 검증한다.

Coverage 숫자를 높이기 위한 테스트를 작성하지 않는다.
```

---

# 2. 테스트 계층

전체 구조는 다음과 같이 볼 수 있습니다.

```txt
                E2E
                 ↑
          Integration Test
                 ↑
           Component Test
                 ↑
             Unit Test
```

위로 갈수록:

```txt
실제 Runtime과 가까움

검증 범위가 넓음

실행 비용이 큼

실패 원인 범위가 넓음
```

아래로 갈수록:

```txt
실행 속도가 빠름

책임이 작고 명확함

실패 원인을 찾기 쉬움

외부 의존성이 적음
```

따라서 모든 기능을 E2E만으로 검증하거나 모든 의존성을 Mock한 Unit Test만으로 검증하지 않습니다.

---

# 3. Unit Test

Unit Test는 하나의 작은 책임을 독립적으로 검증합니다.

대표적인 대상:

```txt
Pure Function

Domain Rule

Permission

Mapper

Error Mapper

Validation Helper

Formatter

Normalizer

Form Utility

Theme Utility
```

예:

```txt
canCancelOrder(...)

calculateRefundableQuantity(...)

normalizeThemeMode(...)

resolveFieldError(...)
```

Unit Test에서는 가능한 한 외부 Runtime과 Database를 사용하지 않습니다.

---

# 4. Unit Test의 목적

Unit Test에서 주로 확인하는 것은 다음과 같습니다.

```txt
입력에 따른 출력

Boundary Value

Business Rule 분기

Invalid State

순수 계산 결과

Error Mapping
```

예:

```txt
PENDING 주문
→ 취소 가능

DELIVERED 주문
→ 취소 불가
```

이 검증을 위해 Browser나 실제 PostgreSQL을 실행할 필요는 없습니다.

---

# 5. Component Test

Component Test는 React Component와 Hook의 **렌더링 및 사용자 Interaction**을 검증합니다.

주로 다음 도구를 사용합니다.

```txt
Vitest

jsdom

Testing Library

user-event

jest-dom
```

대표적인 대상:

```txt
Design System Component

Entity Component

Feature Component

Form

Dialog

Hook
```

---

# 6. Component Test에서 검증하는 것

대표적인 범위:

```txt
텍스트와 UI 출력

Props에 따른 상태

사용자 Click / Input

Disabled State

Error Message

Dialog Open / Close

Form Interaction

Keyboard Interaction

Accessibility Contract

Callback 실행
```

예:

```txt
Button 클릭
→ Callback 호출

ActionResult에 Field Error 존재
→ Input Error 출력

Mutation 성공
→ Dialog 닫기
→ router.refresh()
```

마지막 예에서 `router.refresh()`는 Server Action Test가 아니라 해당 Feature Component 또는 Hook Test의 책임입니다.

---

# 7. Integration Test

Integration Test는 여러 실제 계층 또는 Infrastructure가 함께 동작하는 것을 검증합니다.

대표적으로 다음 대상에 사용합니다.

```txt
Repository + PostgreSQL

Transaction

Database Constraint

Domain Service + Repository

Server Infrastructure 조합

여러 Module의 실제 연결
```

Unit Test보다 넓은 범위를 다루지만 전체 Browser Application을 실행하지는 않습니다.

---

# 8. E2E Test

E2E Test는 실제 Application을 실행하고 Browser 관점에서 사용자 흐름을 검증합니다.

사용 도구:

```txt
Playwright
```

대표적인 대상:

```txt
페이지 진입

로그인된 사용자 흐름

검색

필터

Form 제출

CRUD

Navigation

상태 변경

Server Action

Database 반영

화면 갱신
```

E2E는 여러 계층이 실제로 연결되었을 때 기능이 정상적으로 작동하는지 확인합니다.

---

# 9. 테스트 책임 요약

기본 구분은 다음과 같습니다.

```txt
Unit
  작은 Logic

Component
  React UI / Interaction

Integration
  실제 Module / Database 연결

E2E
  실제 Application 사용자 흐름
```

같은 기능도 테스트 종류에 따라 검증 대상이 다릅니다.

예를 들어 회원 차단 기능이라면:

```txt
Permission Unit Test
  자기 자신 차단 불가

Domain Service Test
  Permission 실패 시 Repository Update 없음

Server Action Test
  인증 / Validation / Service 호출 / ActionResult

Feature Test
  성공 시 Dialog 닫기 / Toast / refresh

E2E
  관리자가 실제 회원을 차단하고 화면에서 상태 변경 확인
```

으로 나눕니다.

# 10. Vitest 공통 설정

Vitest 공통 설정은:

```txt

```

에서 제공합니다.

현재 Public Config:

```txt
@repo/vitest-config/node

@repo/vitest-config/react

@repo/vitest-config/node-integration

@repo/vitest-config/react-integration
```

각 Package와 App은 자신의 Runtime에 맞는 Config를 확장해서 사용합니다.

---

# 11. Node Test 환경

Node 환경은 다음 Config를 사용합니다.

```txt
@repo/vitest-config/node
```

Runtime:

```txt
environment: node
```

대표적인 대상:

```txt
core

domain

database 외 순수 Helper

auth Server Logic

mailer

storage

Server Action

Node Utility
```

React DOM이 필요하지 않은 코드는 Node 환경을 우선합니다.

---

# 12. React Test 환경

React Component와 Hook은:

```txt
@repo/vitest-config/react
```

를 사용합니다.

Runtime:

```txt
environment: jsdom
```

추가 설정:

```txt
@vitejs/plugin-react

@testing-library/jest-dom/vitest
```

대표적인 대상:

```txt
React Component

React Hook

Form Interaction

Client Feature

Design System UI
```

단순 TypeScript Logic을 테스트하기 위해 불필요하게 jsdom을 사용하지 않습니다.

---

# 13. `server-only` 처리

Vitest 공통 Config에서는:

```txt
server-only
```

Package를 Test용 빈 Module로 Alias합니다.

Test 환경에서는 Next.js의 실제 Server Boundary 검사보다 해당 Server Module의 Logic 자체를 테스트해야 할 수 있기 때문입니다.

개념:

```txt
Runtime
  server-only
  → Server Boundary 보호

Vitest
  server-only
  → Test Stub
```

이 설정을 이용해 Production 코드에서 `server-only` Import를 제거하지 않습니다.

---

# 14. Test Environment

Vitest 실행 시 공통 Environment Loader가:

```txt
.env.test
.env.test.local
```

을 읽습니다.

그리고:

```txt
NODE_ENV=test
```

를 설정합니다.

우선순위는 다음과 같이 관리합니다.

```txt
현재 Process / CI Environment
        ↓
.env.test
        ↓
.env.test.local
```

`.env.test.local`은 개발자의 Local Override를 위한 파일입니다.

환경변수 전체 기준은 `06_환경변수.md`에서 설명합니다.

---

# 15. `passWithNoTests`

공통 Vitest Config에서는:

```txt
passWithNoTests: true
```

를 사용합니다.

Turborepo Boilerplate에서는 모든 Workspace Package와 App에 항상 Test File이 존재하는 것은 아닙니다.

따라서:

```txt
테스트가 없는 Package
→ Test Command 실패
```

로 처리하지 않습니다.

대신:

```txt
테스트가 없는 Package
→ 정상 종료
```

하도록 구성합니다.

이는 테스트 실패를 숨기기 위한 설정이 아니라 **Test File이 아직 존재하지 않는 Workspace를 정상 상태로 허용하기 위한 설정**입니다.

# 18. Node Integration

Node Integration은:

```txt
environment: node
```

를 사용합니다.

대표적인 대상:

```txt
Repository

Domain Service + Repository

Transaction

Database Constraint

Server Infrastructure
```

Database 관련 Integration Test는 일반적으로 이 환경을 사용합니다.

---

# 19. React Integration

React Integration은:

```txt
environment: jsdom
```

을 사용합니다.

여러 React 계층과 실제 Module의 연결을 함께 검증해야 할 때 사용할 수 있습니다.

다만 단일 Component의 Interaction만 검증한다면 일반 React Component Test를 우선합니다.

```txt
단일 Component
→ react

여러 UI Module과 실제 연결
→ react-integration 검토
```

---

# 20. Integration Test Timeout

Integration Test는 일반 Unit Test보다 실제 Infrastructure 작업이 많을 수 있으므로 공통 설정에서 다음 Timeout을 사용합니다.

```txt
testTimeout: 30_000

hookTimeout: 30_000
```

Timeout을 늘리는 것으로 느린 테스트를 무조건 해결하지 않습니다.

테스트가 반복적으로 오래 걸린다면:

```txt
Database Setup

불필요한 Network 접근

과도한 Fixture

잘못된 Transaction

Connection 종료
```

등을 먼저 확인합니다.

---

# 21. Integration Test Parallelism

Integration Test에서는:

```txt
fileParallelism: false
```

를 기본값으로 사용합니다.

실제 Database 등 공유 Resource를 여러 Test File이 동시에 수정하면 다음 문제가 발생할 수 있기 때문입니다.

```txt
Fixture 충돌

Unique Constraint 충돌

테스트 순서 의존

Data Cleanup 충돌

재현하기 어려운 실패
```

따라서 Boilerplate 기본 전략은 **실행 속도보다 Integration Test 재현성을 우선**합니다.

---

# 22. Test Database

Integration Test는 개발 Database와 분리된 Test Database를 사용합니다.

흐름:

```txt
.env.test
.env.test.local
      ↓
Test DATABASE_URL
      ↓
Test Schema
      ↓
Integration Test
```

관련 명령:

```bash
pnpm db:test:generate
pnpm db:test:push
pnpm db:test:migrate
```

Database 환경 분리는 `07_데이터베이스.md`에서 설명합니다.

---

# 23. Repository Test

Repository는 Persistence를 담당하므로 실제 PostgreSQL을 사용하는 Integration Test를 우선합니다.

대표적인 검증 대상:

```txt
조회 조건

생성

수정

삭제

Relation

Select / Include

Pagination

Unique Constraint

Transaction

Database Error Mapping
```

Repository Test에서 Prisma를 광범위하게 Mock하여 실제 Database 동작을 흉내 내는 방식을 우선하지 않습니다.

---

# 24. Repository에서 Mock보다 실제 DB를 사용하는 이유

Repository의 핵심 책임은:

```txt
Database와 실제로 올바르게 상호작용하는가?
```

이기 때문입니다.

Mocked Prisma는 다음을 정확하게 검증할 수 없습니다.

```txt
PostgreSQL Constraint

Relation

Migration 결과

Prisma Query 실제 동작

Transaction Rollback

Database Type
```

따라서 중요한 Repository 동작은 Integration Test로 검증합니다.

---

# 25. Domain Rule과 Permission Test

다음처럼 순수하게 판단 가능한 Domain Logic은 Unit Test가 적합합니다.

```txt
Rule

Permission

Calculation

State Transition
```

예:

```txt
canPublishContent(...)

canBlockUser(...)

calculateRefundableQuantity(...)
```

Database가 필요 없는 판단을 Integration Test로 만들지 않습니다.

---

# 26. Domain Service Test

Domain Service는 Use Case Orchestration을 검증합니다.

대표적인 대상:

```txt
Repository 호출 순서

Resource Not Found

Permission 실패

Rule 실패

정상 성공

Domain Result

Transaction 조합
```

Service의 성격에 따라 Unit 수준의 Dependency Mock 또는 Integration Test를 선택할 수 있습니다.

---

# 27. Domain Service의 Mock 기준

Service가 다음 역할만 조립한다면 Repository를 Mock하여 Business Flow를 빠르게 검증할 수 있습니다.

```txt
Repository 조회

Rule

Permission

Repository 변경

Result
```

예:

```txt
Repository가 Resource 없음 반환
→ NOT_FOUND Result

Permission 실패
→ Update Repository 호출 없음
```

이 테스트에서는 Repository SQL 동작 자체를 다시 검증하지 않습니다.

---

# 28. Domain Service Integration Test

다음과 같은 경우 실제 Repository와 Database를 포함한 Integration Test를 추가할 가치가 있습니다.

```txt
복잡한 Transaction

여러 Repository 조합

Database Constraint와 Business Flow가 강하게 연결됨

실제 Persistence 결과가 Use Case의 핵심임
```

모든 Service에 Integration Test를 강제하지 않습니다.

---

# 29. Mapper Test

Mapper가 단순한 Field 복사 수준이면 별도 Test가 필요하지 않을 수 있습니다.

다음 경우 Unit Test를 검토합니다.

```txt
복잡한 Nested Mapping

nullable 처리

여러 상태에 따른 Response 변환

Persistence Field 숨김

계산된 Response Field
```

구현 세부사항보다 최종 DTO 결과를 검증합니다.

---

# 30. Schema Test

Zod Schema는 중요한 Boundary Rule이 있을 때 독립적으로 테스트할 수 있습니다.

대표적인 대상:

```txt
최소 / 최대 길이

Enum

Coercion

Optional / Nullable

복잡한 refine

여러 Field 관계
```

단순한:

```txt
z.string()

z.uuid()
```

같은 Zod 자체의 기본 동작까지 모두 테스트하지 않습니다.

---

# 31. Server Action Test

Server Action Test는 Application Boundary를 검증합니다.

주요 대상:

```txt
Authentication

FormData Parsing

Input Normalization

Zod Validation

Domain Service 호출

ActionResult 변환

revalidatePath

redirect
```

Server Action 내부에서 Business Rule을 다시 테스트하지 않습니다.

---

# 32. Server Action 인증 테스트

보호된 Action에서는 다음을 검증할 수 있습니다.

```txt
인증 실패
→ Service 호출 없음

관리자 인증 실패
→ Admin Service 호출 없음

인증 성공
→ 적절한 Actor로 Service 호출
```

구체적인 Resource Permission은 Domain Test에서 검증합니다.

---

# 33. Server Action Validation Test

잘못된 입력에서는:

```txt
Validation 실패

Domain Service 호출 없음

적절한 ActionResult 반환
```

을 검증합니다.

모든 Schema Edge Case를 Action Test에서 반복하지 않습니다.

Schema 자체의 세부 규칙은 필요한 경우 Schema Unit Test에서 검증합니다.

---

# 34. Server Action 후처리 Test

Mutation 성공 시:

```txt
revalidatePath
```

가 필요한 Action이라면 올바른 Path가 무효화되는지 확인합니다.

실패 결과에서는 불필요한 Revalidation이 실행되지 않아야 합니다.

`redirect`가 성공 흐름에 포함된다면 Navigation도 검증합니다.

---

# 35. `router.refresh()` Test 위치

`router.refresh()`는 Server Action의 책임이 아닙니다.

따라서 Action Test에서 검증하지 않습니다.

해당 Mutation의 Client Interaction을 소유한:

```txt
Feature Form

Feature Dialog

Action Button

공통 Feature Hook
```

테스트에서 확인합니다.

예:

```txt
Action 성공
→ Dialog Close
→ router.refresh()
```

구체적인 책임은 `09_Server_Actions.md`를 따릅니다.

---

# 36. React Entity Test

Entity Component는 Business Object의 표현을 검증합니다.

예:

```txt
Status별 Label

DTO 값 출력

Empty Value 표현

Link 구성

Conditional Presentation
```

Entity가 Domain Business Rule 자체를 새로 판단하지 않도록 합니다.

이미 Domain에서 검증된 Rule을 UI Test에서 다시 전부 테스트하지 않습니다.

---

# 37. React Feature Test

Feature Component는 사용자 Interaction과 Application 연결을 검증합니다.

대표적인 대상:

```txt
Form 입력

Client Validation

Server Action 호출

Pending State

ActionResult 처리

Toast

Dialog Close

router.refresh

Callback
```

Server Action 내부 로직을 Feature Test에서 다시 구현하지 않습니다.

---

# 38. Design System Test

Design System은 Domain과 무관한 UI Contract를 검증합니다.

대표적인 Component Test:

```txt
Rendering

Interaction

Disabled State

Keyboard

ARIA

Error Presentation

Theme Interaction
```

대표적인 Unit Test:

```txt
Form Error Utility

Theme Utility

Class Utility
```

Storybook의 역할과는 구분합니다.

```txt
Storybook
  상태를 보고 탐색

Test
  기대 동작을 자동 검증
```

---

# 39. View Test

View는 여러 Entity와 Feature를 조립하는 역할이므로 모든 View에 Component Test를 강제하지 않습니다.

다음 경우 Test 가치가 있습니다.

```txt
복잡한 Conditional Assembly

Error / Empty / Success State 분기

여러 Feature 연결

중요한 UI 계약
```

단순히 Component를 나열하는 View는 E2E에서 충분히 검증될 수 있습니다.

---

# 40. Page Test

Next.js `page.tsx`가 단순히:

```txt
params / searchParams resolve
      ↓
View 전달
```

만 담당한다면 별도의 Unit Test 가치가 낮을 수 있습니다.

반대로 Page에서 중요한 Routing Contract가 있다면 Test를 추가할 수 있습니다.

Page에 Business Logic을 넣고 그 때문에 Test가 복잡해지는 구조는 피합니다.

# 44. 기존 개발 서버 재사용

```txt

```

를 사용합니다.

이미 해당 Port에서 개발 서버가 실행 중이라면 Playwright가 새 서버를 만들지 않고 재사용할 수 있습니다.

CI에서는 기존 서버를 가정하지 않습니다.

---

# 45. E2E Parallelism

Playwright Test 자체는:

```txt
fullyParallel: true
```

를 사용합니다.

다만 CI에서는:

```txt
workers: 1
```

을 사용하여 실행 안정성을 우선합니다.

즉:

```txt
Local
  가능한 Parallel 실행

CI
  Worker 1
  재현성과 안정성 우선
```

으로 구성합니다.

E2E 데이터가 서로 충돌하는 Test를 작성해서는 안 됩니다.

---

# 46. CI Retry

CI에서는:

```txt
retries: 2
```

를 사용합니다.

Local에서는:

```txt
retries: 0
```

입니다.

Retry는 Flaky Test를 정상으로 간주하기 위한 기능이 아닙니다.

반복적으로 Retry에서만 성공하는 Test는 원인을 찾아 수정합니다.

---

# 47. `forbidOnly`

CI에서는:

```txt
forbidOnly: true
```

를 사용합니다.

따라서 실수로 다음 코드가 Commit되어 전체 E2E 범위를 건너뛰는 것을 방지합니다.

```ts
test.only(...)
```

Local 개발에서는 필요한 경우 임시 Focus 실행을 사용할 수 있습니다.

---

# 48. Browser Project

현재 E2E는 대표적으로 다음 환경을 검증합니다.

```txt
Mobile Chrome
```

각각:

```txt

```

Device Profile을 사용합니다.

기본 Boilerplate에서 모든 Browser Engine을 강제하지 않습니다.

실제 서비스 요구가 생긴 경우 Safari/WebKit, Firefox 등의 확대를 검토합니다.

# 51. E2E 인증

각 앱의 E2E에서는 `globalSetup`을 통해 인증 상태를 준비할 수 있습니다.

현재 흐름은 다음과 같습니다.

```txt
E2E Seed
    ↓
고정 E2E 사용자
    ↓
Global Setup
    ↓
Session Record 생성 / 갱신
    ↓
Storage State 작성
    ↓
Browser Test
```

실제 OAuth Provider UI를 모든 E2E Test에서 반복해서 통과하지 않습니다.

---

# 52. E2E 인증과 실제 Auth

E2E에서 Session을 직접 준비하는 목적은 OAuth Provider 자체를 테스트하기 위한 것이 아닙니다.

검증 대상은:

```txt
로그인된 사용자 상태에서

Application이 올바르게 동작하는가?
```

입니다.

Google, Naver, Kakao 등의 실제 OAuth Provider는 외부 시스템이므로 일반 E2E Scenario의 핵심 Dependency로 만들지 않습니다.

---

# 53. Global Setup에서 Script Client 사용

E2E 인증 준비에서는:

```txt
@repo/database/script-client
```

를 사용할 수 있습니다.

Global Setup은 Application Runtime이 아니라 독립적인 Test Infrastructure Script이기 때문입니다.

이 경우:

```txt
Seed 사용자 존재 확인

Session Fixture 구성

Storage State 구성
```

과 같은 E2E Infrastructure 작업을 수행할 수 있습니다.

이는 앱 또는 Domain Layer에서 Prisma를 직접 사용하는 것과는 다른 경계입니다.

---

# 54. E2E Seed

E2E Test는:

```txt
pnpm db:e2e:seed
```

로 준비된 고정 Fixture를 사용합니다.

대표적인 대상:

```txt
E2E User

E2E Admin

정해진 상태의 Domain Data
```

Test가 개발자의 현재 Local Database 상태에 의존해서는 안 됩니다.

---

# 55. E2E Test 대상 선정

모든 세부 동작을 E2E로 작성하지 않습니다.

E2E 우선 대상:

```txt
핵심 사용자 Flow

중요 CRUD

인증이 필요한 흐름

Navigation

검색과 필터

중요 상태 변경

여러 Layer 연결이 핵심인 기능

Regression 비용이 큰 기능
```

---

# 56. E2E로 검증하지 않아도 되는 것

다음과 같은 작은 규칙을 E2E에서 모두 조합해서 검증하지 않습니다.

```txt
Pure Formatter

Zod 길이 제한의 모든 Boundary

Rule 함수의 모든 상태 조합

Mapper의 Field 변환

Utility 함수
```

이들은 Unit Test가 더 빠르고 명확합니다.

---

# 57. E2E Selector

E2E에서는 가능한 한 사용자 관점의 Selector를 사용합니다.

우선순위 예:

```txt
Role

Accessible Name

Label

Visible Text
```

예:

```ts
page.getByRole("button", {
  name: "저장",
});
```

DOM 구조나 Styling 구현 세부사항에 과도하게 의존하는 Selector는 피합니다.

---

# 58. `data-testid`

사용자가 인식할 수 있는 접근 가능한 Selector로 안정적으로 찾기 어려운 경우에만 `data-testid`를 검토합니다.

다음 이유만으로 모든 Element에 추가하지 않습니다.

```txt
Selector 작성이 편해서

CSS Selector보다 짧아서
```

UI 접근성 구조와 테스트 구조가 함께 좋아지는 Selector를 우선합니다.

---

# 59. E2E에서 직접 Database를 검증하는 기준

대부분의 E2E는 최종 UI 결과를 통해 성공 여부를 확인합니다.

예:

```txt
회원 차단
      ↓
상태 Badge가 차단으로 변경
```

매 Test마다 Browser 동작 후 Database Row를 직접 조회할 필요는 없습니다.

단 다음처럼 UI만으로 확인하기 어려운 중요한 Side Effect가 있다면 Database 검증을 추가할 수 있습니다.

# 65. Test File Colocation

Vitest Test는 기본적으로 테스트 대상 Source와 가까이 둡니다.

예:

```txt
src/user/
├─ user.permission.ts
├─ user.permission.test.ts
├─ user.service.ts
└─ user.service.test.ts
```

Integration Test도 해당 책임과 가까이 둘 수 있습니다.

```txt
src/user/
├─ user.repository.ts
└─ user.repository.integration.test.ts
```

E2E만 App의:

```txt
e2e/
```

Directory에 별도로 둡니다.

---

# 66. Mock의 목적

Mock은 실제 구현을 흉내 내는 것이 목적이 아니라 **테스트하려는 책임의 경계를 만드는 것**이 목적입니다.

좋은 질문:

```txt
이 테스트에서 이 Dependency의 실제 동작까지 검증해야 하는가?
```

아니라면 Mock을 사용할 수 있습니다.

---

# 67. Mock하기 좋은 대상

대표적으로:

```txt
Domain Service를 테스트하는 Repository

Server Action을 테스트하는 Domain Service

Feature를 테스트하는 Server Action

External API

시간

Randomness

Next Navigation

Next Cache
```

등이 있습니다.

---

# 68. 실제 의존성을 우선하는 대상

다음은 실제 동작 자체가 테스트의 핵심이므로 Mock보다 실제 Dependency를 우선합니다.

```txt
Repository의 PostgreSQL 동작

Database Constraint

Transaction

React DOM Interaction

Playwright Browser

E2E Application
```

---

# 69. Prisma Mock 남용을 피한다

Repository Test에서 Prisma API를 전부 Mock하면 다음 코드는 검증할 수 있습니다.

```txt
findUnique가 호출되었는가?
```

하지만 실제로 중요한:

```txt
그 Query가 PostgreSQL에서 올바르게 동작하는가?
```

는 검증하지 못합니다.

따라서 Repository는 실제 Test Database를 사용하는 Integration Test를 우선합니다.

---

# 70. Mock 구현을 다시 만들지 않는다

Mock 안에 실제 Production Logic을 복제하지 않습니다.

예를 들어:

```txt
실제 Permission Logic

실제 State Transition

실제 Mapper
```

를 Mock 함수 안에서 다시 작성하면 Test와 Production 구현이 동시에 잘못될 수 있습니다.

Mock은 가능한 한 단순한 고정 결과를 반환합니다.

---

# 71. External Provider

Mailer, Storage 등 External Provider는 테스트 종류에 따라 다르게 처리합니다.

Unit / Service Test:

```txt
Fake / Mock Provider
```

Integration Test:

```txt
Infrastructure 자체를 검증해야 할 때 Test Provider
```

E2E:

```txt
외부 Production Service 호출을 기본으로 하지 않음
```

실제 Mail 발송이나 Storage 비용이 E2E 실행에 포함되지 않도록 설계합니다.

---

# 72. 시간과 Randomness

시간이나 Random 값에 따라 결과가 달라지는 코드는 테스트 재현성을 떨어뜨립니다.

필요한 경우:

```txt
Clock Mock

고정 Date

고정 UUID

고정 Fixture
```

를 사용합니다.

특히 Seed와 E2E Fixture는 가능한 한 결정적으로 유지합니다.

---

# 73. 테스트 독립성

각 Test는 다른 Test의 성공이나 실행 순서에 의존하지 않아야 합니다.

지양:

```txt
Test A가 User 생성

Test B가 Test A User 사용
```

권장:

```txt
각 Test가 필요한 Fixture를 명시적으로 준비
```

또는 공통 Setup에서 안정적으로 초기화합니다.

---

# 74. Test Cleanup

실제 Database를 사용하는 Test에서는 다음 Test에 영향을 주지 않도록 데이터를 정리합니다.

방법은 Test 특성에 따라 선택합니다.

```txt
Test별 Fixture Cleanup

beforeEach 초기화

afterEach Cleanup

Transaction Rollback

Suite 단위 Reset
```

어떤 방법을 사용하든 결과적으로:

```txt
테스트 실행 순서가 바뀌어도 통과
```

해야 합니다.


를 찾기 위한 도구입니다.

Coverage 자체가 품질 점수는 아닙니다.

# 76. Coverage Provider

공통 Vitest Config는:

```txt
provider: v8
```

을 사용합니다.

Reporter:

```txt
text

html
```

을 제공합니다.

CLI에서는 빠르게 Text 결과를 확인하고 필요할 때 HTML Report로 상세한 누락 범위를 확인합니다.

# 77. Coverage 제외

다음과 같은 파일은 Coverage 대상에서 제외할 수 있습니다.

```txt
*.d.ts

Config File

index.ts Barrel

Integration Test File

Test File
```

이들은 Application Logic Coverage를 해석할 때 의미가 낮거나 Coverage 자체의 대상이 아니기 때문입니다.

---

# 78. Coverage Threshold

Boilerplate 기본 정책으로 전체 Repository에 강제적인 숫자 Threshold를 두지 않습니다.

예:

```txt
Statements 90%

Branches 90%
```

같은 숫자를 품질 목표로 먼저 설정하지 않습니다.

이유:

```txt
Package마다 위험도가 다름

UI와 Pure Logic의 테스트 가치가 다름

숫자를 채우기 위한 의미 없는 Test가 생길 수 있음
```

필요한 프로젝트에서 실제 운영 요구에 따라 Threshold를 추가할 수 있습니다.

---

# 79. Coverage를 우선 확인할 영역

Coverage 숫자 자체보다 다음 영역에 테스트가 빠져 있지 않은지 우선 확인합니다.

```txt
Business Rule

Permission

중요 Domain Service

Error Branch

Transaction

중요 Server Action

복잡한 Feature Interaction
```

단순 Getter나 Barrel Export의 Coverage를 채우는 데 시간을 쓰지 않습니다.

---

# 80. 테스트를 작성하지 않아도 되는 코드

모든 Source File에 1:1 Test File을 만들지 않습니다.

별도 Test 가치가 낮은 예:

```txt
단순 Barrel Export

단순 Type Definition

상수 선언만 있는 파일

아무 Logic 없는 Wrapper

단순 Page Composition

Library API를 그대로 전달하는 코드
```

해당 코드가 상위 Integration / E2E에서 자연스럽게 검증된다면 별도 Test가 필요하지 않을 수 있습니다.

---

# 81. Regression Test

Bug를 수정할 때 가능하면 먼저 해당 Bug를 재현하는 적절한 수준의 Test를 추가합니다.

선택 기준:

```txt
Pure Rule Bug
→ Unit

Repository Bug
→ Integration

UI Interaction Bug
→ Component

전체 Flow Bug
→ E2E
```

Bug가 발생한 위치보다 **Bug를 가장 작고 안정적으로 재현할 수 있는 계층**을 선택합니다.

---

# 82. 테스트 추가 판단 순서

새로운 기능을 구현할 때 다음 순서로 판단합니다.

```txt
1. 새로운 Pure Business Rule이 있는가?

2. Permission이 있는가?

3. Repository Query가 추가되는가?

4. 복잡한 Domain Service인가?

5. Server Action Boundary가 중요한가?

6. React Interaction이 있는가?

7. 중요한 사용자 Flow인가?
```

각 질문에 필요한 Test만 추가합니다.

모든 단계에 Test를 의무적으로 하나씩 만들지 않습니다.

---

# 83. 기능 구현과 테스트 흐름 예

새로운 Mutation Feature:

```txt
Schema
  ↓ 필요 시 Unit Test

Permission / Rule
  ↓ Unit Test

Repository
  ↓ Integration Test

Domain Service
  ↓ Unit 또는 Integration Test

Server Action
  ↓ Boundary Test

Feature Component
  ↓ Component Test

핵심 사용자 Flow
  ↓ E2E
```

기능의 복잡도에 따라 불필요한 단계를 생략합니다.


# 86. CI

CI에서는 일반적으로 다음 범위를 단계적으로 검증합니다.

```txt
Lint / Type Check / Format

Unit / Component Test

Build

Integration Test

E2E
```

모든 Test가 동일한 Runtime을 사용하지 않으므로 환경변수와 Database Setup 역시 단계별로 분리합니다.

---

# 87. Test Failure 해석

Test가 실패했을 때 곧바로 Assertion을 느슨하게 변경하지 않습니다.

먼저 다음을 판단합니다.

```txt
Production Bug인가?

Test Fixture가 잘못되었는가?

Architecture 책임이 바뀌었는가?

실제 Requirement가 바뀌었는가?

Flaky Test인가?

환경 설정 문제인가?
```

의도적으로 동작이 변경되었다면 Test도 새로운 Contract에 맞게 수정합니다.

---

# 88. 테스트가 구현을 방해할 때

Test 때문에 Production 구조가 지나치게 복잡해진다면 Test 전략을 다시 검토합니다.

다음과 같은 Test 전용 Production API를 무분별하게 만들지 않습니다.

```txt
테스트에서 private state를 읽기 위한 export

테스트에서만 호출하는 method

테스트를 위한 Production flag
```

좋은 Architecture는 일반적으로 외부 Contract를 통해 테스트할 수 있어야 합니다.

# 90. 핵심 원칙

```txt
Unit Test는 작은 Logic을 검증한다.

Component Test는 React UI와 Interaction을 검증한다.

Integration Test는 실제 Module과 Infrastructure의 연결을 검증한다.

E2E Test는 실제 사용자 흐름을 검증한다.

Node Logic에는 node 환경을 사용한다.

React UI에는 jsdom 환경을 사용한다.

Integration Test는 일반 Test와 파일 및 실행 명령을 분리한다.

Integration Test의 재현성을 위해 File Parallelism을 기본적으로 끈다.

Test가 없는 Workspace는 passWithNoTests로 정상 상태를 허용한다.

Repository는 실제 PostgreSQL Integration Test를 우선한다.

Domain Rule과 Permission은 Unit Test를 우선한다.

Domain Service는 책임에 따라 Mock 기반 Test와 Integration Test를 선택한다.

Server Action Test는 Authentication, Validation, Service 연결, ActionResult를 검증한다.

router.refresh는 Feature Test에서 검증한다.

React Component는 사용자가 관찰할 수 있는 결과와 Interaction을 검증한다.

E2E는 모든 Edge Case가 아니라 중요한 사용자 Flow를 검증한다.

E2E 인증은 고정된 Seed와 Storage State를 사용한다.

외부 OAuth Provider를 일반 E2E의 필수 Dependency로 만들지 않는다.

Mock은 테스트 경계를 만들기 위해 사용한다.

실제 Infrastructure 동작이 핵심이면 실제 의존성을 사용한다.

Coverage는 누락된 중요한 테스트 경로를 발견하는 도구다.

Coverage 숫자 자체를 품질 목표로 삼지 않는다.

모든 Source File에 Test File을 강제하지 않는다.

중복 테스트보다 각 계층의 책임에 맞는 테스트를 작성한다.
```
