# 의존성 경계

이 문서는 `boilerplate-turborepo`의 Workspace 간 의존성 방향과 금지 규칙을 정의합니다.

목표는 단순히 순환 의존성을 피하는 것이 아니라 각 Package의 책임을 유지하고, 하위 계층이 상위 계층의 구현에 끌려가지 않도록 하는 것입니다.

이 문서는 다음 질문에 대한 기준을 제공합니다.

```txt
이 Package가 저 Package를 의존해도 되는가?

새로운 Workspace Dependency를 추가해도 되는가?

왜 특정 방향의 Dependency는 금지되는가?

순환 의존성이 생기려 할 때 구조를 어떻게 풀어야 하는가?

pnpm check:boundaries는 무엇을 검사하는가?
```

Package별 책임 자체는 `04_패키지_구조.md`에서 설명합니다.

---

## 1. 기본 원칙

Workspace Dependency는 가능한 한 위에서 아래로 흐릅니다.

전체적인 방향은 다음과 같습니다.

```txt
apps/*
  ↓
Runtime Packages
  ↓
Lower-level Packages
```

핵심 원칙:

```txt
앱은 Package를 조립한다.

하위 Package는 자신을 사용하는 상위 Package를 모른다.

비즈니스 계층은 UI 계층을 모른다.

Database 계층은 Domain 계층을 모른다.

Infrastructure Package는 특정 앱을 모른다.

Package는 apps/*를 의존하지 않는다.

양방향 Dependency를 만들지 않는다.

순환 의존성을 허용하지 않는다.
```

Dependency를 추가할 때는 단순히 import가 가능하다는 이유가 아니라 책임의 방향이 맞는지를 먼저 판단합니다.

---

# 2. 전체 Runtime Dependency 방향

현재 Runtime Package의 큰 방향은 다음과 같습니다.

```txt
apps/*
  ├─→ @repo/auth
  ├─→ @repo/domain
  ├─→ @repo/database
  ├─→ @repo/design-system
  ├─→ @repo/core
  ├─→ @repo/env
  ├─→ @repo/mailer
  └─→ @repo/storage
```

Package 내부에서는 다음 방향을 사용합니다.

```txt
@repo/auth
  ├─→ @repo/domain
  ├─→ @repo/database
  ├─→ @repo/core
  └─→ @repo/env

@repo/domain
  ├─→ @repo/database
  └─→ @repo/core

@repo/database
  ├─→ @repo/core
  └─→ @repo/env

@repo/design-system
  └─→ @repo/core

@repo/core
  → 다른 Runtime Workspace Package에 의존하지 않음

@repo/env
  → 다른 Runtime Workspace Package에 의존하지 않음

@repo/mailer
  → 다른 Runtime Workspace Package에 의존하지 않음

@repo/storage
  → 다른 Runtime Workspace Package에 의존하지 않음
```

이 관계는 모든 Package가 반드시 표시된 Dependency를 가져야 한다는 뜻이 아닙니다.

```txt
허용된 방향
≠
반드시 가져야 하는 의존성
```

필요하지 않은 Dependency는 추가하지 않습니다.

---

# 3. 계층 관점의 방향

Runtime 구조를 단순화하면 다음과 같이 볼 수 있습니다.

```txt
Application
     ↓
Domain / Auth / Infrastructure / Design System
     ↓
Database / Core / Env
```

Backend 흐름은 다음과 같습니다.

```txt
App
 ↓
Domain
 ↓
Database
 ↓
Core
```

인증 흐름은 다음처럼 별도의 Infrastructure 경계를 가집니다.

```txt
App
 ↓
Auth
 ├─→ Domain
 ├─→ Database
 ├─→ Core
 └─→ Env
```

UI 흐름은 다음과 같습니다.

```txt
App
 ↓
Design System
 ↓
Core
```

외부 Infrastructure는 독립적인 경계를 유지합니다.

```txt
App
 ├─→ Mailer
 └─→ Storage
```

---

# 4. `apps/*`

`apps/*`는 최상위 조립 계층이므로 필요한 Runtime Package를 사용할 수 있습니다.

대표적인 허용 관계:

```txt
apps/*
  → @repo/auth
  → @repo/core
  → @repo/database
  → @repo/design-system
  → @repo/domain
  → @repo/env
  → @repo/mailer
  → @repo/storage
```

앱은 실행 가능한 최상위 Workspace이므로 다른 Runtime Package가 앱을 다시 참조해서는 안 됩니다.

금지:

```txt
@repo/core → apps/web
@repo/domain → apps/admin
@repo/auth → apps/web
@repo/design-system → apps/admin
```

일반화하면:

```txt
packages/* → apps/*
```

는 금지합니다.

앱에만 존재하는 기능이 Package에서 필요해졌다면 Package가 앱을 참조하는 것이 아니라 책임을 재배치해야 합니다.

---

# 5. `@repo/core`

`@repo/core`는 Runtime Package 중 가장 아래에 있는 공통 기반입니다.

따라서 다른 Runtime Workspace Package에 의존하지 않습니다.

허용:

```txt
@repo/core
  → 외부 범용 Library
```

예:

```txt
zod
```

금지:

```txt
@repo/core → @repo/domain
@repo/core → @repo/database
@repo/core → @repo/auth
@repo/core → @repo/design-system
@repo/core → @repo/env
@repo/core → @repo/mailer
@repo/core → @repo/storage
```

`core`가 상위 Package를 참조하기 시작하면 공통 기반이라는 역할을 잃게 됩니다.

---

# 6. `@repo/env`

`@repo/env`는 환경변수 검증과 접근 기반을 제공하는 낮은 계층의 Package입니다.

다른 Runtime Workspace Package의 비즈니스 또는 Infrastructure 구현에 의존하지 않습니다.

금지:

```txt
@repo/env → @repo/domain
@repo/env → @repo/database
@repo/env → @repo/auth
@repo/env → @repo/design-system
@repo/env → @repo/mailer
@repo/env → @repo/storage
```

`env`는 값을 검증하고 노출할 뿐, 해당 값을 사용하는 기능을 구현하지 않습니다.

예:

```txt
@repo/env
  DATABASE_URL 검증

@repo/database
  DATABASE_URL 사용
```

방향은:

```txt
database → env
```

이지:

```txt
env → database
```

가 아닙니다.

---

# 7. `@repo/database`

`@repo/database`는 DB 접근 계층입니다.

현재 허용되는 하위 Dependency:

```txt
@repo/database
  → @repo/core
  → @repo/env
```

의미:

```txt
core
  Result, Error 등의 공통 기반 사용

env
  Database Connection 설정 사용
```

금지:

```txt
@repo/database → @repo/domain
@repo/database → @repo/auth
@repo/database → @repo/design-system
@repo/database → @repo/mailer
@repo/database → @repo/storage
@repo/database → apps/*
```

특히 중요한 규칙은 다음입니다.

```txt
domain → database
```

는 허용하지만:

```txt
database → domain
```

은 금지합니다.

Repository는 Domain Service가 자신을 사용하는 것은 알 필요가 없습니다.

---

# 8. `@repo/domain`

`@repo/domain`은 비즈니스 규칙을 담당합니다.

현재 기본 Dependency 방향:

```txt
@repo/domain
  ├─→ @repo/database
  └─→ @repo/core
```

Domain Service는 Repository를 통해 데이터를 조회하거나 저장할 수 있고 공통 Result, Error 등의 기반을 사용할 수 있습니다.

금지:

```txt
@repo/domain → @repo/auth
@repo/domain → @repo/design-system
@repo/domain → @repo/mailer
@repo/domain → @repo/storage
@repo/domain → apps/*
```

특히 UI와 Next.js 앱 구현을 Domain으로 가져오지 않습니다.

```txt
Domain
  비즈니스 판단

App
  사용자 인터랙션과 조립
```

이라는 경계를 유지합니다.

---

## 8.1 Domain과 Infrastructure

Mailer나 Storage 사용이 필요한 비즈니스 흐름이 생기더라도 기본적으로 Domain이 Infrastructure Package를 직접 가져오는 방향부터 선택하지 않습니다.

예:

```txt
회원 생성
+
환영 메일 발송
```

이런 흐름이 생겼다고 해서 바로:

```txt
domain → mailer
```

로 만들지 않습니다.

먼저 상위 Use Case 또는 App 조립 계층에서:

```txt
App / Use Case
├─→ Domain
└─→ Mailer
```

형태로 책임을 조립할 수 있는지 검토합니다.

Storage 역시 동일합니다.

```txt
App
├─→ Storage
└─→ Domain
     └─→ Database
```

Infrastructure가 비즈니스 계층을 끌어당기지 않도록 합니다.

---

# 9. `@repo/auth`

`@repo/auth`는 인증, OAuth, Session을 담당하는 Infrastructure Package입니다.

현재 구조에서는 다음 Package를 사용할 수 있습니다.

```txt
@repo/auth
  ├─→ @repo/core
  ├─→ @repo/database
  ├─→ @repo/domain
  └─→ @repo/env
```

각 Dependency의 의미:

```txt
core
  Result / Error / 공통 기반

database
  User / Session / OAuth Account 저장

domain
  User 관련 데이터 계약 및 필요한 도메인 규칙

env
  OAuth / Session 환경 설정
```

금지:

```txt
@repo/auth → @repo/design-system
@repo/auth → @repo/mailer
@repo/auth → @repo/storage
@repo/auth → apps/*
```

특정 앱의 로그인 화면이나 URL 구조는 `auth`가 알지 않습니다.

---

# 10. `@repo/design-system`

`@repo/design-system`은 UI 기반 Package입니다.

현재 허용되는 Runtime Workspace Dependency:

```txt
@repo/design-system
  → @repo/core
```

금지:

```txt
@repo/design-system → @repo/domain
@repo/design-system → @repo/database
@repo/design-system → @repo/auth
@repo/design-system → @repo/env
@repo/design-system → @repo/mailer
@repo/design-system → @repo/storage
@repo/design-system → apps/*
```

Design System이 Domain Package를 참조하기 시작하면 UI Primitive와 비즈니스 UI의 경계가 무너집니다.

예:

```txt
Button
Dialog
Select
Toast
```

는 Design System에 둘 수 있지만:

```txt
UserStatusBadge
OrderTable
ContentPublishDialog
```

는 앱의 Entity 또는 Feature에 둡니다.

---

# 11. `@repo/mailer`

`@repo/mailer`는 이메일 전송 방식 자체를 담당하는 독립적인 Infrastructure Package입니다.

현재 다른 Runtime Workspace Package에 의존하지 않습니다.

기본적으로 다음 방향을 유지합니다.

```txt
apps/* → @repo/mailer
```

반대 방향은 금지합니다.

```txt
@repo/mailer → apps/*
@repo/mailer → @repo/domain
@repo/mailer → @repo/database
@repo/mailer → @repo/auth
@repo/mailer → @repo/design-system
```

공통 기반이 실제로 필요해질 경우 `core`나 `env` 의존성을 추가할 수 있는지는 별도로 Boundary를 검토합니다.

단순히 편의를 위해 Dependency를 늘리지 않습니다.

---

# 12. `@repo/storage`

`@repo/storage`는 파일 저장 Infrastructure를 담당합니다.

현재 다른 Runtime Workspace Package에 의존하지 않습니다.

기본 방향:

```txt
apps/* → @repo/storage
```

금지:

```txt
@repo/storage → apps/*
@repo/storage → @repo/domain
@repo/storage → @repo/database
@repo/storage → @repo/auth
@repo/storage → @repo/design-system
```

Storage Metadata를 Database에 저장해야 하더라도 Storage Package가 Database를 직접 소유하는 구조로 만들지 않습니다.

기본 조립:

```txt
App
├─→ Storage
└─→ Domain
     └─→ Database
```

---

# 13. Config Package의 의존성

다음 Package는 Runtime Layer가 아니라 개발 Tool 설정을 제공합니다.

```txt
@repo/eslint-config
@repo/typescript-config
@repo/vitest-config
@repo/playwright-config
@repo/storybook-config
```

이들은 Runtime Package Dependency Graph와 별도로 생각합니다.

일반적인 방향:

```txt
apps/*
packages/*
tooling/*
  ↓ devDependencies

Config Packages
```

예:

```txt
@repo/design-system
  ├─dev→ @repo/eslint-config
  ├─dev→ @repo/typescript-config
  ├─dev→ @repo/vitest-config
  └─dev→ @repo/storybook-config
```

Config Package는 비즈니스 Runtime Package를 의존하지 않습니다.

금지할 방향:

```txt
@repo/eslint-config → @repo/domain
@repo/typescript-config → @repo/database
@repo/vitest-config → @repo/auth
@repo/storybook-config → @repo/design-system
```

특정 앱이나 Runtime Package의 구현을 Config Package로 끌어오지 않습니다.

---

# 14. Runtime Dependency와 Dev Dependency

Boundary를 판단할 때 Dependency 종류를 구분합니다.

Runtime에 영향을 주는 Dependency:

```txt
dependencies
peerDependencies
optionalDependencies
```

개발 도구만을 위한 Dependency:

```txt
devDependencies
```

예:

```json
{
  "dependencies": {
    "@repo/core": "workspace:*"
  },
  "devDependencies": {
    "@repo/eslint-config": "workspace:*",
    "@repo/typescript-config": "workspace:*"
  }
}
```

이 둘은 같은 의미가 아닙니다.

```txt
dependencies
  실제 실행 코드의 의존 관계

devDependencies
  개발 / 검사 / 테스트 / 문서화 도구의 의존 관계
```

Runtime Package가 Config Package를 `devDependencies`로 사용하는 것은 정상적인 구조입니다.

---

# 15. 금지되는 대표 방향

현재 아키텍처에서 특히 중요한 금지 관계는 다음과 같습니다.

```txt
packages/* → apps/*

core → domain
core → database
core → auth
core → design-system

env → domain
env → database
env → auth

database → domain

domain → design-system
domain → auth

design-system → domain
design-system → database
design-system → auth

mailer → domain
mailer → database

storage → domain
storage → database
```

모든 조합을 외워야 하는 것은 아닙니다.

다음 질문으로 판단할 수 있습니다.

```txt
이 Dependency가 상위 책임을 하위 계층으로 끌고 내려오는가?

이 Package가 자신을 사용하는 Package를 알게 되는가?

이 Dependency 때문에 두 Package가 서로를 참조하게 되는가?
```

하나라도 그렇다면 구조를 다시 검토합니다.

# 16. 순환 의존성

다음과 같은 관계는 금지합니다.

```txt
A → B
B → A
```

더 긴 Cycle 역시 금지합니다.

```txt
A → B → C → A
```

예:

```txt
domain → database
database → domain
```

은 허용하지 않습니다.

---

## 16.1 순환 의존성이 문제가 되는 이유

순환 의존성은 다음 문제를 만듭니다.

```txt
Package 책임이 모호해진다.

독립적인 테스트가 어려워진다.

Build 순서를 명확하게 정하기 어렵다.

하위 계층을 독립적으로 재사용하기 어려워진다.

하나의 변경이 여러 Package에 전파된다.

결국 Package 분리 자체가 의미를 잃는다.
```

Turborepo Build Graph가 동작한다고 해서 Architecture Cycle까지 허용되는 것은 아닙니다.

---

# 17. 순환 의존성을 발견했을 때

순환 관계가 필요해 보인다면 바로 Dependency를 추가하지 않습니다.

다음 순서로 검토합니다.

### 17.1 책임이 잘못 배치되었는지 확인

예:

```txt
database가 domain type을 필요로 한다.
```

먼저 해당 Type이 정말 Domain Type인지 확인합니다.

Database에서도 필요한 순수 공통 계약이라면 더 낮은 계층으로 이동할 수 있습니다.

```txt
domain
   ↘
    core
   ↗
database
```

---

### 17.2 조립 책임을 상위로 올릴 수 있는지 확인

예:

```txt
domain → storage
storage → domain
```

같은 관계가 필요해 보인다면:

```txt
App
├─→ domain
└─→ storage
```

로 조립 책임을 올리는 방법을 우선 검토합니다.

---

### 17.3 계약만 낮은 계층으로 분리할 수 있는지 확인

두 Package가 동일한 Type이나 작은 Contract 때문에 서로 참조한다면 공통 기반으로 추출할 수 있습니다.

단:

```txt
순환 의존성을 없애기 위해 무조건 core로 이동
```

해서는 안 됩니다.

`core`에 적합한 책임인지 먼저 확인합니다.

---

### 17.4 새로운 Package가 필요한지 검토

실제로 독립적인 책임이 존재하고 여러 Package가 해당 책임을 필요로 한다면 새로운 Package로 분리할 수 있습니다.

다만 단순히 Cycle을 없애기 위한 중간 Package를 만드는 것은 피합니다.

---

# 18. 의존성 방향과 Import 방향

`package.json`에 Dependency가 허용되어 있다고 해서 모든 내부 API를 자유롭게 사용할 수 있다는 뜻은 아닙니다.

예:

```txt
apps/* → @repo/domain
```

이 허용되어도:

```ts
import ... from "@repo/domain/src/user/user.service";
```

같은 Deep Import를 허용한다는 의미는 아닙니다.

Public API를 사용합니다.

```ts
import ... from "@repo/domain/user/server";
```

Dependency Boundary와 Public API Boundary는 함께 지켜야 합니다.

자세한 Export 규칙은 `04_패키지_구조.md`에서 설명합니다.

---

# 19. `pnpm check:boundaries`

Workspace 의존성 경계는 다음 명령어로 검사합니다.

```bash
pnpm check:boundaries
```

루트 Script는 `@repo/scripts`의 Boundary 검사기를 실행합니다.

```txt
Root
  pnpm check:boundaries

        ↓

@repo/scripts
  check:boundaries

        ↓

Workspace package.json 검사
```

목적:

```txt
금지된 Runtime Workspace Dependency를 조기에 발견한다.

Package 책임이 역전되는 것을 방지한다.

packages/* → apps/* 같은 잘못된 방향을 차단한다.

Architecture 규칙을 사람의 기억에만 의존하지 않는다.
```

---

# 20. 현재 Boundary 검사의 범위

현재 Boundary 검사는 Workspace의 `package.json`에 선언된 Runtime Dependency 관계를 기준으로 동작합니다.

주요 검사 대상:

```txt
dependencies
peerDependencies
optionalDependencies
```

즉 다음과 같은 선언을 검사합니다.

```json
{
  "dependencies": {
    "@repo/domain": "workspace:*"
  }
}
```

현재 Boundary 검사의 주된 목적은 **Workspace Package Graph의 Runtime 의존성 방향을 검증하는 것**입니다.

따라서 다음과 같은 모든 종류의 Architecture 문제를 하나의 Script가 전부 검사한다고 생각해서는 안 됩니다.

```txt
Source File 단위 Layer Rule

apps/* 내부 FSD Layer Rule

Public API Deep Import

Server / Client Import Boundary

같은 Layer의 Slice 간 Dependency
```

이러한 규칙은 ESLint, TypeScript, Package Export, 코드 리뷰와 각 전문 문서를 함께 사용해 관리합니다.

---

# 21. Boundary 검사와 `devDependencies`

공통 Tool Config는 일반적으로 `devDependencies`를 통해 사용됩니다.

예:

```json
{
  "devDependencies": {
    "@repo/eslint-config": "workspace:*",
    "@repo/typescript-config": "workspace:*",
    "@repo/vitest-config": "workspace:*"
  }
}
```

이러한 관계는 Runtime Architecture와 구분합니다.

현재 Boundary 정책의 핵심 대상은 Runtime Dependency Graph입니다.

따라서:

```txt
Runtime Boundary
  dependencies
  peerDependencies
  optionalDependencies

Tooling Dependency
  devDependencies
```

를 같은 의미로 취급하지 않습니다.

# 22. 언제 실행하는가

Dependency를 변경했다면 반드시 실행합니다.

```bash
pnpm check:boundaries
```

특히 다음 변경 후에는 필수로 확인합니다.

```txt
새 Workspace Package 추가

Package 간 dependency 추가

dependency 위치 변경

Runtime Package 역할 변경

기존 Package 분리

Package 통합

새 Infrastructure Package 추가
```

일상적인 전체 검사에서는 다음 명령을 사용할 수 있습니다.

```bash
pnpm check
```

현재 전체 품질 검사는 Boundary 검사도 포함합니다.

```txt
lint
 ↓
check:boundaries
 ↓
check-types
 ↓
format:check
```

# 23. Boundary 오류가 발생했을 때

Boundary 오류가 발생했다고 규칙을 바로 완화하지 않습니다.

먼저 다음 순서로 확인합니다.

```txt
1. Dependency가 정말 필요한가?

2. 코드가 잘못된 Package에 있는가?

3. 상위 계층에서 조립할 수 있는가?

4. 더 낮은 공통 책임으로 이동할 수 있는가?

5. 기존 Public API만으로 해결할 수 있는가?

6. 현재 Package 책임 자체를 변경해야 하는가?
```

Boundary 규칙 수정은 마지막 선택지입니다.

잘못된 대응:

```txt
검사가 실패하니까 예외 추가

일단 허용 목록에 넣기

순환 관계지만 실제로 동작하므로 유지
```

올바른 접근:

```txt
왜 기존 경계로 표현할 수 없는지 먼저 확인

새로운 Architecture 책임이 실제로 생겼는지 판단

필요하다면 코드 구조와 문서를 함께 변경
```

# 24. 새로운 Package 추가 시 Boundary 검토

새로운 Package를 추가할 때는 먼저 Package의 위치를 Dependency Graph에서 결정합니다.

예를 들어 새로운 Infrastructure Package:

```txt
@repo/analytics
```

를 만든다고 가정합니다.

다음 질문에 답합니다.

```txt
누가 analytics를 사용하는가?

analytics는 어떤 Workspace Package를 알아야 하는가?

domain을 알아야 하는가?

database를 직접 사용할 필요가 있는가?

core만 있으면 되는가?

env가 필요한가?

다른 Infrastructure Package를 알아야 하는가?
```

먼저 이상적인 위치를 정합니다.

예:

```txt
apps/*
  ↓
analytics
  ↓
core / env
```

그 후 실제 `package.json` Dependency를 구성합니다.

# 26. Boundary 규칙을 변경해야 하는 경우

다음 경우에는 Boundary 규칙 자체의 변경을 검토할 수 있습니다.

```txt
새 Runtime Package가 추가됨

기존 Package 책임이 공식적으로 변경됨

새로운 Infrastructure 계층이 생김

Architecture Layer가 추가됨

기존 Dependency 방향이 더 이상 현재 설계를 표현하지 못함
```

그 경우 다음 항목을 함께 수정합니다.

```txt
Package 구현

package.json

Boundary 검사 Script

04_패키지_구조.md

05_의존성_경계.md

필요한 경우 01_아키텍처.md
```

코드만 허용하고 문서를 그대로 두거나, 문서만 수정하고 검사 Script를 그대로 두지 않습니다.

# 27. Boundary Script와 문서의 관계

Boundary 규칙에는 두 종류가 있습니다.

### Architecture Rule

이 문서가 정의하는 설계 기준입니다.

```txt
database는 domain을 의존하지 않는다.

packages는 apps를 의존하지 않는다.

design-system은 business domain을 모른다.
```

### Automated Rule

`check-boundaries.ts`가 자동으로 검사하는 규칙입니다.

```txt
package.json에 잘못된 Runtime Workspace Dependency가 선언되었는가?
```

이 둘은 가능한 한 일치해야 합니다.

```txt
Architecture Rule
        ↓
Boundary Script
        ↓
CI / Local Check
```

Architecture Rule이 변경되면 Script도 검토합니다.

Script가 모든 Architecture 규칙을 검사하지 못한다고 해서 해당 규칙이 사라지는 것은 아닙니다.

# 28. Runtime Package Boundary 요약

현재 Runtime Package의 기본 관계는 다음과 같습니다.

```txt
apps/*
  ├─→ auth
  ├─→ core
  ├─→ database
  ├─→ design-system
  ├─→ domain
  ├─→ env
  ├─→ mailer
  └─→ storage


auth
  ├─→ core
  ├─→ database
  ├─→ domain
  └─→ env


domain
  ├─→ core
  └─→ database


database
  ├─→ core
  └─→ env


design-system
  └─→ core


core
  → 독립


env
  → 독립


mailer
  → 독립


storage
  → 독립
```

# 29. 의존성 Matrix

현재 Runtime Workspace 기준으로 단순화하면 다음과 같습니다.

| From                  | 허용되는 주요 Runtime Workspace Dependency                                        |
| --------------------- | --------------------------------------------------------------------------------- |
| `apps/*`              | `auth`, `core`, `database`, `design-system`, `domain`, `env`, `mailer`, `storage` |
| `@repo/auth`          | `core`, `database`, `domain`, `env`                                               |
| `@repo/domain`        | `core`, `database`                                                                |
| `@repo/database`      | `core`, `env`                                                                     |
| `@repo/design-system` | `core`                                                                            |
| `@repo/core`          | 없음                                                                              |
| `@repo/env`           | 없음                                                                              |
| `@repo/mailer`        | 없음                                                                              |
| `@repo/storage`       | 없음                                                                              |

이 표는 Runtime Workspace Dependency를 기준으로 합니다.

외부 npm Package와 Config Package의 `devDependencies`는 별도입니다.
