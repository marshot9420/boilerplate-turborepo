# 프로젝트 구조

이 문서는 `boilerplate-turborepo` Repository의 전체 구조와 각 최상위 디렉터리의 역할을 설명합니다.

세부 구현 규칙을 모두 나열하기보다 처음 Repository를 열었을 때 다음 질문에 빠르게 답할 수 있도록 구성합니다.

```txt
실행 가능한 앱은 어디에 있는가?

공통 코드는 어디에 있는가?

개발 도구와 자동화 코드는 어디에 있는가?

프로젝트 문서는 어디에 있는가?

새로운 코드를 추가할 때 어느 영역부터 확인해야 하는가?
```

앱 내부의 세부 구조, Package별 책임, 의존성 규칙은 각각의 전문 문서에서 다룹니다.

---

## 1. 전체 구조

Repository의 주요 구조는 다음과 같습니다.

```txt
.
├─ apps/
├─ packages/
├─ tooling/
├─ docs/
├─ package.json
├─ pnpm-workspace.yaml
├─ turbo.json
├─ .nvmrc
├─ CLAUDE.md
├─ CLAUDE.local.example.md
└─ README.md
```

각 영역의 책임은 다음과 같습니다.

```txt
apps
  실행 가능한 애플리케이션

packages
  여러 Workspace에서 재사용하는 Package와 공통 설정

tooling
  코드 생성, 초기화, 검증 등 개발 자동화

docs
  아키텍처와 개발 규칙 문서

Repository Root
  Workspace, Runtime, Task Runner 등 전체 프로젝트 설정
```

---

## 2. `apps`

`apps/`에는 독립적으로 실행하고 배포할 수 있는 애플리케이션을 둡니다.

현재 구조:

```txt
apps/
├─ admin/
└─ web/
```

### `apps/web`

일반 사용자에게 제공하는 웹 애플리케이션입니다.

```txt
apps/web/
├─ .storybook/
├─ e2e/
├─ public/
├─ src/
├─ eslint.config.js
├─ next.config.ts
├─ playwright.config.ts
├─ postcss.config.mjs
├─ tsconfig.json
├─ vitest.config.ts
├─ vitest.integration.config.ts
└─ package.json
```

### `apps/admin`

관리 기능을 제공하는 웹 애플리케이션입니다.

기본적인 프로젝트 구성은 `web`과 동일한 Next.js App Router 기반을 사용합니다.

```txt
apps/admin/
├─ .storybook/
├─ e2e/
├─ public/
├─ src/
├─ eslint.config.js
├─ next.config.ts
├─ playwright.config.ts
├─ postcss.config.mjs
├─ tsconfig.json
├─ vitest.config.ts
├─ vitest.integration.config.ts
└─ package.json
```

각 앱은 가능한 한 비즈니스 규칙이나 Infrastructure 구현을 직접 소유하기보다 `packages/*`의 기능을 조립하여 사용합니다.

앱의 `src` 내부 구조와 `app`, `views`, `features`, `entities` 등의 역할은 `10_앱_구조.md`에서 설명합니다.

---

## 3. 앱 내부의 큰 구조

각 앱의 `src`는 대체로 다음 영역으로 구성됩니다.

```txt
src/
├─ actions/
├─ app/
├─ config/
├─ constants/
├─ entities/
├─ features/
├─ hooks/
├─ libs/
├─ shared/
├─ types/
├─ utils/
└─ views/
```

모든 디렉터리를 항상 만들 필요는 없습니다.

실제로 필요한 책임이 있을 때만 생성하며 사용하지 않는 빈 구조를 미리 만들지 않습니다.

이 문서에서는 위치만 소개하며 각 계층의 세부 책임과 의존 방향은 `10_앱_구조.md`를 기준으로 합니다.

## 4. `packages`

`packages/`에는 여러 앱 또는 Tooling에서 재사용할 수 있는 독립적인 Package를 둡니다.

현재 주요 구조:

```txt
packages/
├─ auth/
├─ core/
├─ database/
├─ design-system/
├─ domain/
├─ env/
├─ mailer/
├─ storage/
├─ eslint-config/
├─ playwright-config/
├─ storybook-config/
├─ typescript-config/
└─ vitest-config/
```

Package는 크게 Runtime Package와 개발 설정 Package로 나눌 수 있습니다.

---

### 4.1 Runtime Package

애플리케이션 실행 과정에서 사용하는 기능을 제공합니다.

```txt
packages/
├─ core/
├─ domain/
├─ database/
├─ auth/
├─ design-system/
├─ env/
├─ mailer/
└─ storage/
```

큰 역할은 다음과 같습니다.

```txt
core
  Result, Error, Action, Input, Pagination, Query, Formatter, Parser, Resolver 등 순수 공통 기반 코드

domain
  비즈니스 규칙과 데이터 계약

database
  Prisma와 Repository를 통한 데이터 저장 계층

auth
  인증, OAuth, Session

design-system
  앱에 독립적인 공통 UI 기반

env
  환경변수 검증과 접근

mailer
  메일 전송 추상화

storage
  파일 Storage 추상화
```

각 Package의 정확한 책임과 내부 구조는 `04_패키지_구조.md`에서 설명합니다.

---

### 4.2 Config Package

여러 Workspace에서 반복되는 개발 Tool 설정을 공통으로 제공합니다.

```txt
packages/
├─ eslint-config/
├─ playwright-config/
├─ storybook-config/
├─ typescript-config/
└─ vitest-config/
```

역할:

```txt
eslint-config
  ESLint 공통 규칙

typescript-config
  TypeScript 공통 Compiler 설정

vitest-config
  Unit / Component / Integration Test 공통 실행 설정

playwright-config
  E2E Test 공통 실행 설정

storybook-config
  Next.js 및 React Storybook 공통 설정
```

각 Workspace는 이 설정을 복제하지 않고 필요한 Config를 가져와 고유한 차이만 추가합니다.

공통 설정 정책은 `02_기본설정.md`에서 설명합니다.

---

## 5. `tooling`

`tooling/`에는 프로젝트를 실행하는 Runtime 코드가 아니라 개발 과정의 반복 작업을 자동화하기 위한 도구를 둡니다.

현재 구조:

```txt
tooling/
├─ generators/
└─ scripts/
```

---

### 5.1 `tooling/generators`

반복되는 코드와 디렉터리 구조를 생성합니다.

현재 다음 종류의 Generator를 제공합니다.

```txt
domain
component
entity
feature
view
```

예를 들어 앱의 Feature나 Entity를 생성할 때 프로젝트의 기본 구조와 Naming Convention을 일관되게 적용하는 데 사용합니다.

Generator의 명령어와 생성 규칙은 `14_코드_생성기.md`에서 설명합니다.

---

### 5.2 `tooling/scripts`

Repository 전체를 대상으로 하는 개발 및 유지보수 자동화 Script를 둡니다.

대표적인 역할:

```txt
프로젝트 초기화

Scope 변경

Database Seed

E2E Seed

Dependency Boundary 검사

Workspace 정리
```

초기 프로젝트 구성은 `15_프로젝트_초기화.md`, 일반적인 사용 흐름은 `16_개발_워크플로우.md`에서 설명합니다.

## 7. Repository Root

Repository Root에는 특정 Workspace가 아니라 프로젝트 전체에 영향을 주는 설정을 둡니다.

대표적인 파일:

```txt
package.json
pnpm-workspace.yaml
turbo.json
.nvmrc
```

역할은 다음과 같습니다.

### `package.json`

Workspace 전체에서 사용하는 Script와 Node.js, pnpm 버전 정책을 정의합니다.

### `pnpm-workspace.yaml`

Workspace 범위, pnpm 공통 정책, Catalog를 관리합니다.

```txt
apps/*
packages/*
tooling/*
```

를 Workspace로 등록합니다.

### `turbo.json`

Workspace Task의 실행 순서, Cache, Output, Persistent Task 등을 관리합니다.

### `.nvmrc`

로컬 개발 환경의 기준 Node.js 버전을 정의합니다.

Root 설정에 대한 자세한 내용은 `02_기본설정.md`에서 설명합니다.

## 8. 프로젝트 보조 파일

Root에는 코드 구조와 직접 관련되지는 않지만 개발 과정에 사용되는 파일도 존재합니다.

### `README.md`

Repository의 가장 빠른 진입점입니다.

프로젝트 소개와 기본 실행 방법 등 처음 사용하기 위해 필요한 최소 정보를 제공합니다.

상세 설계 규칙은 `docs/`로 연결합니다.

### `CLAUDE.md`

Claude Code가 Repository에서 작업할 때 따라야 하는 프로젝트 공통 지침을 제공합니다.

관련 내용은 `20_Claude_Code.md`에서 설명합니다.

### `CLAUDE.local.example.md`

개발자 개인 환경에서 추가할 수 있는 Claude Code 로컬 설정의 예시입니다.

개인 설정 파일 자체는 Repository 공통 정책과 분리합니다.

### `TODO.md`

아직 처리되지 않은 프로젝트 단위 작업을 기록하는 용도로 사용할 수 있습니다.

### `MEMO.md`

개발 과정에서 임시로 기록할 내용이나 이후 정리가 필요한 메모를 보관하는 용도로 사용할 수 있습니다.

`TODO.md`와 `MEMO.md`는 아키텍처의 Source of Truth로 사용하지 않습니다.

확정된 규칙은 적절한 `docs/*` 문서 또는 코드 설정으로 옮깁니다.

## 9. 코드를 추가할 위치 찾기

새로운 코드를 추가할 때는 먼저 책임의 범위를 판단합니다.

```txt
특정 앱의 화면인가?
→ apps/[app]

여러 앱이 공유하는 비즈니스 규칙인가?
→ packages/domain

Database 접근인가?
→ packages/database

앱에 독립적인 UI인가?
→ packages/design-system

인증 기능인가?
→ packages/auth

파일 저장 기능인가?
→ packages/storage

메일 전송 기능인가?
→ packages/mailer

공통 개발 설정인가?
→ packages/*-config

반복 작업 자동화인가?
→ tooling

프로젝트 설계 또는 개발 규칙인가?
→ docs
```

코드 위치는 단순히 재사용 가능해 보인다는 이유만으로 결정하지 않습니다.

우선 실제 사용하는 위치 가까이에 두고, 여러 영역에서 공유되거나 독립적인 책임이 생겼을 때 상위 Package로 분리합니다.

## 10. 구조 변경 시 확인할 문서

Repository 구조를 변경하는 경우 해당 변경이 다른 영역에 미치는 영향도 함께 검토합니다.

예를 들어 새로운 Package를 추가한다면 다음 문서를 확인합니다.

```txt
03_프로젝트_구조.md
  Repository 구조 반영

04_패키지_구조.md
  Package 책임 정의

05_의존성_경계.md
  Dependency 허용 여부 검토

19_확장_가이드.md
  Package 분리 기준 확인
```

앱 내부 구조를 변경한다면:

```txt
10_앱_구조.md
14_코드_생성기.md
18_컨벤션.md
```

도 함께 검토합니다.

특히 Generator가 기존 디렉터리 구조를 자동으로 생성하고 있다면 구조 변경과 Generator 변경을 함께 수행해야 합니다.

## 11. 핵심 원칙

Repository 구조의 기본 원칙은 다음과 같습니다.

```txt
apps에는 실행 가능한 애플리케이션을 둔다.

packages에는 독립적인 공통 책임을 둔다.

tooling에는 개발 자동화를 둔다.

docs에는 설계와 개발 규칙을 둔다.

Root에는 Workspace 전체 설정을 둔다.

앱 내부 구조와 Package 내부 구조를 혼동하지 않는다.

사용하지 않는 디렉터리를 미리 만들지 않는다.

실제 공유와 독립적인 책임이 생겼을 때만 상위 계층으로 분리한다.

전체 파일 Tree 자체가 아니라 구조의 의미를 문서화한다.
```
