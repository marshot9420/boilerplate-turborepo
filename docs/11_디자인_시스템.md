# 디자인 시스템

이 문서는 `boilerplate-turborepo`의 `@repo/design-system`이 담당하는 책임과 App UI 사이의 경계를 정의합니다.

Design System의 목적은 모든 UI를 하나의 Package에 모으는 것이 아닙니다.

다음과 같은 **도메인에 독립적인 UI 기반과 공통 Interaction Infrastructure**를 제공합니다.

```txt
App별 공통 UI
Form Interaction
Toast
Theme
공통 UI Hook
Design Token
공통 UI Utility
```

반대로 사용자, 주문, 콘텐츠 등 특정 비즈니스 개념을 표현하거나 특정 Use Case를 실행하는 UI는 각 앱의 `entities`, `features`, `views`에 둡니다.

기본 방향은 다음과 같습니다.

```txt
App
 ↓
View / Feature / Entity / Shared
 ↓
Design System
```

Design System은 자신을 사용하는 App이나 Domain의 구체적인 비즈니스 규칙을 알지 않습니다.

---

# 1. 기본 원칙

Design System은 다음 원칙을 따릅니다.

```txt
도메인에 독립적이어야 한다.

특정 Domain DTO나 Service를 알지 않는다.

특정 Server Action을 호출하지 않는다.

특정 URL이나 Permission을 알지 않는다.

공통화할 실제 책임이 있을 때만 코드를 추가한다.

미래를 예상해 Component나 Directory를 미리 만들지 않는다.

Web과 Admin의 UI 요구가 다르면 억지로 하나로 합치지 않는다.

동일하게 생겼다는 이유만으로 공통화하지 않는다.

Business UI는 App Entity / Feature에 둔다.

실제 책임이 생기면 구조가 따라온다.
```

---

# 2. 전체 구조

Design System은 현재와 향후 필요에 따라 다음과 같은 책임으로 구성합니다.

```txt
packages/design-system/src/
├─ form/
├─ toast/
├─ styles/
├─ utils/
├─ web/
├─ admin/
│
├─ hooks/     # 실제 공통 UI Hook이 추가될 때
└─ theme/     # Theme Runtime이 추가될 때
```

`primitives` 계층은 사용하지 않습니다.

```txt
primitives/
```

를 별도의 중간 Layer로 두지 않고 `web`과 `admin`이 각 Application Context에서 필요한 공통 UI를 직접 제공합니다.

---

# 3. 외부 UI Library에 대한 원칙

현재 Design System은 특정 Headless UI Library를 Architecture의 기반으로 전제하지 않습니다.

예를 들어:

```txt
@radix-ui/*
```

를 Design System 구조의 필수 요소로 두지 않습니다.

공통 Component는 기본적으로:

```txt
React

HTML

CSS

Tailwind CSS
```

등 현재 프로젝트에서 필요한 기반을 사용하여 구현합니다.

향후 특정 UI Library가 실제 요구사항을 해결하는 데 필요해진다면 그 시점에 Dependency 추가를 별도로 검토합니다.

즉:

```txt
Library가 있으므로 구조를 만든다.
```

가 아니라:

```txt
필요한 UI 책임이 있다.
        ↓
구현 방법을 선택한다.
```

순서를 따릅니다.

---

# 4. `web`

`web`은 Web Application에서 반복적으로 사용하는 **도메인 독립 UI Component와 Style**을 담당합니다.

Public API:

```txt
@repo/design-system/web
@repo/design-system/web/styles.css
```

예상할 수 있는 대상:

```txt
Button

Input

Card

Dialog

Page Section

Navigation UI

Feedback UI

Layout UI
```

단, 실제 필요가 생긴 Component만 추가합니다.

---

# 5. `admin`

`admin`은 Admin Application에서 반복적으로 사용하는 **도메인 독립 관리 UI Component와 Style**을 담당합니다.

Public API:

```txt
@repo/design-system/admin
@repo/design-system/admin/styles.css
```

예상할 수 있는 대상:

```txt
Button

Input

Dialog

Table 기반 UI

Page Header

Filter Layout

Form Section

Management Layout
```

Admin UI는 Web UI와 시각적·Interaction 요구가 다를 수 있으므로 필요 이상으로 하나의 공통 Component로 합치지 않습니다.

---

# 6. `web`과 `admin`을 나누는 이유

Web과 Admin은 동일한 HTML 요소를 사용하더라도 요구하는 UI 언어가 다를 수 있습니다.

예:

```txt
Web
  콘텐츠 중심
  사용자 경험 중심
  서비스 Branding 중심

Admin
  정보 밀도 중심
  관리 작업 중심
  Table / Filter / Form 중심
```

따라서 다음과 같은 구조를 강제하지 않습니다.

```txt
하나의 Button
  ↓
variant="web"
variant="admin"
```

두 Context의 API와 표현이 실제로 다르다면:

```txt
@repo/design-system/web
  Button

@repo/design-system/admin
  Button
```

처럼 독립적으로 유지할 수 있습니다.

---

# 7. Web과 Admin 사이의 중간 Primitive를 두지 않는다

현재 구조에서는:

```txt
Primitive
  ↓
Web / Admin
```

같은 Layer를 만들지 않습니다.

대신:

```txt
Web Component
   ↓
React / HTML / CSS

Admin Component
   ↓
React / HTML / CSS
```

형태를 기본으로 합니다.

Web과 Admin 사이에서 동일한 구현이 반복되더라도 즉시 별도의 Primitive Layer를 만들지 않습니다.

먼저 다음을 확인합니다.

```txt
정말 동일한 책임인가?

API도 동일한가?

변경 이유도 동일한가?

두 Context가 앞으로도 함께 변경될 가능성이 높은가?
```

단순한 JSX 중복보다 책임의 명확성을 우선합니다.

---

# 8. Design System과 App Entity의 경계

Entity는 특정 비즈니스 대상을 표현합니다.

예:

```txt
MemberStatusBadge

OrderSummary

ContentCard

PaymentStatusBadge

AuditLogTable
```

이러한 Component는 Design System에 두지 않습니다.

다음과 같은 Domain 개념을 알아야 하기 때문입니다.

```txt
UserStatus

OrderStatus

PaymentStatus

Domain DTO

Business Label
```

기본 관계:

```txt
Design System Badge
        ↓
MemberStatusBadge
```

또는:

```txt
Admin Table UI
        ↓
MemberTable
```

입니다.

---

# 9. Design System과 App Feature의 경계

Feature는 사용자가 수행하는 Business Action을 구현합니다.

예:

```txt
BlockMemberDialog

RefundPaymentDialog

PublishContentButton

UpdateProfileForm
```

Feature는 다음과 같은 정보를 알 수 있습니다.

```txt
Server Action

Domain Result

Permission

router.refresh()

Toast

Business State
```

따라서 Feature를 Design System으로 옮기지 않습니다.

예:

```txt
Admin Dialog
      ↓
BlockMemberDialog
      ↓
blockMemberAction
```

에서 `BlockMemberDialog`는 App Feature입니다.

---

# 10. Design System 후보 판단

새 Component를 Design System에 넣을지 판단할 때 다음 질문을 사용합니다.

```txt
특정 Domain 이름을 제거해도 의미가 유지되는가?

Domain DTO 없이 사용할 수 있는가?

Server Action 없이 독립적으로 동작하는가?

특정 Permission을 알지 않아도 되는가?

특정 URL 구조를 알지 않아도 되는가?

여러 UI에서 동일한 Presentation 책임을 갖는가?
```

대부분 `예`라면 Design System 후보입니다.

---

# 11. 판단 예

```txt
Button
→ Design System 후보

BlockMemberButton
→ Feature
```

```txt
Badge
→ Design System 후보

OrderStatusBadge
→ Entity
```

```txt
Dialog
→ Design System 후보

RefundPaymentDialog
→ Feature
```

```txt
Table
→ Design System 후보

AuditLogTable
→ Entity
```

Component의 외형보다 **의미와 책임**을 기준으로 판단합니다.

---

# 12. `form`

`form`은 특정 Domain Form을 구현하는 영역이 아닙니다.

Server Action 결과와 Client Form Interaction을 여러 Feature에서 일관되게 처리하기 위한 **도메인 독립 Form Infrastructure**입니다.

현재 구조:

```txt
form/
├─ form-action-result.types.ts
├─ form-error.utils.ts
├─ form.utils.ts
└─ index.ts
```

현재 Public API는 다음과 같은 역할을 제공합니다.

```txt
FormActionResult

getFieldError

getFormError

hasFieldErrors

hasAnyFieldError

resolveFieldError

getFormStringValue

getTargetFieldName
```

---

# 13. `FormActionResult`

`FormActionResult`는 `@repo/core`의 `ActionResult`를 Form UI에서 사용할 수 있도록 표현합니다.

개념:

```txt
ActionResult<T>
     +
null / undefined
     ↓
FormActionResult<T>
```

다음 상태를 모두 표현할 수 있습니다.

```txt
아직 Action 실행 전

Action 결과 없음

Action 성공

Action 실패
```

특정 Domain을 알지 않으므로 Design System Form Infrastructure에 둘 수 있습니다.

---

# 14. Form Error Utility

`form-error.utils.ts`는 Action 결과에서 UI가 표시할 Error를 해석합니다.

대표적인 책임:

```txt
특정 Field Error 조회

Form 전체 Error 조회

Field Error 존재 여부 확인

ActionResult에 Field Error가 있는지 확인

Client Error와 Server Error의 표시 우선순위 결정
```

예:

```txt
Server Action
      ↓
ActionResult
      ↓
getFieldError
      ↓
Input Error UI
```

이 Utility는 Business Error 자체를 생성하거나 판단하지 않습니다.

---

# 15. `resolveFieldError`

Form에는 다음 두 종류의 Error가 함께 존재할 수 있습니다.

```txt
Client Validation Error

Server Validation Error
```

그리고 사용자가 Server 결과를 받은 뒤 Field를 다시 편집했다면 이전 Server Error는 더 이상 현재 입력을 정확히 설명하지 않을 수 있습니다.

따라서 다음과 같은 Form UX Policy를 공통화할 수 있습니다.

```txt
Field가 touched 됨

Submit을 시도함

Action 결과 이후 값을 수정함
```

이 상태를 기준으로 어떤 Error를 표시할지 결정합니다.

이는 Business Rule이 아니라 UI Interaction Rule입니다.

---

# 16. `form.utils.ts`

Form Web API를 다루는 범용 Utility를 제공합니다.

현재 예:

```txt
getFormStringValue

getTargetFieldName
```

적절한 대상:

```txt
FormData Value를 안전하게 읽는 Helper

Form Event Target 처리

Form Interaction 범용 Helper
```

부적절한 대상:

```txt
getOrderIdFromForm

normalizePaymentAmount

getMemberStatus
```

특정 Domain 의미가 들어가면 App 또는 Domain에 둡니다.

---

# 17. `toast`

`toast`는 Client Notification Infrastructure입니다.

현재 구성은 다음 책임을 가집니다.

```txt
ToastProvider

toastActionResult

기본 Success Message

기본 Error Message
```

기본 흐름:

```txt
ActionResult
    ↓
toastActionResult
    ↓
Toast UI
```

현재 구현에서는 `sonner`를 내부 구현으로 사용합니다.

App은 가능한 한 `sonner` 자체보다 Design System Public API를 사용합니다.

---

# 18. `ToastProvider`

`ToastProvider`는 Application Root에 배치할 Toast Runtime을 제공합니다.

기본 Presentation Policy를 가질 수 있습니다.

예:

```txt
richColors

closeButton

position
```

각 앱에서 필요하면 Props를 통해 조정합니다.

---

# 19. `toastActionResult`

`toastActionResult`는 `ActionResult`를 Toast로 표현합니다.

기본 판단:

```txt
result.ok === true
→ Success Toast

result.ok === false
→ Error Toast
```

Design System은 특정 Domain Error Code의 의미를 판단하지 않습니다.

예:

```txt
USER_BLOCKED

ORDER_NOT_REFUNDABLE
```

같은 Business 의미는 Domain과 Server Action에서 처리합니다.

Toast Layer는 최종적으로 전달된 Message를 표현합니다.

---

# 20. Toast를 언제 호출할지는 Feature가 결정한다

Design System은 Toast 기능을 제공하지만 호출 시점은 Business Flow를 소유한 Feature가 결정합니다.

예:

```txt
BlockMemberDialog
      ↓
Action 성공
      ↓
Toast
      ↓
Dialog 닫기
      ↓
router.refresh()
```

따라서:

```txt
Design System
  Toast API 제공

Feature
  Toast 사용 여부 판단
```

으로 나눕니다.

---

# 21. `hooks`

여러 App UI에서 실제로 반복되는 도메인 독립 React Interaction이 생기면:

```txt
packages/design-system/src/hooks/
```

를 추가할 수 있습니다.

Hook은 다음 조건을 만족해야 합니다.

```txt
Domain에 독립적

특정 Server Action을 모름

특정 App URL을 모름

특정 Entity를 모름

UI Interaction 자체를 담당
```

---

# 22. `useActionResultEffect`

추후 추가할 수 있는 대표적인 공통 Hook입니다.

목적:

```txt
ActionResult 감지
      ↓
Field Error 여부 확인
      ↓
필요한 Toast
      ↓
onSuccess
```

예상 책임:

```txt
ActionResult 변화 감지

Field Error가 있는 실패에서는 Toast 생략

일반 실패 Toast

성공 Toast

성공 Callback 실행
```

이 Hook 자체가 다음을 결정하지는 않습니다.

```txt
어떤 Dialog를 닫는가?

어떤 Route를 refresh하는가?

어떤 Local State를 변경하는가?
```

Feature가 `onSuccess`를 통해 결정합니다.

---

# 23. `useFormInteractionState`

Form UX 상태를 공통화하기 위한 Hook입니다.

예상 관리 상태:

```txt
touchedFields

submitAttempted

editedAfterResult

editedFieldsAfterResult
```

목적은:

```txt
Client Validation

Server Field Error

사용자의 재편집
```

사이의 UI 흐름을 일관되게 처리하는 것입니다.

특정 Domain Schema를 알지 않습니다.

---

# 24. `useMediaQuery`

Runtime에서 Media Query 결과 자체가 Component Logic에 필요한 경우 사용할 수 있는 범용 Hook입니다.

예:

```txt
Viewport Condition

prefers-reduced-motion

prefers-color-scheme
```

다만 Presentation만 달라지는 문제라면 JavaScript보다 CSS를 우선합니다.

```txt
CSS로 해결 가능
→ CSS

Component Logic 자체가 달라져야 함
→ useMediaQuery 검토
```

---

# 25. 공통 Hook을 미리 채우지 않는다

다음과 같은 Hook을 단순히 흔하다는 이유로 모두 추가하지 않습니다.

```txt
useBoolean

useToggle

usePrevious

useDebounce

useMounted

useClickOutside

useEventListener
```

실제 반복되는 문제가 발견되었을 때 추가합니다.

Hook Library 자체를 만드는 것이 목적이 아닙니다.

---

# 26. `theme`

Theme Runtime이 실제로 추가되면:

```txt
packages/design-system/src/theme/
```

에서 관리합니다.

예상 구조:

```txt
theme/
├─ theme-init-script.tsx
├─ theme-provider.tsx
├─ theme-toggle-button.tsx
├─ theme.constants.ts
├─ theme.context.ts
├─ theme.types.ts
├─ theme.utils.ts
├─ useTheme.ts
└─ index.ts
```

정확한 파일은 구현 시 현재 Naming Convention에 맞게 확정합니다.

---

# 27. Theme의 책임

Theme Layer는 다음 UI 상태를 관리합니다.

```txt
light

dark

system
```

개념적으로 다음 두 값을 구분합니다.

```txt
ThemeMode
  light | dark | system

ResolvedThemeMode
  light | dark
```

`system`을 선택하면 사용자 OS의 Color Scheme을 기준으로 실제 Mode를 결정합니다.

---

# 28. App Theme와 Color Mode는 다른 개념이다

Design System에는 두 종류의 Theme Context가 존재할 수 있습니다.

```txt
App Theme
  web | admin

Color Mode
  light | dark
```

이를 별도로 관리합니다.

예:

```html
<html data-ds-theme="web" data-ds-mode="dark"></html>
```

Admin:

```html
<html data-ds-theme="admin" data-ds-mode="light"></html>
```

---

# 29. Theme 초기화

Theme Runtime에서는 초기 Render 이전에 적절한 Mode를 DOM에 적용하여 Theme Flash를 줄일 수 있습니다.

흐름:

```txt
Theme Cookie
     ↓
Server Layout
     ↓
initialThemeMode
     ↓
ThemeInitScript
     ↓
data-ds-mode
```

이 초기화 로직은 Business Logic이 아닌 UI Runtime 책임이므로 Design System에 둘 수 있습니다.

---

# 30. Theme Provider

Client Runtime에서는 `ThemeProvider`가 Theme State를 관리할 수 있습니다.

대표적인 책임:

```txt
현재 ThemeMode

Resolved ThemeMode

Mode 변경

Mode Toggle

System Theme 변경 감지

Cookie 저장
```

App은 Theme 구현 세부사항보다 Public Theme API를 사용합니다.

---

# 31. Theme Cookie

사용자의 Theme Preference는 Cookie에 저장할 수 있습니다.

다만 재사용 가능한 Boilerplate이므로 특정 제품명이 Cookie 이름에 하드코딩되지 않도록 합니다.

예:

```txt
theme_mode
```

또는 Project Initialization 과정에서 Scope에 맞게 설정할 수 있습니다.

다음과 같은 제품 전용 이름을 Boilerplate 기본값으로 사용하지 않습니다.

```txt
athena_theme_mode
```

---

# 32. Theme Toggle

`ThemeToggleButton`처럼 Theme 자체를 제어하는 UI는 특정 Business Domain에 종속되지 않으므로 Theme 영역에 둘 수 있습니다.

책임:

```txt
현재 Theme 표시

Theme Toggle

접근성 Label
```

알지 않아야 하는 것:

```txt
User DTO

User Preference Service

Server Action

Database

특정 App Permission
```

향후 사용자의 Theme Preference를 계정 정보로 저장하는 기능이 추가된다면 해당 Persistence는 App / Domain 책임입니다.

---

# 33. `styles`

`styles`는 Design System의 CSS 기반을 관리합니다.

현재 정리 방향에서는 다음 파일을 중심으로 사용합니다.

```txt
styles/
├─ tokens.css
└─ storybook.css
```

별도의 `theme.css`는 유지하지 않습니다.

App Theme와 Color Mode에 필요한 실제 CSS 변수는 각 Style Entry에서 명확하게 관리합니다.

---

# 34. `tokens.css`

`tokens.css`는 공통 Semantic Design Token을 정의합니다.

Color Token은 Tailwind가 사용하는 공통 Contract와 Style Entry가 제공하는 실제 값을 분리합니다.

```css
/* tokens.css */
--color-primary: var(--ds-color-primary);
```

`--color-*`는 Component가 Tailwind Utility 또는 CSS에서 사용하는 공통 Contract입니다. `--ds-color-*`는 Web/Admin Style Entry가 실제 값을 주입하기 위한 내부 Slot이며 Component에서 직접 사용하지 않습니다.

현재 대표적인 Token:

```txt
background

foreground

surface

surface-foreground

primary

primary-foreground

secondary

secondary-foreground

muted

muted-foreground

accent

accent-foreground

destructive

destructive-foreground

success

success-foreground

warning

warning-foreground

info

info-foreground

border

input

ring

overlay
```

Component에서는 가능한 한 Raw Color보다 Semantic Token을 사용합니다.

권장:

```txt
bg-background

text-foreground

border-border

bg-overlay/50
```

Color 외에는 현재 Component가 실제로 사용하는 범위에서 다음 기반 Token을 관리합니다.

```txt
Radius
  xs ~ 2xl
  full

Shadow
  xs ~ xl

Typography
  sans
  mono

Motion
  fast
  normal
  standard easing
```

Tailwind 기본 Scale로 충분한 Spacing은 별도 Token으로 복제하지 않습니다.

---

# 35. Semantic Token

Token은 특정 색상 이름보다 UI에서의 역할을 표현합니다.

좋은 예:

```txt
primary

destructive

success

warning
```

다음처럼 실제 색상 이름 중심으로 API를 만들지 않습니다.

```txt
blue

red

green

yellow
```

실제 색상은 App Theme와 Color Mode에 따라 달라질 수 있습니다.

Palette와 Raw Color Value는 Theme의 실제 값을 구성하는 구현 세부사항입니다. Component는 이를 직접 사용하지 않고 Semantic Token만 사용합니다.

```txt
Palette / Raw Color
        ↓
Semantic Token
        ↓
Component
```

---

# 36. Web / Admin Theme

동일한 Semantic Token 이름에 서로 다른 값을 적용할 수 있습니다.

예:

```txt
Web Light
  --ds-color-primary: ...

Web Dark
  --ds-color-primary: ...

Admin Light
  --ds-color-primary: ...

Admin Dark
  --ds-color-primary: ...
```

Component는 Theme의 실제 Color를 알 필요가 없습니다.

```txt
bg-primary
```

처럼 Semantic Contract만 사용합니다.

`web/styles.css`와 `admin/styles.css`는 같은 `--ds-color-*` Slot을 각각 독립적으로 정의합니다. 한 Context의 실제 Color Value나 Palette 이름을 다른 Context 또는 Component가 Import하지 않습니다.

---

# 37. `storybook.css`

Storybook은 실제 Next.js App Runtime과 분리된 UI 환경입니다.

`storybook.css`는 Design System Story를 표시하기 위한 공통 CSS Entry입니다.

대표적인 역할:

```txt
Tailwind CSS 로드

tokens.css 로드

Design System Source Scan

Web Theme

Admin Theme

Light / Dark Mode

Storybook Base Style
```

Source Scan 역시 실제 존재하는 Component 영역만 대상으로 합니다.

현재 기준:

```css
@source "../web";
@source "../admin";
```

존재하지 않는 `primitives`를 Source에 포함하지 않습니다.

---

# 38. App Style과 Design System Style

Design System은 공통 Token과 App Theme 기반을 제공합니다.

각 App은 자신의 Global CSS Entry를 통해 해당 Style을 사용합니다.

```txt
Design System Styles
        ↓
App globals.css
        ↓
Application
```

특정 Feature나 Entity의 Style을 Design System Global Style로 올리지 않습니다.

---

# 39. `utils`

`utils`는 Design System 구현에서 여러 영역이 공유하는 도메인 독립 UI Utility를 제공합니다.

대표적인 현재 예:

```txt
cn
```

`cn`은 Class Name 조합을 일관되게 처리하기 위한 Utility입니다.

적절한 대상:

```txt
Class Name Merge

Presentation용 순수 Helper
```

부적절한 대상:

```txt
calculateRefundAmount

formatUserStatus

canPublishContent

normalizePayment
```

비즈니스 의미가 있다면 Domain 또는 App에 둡니다.

---

# 40. `@repo/core`와의 관계

Design System은 UI와 무관하게 정의된 공통 Contract를 사용하기 위해 `@repo/core`를 의존할 수 있습니다.

현재 대표적인 예:

```txt
ActionResult

FieldErrors
```

관계:

```txt
@repo/design-system
       ↓
@repo/core
```

반대 방향은 허용하지 않습니다.

```txt
@repo/core
       ✕
@repo/design-system
```

---

# 41. Domain을 의존하지 않는다

Design System에서 다음과 같은 Import는 만들지 않습니다.

```ts
import type { UserStatus } from "@repo/domain/user/client";
```

```ts
import type { OrderStatus } from "@repo/domain/order/client";
```

이러한 Import가 필요하다면 해당 UI가 사실상 App Entity인지 다시 검토합니다.

```txt
Design System
  Domain을 모름

Entity / Feature
  Domain을 알 수 있음
```

---

# 42. Server Action을 의존하지 않는다

Design System은 `ActionResult` 같은 공통 결과 형식을 처리할 수 있지만 구체적인 Action은 호출하지 않습니다.

적절함:

```txt
ActionResult 해석

Field Error 표시

Toast 표시
```

부적절함:

```txt
blockMemberAction()

updateProfileAction()

refundPaymentAction()
```

이러한 Action 실행은 Feature 책임입니다.

---

# 43. `router.refresh()`와의 경계

공통 Design System Component나 Hook이 `router.refresh()`를 자동으로 수행하지 않습니다.

예:

```txt
Admin Dialog
  ✕ router.refresh()

Admin Button
  ✕ router.refresh()

useActionResultEffect
  ✕ router.refresh() 강제
```

해당 Mutation Flow를 소유한 Feature가 결정합니다.

```txt
Feature
  ↓
Action 성공
  ↓
Dialog Close
Toast
router.refresh()
```

공통 Hook은 `onSuccess` 같은 확장 지점을 제공할 수 있습니다.

---

# 44. 새로운 공통 Component를 추가하는 기준

새로운 Component를 Design System에 추가하기 전에 다음을 확인합니다.

```txt
실제 사용하는 위치가 있는가?

특정 Domain을 모르는가?

특정 Business Action을 모르는가?

App Shared보다 Workspace Package가 더 적절한가?

동일한 Presentation / Interaction 책임이 반복되는가?

공통 API가 충분히 명확한가?

기존 HTML / CSS 조합으로 충분하지 않은가?
```

---

# 45. App에서 먼저 시작한다

새로운 UI는 기본적으로 사용하는 위치에서 시작합니다.

```txt
Feature에 한 번 사용
→ Feature에 colocate

한 앱의 여러 Slice에서 공유
→ App Shared 검토

Web 전체에서 공통
→ @repo/design-system/web 검토

Admin 전체에서 공통
→ @repo/design-system/admin 검토
```

처음부터 Design System에 넣지 않습니다.

---

# 46. 여러 앱에서 비슷하다고 무조건 합치지 않는다

Web과 Admin에서 각각 Button이 필요하더라도 즉시 하나로 통합하지 않습니다.

```txt
Web Button

Admin Button
```

이 둘이 실제로:

```txt
동일한 API

동일한 Interaction

동일한 변경 이유
```

를 가질 때만 공통 구현 가능성을 검토합니다.

별도의 `primitives` 계층을 만들어 해결하지 않습니다.

---

# 47. App Shared와의 경계

도메인에는 독립적이지만 한 앱에서만 사용하는 UI라면 먼저 App Shared를 검토합니다.

```txt
하나의 Feature
→ Feature

한 앱 여러 Slice
→ apps/*/shared

App 전체의 Design Language
→ @repo/design-system/web 또는 admin
```

단순히 재사용된다는 이유만으로 Workspace Package까지 승격하지 않습니다.

---

# 48. Storybook

Design System Component는 독립적인 Presentation Contract를 가지므로 Storybook 작성 가치가 높습니다.

대표적인 Story 대상:

```txt

Admin Component

Theme Toggle

복잡한 Form UI

Interactive Common Component
```

```txt

cn
```

Utility는 Unit Test로 검증합니다.

# 50. Public API

Package 외부에서는 명시적인 Export를 사용합니다.

권장:

```ts
import { ToastProvider } from "@repo/design-system/toast";

import { getFieldError, getFormError } from "@repo/design-system/form";
```

지양:

```ts
import ToastProvider from "@repo/design-system/src/toast/toast-provider";
```

내부 파일 구조는 Public Contract가 아닙니다.

---

# 51. Package Export

`package.json`의 `exports`는 실제 제공하는 Public API와 일치해야 합니다.

현재 방향:

```txt
@repo/design-system

@repo/design-system/utils

@repo/design-system/form

@repo/design-system/toast

@repo/design-system/web

@repo/design-system/web/styles.css

@repo/design-system/admin

@repo/design-system/admin/styles.css
```

`primitives`를 제거했다면 다음 Export도 제거합니다.

```txt
@repo/design-system/primitives
```

향후 `theme`, `hooks`가 실제 구현되면 그 시점에:

```txt
@repo/design-system/theme

@repo/design-system/hooks
```

등의 Public API를 추가합니다.

---

# 52. Dependency도 실제 구현과 일치시킨다

Package Dependency 역시 실제 코드에서 사용하는 Library만 유지합니다.

어떤 Dependency가 현재 구현에서 더 이상 사용되지 않는다면 제거를 검토합니다.

특히 현재 Design System이 `@radix-ui/*`를 사용하지 않는 방향이라면 실제 Source 참조가 모두 제거된 뒤 관련 Dependency 역시 정리합니다.

```txt
설계에서 사용하지 않음
      ↓
Source Import 없음 확인
      ↓
package.json Dependency 제거
```

사용하지 않는 Library를 미래 가능성만으로 유지하지 않습니다.

---

# 53. 파일 구조도 실제 책임에 맞춘다

Form Utility처럼 관련된 작은 함수가 많다면 함수 하나당 파일 하나를 강제하지 않습니다.

현재 예:

```txt
form-action-result.types.ts

form-error.utils.ts

form.utils.ts
```

처럼 책임별로 묶습니다.

Theme도 구현 시 같은 원칙을 적용합니다.

```txt
theme.constants.ts

theme.types.ts

theme.utils.ts
```

Component는 각각 독립적인 UI 책임을 가진다면 개별 파일로 분리할 수 있습니다.

---

# 54. 현재 구현과 예정 구조를 구분한다

현재 구현되어 있는 기능과 향후 추가할 기능을 문서에서 구분합니다.

현재 기반:

```txt
form

toast

styles

utils

web / admin Public 영역
```

추후 실제 구현 시 추가 예정:

```txt
theme

hooks

Web Design System Component

Admin Design System Component
```

아직 존재하지 않는 기능을 현재 제공되는 기능처럼 문서화하지 않습니다.

구현 시 이 문서와 Package Export를 함께 갱신합니다.

# 58. 핵심 원칙

```txt
Design System은 도메인에 독립적인 UI 기반이다.

모든 UI를 Design System에 넣지 않는다.

primitives 계층을 사용하지 않는다.

Web과 Admin은 각자의 공통 UI를 직접 소유한다.

Web과 Admin의 차이를 억지로 하나의 API로 통합하지 않는다.

현재 특정 Headless UI Library를 Design System의 전제로 사용하지 않는다.

외부 UI Dependency는 실제 필요가 생길 때 추가한다.

Entity는 Business Object를 표현한다.

Feature는 Business Action을 수행한다.

Form은 공통 Form Interaction Infrastructure다.

Toast는 Notification Infrastructure다.

Toast 호출 시점은 Feature가 결정한다.

Theme은 Business Domain과 독립된 UI Runtime이다.

공통 Hook은 실제 반복되는 UI Interaction이 있을 때 추가한다.

Semantic Token을 중심으로 Theme를 구성한다.

App Theme와 Color Mode를 구분한다.

Design System은 @repo/core를 사용할 수 있지만 Domain을 알지 않는다.

구체적인 Server Action을 Design System에서 호출하지 않는다.

router.refresh 같은 Mutation 후처리는 Feature가 소유한다.

한 앱 내부 공유라면 먼저 App Shared를 검토한다.

실제 반복과 안정된 책임이 확인된 뒤 Design System으로 승격한다.

Public Export와 Dependency는 실제 구현과 일치시킨다.

사용하지 않는 Dependency를 미래 가능성만으로 유지하지 않는다.

미래를 예상해 빈 Directory와 Component를 만들지 않는다.

책임이 생기면 구조가 따라온다.
```
