# 디자인 시스템

이 문서는 `boilerplate-turborepo`의 `@repo/design-system`이 담당하는 UI 기반과 앱 UI 사이의 경계를 정의합니다.

Design System의 목적은 모든 UI 코드를 한 Package에 모으는 것이 아닙니다.

다음과 같은 **도메인에 독립적인 UI 기반**만 공통화합니다.

```txt
UI Token

App Theme

공통 Form Helper

Toast

공통 UI Utility

재사용 가능한 UI Component

공통 UI Hook
```

반대로 사용자, 주문, 콘텐츠 등 특정 비즈니스 개념을 표현하거나 특정 Use Case를 수행하는 UI는 각 앱의 `entities`, `features`, `views`에 둡니다.

기본 방향은 다음과 같습니다.

```txt
App
 ↓
Entity / Feature / Shared UI
 ↓
Design System
```

Design System은 상위 App Layer를 알지 않습니다.

---

# 1. 기본 원칙

Design System의 기본 원칙은 다음과 같습니다.

```txt
도메인에 독립적이어야 한다.

특정 앱의 Use Case를 알지 않는다.

특정 Domain DTO나 Service에 의존하지 않는다.

여러 위치에서 실제로 공유되는 UI 기반만 둔다.

앱별 시각적 차이는 web / admin 경계에서 표현할 수 있다.

공통화 가능성을 예상해 미리 Component를 만들지 않는다.

Primitive 계층을 반드시 가져야 하는 것은 아니다.

필요한 책임이 생겼을 때 구조를 추가한다.

App의 Entity와 Feature를 Design System으로 승격하지 않는다.
```

---

# 2. Package 역할

Design System Package:

```txt
@repo/design-system
```

은 다음과 같은 책임을 가집니다.

```txt
공통 UI 스타일 기반

Design Token

앱별 Theme

Form Interaction Helper

Toast Infrastructure

UI Utility

공통 UI Hook

재사용 가능한 Presentation Component
```

현재 Public API는 책임별 Subpath를 통해 제공합니다.

예:

```txt
@repo/design-system/form
@repo/design-system/toast
@repo/design-system/utils
@repo/design-system/web
@repo/design-system/admin
```

실제 구현되지 않은 영역은 Public API에 미리 추가하지 않는 것을 기본으로 합니다.

---

# 3. 현재 구조와 확장 구조

Design System은 모든 디렉터리를 미리 갖춘 고정 Template으로 관리하지 않습니다.

현재 실제 책임을 기준으로 시작하고 필요에 따라 확장합니다.

개념적인 성장 구조:

```txt
packages/design-system/src/
├─ form/
├─ toast/
├─ styles/
├─ utils/
│
├─ web/          # 앱별 공통 UI가 생길 때 확장
├─ admin/        # 앱별 공통 UI가 생길 때 확장
│
├─ hooks/        # 공통 UI Hook이 생길 때 추가
├─ theme/        # Theme Runtime 기능이 구현될 때 추가
└─ primitives/   # 실제 공통 Primitive가 필요할 때만 추가
```

이 구조에서 중요한 것은:

```txt
Directory가 Architecture를 만드는 것이 아니라
실제 책임이 Directory를 만든다.
```

는 원칙입니다.

---

# 4. `primitives`

`primitives`는 가장 낮은 수준의 재사용 가능한 UI Component를 위한 영역입니다.

다만 **현재 보일러플레이트에서는 Primitive Component를 제거한 상태이며, 필수 Layer로 취급하지 않습니다.**

향후 다음과 같은 요구가 실제로 발생할 때 다시 도입할 수 있습니다.

```txt
web과 admin에서 동일한 Interaction Contract를 사용

여러 공통 Component가 같은 기반 Component를 반복 구현

Radix UI 등의 Headless Primitive를 동일한 방식으로 감싸야 함

접근성, 상태 처리, Variant API를 하나로 통일할 필요가 있음
```

예를 들어 향후 다음 Component가 여러 Theme에서 정말 동일한 기반을 공유한다면 Primitive 후보가 될 수 있습니다.

```txt
Button

Dialog

Select

Popover

Tabs
```

하지만 단순히 일반적인 Design System에서 흔히 제공된다는 이유로 추가하지 않습니다.

---

# 5. Primitive를 만들지 않는 경우

다음 이유만으로 Primitive를 추가하지 않습니다.

```txt
다른 프로젝트에도 있으니까

Radix Dependency가 있으니까

나중에 필요할 것 같아서

Design System이라면 Button이 있어야 할 것 같아서

web과 admin에서 이름이 비슷한 Component가 있으니까
```

실제 공유 계약이 없다면 각 App Theme 영역에서 독립적으로 구현할 수 있습니다.

---

# 6. `web`

`web`은 Web Application의 시각 언어를 공유하는 UI를 위한 영역입니다.

다음과 같은 특성을 가질 수 있습니다.

```txt
Web Theme

Web Typography

Web Layout Pattern

Web 전용 Visual Component

Web에서 반복되는 Presentation Wrapper
```

예를 들어 향후:

```txt
WebButton

WebCard

WebDialog

WebHeader Primitive
```

등이 필요해질 수 있습니다.

다만 이름에 `Web`을 반드시 붙여야 한다는 의미는 아닙니다.

Public API의 의미가:

```txt
@repo/design-system/web
```

으로 이미 구분된다면 소비 측에서는 자연스러운 Component 이름을 사용할 수 있습니다.

---

# 7. `admin`

`admin`은 Admin Application에서 반복되는 관리 UI의 시각적 기반을 담당합니다.

예:

```txt
Admin Theme

Admin Layout Pattern

Admin Form Presentation

Admin Table Presentation

Admin Navigation Presentation
```

하지만 다음과 같은 비즈니스 Component는 포함하지 않습니다.

```txt
MemberTable

OrderStatusBadge

PaymentRefundDialog

QuestionAnswerDialog

AuditLogTable
```

이들은 이름부터 특정 Domain 또는 Use Case를 표현하므로 App Entity / Feature에 속합니다.

---

# 8. `web` / `admin`은 Domain Layer가 아니다

`web`과 `admin`이라는 이름은 **시각적 Application Context**를 의미합니다.

다음을 의미하지 않습니다.

```txt
web
  Web 앱의 모든 Component

admin
  Admin 앱의 모든 Component
```

Design System에 포함될 수 있는 것은 여전히 도메인에 독립적인 UI뿐입니다.

예:

```txt
적절함

AdminTable
AdminPageHeader
AdminFormSection
WebCard
WebSection


부적절함

AdminMemberTable
AdminOrderRefundDialog
WebUserProfileCard
WebContentPublishButton
```

---

# 9. Primitive와 App Wrapper의 경계

향후 Primitive 계층을 다시 도입한다면 다음 관계를 기본으로 합니다.

```txt
Primitive
   ↓
web / admin Wrapper
   ↓
App Entity / Feature
```

예:

```txt
Dialog Primitive
      ↓
Admin Dialog Styling
      ↓
BlockMemberDialog
```

각 단계의 책임:

```txt
Primitive
  Interaction Contract
  Accessibility
  Headless Component Wrapping
  공통 Variant 기반

Admin / Web Wrapper
  App Theme
  Visual Style
  Presentation Policy

Feature
  Business Action
  Domain State
  Server Action
  Toast / Refresh
```

---

# 10. Primitive를 우회할 수 있다

모든 `web` / `admin` Component가 반드시 Primitive를 거칠 필요는 없습니다.

```txt
admin
  ↓
Radix UI
```

또는:

```txt
web
  ↓
React + CSS
```

형태로 직접 구현할 수도 있습니다.

실제 공통 기반이 생겼을 때만 Primitive로 추출합니다.

```txt
먼저 구현

반복 확인

공통 계약 확인

Primitive 승격
```

순서를 따릅니다.

---

# 11. App Entity와의 경계

Entity UI는 비즈니스 대상을 **표현**합니다.

예:

```txt
UserStatusBadge

OrderSummary

ContentCard

PaymentStatusBadge

AuditLogTable
```

이러한 Component는 Design System으로 이동하지 않습니다.

왜냐하면 Design System이 다음 개념을 알아야 하기 때문입니다.

```txt
UserStatus

OrderStatus

PaymentStatus

Domain DTO
```

Design System은 이러한 Business Domain을 모릅니다.

---

# 12. App Feature와의 경계

Feature는 사용자가 수행하는 비즈니스 행동을 구현합니다.

예:

```txt
BlockMemberDialog

RefundPaymentDialog

PublishContentButton

UpdateProfileForm
```

Feature는 다음을 알 수 있습니다.

```txt
Server Action

Domain Result

router.refresh()

Toast

Business Permission

Domain Request
```

따라서 Feature 자체를 Design System으로 옮기지 않습니다.

---

# 13. Design System Component 판단 기준

다음 질문을 사용합니다.

```txt
이 Component 이름에서 Domain 명사를 제거할 수 있는가?

다른 Domain에서도 의미가 동일한가?

Business DTO 없이 사용할 수 있는가?

Server Action 없이 독립적으로 사용할 수 있는가?

특정 URL이나 Permission을 알지 않아도 되는가?

다른 앱에서도 동일한 Presentation 책임으로 사용할 수 있는가?
```

대부분 `예`라면 Design System 후보입니다.

---

# 14. Domain UI 판단 예

다음 Component가 있다고 가정합니다.

```txt
OrderStatusBadge
```

단순히 Badge처럼 생겼다고 해서 Design System Component가 아닙니다.

```txt
Badge
  → Design System 후보

OrderStatusBadge
  → Entity
```

마찬가지로:

```txt
Dialog
  → Design System 후보

BlockMemberDialog
  → Feature
```

```txt
Table
  → Design System 후보

MemberTable
  → Entity
```

처럼 구분합니다.

---

# 15. `form`

`form`은 특정 Domain Form을 구현하는 영역이 아닙니다.

Form 제출 결과와 Validation UI를 여러 Feature에서 일관되게 처리하기 위한 **도메인 독립 Form Infrastructure**입니다.

현재 주요 역할:

```txt
ActionResult Form Type

Field Error 추출

Form Error 추출

Field Error 존재 여부 판단

Client / Server Error 표시 우선순위

FormData 관련 범용 Utility
```

구조는 역할을 기준으로 묶습니다.

예:

```txt
form/
├─ form-action-result.types.ts
├─ form-error.utils.ts
├─ form.utils.ts
└─ index.ts
```

작은 함수 하나마다 파일을 분리하기보다 관련 책임을 하나의 Utility Module로 묶을 수 있습니다.

---

# 16. `FormActionResult`

`FormActionResult`는 Server Action 결과를 Form UI에서 소비하기 위한 공통 Type입니다.

개념:

```txt
ActionResult<T>
       ↓
Form UI
```

다음 상태까지 표현합니다.

```txt
아직 Action 실행 전

Action 처리 중 기존 결과 없음

Action 성공

Action 실패
```

따라서:

```txt
ActionResult<T> | null | undefined
```

형태를 공통화할 수 있습니다.

이 Type은 특정 Domain 결과를 알지 않습니다.

---

# 17. Form Error Utility

Form Error Utility는 `ActionResult`에서 UI가 필요한 오류를 해석합니다.

대표적인 책임:

```txt
getFieldError

getFormError

hasFieldErrors

hasAnyFieldError

resolveFieldError
```

예:

```txt
Server Validation Result
      ↓
getFieldError
      ↓
Input Error Message
```

이 Utility는 오류를 생성하지 않습니다.

오류의 의미는 Server Action / Domain이 결정하고 Design System은 이를 **표시하기 쉬운 형태로 해석**합니다.

---

# 18. Client Error와 Server Error

Form에서는 다음 두 종류의 오류가 동시에 존재할 수 있습니다.

```txt
Client Validation Error

Server Action Field Error
```

사용자가 Server 결과 이후 Field를 다시 수정했다면 이전 Server Error를 계속 표시하는 것이 부자연스러울 수 있습니다.

이러한 **UI Interaction Policy**는 Design System Form Utility가 공통화할 수 있습니다.

예:

```txt
Field가 수정됨
→ 이전 Server Error 숨김

Client Validation 실패
→ Client Error 우선 표시

Submit 시도
→ 필요한 Client Error 표시
```

이것은 Business Validation이 아니라 Form UX 규칙이므로 Design System 책임에 적합합니다.

---

# 19. `form.utils.ts`

Form 자체의 범용 Web API 처리는 별도의 Utility로 둘 수 있습니다.

예:

```txt
getFormStringValue

getTargetFieldName
```

이러한 함수는 특정 Domain Field 이름을 알지 않습니다.

적절함:

```txt
FormData 값 안전하게 문자열로 읽기

Event Target의 Field Name 추출
```

부적절함:

```txt
getOrderIdFromForm

getMemberStatusFromForm

normalizePaymentAmount
```

후자는 App 또는 Domain 책임입니다.

---

# 20. `toast`

`toast`는 Client Notification Infrastructure를 제공합니다.

현재 대표적인 책임:

```txt
ToastProvider

ActionResult → Toast 변환

기본 성공 메시지

기본 오류 메시지
```

사용 예의 개념:

```txt
ActionResult
    ↓
toastActionResult
    ↓
Sonner
```

Design System은 Sonner라는 구체적인 Library를 App 코드에서 직접 다루지 않도록 공통 경계를 제공할 수 있습니다.

---

# 21. `ToastProvider`

`ToastProvider`는 앱 Root Layout 등에 배치하는 공통 Toast Runtime입니다.

기본 Presentation Policy를 제공할 수 있습니다.

예:

```txt
richColors

closeButton

position
```

App에서 필요한 경우 Props를 통해 정책을 조정할 수 있습니다.

---

# 22. `toastActionResult`

`toastActionResult`는 공통 `ActionResult`를 Toast로 표현합니다.

다음 정도만 판단합니다.

```txt
result.ok
→ Success Toast

result.ok === false
→ Error Toast
```

특정 Domain Error Code에 따른 복잡한 Business Message 판단은 하지 않습니다.

그러한 메시지는 Action 결과를 만드는 상위 Layer에서 결정합니다.

---

# 23. Toast와 Feature의 경계

Design System은 Toast 기능을 제공하지만 **언제 Toast를 보여줄지는 Feature가 결정**합니다.

```txt
Design System
  toastActionResult 제공

Feature
  Action 결과 감지
  Toast 호출 여부 결정
```

예:

```txt
BlockMemberDialog
      ↓
Action 성공
      ↓
Toast
      ↓
Dialog Close
      ↓
router.refresh()
```

이 Client Interaction 흐름은 Feature 책임입니다.

---

# 24. `hooks`

공통 UI Hook이 실제로 필요해지면:

```txt
packages/design-system/src/hooks/
```

영역을 추가할 수 있습니다.

조건:

```txt
Domain에 독립적

여러 UI에서 재사용

React Interaction 자체를 다룸

특정 App URL이나 Business Service를 모름
```

현재 구현되지 않은 Hook을 문서에서 현재 기능으로 취급하지 않습니다.

---

# 25. 공통 Hook 후보

실제 필요가 확인되면 다음과 같은 Hook을 Design System에 둘 수 있습니다.

```txt
useActionResultEffect

useFormInteractionState

useMediaQuery
```

각각의 책임은 다음과 같이 정의할 수 있습니다.

---

## `useActionResultEffect`

Server Action 결과에 따른 공통 Client Side Effect를 조합합니다.

예:

```txt
ActionResult
   ↓
Field Error 여부 확인
   ↓
Toast
   ↓
onSuccess
```

이 Hook 자체는:

```txt
어떤 Dialog를 닫을지

어떤 Route를 refresh할지

어떤 Business State를 변경할지
```

알지 않습니다.

그러한 처리는 `onSuccess`를 통해 Feature가 결정합니다.

---

## `useFormInteractionState`

Form UX 상태를 관리합니다.

예:

```txt
touchedFields

submitAttempted

editedAfterResult

editedFieldsAfterResult
```

목적은 Client Validation과 Server Validation 결과가 자연스럽게 함께 동작하도록 하는 것입니다.

특정 Domain Schema나 Field 이름을 직접 알지 않습니다.

---

## `useMediaQuery`

반응형 UI나 사용자 환경 Media Query를 React에서 관찰하는 범용 Hook입니다.

예:

```txt
viewport condition

prefers-reduced-motion

기타 CSS Media Query
```

다만 CSS만으로 충분한 Presentation 문제를 무조건 JavaScript Hook으로 해결하지 않습니다.

Runtime 값이 실제 Component Logic에 필요한 경우에 사용합니다.

---

# 26. Hook을 과도하게 추가하지 않는다

다음과 같은 Generic Hook Library를 미리 구축하지 않습니다.

```txt
usePrevious

useToggle

useBoolean

useDebounce

useMounted

useEventListener

useClickOutside
```

각 Hook은 실제 반복 요구가 생긴 뒤 추가합니다.

특히 Radix UI나 React 자체가 이미 해결하는 Interaction을 별도 Hook으로 중복 구현하지 않습니다.

---

# 27. `theme`

Theme Runtime 기능이 실제로 구현되면:

```txt
packages/design-system/src/theme/
```

영역으로 분리할 수 있습니다.

Theme은 Business Domain이 아니라 Design System 자체의 UI 상태이므로 이 Package에 적합합니다.

예상할 수 있는 책임:

```txt
ThemeMode

ThemeProvider

ThemeContext

Theme Initialization

Theme Cookie

System Theme Detection

Theme Toggle

useTheme
```

현재 구현되지 않은 경우 Public API에 미리 포함하지 않습니다.

---

# 28. Theme Mode

Theme는 다음 상태를 표현할 수 있습니다.

```txt
light

dark

system
```

`system`은 실제 표시 시:

```txt
prefers-color-scheme
```

를 사용하여 `light` 또는 `dark`로 resolve할 수 있습니다.

개념:

```txt
ThemeMode
   ↓
resolve
   ↓
ResolvedThemeMode
   ↓
data-ds-mode
```

---

# 29. Theme 초기화

Theme Runtime을 추가할 경우 초기 Render 전에 올바른 Theme를 적용하여 Theme Flash를 줄이는 초기화 Script를 사용할 수 있습니다.

개념:

```txt
Server Cookie
      ↓
Initial Theme Mode
      ↓
ThemeInitScript
      ↓
<html data-ds-mode="...">
```

이 기능은 앱의 Business Logic이 아니라 Design System Runtime 책임입니다.

---

# 30. Theme Provider

Client Runtime에서는 Provider를 통해 Theme State를 관리할 수 있습니다.

대표적인 책임:

```txt
현재 ThemeMode

Resolved ThemeMode

Theme 변경

Theme Toggle

System Theme 변화 감지

Cookie 동기화
```

App은 Theme 구현 세부사항보다 Public Theme API를 사용합니다.

---

# 31. Theme Cookie

Theme Preference는 Cookie 등을 통해 저장할 수 있습니다.

단 Cookie 이름은 보일러플레이트에 특정 제품 이름을 하드코딩하지 않습니다.

예:

```txt
repo_theme_mode
```

또는 Project Initialization 과정에서 변경 가능한 값을 사용할 수 있습니다.

Reusable Boilerplate에서:

```txt
athena_theme_mode
```

와 같은 제품 전용 이름을 그대로 사용하지 않습니다.

---

# 32. Theme Toggle

Theme Toggle Button은 특정 Business Domain과 무관하므로 Design System에 둘 수 있습니다.

하지만 다음 책임만 가져야 합니다.

```txt
현재 Theme 표시

Theme 전환

접근 가능한 Label
```

다음은 알지 않습니다.

```txt
User Profile

Database Preference

Server Action

특정 App Permission
```

사용자 Theme 설정을 Database 계정 설정으로 저장하는 기능이 생긴다면 해당 Persistence Use Case는 App / Domain에서 별도로 처리합니다.

---

# 33. `styles`

`styles`는 Design Token과 Storybook 등 Design System 자체의 CSS 기반을 관리합니다.

현재 또는 정리 후 주요 역할은 다음과 같습니다.

```txt
tokens.css
storybook.css
```

필요하지 않은 중복 Theme File은 유지하지 않습니다.

---

# 34. `tokens.css`

`tokens.css`는 Design System의 공통 Semantic Token을 정의합니다.

예:

```txt
background

foreground

surface

primary

muted

destructive

success

warning

info

border

input

ring

radius
```

Component는 가능한 한 Raw Color 값보다 Semantic Token을 사용합니다.

권장:

```txt
bg-background

text-foreground

border-border
```

지양:

```txt
bg-[#ffffff]

text-[#111111]
```

특정 Component에서 명확한 이유가 있는 경우는 예외일 수 있습니다.

---

# 35. Semantic Token

Token 이름은 특정 Color 자체보다 역할을 표현합니다.

```txt
primary

destructive

success

warning

info
```

이렇게 하면 같은 Component가:

```txt
web light

web dark

admin light

admin dark
```

Theme에서 서로 다른 실제 색을 사용할 수 있습니다.

---

# 36. App Theme

Web과 Admin은 동일한 Semantic Token 이름을 유지하면서 실제 값은 다르게 정의할 수 있습니다.

개념:

```txt
Web Theme
  --color-primary = ...

Admin Theme
  --color-primary = ...
```

Component에서는:

```txt
var(--color-primary)
```

또는 Tailwind Semantic Class만 사용합니다.

따라서 Component가 자신이 Web인지 Admin인지 직접 판단할 필요가 줄어듭니다.

---

# 37. `data-ds-theme`

Application Theme 종류는 다음 Attribute로 구분할 수 있습니다.

```txt
data-ds-theme="web"

data-ds-theme="admin"
```

예:

```html
<html data-ds-theme="web"></html>
```

```html
<html data-ds-theme="admin"></html>
```

이를 통해 동일 Semantic Token에 앱별 실제 값을 적용할 수 있습니다.

---

# 38. `data-ds-mode`

Light / Dark Mode는 별도의 Attribute로 관리할 수 있습니다.

```txt
data-ds-mode="light"

data-ds-mode="dark"
```

따라서 두 개념을 분리합니다.

```txt
Theme
  web | admin

Mode
  light | dark
```

`system`은 사용자의 설정 값이며 실제 DOM에는 resolved된 Mode를 적용할 수 있습니다.

---

# 39. `storybook.css`

Storybook은 실제 Next.js App Root CSS를 그대로 사용할 수 없는 독립 UI Runtime이므로 Design System Component를 표현할 공통 CSS Entry가 필요합니다.

`storybook.css`는 다음 역할을 가질 수 있습니다.

```txt
Tailwind 로드

Token 로드

Design System Source Scan

Web Theme

Admin Theme

Dark Mode

Storybook Base Style
```

현재 존재하지 않는 `primitives`를 Tailwind `@source`에 유지하지 않습니다.

실제 Source만 추적합니다.

예:

```txt
@source "../web";
@source "../admin";
```

향후 다른 Component 영역이 실제로 추가되면 그때 Source를 추가합니다.

---

# 40. App Styles와 Design System Styles

Design System은 공통 Token과 Theme 기반을 제공합니다.

App은 자신의 Global CSS에서 해당 Theme Style을 사용합니다.

개념:

```txt
Design System
  Token / Theme

       ↓

App globals.css

       ↓

Application
```

특정 페이지나 Feature의 Style을 Design System Global CSS로 올리지 않습니다.

---

# 41. `utils`

`utils`는 UI 구현에서 공통으로 사용하는 도메인 독립적인 Utility를 제공합니다.

대표적인 예:

```txt
cn
```

`cn`은:

```txt
clsx

tailwind-merge
```

등을 조합하여 Class Name을 일관되게 구성할 수 있습니다.

적절한 Utility:

```txt
Class Name 조합

Presentation 관련 순수 Helper
```

부적절한 Utility:

```txt
calculateOrderRefund

formatUserRole

canPublishContent

normalizePayment
```

후자는 Domain 또는 App 책임입니다.

---

# 42. `@repo/core`와의 관계

Design System은 현재 공통 `ActionResult`, `FieldErrors` 등의 UI 독립 Type을 사용하기 위해 `@repo/core`를 의존할 수 있습니다.

예:

```txt
@repo/design-system/form
       ↓
@repo/core/action
```

이 방향은 허용됩니다.

반대로:

```txt
@repo/core
       ↓
@repo/design-system
```

은 허용하지 않습니다.

Dependency 전체 기준은 `05_의존성_경계.md`를 따릅니다.

---

# 43. Domain Package를 의존하지 않는다

Design System에서 다음과 같은 Import를 만들지 않습니다.

```ts
import type { UserStatus } from "@repo/domain/user/client";
```

```ts
import type { OrderStatus } from "@repo/domain/order/client";
```

이러한 의존성이 필요해진다면 Component가 실제로 Entity UI인지 검토합니다.

기본적으로:

```txt
Design System
  ↓
Core

Domain
  ✕
```

경계를 유지합니다.

---

# 44. Server Action과의 경계

Design System의 Form Helper와 Hook은 `ActionResult`를 다룰 수 있지만 **구체적인 Server Action을 import하지 않습니다.**

적절함:

```txt
ActionResult<T> 해석

Field Error 표시

Action 결과 Toast 처리
```

부적절함:

```txt
blockMemberAction 호출

updateProfileAction 호출

refundOrderAction 호출
```

구체적인 Action 실행은 Feature가 담당합니다.

---

# 45. `router.refresh()`와의 경계

Design System의 범용 Component가 특정 Mutation 성공 후 `router.refresh()`를 자동 호출하지 않습니다.

```txt
Design System Dialog
  ✕ router.refresh

Design System Button
  ✕ router.refresh
```

해당 Client Flow를 소유한 Feature가 책임집니다.

```txt
Feature Dialog
  ↓
Action 성공
  ↓
Toast
  ↓
Close
  ↓
router.refresh()
```

공통 `useActionResultEffect` 같은 Hook이 존재하더라도 `router.refresh()`를 내부에서 강제하지 않고 `onSuccess`를 통해 Feature에 제어권을 남기는 것이 기본입니다.

---

# 46. 새로운 공통 Component 추가 기준

새 Component를 Design System에 추가하기 전에 다음을 확인합니다.

```txt
특정 Domain을 모르는가?

특정 Business Action을 모르는가?

여러 위치에서 실제로 사용할 것인가?

Presentation 또는 Interaction 책임이 명확한가?

기존 Component 조합만으로 충분하지 않은가?

공통 API가 실제로 안정적인가?
```

---

# 47. 처음부터 Design System에 넣지 않는다

새 UI가 등장하면 기본적으로 실제 사용하는 앱에서 시작합니다.

```txt
App
 ↓
실제 사용
 ↓
반복 확인
 ↓
공통 책임 발견
 ↓
Design System 승격 검토
```

다음 방향을 피합니다.

```txt
앞으로 사용할 것 같음
 ↓
Design System 먼저 구현
```

---

# 48. App에서 Design System으로 승격하는 기준

다음 상황이면 승격을 검토할 수 있습니다.

```txt
동일한 Presentation Pattern이 반복됨

Interaction Behavior가 동일함

Domain Dependency를 제거할 수 있음

Props Contract를 일반화할 수 있음

여러 Feature에서 동일 구현이 복제됨
```

단순히 JSX가 비슷한 것만으로 승격하지 않습니다.

---

# 49. 승격 시 Domain 의미 제거

예를 들어 다음 Component가 여러 곳에서 반복된다고 가정합니다.

```txt
OrderEmptyState

UserEmptyState

ContentEmptyState
```

공통 Presentation 구조가 동일하다면:

```txt
EmptyState
```

를 Design System 또는 App Shared UI로 추출할 수 있습니다.

하지만:

```txt
주문이 없습니다.
주문 만들기
```

같은 Domain Copy와 행동까지 Design System에 넣지 않습니다.

---

# 50. Design System과 App Shared의 경계

한 앱에서만 공유되는 도메인 독립 UI는 곧바로 Workspace Design System으로 올릴 필요가 없습니다.

```txt
한 Feature에서 사용
→ Feature colocate

한 앱의 여러 Slice에서 사용
→ apps/*/shared

여러 앱 또는 Design System 수준의 공통성
→ @repo/design-system 검토
```

앱 구조의 승격 기준은 `10_앱_구조.md`를 따릅니다.

# 51. Storybook

Design System Component는 독립적인 UI 계약을 가지므로 Storybook 작성 가치가 높습니다.

특히 다음 대상은 Story 작성 후보입니다.

```txt

Theme Component

복잡한 Form UI

Toast Presentation

Interactive Common Component
```

다음 Utility 자체에는 일반적으로 Story가 필요하지 않습니다.

```txt
form-error.utils.ts

form.utils.ts

cn
```

이러한 코드는 필요한 경우 Unit Test로 검증합니다.

Storybook 세부 기준은 `13_스토리북.md`에서 설명합니다.

# 52. 테스트

Design System 테스트는 UI 계약을 중심으로 작성합니다.

대표적인 대상:

```txt

Disabled State

Keyboard Behavior

Error Presentation

Theme State

Hook State Transition
```

Pure Utility:

```txt
form error helper

class utility
```

# 53. Public API

Design System 외부에서는 명시적인 Package Export를 사용합니다.

권장:

```ts
import { ToastProvider } from "@repo/design-system/toast";

import { getFieldError, getFormError } from "@repo/design-system/form";
```

지양:

```ts
import ToastProvider from "@repo/design-system/src/toast/toast-provider";
```

내부 File Structure는 Public Contract가 아닙니다.

---

# 54. Export는 실제 구현과 일치시킨다

`package.json`의 `exports`에는 실제로 존재하고 지원하는 Public API만 둡니다.

예를 들어 `primitives` 구현을 제거했다면:

```txt
@repo/design-system/primitives
```

를 계속 Public API로 유지할 이유가 있는지 검토합니다.

같은 원칙은 미래의:

```txt
theme

hooks
```

에도 적용됩니다.

실제 구현과 Public API가 준비된 시점에 export를 추가합니다.

# 55. File Naming

Form처럼 Utility가 많아질 경우 함수 하나마다 파일을 만들지 않습니다.

예:

```txt
form-action-result.types.ts

form-error.utils.ts

form.utils.ts
```

처럼 책임별로 묶습니다.

동일 원칙은 다른 영역에도 적용합니다.

```txt
theme.types.ts

theme.constants.ts

theme.utils.ts
```

등 구체적인 Naming Convention은 `18_컨벤션.md`의 기준을 따릅니다.

# 56. 새로운 Design System 기능 추가 흐름

새로운 공통 UI 기능을 추가할 때 다음 순서로 검토합니다.

```txt
1. 실제 사용하는 App / Feature가 있는가?

2. Domain에 독립적인가?

3. App Shared로 충분한가?

4. Web / Admin 중 어느 Theme에 속하는가?

5. 두 Theme가 공유하는 낮은 Primitive가 실제로 필요한가?

6. 기존 Utility / Component로 해결할 수 있는가?

7. Public API가 필요한가?

8. Story가 필요한가?

9. Unit / Component Test가 필요한가?

10. Package Export를 수정해야 하는가?
```

필요하지 않은 구조를 미리 만들지 않습니다.

# 57. 현재와 미래 구조를 구분한다

문서에서는 실제 구현 상태와 향후 확장 가능성을 구분합니다.

현재 실제 구현이 존재하는 영역만 현재 기능으로 취급합니다.

향후 후보:

```txt
Web / Admin 공통 Component 확대

Theme Runtime

공통 UI Hooks

필요한 경우 Primitive 계층 재도입
```

이러한 구조는 **확장 위치가 정의되어 있을 뿐 현재 기능으로 간주하지 않습니다.**

구현될 때 문서와 Package Export를 함께 갱신합니다.

# 60. 핵심 원칙

```txt
Design System은 도메인에 독립적인 UI 기반이다.

Design System이 모든 UI를 소유하지 않는다.

Primitive는 필수 Layer가 아니다.

실제 공유 기반이 생겼을 때만 Primitive를 도입한다.

web과 admin은 앱별 시각 언어를 표현한다.

web과 admin에도 Domain UI를 넣지 않는다.

Entity는 Business Object를 표현한다.

Feature는 Business Action을 수행한다.

Form은 Domain Form이 아니라 공통 Form Infrastructure다.

Toast는 Notification Infrastructure를 제공한다.

Toast를 언제 보여줄지는 Feature가 결정한다.

공통 UI Hook은 실제 재사용 요구가 생겼을 때 추가한다.

Theme Runtime은 구현되는 시점에 Design System 책임으로 추가할 수 있다.

Theme와 Mode를 분리한다.

Semantic Token을 중심으로 Theme를 구성한다.

App별 Theme는 같은 Token Contract에 서로 다른 값을 적용할 수 있다.

utils에는 UI에 독립적인 Presentation Helper만 둔다.

Design System은 @repo/core를 사용할 수 있지만 Domain을 알지 않는다.

구체적인 Server Action을 Design System에서 호출하지 않는다.

router.refresh 같은 Business Flow 후처리는 Feature가 소유한다.

한 앱에서만 공유된다면 먼저 App Shared를 검토한다.

실제 반복과 안정된 공통 계약이 생긴 뒤 Design System으로 승격한다.

Public Export는 실제 구현과 일치시킨다.

미래를 예상해 빈 Directory와 Component를 만들지 않는다.

책임이 생기면 구조가 따라온다.
```
