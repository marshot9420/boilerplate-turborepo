# 구현 안전성

이 문서는 `boilerplate-turborepo`에서 기능을 구현할 때 동시 실행, 중복 요청, 재시도, 외부 시스템 실패 등 실제 Runtime 환경에서 발생할 수 있는 문제를 검토하는 기준을 정의합니다.

구현 안전성의 목적은 정상적인 단일 요청에서 코드가 논리적으로 동작하는지만 확인하는 것이 아닙니다.

다음과 같은 상황에서도 반드시 지켜야 하는 Business State와 데이터 불변조건이 유지되는지를 확인하는 것이 목적입니다.

```txt
같은 작업이 동시에 실행됨

같은 요청이 여러 번 전달됨

조회한 상태가 변경된 뒤 Update가 실행됨

여러 변경 중 일부만 성공함

외부 Provider는 성공했지만 Database 저장이 실패함

Timeout이 발생했지만 실제 작업 성공 여부는 알 수 없음

Retry가 원래 작업을 다시 실행함

오래된 UI나 Cache를 기준으로 Mutation이 요청됨
```

이 문서는 다음 질문에 대한 기준을 제공합니다.

```txt
이 구현에는 Race Condition이 존재할 수 있는가?

조회 후 판단하고 Update하는 구조는 동시 실행에서도 안전한가?

Transaction만 사용하면 충분한가?

Database Constraint가 필요한 불변조건은 무엇인가?

같은 요청이 두 번 들어와도 같은 결과를 보장해야 하는가?

외부 Side Effect와 Database 변경 중 하나만 성공하면 어떻게 되는가?

Timeout 이후 같은 작업을 Retry해도 안전한가?

UI에 보이는 상태를 Mutation의 최종 판단 근거로 사용해도 되는가?

동시성이나 실패 시나리오를 어떤 Test Level에서 검증해야 하는가?
```

Database Transaction과 Persistence 구현은 `07_데이터베이스.md`, Business State와 Use Case는 `08_도메인_레이어.md`, Server Action 경계는 `09_서버_액션.md`, 테스트 수준은 `12_테스트_전략.md`, 보안과 운영 정책은 `17_보안_및_운영_기본정책.md`를 따릅니다.

이 문서는 해당 전문 문서의 세부 규칙을 다시 정의하지 않고 **구현 과정에서 어떤 안전성 위험을 발견하고 어떤 보호 수단을 검토해야 하는지**를 연결하는 기준으로 사용합니다.

# 1. 기본 원칙

구현 안전성의 기본 원칙은 다음과 같습니다.

```txt
정상 경로만으로 구현의 안전성을 판단하지 않는다.

동시에 실행될 수 있는 모든 Mutation은 경쟁 상태를 검토한다.

조회한 값은 Update 시점까지 그대로 유지된다고 가정하지 않는다.

Transaction은 Atomicity를 제공하지만 모든 Race Condition을 자동으로 해결하지 않는다.

반드시 유지되어야 하는 데이터 불변조건은 가능한 경우 Database에서도 보호한다.

Client의 중복 제출 방지는 UX 책임이며 Server-side Idempotency를 대체하지 않는다.

Business State Transition은 최종 Mutation 시점의 Server State를 기준으로 검증한다.

외부 Side Effect와 Database 변경을 하나의 완전한 Transaction처럼 가정하지 않는다.

Timeout은 작업 실패를 의미하지 않을 수 있다.

Retry는 원래 작업과 동일한 Side Effect를 다시 발생시킬 수 있음을 전제로 한다.

요청이 시작된 순서와 완료되는 순서는 다를 수 있다.

UI, Cache, 이전 조회 결과는 Stale할 수 있다.

금액, 시간, Null, Boundary Value는 표현 방식 자체가 Business Correctness에 영향을 줄 수 있다.

예상 가능한 Business Failure와 Infrastructure Failure를 구분한다.

중요한 상태 변경은 운영 중 원인을 추적할 수 있어야 한다.
```

핵심 질문은 다음과 같습니다.

```txt
이 코드가 한 번 실행되면 맞는가?
```

에서 끝나지 않고:

```txt
이 코드가 동시에 두 번 실행되어도 맞는가?

중간에 실패해도 복구 가능한가?

성공 여부를 알 수 없는 상태에서도 다음 행동을 결정할 수 있는가?
```

까지 검토합니다.

# 2. 구현 전 안전성 위험 확인

모든 변경에서 동일한 수준의 동시성 설계가 필요한 것은 아닙니다.

다만 다음 중 하나라도 포함된다면 구현 전에 안전성 위험을 명시적으로 검토합니다.

```txt
Database Mutation

상태 전이

재고 / 수량 / 한도 / 잔액 변경

금액 계산 또는 결제

한 번만 생성되어야 하는 Resource

Unique한 값 생성

같은 Resource에 대한 여러 사용자 또는 여러 요청의 변경

Webhook

Scheduled Job / Cron

외부 API Mutation

메일 / 알림 / 파일 업로드 같은 Side Effect

Retry 또는 Timeout

Cache된 데이터를 기준으로 하는 Mutation

만료 시각 또는 시간 기반 상태 변경

대량 처리 / Batch
```

단순 조회나 순수 UI 변경처럼 Runtime 경쟁 상태가 실제 결과를 변경하지 않는 작업까지 복잡한 Concurrency Control을 추가하지 않습니다.

구현 안전성은 위험에 비례하여 적용합니다.

# 3. Business Invariant를 먼저 정의한다

Concurrency나 Transaction 구현을 선택하기 전에 **무엇이 절대로 깨지면 안 되는지**를 먼저 정의합니다.

예:

```txt
동일한 이메일의 User는 하나만 존재한다.

재고는 허용된 정책 아래에서 음수가 되지 않는다.

하나의 주문에 동일한 결제가 중복 생성되지 않는다.

완료된 상태를 이전 상태로 되돌릴 수 없다.

동일한 Provider Event는 한 번만 Business State에 반영된다.

환불 가능 수량을 초과하여 환불 요청할 수 없다.
```

이러한 규칙을 Business Invariant로 봅니다.

구현 순서는 다음과 같이 생각합니다.

```txt
Business Invariant 정의
        ↓
깨질 수 있는 경쟁 / 실패 시나리오 확인
        ↓
보호 수단 선택
        ↓
Test / Observability 결정
```

보호 수단부터 선택하고 나중에 이유를 맞추지 않습니다.

# 4. Race Condition

Race Condition은 둘 이상의 실행 흐름이 같은 상태에 영향을 주고 **실행 순서에 따라 결과가 달라지는 상황**입니다.

예:

```txt
재고 1개

Request A
  재고 조회 → 1

Request B
  재고 조회 → 1

Request A
  주문 생성 / 재고 차감

Request B
  주문 생성 / 재고 차감
```

두 요청을 각각 독립적으로 보면 올바른 코드여도 동시에 실행되면 Business Invariant가 깨질 수 있습니다.

Race Condition은 다음 영역에서 우선적으로 검토합니다.

```txt
Counter

Inventory

Quota

Balance

State Transition

한 번만 수행되어야 하는 작업

중복 생성

Default / Primary Resource 변경

Webhook 처리

Scheduled Job

같은 Resource의 동시 수정
```

Race Condition은 단순히 비동기 코드가 존재한다는 의미가 아닙니다.

다음 조건이 함께 있을 때 문제가 됩니다.

```txt
공유 상태가 있고
+
둘 이상의 실행이 해당 상태를 읽거나 변경하며
+
실행 순서가 결과에 영향을 줌
```

# 5. Read-Modify-Write

특히 주의해야 하는 형태는 Read-Modify-Write입니다.

```txt
현재 상태 조회
   ↓
Application에서 판단
   ↓
별도의 Update
```

예:

```txt
1. 현재 주문 상태 조회
2. PAID인지 확인
3. PREPARING으로 변경
```

단일 요청에서는 자연스럽지만 조회와 Update 사이에 다른 요청이 상태를 변경할 수 있습니다.

```txt
Request A
  status = PAID 조회

Request B
  status = PAID 조회

Request A
  PREPARING으로 변경

Request B
  동일한 전이를 다시 실행하거나 다른 Side Effect 수행
```

따라서 Read-Modify-Write가 존재하면 다음을 확인합니다.

```txt
조회한 상태가 Update 시점까지 유지되어야 하는가?

동시에 같은 Resource가 변경될 수 있는가?

두 요청이 모두 기존 상태를 보고 성공하면 문제가 되는가?

Update 자체에 기대 상태를 조건으로 포함할 수 있는가?

Version 또는 Lock이 필요한가?
```

Business 판단을 Domain에서 수행한다는 Architecture 원칙과 동시성 보호는 별개의 문제입니다.

```txt
Domain에서 상태를 올바르게 판단함
```

만으로:

```txt
동시 실행에서도 상태 전이가 안전함
```

이 자동으로 보장되지는 않습니다.

# 6. Atomic Update

가능하다면 조회와 변경 사이의 경쟁 구간을 줄이는 방향을 우선 검토합니다.

예를 들어 개념적으로:

```txt
UPDATE resource
SET status = NEXT
WHERE id = ?
  AND status = EXPECTED
```

처럼 **기대하는 현재 상태를 Mutation 조건에 포함**할 수 있습니다.

이 경우 결과는 다음과 같이 해석할 수 있습니다.

```txt
변경 성공
  → 기대 상태가 실제로 유지되고 있었음

변경된 Row 없음
  → 이미 다른 요청이 상태를 변경했거나 조건이 더 이상 유효하지 않음
```

수량 변경도 동일합니다.

```txt
현재 수량 조회
→ Application에서 계산
→ 절대값으로 저장
```

보다 실제 요구에 따라:

```txt
조건부 Increment / Decrement
```

를 사용할 수 있는지 검토합니다.

Atomic Update는 모든 문제의 정답이 아니라 **Read-Modify-Write Window를 줄이거나 제거할 수 있는 수단**입니다.

구체적인 Persistence 구현은 `07_데이터베이스.md`의 Repository 책임을 따릅니다.

# 7. Atomicity

Atomicity는 여러 변경이 하나의 논리적 작업일 때 다음 결과만 허용하는 성질입니다.

```txt
전부 성공

또는

전부 실패
```

예:

```txt
Order 생성
+
Order Item 생성
+
Inventory 변경
```

중간 상태를 허용할 수 없다면 Atomicity가 필요합니다.

다음 질문으로 판단합니다.

```txt
A는 성공했지만 B는 실패한 상태를 허용할 수 있는가?

일부 성공 상태를 나중에 복구하는 것이 Business적으로 허용되는가?

이 작업들이 하나의 Database Transaction으로 묶일 수 있는가?

외부 시스템까지 포함되어 Database Transaction만으로 해결할 수 없는가?
```

Atomicity의 범위는 기술이 아니라 Business Use Case가 결정합니다.

Transaction Scope를 Domain Service에서 결정하는 기존 기준은 `08_도메인_레이어.md`를 따릅니다.

# 8. Transaction

Database Transaction은 여러 Database Operation을 하나의 Atomic Unit으로 묶는 핵심 수단입니다.

하지만 다음을 명확하게 구분합니다.

```txt
Transaction
  여러 DB 변경의 Commit / Rollback 경계

Concurrency Control
  동시에 실행되는 작업 사이의 경쟁 제어
```

따라서:

```txt
Transaction을 사용했다.
  ≠
모든 Race Condition이 해결되었다.
```

예를 들어 두 Transaction이 모두 같은 값을 읽고 각자 유효하다고 판단한 뒤 변경을 수행할 수 있다면 Isolation Level, Lock, Conditional Update, Constraint 등 추가 보호가 필요할 수 있습니다.

Transaction을 사용할 때 확인합니다.

```txt
어떤 Operation이 반드시 함께 성공해야 하는가?

Transaction 밖에서 수행된 조회가 안전성 판단에 사용되고 있지 않은가?

Transaction 내부에서도 동일 Resource를 다른 Transaction이 변경할 수 있는가?

필요한 상태를 Transaction 안에서 다시 확인해야 하는가?

Transaction이 불필요하게 오래 유지되고 있지 않은가?

외부 Network 호출을 Transaction 안에서 기다리고 있지 않은가?
```

Transaction의 구체적인 구성과 Repository 사용 방식은 `07_데이터베이스.md`와 `08_도메인_레이어.md`를 따릅니다.

# 9. Database Constraint

Application Validation은 사용자에게 의미 있는 오류를 제공하고 Business Flow를 제어하는 데 필요합니다.

하지만 **반드시 유지되어야 하는 데이터 불변조건**을 Application 코드만으로 보호할 수 있는지는 별도로 검토합니다.

예:

```txt
조회
  동일한 값 없음

다른 요청도 조회
  동일한 값 없음

두 요청 모두 Insert
```

Application에서 중복 여부를 먼저 확인해도 동시 요청에서는 둘 다 통과할 수 있습니다.

따라서 Database가 직접 표현할 수 있는 불변조건은 가능한 경우 Constraint에서도 보호합니다.

대표적인 수단:

```txt
NOT NULL

UNIQUE

Foreign Key

CHECK

적절한 Index / Constraint 조합
```

역할을 다음과 같이 구분합니다.

```txt
Application / Domain Validation
  사용자와 Business 관점의 의미 있는 판단

Database Constraint
  최종 Persistence 불변조건 보호
```

둘은 경쟁 관계가 아닙니다.

```txt
Database Constraint가 있으므로 Domain Validation이 필요 없다.
```

도 아니고:

```txt
Domain에서 검증했으므로 Database Constraint가 필요 없다.
```

도 아닙니다.

Database Constraint로 표현하기 어려운 Business Rule은 Domain에서 유지합니다.

# 10. Idempotency

Idempotency는 같은 의도의 작업이 반복되어도 Business 결과가 중복 적용되지 않도록 하는 성질입니다.

대표적인 대상:

```txt
주문 생성

결제 요청

환불

Webhook 처리

메일 / 알림 발송 요청

Scheduled Job

외부 Provider Mutation

한 번만 생성되어야 하는 Resource
```

예:

```txt
같은 결제 요청이 두 번 전달됨
```

에서 기대하는 것이:

```txt
결제 2건 생성
```

이 아니라:

```txt
동일한 Business Operation으로 처리
```

라면 Idempotency가 필요합니다.

Idempotency를 설계할 때 먼저 정의합니다.

```txt
무엇을 동일한 요청으로 볼 것인가?

Idempotency 범위는 사용자 / Resource / Operation 중 어디인가?

얼마 동안 동일성을 유지해야 하는가?

이미 성공한 요청이 다시 오면 어떤 응답을 반환할 것인가?

첫 요청이 진행 중일 때 동일 요청이 오면 어떻게 처리할 것인가?

실패한 요청은 다시 실행 가능한가?
```

가능한 구현 수단은 상황에 따라 다릅니다.

```txt
Idempotency Key

Provider Event ID

Unique Constraint

Processed Event Record

Business Resource의 Unique Identifier

Conditional State Transition
```

특정 수단 하나를 모든 Mutation에 일괄 적용하지 않습니다.

# 11. Duplicate Request

중복 요청은 다양한 이유로 발생할 수 있습니다.

```txt
사용자 Double Click

Browser 재전송

Network Retry

Client Retry

Proxy / Infrastructure Retry

Webhook 재전송

Scheduled Job 중복 실행

사용자가 응답 전에 다시 제출
```

Client에서 버튼을 Disabled하거나 Pending UI를 표시하는 것은 중요하지만 역할은 다음과 같습니다.

```txt
Client 중복 제출 방지
  → UX
```

Server 안전성은 별도로 보장합니다.

```txt
Server-side Idempotency / Constraint / Concurrency Control
  → Correctness
```

따라서:

```txt
버튼을 Pending 동안 Disabled했다.
  ≠
중복 요청이 발생하지 않는다.
```

입니다.

Server Action은 외부에서 직접 호출될 수 있는 신뢰하지 않는 Boundary라는 기존 원칙을 유지합니다.

---

# 12. State Transition과 동시성

상태 전이는 단순한 값 변경이 아니라 Business Rule입니다.

예:

```txt
PAID
  ↓
PREPARING
  ↓
SHIPPING
  ↓
DELIVERED
```

상태 전이를 구현할 때는 두 종류의 검증을 구분합니다.

```txt
현재 상태에서 다음 상태가 허용되는가?
  → Domain Rule

동시에 다른 요청이 상태를 변경해도 그 판단이 유효한가?
  → Concurrency Control
```

Mutation에서는 UI가 보여준 상태나 이전 조회 결과를 최종 사실로 신뢰하지 않습니다.

```txt
UI
  status = PAID 표시

사용자가 변경 요청

그 사이 다른 요청
  status = CANCELED
```

이 경우 Server / Domain은 Mutation 시점의 최신 Business State를 다시 확인해야 합니다.

기본 원칙:

```txt
UI State
  힌트와 Presentation

Server / Domain State
  최종 Business 판단
```

상태 전이가 중복 Side Effect를 발생시키는 경우에는 기대 상태를 포함한 Atomic Update, Version, Lock, Idempotency 등을 함께 검토합니다.

---

# 13. Optimistic Concurrency

Optimistic Concurrency는 충돌이 항상 발생한다고 가정해 Resource를 미리 잠그기보다 **변경 시점에 내가 읽은 상태가 아직 유효한지 확인**하는 방식입니다.

대표적인 개념:

```txt
version

revision

updatedAt

expected status
```

예:

```txt
조회
  version = 3

Update
  WHERE id = ?
    AND version = 3

성공
  version = 4
```

Update 대상이 없다면 다른 변경이 먼저 발생한 것으로 해석할 수 있습니다.

적합한 경우:

```txt
충돌 빈도가 낮음

오래 Lock을 유지하고 싶지 않음

사용자 편집 충돌을 명시적으로 감지해야 함

상태 전이의 기대 상태를 확인할 수 있음
```

충돌을 발견했을 때 자동으로 덮어쓰지 않고 Business 의미에 따라 다음 중 하나를 선택합니다.

```txt
Conflict 반환

최신 상태 재조회

안전한 경우 Retry

사용자에게 재시도 요구
```

---

# 14. Pessimistic Concurrency

Pessimistic Concurrency는 충돌 가능성이 높거나 동시에 처리되면 안 되는 Resource를 Database Lock 등으로 선점하여 처리하는 방식입니다.

검토 대상:

```txt
높은 경합

순차 처리가 필요한 Critical Section

조건부 Update만으로 표현하기 어려운 복잡한 읽기와 변경
```

다만 Lock은 비용이 있습니다.

```txt
대기 시간 증가

Transaction Connection 점유

Deadlock 가능성

처리량 감소
```

따라서 Lock을 사용한다면 다음을 확인합니다.

```txt
Lock 범위가 최소인가?

Transaction 시간이 짧은가?

여러 Resource를 Lock한다면 순서가 일관적인가?

외부 Network 호출을 Lock 안에서 기다리지 않는가?

Timeout / Deadlock Error를 어떻게 처리할 것인가?
```

Optimistic / Pessimistic 방식 중 하나를 Repository 전체의 고정 정책으로 만들지 않습니다.

Use Case의 충돌 빈도와 불변조건을 기준으로 선택합니다.

---

# 15. External Side Effect

Database 밖에서 발생하는 변경은 별도의 실패 경계를 가집니다.

대표적인 External Side Effect:

```txt
Payment Provider 요청

Email 발송

Storage Upload / Delete

외부 API Mutation

Message Queue Publish

Webhook 호출
```

Database Transaction은 일반적으로 이러한 외부 시스템까지 Rollback할 수 없습니다.

따라서 다음 구조를 하나의 Transaction처럼 생각하지 않습니다.

```txt
Database 변경
+
외부 Provider 변경
```

예를 들어:

```txt
외부 결제 성공
  ↓
Database 저장 실패
```

또는:

```txt
Database Commit 성공
  ↓
외부 메일 발송 실패
```

가 가능합니다.

이 차이를 명시적으로 설계합니다.

---

# 16. Partial Failure

여러 시스템이 참여하는 작업에서는 일부만 성공할 수 있습니다.

대표적인 Partial Failure:

```txt
DB 성공 / Provider 실패

Provider 성공 / DB 실패

파일 업로드 성공 / 메타데이터 저장 실패

주문 생성 성공 / 알림 실패

여러 외부 호출 중 일부만 성공
```

Partial Failure를 검토할 때 다음을 정의합니다.

```txt
어느 시스템이 최종 Source of Truth인가?

일부 성공 상태를 허용할 수 있는가?

실패한 부분을 Retry할 수 있는가?

이미 성공한 부분을 Compensation할 수 있는가?

후속 Webhook이나 Reconciliation으로 상태를 회복할 수 있는가?

진행 중 / 결과 불명 상태를 별도 State로 표현해야 하는가?
```

필요에 따라 다음 설계를 검토할 수 있습니다.

```txt
Outbox

Processed Event Record

Compensating Action

Reconciliation Job

Explicit Processing State

Provider Webhook 기반 최종 확정
```

이 패턴들을 Boilerplate의 기본 구현으로 강제하지 않습니다.

중요한 것은 Partial Failure가 가능하다는 사실을 숨기지 않고 실제 Use Case에 맞는 복구 전략을 갖는 것입니다.

---

# 17. 외부 호출과 Database Transaction

일반적으로 외부 HTTP Request를 Database Transaction 내부에서 오래 기다리지 않습니다.

지양:

```txt
DB Transaction 시작
  ↓
Row 변경
  ↓
외부 Provider 요청 대기
  ↓
응답 후 Commit
```

이 구조는 다음 문제를 만들 수 있습니다.

```txt
Transaction 장시간 유지

Connection 점유

Lock 유지

Provider 지연이 Database 처리량에 영향

Timeout 시 실패 경계 복잡화
```

기본적으로는 Use Case에 따라:

```txt
Business Validation
  ↓
필요한 DB Transaction
  ↓
Commit
  ↓
External Side Effect
```

또는 외부 시스템을 먼저 호출해야 하는 경우:

```txt
External Operation
  ↓
결과 확인
  ↓
Database 반영
  ↓
필요한 Reconciliation
```

같이 실패 경계를 명시합니다.

어느 순서도 모든 상황에 대한 정답은 아닙니다.

핵심은 **한쪽 성공과 다른 쪽 실패가 실제로 발생할 수 있다는 전제 아래 설계하는 것**입니다.

---

# 18. Retry

Retry는 일시적인 실패에서 복구할 수 있는 수단이지만 모든 Error에 적용하지 않습니다.

Retry 전에 다음을 확인합니다.

```txt
이 실패는 일시적인가?

같은 요청을 다시 실행해도 안전한가?

이미 첫 요청이 성공했을 가능성이 있는가?

중복 Side Effect를 막을 Idempotency가 있는가?

Retry 횟수에 상한이 있는가?

계속 실패할 때 최종 상태를 어떻게 기록할 것인가?
```

일반적으로 Retry 후보가 될 수 있는 것은 상황에 따라 다음과 같습니다.

```txt
일시적인 Network Error

일시적인 Provider Unavailable

일시적인 Lock / Serialization Conflict
```

반면 다음 오류를 같은 입력으로 반복한다고 해결되지 않습니다.

```txt
Validation Error

Permission Error

허용되지 않는 Business State

존재하지 않는 Resource
```

Mutation Retry는 특히 Idempotency와 함께 검토합니다.

---

# 19. Timeout

Timeout은 호출자가 일정 시간 동안 결과를 기다리지 않기로 결정했다는 의미입니다.

반드시 다음을 의미하지는 않습니다.

```txt
상대 시스템이 작업을 수행하지 않았다.
```

예:

```txt
Payment Request 전송
  ↓
Provider에서 결제 성공
  ↓
응답 전 Network Timeout
  ↓
Application은 결과를 받지 못함
```

이 상태를 단순히 실패로 확정하고 같은 요청을 다시 보내면 중복 Side Effect가 발생할 수 있습니다.

Timeout이 있는 Mutation에서는 다음을 검토합니다.

```txt
결과를 조회할 API가 있는가?

Provider Idempotency Key를 사용할 수 있는가?

Webhook으로 최종 결과를 받을 수 있는가?

결과 불명 상태를 표현해야 하는가?

Retry 전에 현재 Provider State를 확인해야 하는가?
```

Timeout과 Business Failure를 동일한 Error로 취급하지 않습니다.

---

# 20. 요청 순서와 완료 순서

요청은 시작된 순서대로 완료된다고 가정하지 않습니다.

```txt
Request A 시작

Request B 시작

Request B 완료

Request A 완료
```

가 가능합니다.

문제가 될 수 있는 예:

```txt
검색어 "ord" 요청 A
검색어 "order" 요청 B

B 응답 먼저 도착
A 응답 나중에 도착

오래된 A 결과가 최신 B 결과를 덮어씀
```

또는 Mutation에서도:

```txt
상태 변경 A
상태 변경 B

완료 순서가 역전됨
```

이런 흐름에서 순서가 Business 의미를 가진다면 다음을 검토합니다.

```txt
Sequence / Version

Expected State

Request Cancellation

최신 요청만 반영

Server-side Serialization
```

단순히 JavaScript에서 호출한 순서만으로 최종 상태를 보장하지 않습니다.

---

# 21. Stale Data

다음 데이터는 현재 상태와 다를 수 있습니다.

```txt
UI에 렌더링된 데이터

이전 Server Component 결과

Client State

Browser Cache

Application Cache

이전에 조회한 Repository 결과
```

Stale Data 자체는 항상 오류가 아닙니다.

문제는 오래된 값을 **최종 Business 판단의 권위 있는 상태로 사용하는 경우**입니다.

Mutation에서는 필요한 Business State를 Server / Domain에서 다시 검증합니다.

예:

```txt
UI에 "취소 가능" 표시
  ↓
사용자가 취소 클릭
  ↓
그 사이 다른 요청으로 배송 시작
  ↓
Server에서 현재 상태 재확인
  ↓
취소 불가 처리
```

UI의 표시 조건과 Domain의 Business Rule이 같은 의미를 가질 수는 있지만 최종 Authority는 Server / Domain입니다.

---

# 22. Cache Consistency

Cache는 성능을 위한 복제된 상태일 수 있으므로 Database와 항상 동시에 변경된다고 가정하지 않습니다.

Mutation이 Cache에 영향을 준다면 다음을 확인합니다.

```txt
어떤 Cache가 Stale해지는가?

Commit 전에 Cache를 무효화하고 있지 않은가?

Mutation 성공 후 필요한 Revalidation이 있는가?

중요한 Business Validation을 오래된 Cache만으로 판단하고 있지 않은가?

Cache 갱신 실패가 Business Transaction 실패인지 단순 Presentation 지연인지 구분되는가?
```

기본적인 방향:

```txt
Database / Business State 변경 성공
        ↓
필요한 Cache 무효화 또는 갱신
```

Cache가 일시적으로 오래된 값을 보여줄 수 있는지, 강한 일관성이 필요한지 Use Case별로 판단합니다.

Server Action의 `revalidatePath`와 Client의 `router.refresh()` 책임은 `09_서버_액션.md`를 따릅니다.

---

# 23. Time과 Timezone

시간은 단순한 문자열이 아니라 Business State의 일부가 될 수 있습니다.

대표적인 대상:

```txt
만료 시각

예약

결제 기한

Token 만료

게시 시작 / 종료

Scheduled Job

날짜별 집계
```

시간을 다룰 때 다음을 구분합니다.

```txt
절대 시각
  특정 순간

Local Date / Local Time
  특정 지역의 달력 의미

Duration
  두 시점 사이의 경과 시간
```

기본적으로 절대 시각은 일관된 기준으로 저장하고 사용자에게 표시할 때 필요한 Timezone으로 변환합니다.

다음 문제를 검토합니다.

```txt
Server와 Client의 Timezone이 다른가?

자정 경계가 어떤 Timezone 기준인가?

DST가 있는 지역을 지원하는가?

Client Clock을 만료 판단의 최종 기준으로 사용하고 있지 않은가?

여러 Server의 Clock 차이가 결과에 영향을 주는가?

날짜만 필요한 값을 Timestamp로 잘못 모델링하고 있지 않은가?
```

Business Deadline과 권한 판단은 신뢰 가능한 Server-side 기준을 사용합니다.

---

# 24. Numeric Precision과 금액

부동소수점 표현은 특정 숫자를 정확하게 표현하지 못할 수 있습니다.

따라서 다음 값은 Precision을 명시적으로 검토합니다.

```txt
금액

세금

할인

환불 금액

비율

수량 계산

통계 집계
```

금액은 일반적으로 다음과 같은 방식 중 Domain에 맞는 표현을 사용합니다.

```txt
최소 통화 단위의 Integer

정확한 Decimal Type
```

JavaScript `number`의 부동소수점 계산을 무비판적으로 금액의 Source of Truth로 사용하지 않습니다.

추가로 다음을 정의합니다.

```txt
반올림 규칙

절삭 규칙

세금 계산 시점

개별 Item과 총합의 계산 순서

통화별 최소 단위
```

동일한 금액 계산 규칙을 UI와 Server에서 서로 다르게 구현하지 않습니다.

Business 금액 계산은 Domain 규칙을 기준으로 합니다.

---

# 25. Null / Optional / Empty State

다음 값은 의미가 다를 수 있습니다.

```txt
undefined

null

""

[]

0

false
```

예:

```txt
undefined
  값을 전달하지 않음

null
  명시적으로 값 없음

""
  사용자 입력은 존재하지만 빈 문자열
```

Update 요청에서는 특히 차이가 중요합니다.

```txt
필드를 변경하지 않음
```

과:

```txt
기존 값을 제거함
```

을 같은 값으로 처리하면 의도하지 않은 데이터 손실이 발생할 수 있습니다.

FormData 정규화, Zod Schema, Domain Request에서 의미를 명확하게 유지합니다.

또한 조회 결과의 빈 상태를 Error와 혼동하지 않습니다.

```txt
Resource 없음

빈 목록

Optional Relation 없음

필드 값 없음
```

은 서로 다른 의미일 수 있습니다.

# 26. Resource Limit과 Boundary Value

기능이 정상 입력에서 동작하는 것뿐 아니라 Resource의 최소 / 최대 경계에서도 안전한지 확인합니다.

대표적인 대상:

```txt
Pagination Limit

Batch Size

Upload Size

Upload Count

문자열 길이

배열 길이

수량 최소 / 최대

금액 최소 / 최대

Retry 횟수

Timeout

Transaction Duration

Query Result Size
```

Boundary Value는 다음을 함께 검토합니다.

```txt
0

1

최대 허용값

최대값 + 1

빈 입력

매우 큰 입력
```

Client 제한만으로 보호하지 않고 신뢰하지 않는 외부 입력은 Server에서도 제한합니다.

Resource Limit의 보안·운영 관점은 `17_보안_및_운영_기본정책.md`를 따릅니다.

# 27. Error Classification

모든 실패를 하나의 Generic Error로 처리하면 안전한 Retry, 사용자 안내, 운영 대응을 결정하기 어려워집니다.

최소한 다음 의미를 구분할 수 있는지 검토합니다.

```txt
Validation Failure
  입력 구조가 유효하지 않음

Business Failure
  현재 상태에서 작업이 허용되지 않음

Authorization Failure
  현재 Actor가 작업할 권한이 없음

Conflict / Concurrency Failure
  기대한 상태가 이미 변경됨

Infrastructure Failure
  Database / Network / Provider 문제

Timeout / Unknown Outcome
  실제 작업 성공 여부가 확정되지 않음

Unexpected Error
  예상하지 못한 Runtime / Programming Error
```

구분은 단순히 Error Class를 많이 만드는 것이 목적이 아닙니다.

호출자가 다음 행동을 결정할 수 있어야 합니다.

```txt
사용자 입력 수정

최신 상태 재조회

Retry

Retry 금지

운영 알림

일반 오류 표시
```

Database Raw Error와 Provider Raw Error를 Client에 그대로 노출하지 않는 기존 정책을 유지합니다.

---

# 28. Conflict를 일반 Validation Error로 숨기지 않는다

동시성 충돌은 사용자가 잘못된 값을 입력한 것과 의미가 다를 수 있습니다.

예:

```txt
사용자가 수정 화면을 열었을 때 version = 4

다른 사용자가 먼저 수정하여 version = 5

첫 사용자가 저장
```

이때 단순히:

```txt
입력값이 올바르지 않습니다.
```

로 처리하면 실제 원인을 잃습니다.

필요한 경우:

```txt
이미 상태가 변경되었습니다.
최신 상태를 다시 확인해 주세요.
```

처럼 Conflict 의미를 Domain Result 또는 적절한 Application Error로 표현합니다.

정확한 사용자 메시지는 각 앱의 UX 책임입니다.

---

# 29. Logging / Observability

안전성 문제가 운영에서 발생하면 **어떤 요청이 어떤 상태를 보고 어떤 변경을 시도했고 어디에서 실패했는지** 추적할 수 있어야 합니다.

중요 Mutation에서 상황에 따라 다음 Context를 남길 수 있습니다.

```txt
Event Name

Request / Correlation ID

Actor ID

Resource ID

Operation

Expected State

Observed / Result State

Domain Error Code

Provider Operation ID

Retry Attempt

Latency

Outcome
```

Idempotency Key나 외부 Identifier를 기록할 필요가 있다면 민감정보가 아닌지 확인하고 필요한 최소 범위만 남깁니다.

다음은 그대로 Logging하지 않습니다.

```txt
Password

Session Token

Access Token

Authorization Header

Cookie 전체

API Secret

Database URL

Payment Credential

불필요한 개인정보
```

Logging은 구현 안전성을 대신하지 않습니다.

```txt
문제를 기록할 수 있음
  ≠
문제가 발생하지 않도록 보호됨
```

다만 복구와 원인 분석이 필요한 중요 작업에서는 Observability도 안전성의 일부로 봅니다.

세부 Logging 정책은 `17_보안_및_운영_기본정책.md`를 따릅니다.

---

# 30. 보호 수단 선택

안전성 위험을 발견했다고 해서 항상 가장 강한 Lock이나 가장 큰 Transaction을 사용하지 않습니다.

문제에 맞는 최소한의 보호 수단을 선택합니다.

개념적인 판단 예:

```txt
중복 생성 방지
  → Unique Constraint
  → Idempotency Key

기대 상태에서만 전이
  → Conditional Atomic Update
  → Optimistic Concurrency

여러 DB 변경을 함께 성공 / 실패
  → Transaction

높은 경합의 복잡한 Critical Section
  → Pessimistic Lock 검토

외부 Event 중복 처리
  → Event ID + Unique Constraint / Processed Record

외부 Side Effect 결과 불명
  → Provider 조회 / Webhook / Reconciliation

오래된 수정 덮어쓰기 방지
  → Version 기반 Conflict Detection
```

한 Use Case에서 여러 수단을 함께 사용할 수도 있습니다.

예:

```txt
Transaction
+
Unique Constraint
+
Conditional Update
+
Idempotency
```

각 수단이 보호하는 위험이 무엇인지 설명할 수 있어야 합니다.

---

# 31. 과도한 안전성 구현을 피한다

안전성은 복잡성을 추가할 수 있습니다.

다음과 같은 구조를 근거 없이 도입하지 않습니다.

```txt
모든 Query에 Transaction

모든 Mutation에 Pessimistic Lock

모든 Endpoint에 Idempotency Table

모든 Error에 자동 Retry

모든 데이터에 Version Column

모든 외부 호출에 복잡한 Saga
```

먼저 실제 Invariant와 실패 시나리오를 확인합니다.

```txt
어떤 문제가 발생할 수 있는가?

발생하면 실제 Business State가 깨지는가?

현재 보호 수단으로 충분한가?

추가 복잡성의 비용보다 보호 가치가 큰가?
```

미래의 가능성만으로 복잡한 분산 시스템 패턴을 미리 만들지 않습니다.

---

# 32. 구현 위치와 책임

구현 안전성은 하나의 계층만의 책임이 아닙니다.

각 계층은 자신의 책임 범위에서 안전성을 제공합니다.

```txt
App / Client
  중복 인터랙션 완화
  Pending / Error UX
  오래된 응답 처리

Server Action
  외부 입력 Validation
  Authentication
  Domain Service 진입
  안전한 ActionResult

Domain
  Business Invariant
  State Transition
  Idempotency 의미
  Transaction 범위 결정

Repository / Database
  Atomic Persistence Operation
  Constraint
  Transaction 실행 기반
  필요한 Concurrency Primitive

Infrastructure
  Provider Timeout
  Retry
  Provider Idempotency
  Error Mapping
  Reconciliation 기반

Operations
  Logging
  Monitoring
  Alert
```

이 문서는 이 책임들을 하나의 Layer로 이동시키지 않습니다.

기존 Architecture Boundary를 유지한 상태에서 안전성을 조합합니다.

---

# 33. 테스트 관점

Concurrency와 Idempotency는 코드만 읽어서 완전히 검증하기 어려운 경우가 있습니다.

테스트가 필요한지는 Business Correctness에 미치는 영향에 따라 판단합니다.

대표적인 대상:

```txt
Database Constraint

Transaction Rollback

동시에 같은 Resource를 변경하는 흐름

Conditional Update 충돌

동일 Idempotency Key 중복 요청

Webhook 중복 Event

Retry 후 중복 Side Effect 방지

상태 전이 충돌
```

테스트 수준은 `12_테스트_전략.md`를 따릅니다.

개념적인 기준:

```txt
순수 State Transition Rule
  → Unit Test

Repository Constraint / Atomic Update
  → Integration Test

Domain Service + 여러 Repository + Transaction
  → Integration Test 검토

Client 중복 인터랙션 UX
  → Component Test

전체 Browser 흐름
  → 필요한 경우 E2E
```

Concurrency가 핵심인 Persistence 동작을 Prisma Mock만으로 검증하지 않습니다.

실제 Database의 Constraint, Transaction, Lock, Update 조건이 중요한 경우 Integration Test를 우선 검토합니다.

---

# 34. 동시성 테스트 작성 시 주의

동시성 테스트는 단순히 같은 함수를 두 번 호출하는 것만으로 경쟁 상태를 재현하지 못할 수 있습니다.

검증하려는 경쟁 지점을 명확하게 합니다.

예:

```txt
두 실행이 같은 초기 상태를 읽음
  ↓
동시에 Mutation 시도
  ↓
하나는 성공
  ↓
다른 하나는 Conflict / No-op
```

테스트는 결과의 핵심 불변조건을 검증합니다.

예:

```txt
최종 재고가 음수가 아님

동일 Event가 한 번만 반영됨

허용되지 않은 중복 Resource가 없음

상태 전이가 한 번만 수행됨
```

실행 순서에 우연히 의존하는 Flaky Test를 만들지 않습니다.

필요하다면 Test Barrier, 명시적인 Fixture, 실제 Transaction 경계를 사용하여 경쟁 조건을 재현할 수 있는지 검토합니다.

---

# 35. 예시: 재고 차감

단순 구현:

```txt
재고 조회
  5

요청 수량 확인
  3 이하이므로 가능

재고를 2로 Update
```

동시에 같은 요청이 들어오면 둘 다 5를 보고 성공할 수 있습니다.

검토:

```txt
Invariant
  재고가 허용 범위 아래로 내려가면 안 됨

Risk
  Read-Modify-Write Race

Possible Protection
  조건부 Atomic Decrement
  Transaction
  Constraint
  필요하면 Lock
```

정확한 선택은 실제 재고 모델과 예약 정책에 따라 결정합니다.

---

# 36. 예시: 주문 상태 변경

단순 구현:

```txt
Order 조회

status === PAID 확인

PREPARING으로 Update

알림 발송
```

검토해야 할 위험:

```txt
두 요청이 동시에 PAID를 조회

둘 다 PREPARING 전이 성공으로 판단

알림이 두 번 발송
```

가능한 설계:

```txt
Domain
  PAID → PREPARING Rule

Persistence
  status = PAID인 경우에만 Atomic Update

Side Effect
  실제 전이가 성공한 요청만 알림 수행

필요하면
  알림 자체의 Idempotency 검토
```

---

# 37. 예시: 외부 결제 요청

흐름:

```txt
Payment Provider 요청
  ↓
Timeout
```

이때 다음과 같이 단정하지 않습니다.

```txt
Timeout
  → 결제 실패
```

실제 가능한 상태:

```txt
Provider에서 실패

Provider에서 성공했지만 응답만 유실

Provider에서 아직 처리 중
```

따라서 다음을 검토합니다.

```txt
Provider Idempotency Key

Payment 조회 API

Webhook

Processing / Unknown 상태

Retry 정책

Reconciliation
```

Payment처럼 중복 Side Effect의 비용이 큰 작업은 특히 결과 불명 상태를 명시적으로 다룹니다.

---

# 38. 예시: 중복 Webhook

Provider는 동일 Event를 여러 번 전송할 수 있다고 가정합니다.

```txt
Event A 도착
  ↓
처리 성공

응답 유실
  ↓
Provider가 Event A 재전송
```

Webhook Handler가 단순히 Event를 다시 적용하면 상태나 Side Effect가 중복될 수 있습니다.

검토:

```txt
Provider Event ID 존재 여부

Event ID Unique Constraint

Processed Event Record

이미 적용된 상태에서 재실행 시 No-op 가능한가?

응답과 Transaction 경계가 적절한가?
```

Webhook 인증과 Signature 검증은 `17_보안_및_운영_기본정책.md`를 따릅니다.

---

# 39. 피해야 하는 구조

## Transaction이면 모든 동시성 문제가 해결된다고 가정

```txt
transaction(async () => {
  조회
  판단
  update
})
```

만 보고 안전하다고 결론내리지 않습니다.

다른 Transaction이 같은 상태를 읽고 변경할 수 있는지 확인합니다.

---

## Client Disabled만으로 중복 요청 보호

```txt
isPending
  → Button disabled
```

는 UX에는 유용하지만 Server Correctness 보호 수단이 아닙니다.

---

## UI 상태를 최종 Business State로 신뢰

```txt
화면에 PAID로 보였음
  → Server에서 상태 재검증 없이 취소
```

하지 않습니다.

---

## 외부 요청을 DB Transaction 안에서 장시간 대기

```txt
Transaction
  ↓
Provider HTTP Request
  ↓
Timeout까지 대기
```

구조는 Lock, Connection, 실패 경계를 복잡하게 만들 수 있습니다.

---

## Timeout을 확정 실패로 처리

```txt
Timeout
  → 즉시 동일 Mutation Retry
```

하기 전에 첫 작업 성공 가능성과 Idempotency를 확인합니다.

---

## Application Validation만으로 Unique Invariant 보호

```txt
exists 확인
  ↓
없음
  ↓
insert
```

만으로 동시 Insert를 막을 수 있다고 가정하지 않습니다.

---

## 모든 실패를 동일 Error로 변환

```txt
Invalid Input
Conflict
Provider Timeout
Database Down
```

을 모두 같은 실패로 만들면 복구 전략을 구분하기 어렵습니다.

---

# 40. 구현 전 Checklist

Mutation이나 Runtime 상태 변경을 구현하기 전에 필요한 항목을 확인합니다.

```txt
[ ] 반드시 유지되어야 하는 Business Invariant를 설명할 수 있는가?

[ ] 같은 Resource에 여러 요청이 동시에 접근할 수 있는가?

[ ] Read-Modify-Write 구조가 존재하는가?

[ ] 조회한 상태가 Update 시점까지 유지된다고 가정하고 있지 않은가?

[ ] Conditional Atomic Update로 경쟁 구간을 줄일 수 있는가?

[ ] 여러 DB 변경이 하나의 Atomic Unit이어야 하는가?

[ ] Transaction을 사용하더라도 다른 Transaction과의 Race가 남아 있지 않은가?

[ ] Database Constraint로 보호할 수 있는 Invariant가 있는가?

[ ] 같은 요청이 중복 전달될 수 있는가?

[ ] Server-side Idempotency가 필요한가?

[ ] State Transition을 Mutation 시점의 최신 Server State로 검증하는가?

[ ] Optimistic Concurrency 또는 Lock이 필요한가?

[ ] 외부 Side Effect가 존재하는가?

[ ] DB와 외부 Provider 중 일부만 성공할 수 있는가?

[ ] Partial Failure 이후 복구 / Retry / Compensation 전략이 있는가?

[ ] Timeout 이후 실제 작업 성공 여부를 알 수 있는가?

[ ] Retry가 중복 Side Effect를 만들지 않는가?

[ ] 요청 시작 순서와 완료 순서가 바뀌어도 안전한가?

[ ] UI / Cache / 이전 조회 결과가 Stale해도 Mutation이 안전한가?

[ ] 시간과 Timezone 경계가 명확한가?

[ ] 금액과 Numeric Precision 규칙이 명확한가?

[ ] null / undefined / empty 값의 의미가 구분되는가?

[ ] 입력 크기와 Resource Limit의 Boundary Value를 검토했는가?

[ ] Validation / Business / Conflict / Infrastructure / Timeout Error를 필요한 수준으로 구분하는가?

[ ] 중요한 실패를 운영에서 추적할 수 있는 Logging Context가 있는가?

[ ] Business Correctness에 중요한 동시성 동작은 적절한 Test Level에서 검증하는가?
```

모든 항목이 모든 기능에 적용되는 것은 아닙니다.

해당하지 않는 항목을 억지로 구현하지 않고 **현재 Use Case에 실제로 존재하는 위험을 빠뜨리지 않는 것**이 목적입니다.

---

# 41. 구현 완료 후 Checklist

구현이 끝난 뒤에는 정상 경로 외에 다음 실패 시나리오를 다시 확인합니다.

```txt
[ ] 같은 Mutation이 거의 동시에 두 번 실행되면 어떻게 되는가?

[ ] 첫 요청 성공 후 응답이 유실되어 같은 요청이 다시 들어오면 어떻게 되는가?

[ ] Transaction 중간 Operation이 실패하면 이전 변경이 남지 않는가?

[ ] Database Constraint가 발생했을 때 의미 있는 Error로 처리되는가?

[ ] 예상 상태가 이미 바뀐 Resource를 수정하려 하면 안전하게 실패하는가?

[ ] 외부 Provider가 느리거나 응답하지 않으면 Resource 상태가 모호하게 남지 않는가?

[ ] 외부 Provider는 성공했지만 Local Database 반영이 실패하면 복구 가능한가?

[ ] Local Database는 성공했지만 후속 Side Effect가 실패하면 복구 가능한가?

[ ] Retry가 실제로 필요한 Error에만 적용되는가?

[ ] 오래된 UI에서 Mutation을 보내도 Server가 최신 Business Rule을 다시 확인하는가?

[ ] 중요한 Conflict / Timeout / Provider Failure를 운영에서 식별할 수 있는가?
```

이 문서는 위 문서들 사이에 흩어진 안전성 관련 책임을 복제하는 것이 아니라 다음 질문을 위한 Source of Truth입니다.

```txt
이 구현에서 어떤 Runtime 위험을 검토해야 하는가?

어떤 Invariant가 깨질 수 있는가?

어떤 종류의 보호 수단이 필요한가?
```

---

# 43. 핵심 원칙

```txt
정상 경로의 Correctness만으로 구현 안전성을 판단하지 않는다.

동시 실행과 실패 상황에서도 Business Invariant가 유지되어야 한다.

Read-Modify-Write는 Race Condition 가능성을 명시적으로 검토한다.

Transaction은 Atomicity를 제공하지만 모든 Race Condition을 해결하지 않는다.

Transaction Scope는 Use Case가 결정한다.

Database가 보호할 수 있는 필수 Invariant는 가능한 경우 Constraint에서도 보호한다.

Client 중복 제출 방지는 UX이며 Server-side Idempotency를 대체하지 않는다.

Mutation은 UI에 표시된 상태가 아니라 최신 Server / Domain State를 기준으로 최종 판단한다.

상태 전이에서는 Business Rule과 Concurrency Control을 함께 검토한다.

Optimistic / Pessimistic Concurrency는 Use Case의 경합과 비용에 따라 선택한다.

Database Transaction과 외부 Side Effect는 하나의 Atomic Transaction이 아니다.

Partial Failure를 숨기지 않고 복구 가능한 상태와 흐름을 설계한다.

Timeout은 실제 작업 실패를 의미하지 않을 수 있다.

Retry는 Idempotency와 중복 Side Effect를 함께 검토한다.

요청 순서와 완료 순서는 다를 수 있다.

UI, Cache, 이전 조회 결과는 Stale할 수 있다.

시간, 금액, Null, Boundary Value도 Business Correctness의 일부다.

예상 가능한 Business Failure, Conflict, Infrastructure Failure, Timeout을 필요한 수준으로 구분한다.

중요한 상태 변경은 운영에서 원인을 추적할 수 있어야 한다.

안전성 구현은 위험에 비례하여 적용하고 불필요한 복잡성을 만들지 않는다.
```
