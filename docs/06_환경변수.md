# 환경변수

이 문서는 `boilerplate-turborepo`에서 환경변수를 정의하고 검증하며 각 Runtime에 노출하는 기준을 설명합니다.

환경변수의 실제 값 목록을 모두 나열하기보다 다음 내용을 중심으로 다룹니다.

```txt
환경변수를 어디에서 정의하는가?

Server와 Client 환경변수는 어떻게 구분하는가?

@repo/env와 apps/*/src/config의 책임은 어떻게 다른가?

NEXT_PUBLIC_*은 언제 사용하는가?

개발, 테스트, E2E 환경은 어떻게 분리하는가?

Turborepo는 환경변수를 어떻게 추적하는가?

Secret은 어떻게 보호하는가?
```

Package 자체의 Public API와 역할은 `04_패키지_구조.md`, 보안 전반의 원칙은 `17_보안_및_운영_기본정책.md`에서 다룹니다.

---

## 1. 기본 원칙

환경변수는 단순한 문자열 저장소가 아니라 Runtime Configuration의 외부 입력입니다.

기본 원칙은 다음과 같습니다.

```txt
환경변수는 Zod Schema를 통해 검증한다.

Server와 Client의 환경변수 경계를 명확하게 나눈다.

Browser에 공개할 필요가 없는 값은 Server에 둔다.

특정 앱의 설정을 공통 @repo/env에 넣지 않는다.

여러 앱과 Package가 공유하는 계약만 @repo/env에서 관리한다.

환경별 값은 코드에 하드코딩하지 않는다.

Secret은 코드, Client Bundle, 로그, 문서에 노출하지 않는다.

환경변수 변경 시 Turbo, Test, CI, 배포 설정도 함께 검토한다.
```

---

# 2. 환경변수 책임 구조

환경변수는 크게 세 영역에서 관리합니다.

```txt
@repo/env
  Repository 공통 환경변수 계약

apps/*/src/config
  특정 앱에만 필요한 환경변수 계약

.env* / CI / 배포 환경
  실제 환경별 값
```

개념적인 흐름:

```txt
.env* / CI / Deployment Environment
                ↓
           process.env
                ↓
      Zod Schema Validation
                ↓
    Typed Environment Object
                ↓
           Runtime Code
```

애플리케이션 코드에서는 가능한 한 검증되지 않은 `process.env`를 직접 사용하지 않고 검증된 Environment API를 사용합니다.

---

# 3. `@repo/env`

공통 환경변수 Package는 다음 세 경계를 제공합니다.

```txt
@repo/env/shared
@repo/env/server
@repo/env/client
```

구조:

```txt
packages/env/
└─ src/
   ├─ shared.ts
   ├─ server.ts
   └─ client.ts
```

---

## 3.1 Shared Env

`shared.ts`는 Server와 Client에서 공통으로 사용할 수 있는 환경변수를 정의합니다.

현재 대표적인 값:

```txt
NODE_ENV
```

허용 값:

```txt
development
test
production
```

Shared Env에는 다음 조건을 만족하는 값만 둡니다.

```txt
Server와 Client 모두에서 의미가 있다.

Secret이 아니다.

특정 앱에 종속되지 않는다.
```

---

## 3.2 Server Env

`server.ts`는 여러 앱과 Server Package에서 공통으로 사용하는 환경변수를 관리합니다.

대표적인 범위:

```txt
Database
Authentication
OAuth
Mailer
Test Infrastructure
```

예:

```txt
DATABASE_URL
DIRECT_URL

AUTH_SESSION_COOKIE_NAME
AUTH_SESSION_MAX_AGE_SECONDS

GOOGLE_CLIENT_ID
GOOGLE_CLIENT_SECRET
NAVER_CLIENT_ID
NAVER_CLIENT_SECRET
KAKAO_CLIENT_ID
KAKAO_CLIENT_SECRET

MAIL_PROVIDER
MAIL_FROM
RESEND_API_KEY

E2E_AUTH_SECRET
```

Server Env는 `server-only` 경계를 사용합니다.

사용 가능한 대표 영역:

```txt
Server Component
Server Action
Route Handler
Domain의 Server 진입점
Database
Auth
Mailer
Storage
Node.js Runtime Code
```

사용하면 안 되는 영역:

```txt
"use client" Component
Browser Hook
Client-side Utility
Client Bundle에 포함될 수 있는 코드
```

---

## 3.3 Client Env

`client.ts`는 Browser에서도 안전하게 사용할 수 있는 공통 환경변수를 관리합니다.

현재 보일러플레이트에서는 공통 Client Env에 실질적인 공개 설정을 두지 않으며 `NODE_ENV`만 Shared Env를 통해 제공합니다.

예:

```ts
import { clientEnv } from "@repo/env/client";

const nodeEnv = clientEnv.NODE_ENV;
```

Client Env가 존재한다고 해서 반드시 `NEXT_PUBLIC_*` 환경변수를 만들어야 하는 것은 아닙니다.

```txt
Client Env
≠
NEXT_PUBLIC_*을 반드시 사용해야 하는 공간
```

Browser에서 실제로 필요한 값이 생겼을 때만 명시적으로 추가합니다.

---

# 4. Server / Client Boundary

환경변수를 추가할 때 가장 먼저 판단해야 하는 것은 실행 위치입니다.

```txt
Server에서만 사용하는가?
→ Server Env

Browser가 직접 읽어야 하는가?
→ Client Env 검토

Server와 Client 모두 필요한가?
→ Shared Env 검토
```

판단이 애매하다면 기본적으로 Server에 둡니다.

```txt
공개 필요성을 증명할 수 있음
→ Client

그 외
→ Server
```

Client로 값을 내보내는 것은 단순한 구현 선택이 아니라 해당 값을 사용자 Browser에 공개하는 결정입니다.

---

# 5. `NEXT_PUBLIC_*`

Next.js에서 `NEXT_PUBLIC_*` 환경변수는 Browser Bundle에 포함될 수 있습니다.

따라서 `NEXT_PUBLIC_*`은 단순한 Naming Convention이 아니라 공개 범위를 나타내는 계약으로 취급합니다.

---

## 5.1 사용해야 하는 경우

다음 조건을 모두 만족할 때 사용을 검토합니다.

```txt
Browser JavaScript가 직접 값을 알아야 한다.

Secret이 아니다.

사용자에게 공개되어도 문제가 없다.

Server를 통해 값을 전달하는 것보다 Client에서 직접 읽는 것이 명확하다.
```

예:

```txt
공개 Analytics Identifier
공개 Map Provider Key
Browser SDK에서 요구하는 Public Identifier
```

---

## 5.2 사용하면 안 되는 경우

다음 값은 `NEXT_PUBLIC_*`로 만들지 않습니다.

```txt
Database URL

API Secret

OAuth Client Secret

Session Secret

Private Token

Mailer Secret

Storage Secret

Signing Key

Admin Credential
```

앱의 Base URL 역시 Server에서만 필요하다면 Public Env로 만들지 않습니다.

현재 보일러플레이트는 별도의:

```txt
NEXT_PUBLIC_APP_URL
```

을 사용하지 않습니다.

---

# 6. 공통 Env와 앱 Env의 경계

`@repo/env`는 Repository 전체에서 공유되는 환경변수만 소유합니다.

특정 앱에서만 의미가 있는 설정은 해당 앱의 `config`에 둡니다.

---

## 6.1 Web 앱

```txt
apps/web/src/config/server-env.ts
```

에서 Web 앱 전용 Server Env를 관리합니다.

현재 대표적인 값:

```txt
WEB_APP_URL
```

앱은 공통 Server Env와 자신의 App Env를 결합하여 하나의 `serverEnv`를 제공합니다.

개념적인 구조:

```txt
@repo/env/server
      ↓
commonServerEnv

        +

WEB_APP_URL Schema
      ↓
apps/web/src/config/server-env.ts
      ↓
web serverEnv
```

---

## 6.2 Admin 앱

```txt
apps/admin/src/config/server-env.ts
```

에서 Admin 앱 전용 Server Env를 관리합니다.

현재 대표적인 값:

```txt
ADMIN_APP_URL
```

구조:

```txt
@repo/env/server
      ↓
commonServerEnv

        +

ADMIN_APP_URL Schema
      ↓
apps/admin/src/config/server-env.ts
      ↓
admin serverEnv
```

---

## 6.3 App Config를 두는 이유

다음과 같은 구조를 피하기 위함입니다.

```txt
@repo/env
  WEB_APP_URL
  ADMIN_APP_URL
  향후 THIRD_APP_URL
  향후 FOURTH_APP_URL
  ...
```

이렇게 되면 공통 Package가 모든 앱의 존재를 알아야 합니다.

대신:

```txt
@repo/env
  공통 계약

apps/web
  Web 계약

apps/admin
  Admin 계약
```

으로 나눕니다.

---

# 7. 앱 내부 Environment 진입점

앱 코드에서는 가능한 한 다음 진입점을 사용합니다.

```txt
@/config/server-env
@/config/client-env
```

예:

```ts
import { serverEnv } from "@/config/server-env";

const appUrl = serverEnv.WEB_APP_URL;
```

Admin:

```ts
import { serverEnv } from "@/config/server-env";

const appUrl = serverEnv.ADMIN_APP_URL;
```

공통 Package가 아닌 앱 코드가 `@repo/env/server`를 직접 여기저기 import하기보다 앱 Config를 통해 접근하면 다음 장점이 있습니다.

```txt
앱별 추가 Env가 하나의 API로 합쳐진다.

환경변수 접근 지점이 일관된다.

향후 앱별 Validation 변경이 쉬워진다.

공통 Env와 앱 Env의 구현 세부사항이 소비 코드에 노출되지 않는다.
```

---

# 8. App URL

각 애플리케이션의 Base URL은 Server 환경변수로 관리합니다.

```txt
Web
  WEB_APP_URL

Admin
  ADMIN_APP_URL
```

로컬 예:

```env
WEB_APP_URL="http://localhost:3000"
ADMIN_APP_URL="http://localhost:3001"
```

앱 URL은 다음과 같은 Server 영역에서 사용될 수 있습니다.

```txt
metadataBase
Redirect URL 생성
OAuth Callback URL
Server-side Absolute URL 생성
```

Browser가 직접 값을 읽을 필요가 없다면 `NEXT_PUBLIC_*`으로 다시 노출하지 않습니다.

---

## 8.1 Vercel Fallback

앱의 `server-env`에서는 명시적인 App URL이 없을 때 배포 Platform의 환경변수를 fallback으로 사용할 수 있습니다.

현재 Vercel 환경에서는:

```txt
VERCEL_PROJECT_PRODUCTION_URL
```

을 fallback으로 사용할 수 있습니다.

우선순위:

```txt
명시적인 APP_URL
      ↓ 없으면
VERCEL_PROJECT_PRODUCTION_URL
```

이 fallback은 앱별 Config의 책임입니다.

```txt
@repo/env
  Vercel 앱 URL 정책을 알 필요 없음

apps/*/config/server-env
  자신의 배포 URL 해석
```

# 9. 환경변수 파일

환경에 따라 서로 다른 파일을 사용합니다.

대표적인 구조:

```txt
.env.local
.env.test
.env.test.local
.env.e2e.local
```

각 파일의 책임을 명확하게 구분합니다.

---

## 9.1 `.env.local`

로컬 개발 환경에서 사용하는 설정입니다.

예:

```txt
로컬 Database
로컬 App URL
개발용 OAuth Credential
개발용 Mailer 설정
```

실제 Secret이 포함될 수 있으므로 Git에 Commit하지 않습니다.

---

## 9.2 `.env.test`

Vitest 기반 테스트에서 사용하는 공통 Test Environment입니다.

목적:

```txt
개발 환경과 테스트 환경을 분리

테스트가 기대하는 기본값 제공

테스트 실행마다 동일한 환경 구성
```

가능하면 실제 Production Credential이 아니라 테스트용 값 또는 안전한 Dummy 값을 사용합니다.

---

## 9.3 `.env.test.local`

개발자 개인의 Test Environment Override입니다.

로드 순서:

```txt
.env.test
   ↓
.env.test.local
```

동일한 변수가 있다면 로컬 Override 값이 우선할 수 있습니다.

개인 DB 주소나 로컬 환경 차이가 있을 때 사용합니다.

---

## 9.4 `.env.e2e.local`

E2E 전용 환경을 구성합니다.

대표적인 설정:

```txt
WEB_E2E_PORT
WEB_E2E_BASE_URL

ADMIN_E2E_PORT
ADMIN_E2E_BASE_URL

E2E_AUTH_SECRET

E2E Database URL
```

일반 개발 환경과 E2E 환경을 분리하여 테스트가 개발 중인 데이터를 변경하지 않도록 합니다.

---

# 10. 테스트 Environment Loading

공통 Vitest 설정은 Test Environment Loader를 통해 Repository Root의 테스트 파일을 읽습니다.

기본 흐름:

```txt
.env.test
      ↓
.env.test.local
      ↓
process.env
      ↓
@repo/env Validation
```

Test Runtime에서는:

```txt
NODE_ENV=test
```

를 사용합니다.

Environment Loader는 환경변수를 읽는 역할만 담당합니다.

다음과 같은 앱별 정책을 포함하지 않습니다.

```txt
앱 이름에 따라 URL 생성

Public Env 합성

앱 Config 대신 환경변수 변환
```

앱별 환경변수 해석은 앱의 `config`에서 처리합니다.

---

# 11. E2E Environment

E2E는 Unit / Integration Test와 별도 Runtime으로 취급합니다.

대표적인 흐름:

```txt
.env.local
      ↓
.env.e2e.local
      ↓
Playwright Config
      ↓
Next.js App
      ↓
E2E Test
```

CI에서는 파일 대신 Workflow의 `env`를 사용하여 동일한 계약을 제공합니다.

E2E에서 사용하는 App URL과 Port는 일반 개발 환경과 분리할 수 있습니다.

예:

```txt
Local Development

web
  3000

admin
  3001


E2E

web
  3100

admin
  3101
```

```txt
      ↓
  개발 DB


Integration Test
  DATABASE_URL
      ↓
  테스트 DB


E2E

      ↓

```

# 13. Turborepo와 환경변수

Repository는 `turbo.json`에서:

```json
{
  "envMode": "strict"
}
```

를 사용합니다.

Strict Mode에서는 Task에서 사용할 환경변수를 Turborepo가 명시적으로 인식할 수 있도록 구성합니다.

환경변수는 크게 다음 관점으로 나눕니다.

```txt
globalEnv
env
passThroughEnv
inputs
```

---

## 13.1 `globalEnv`

모든 Task에 영향을 줄 수 있는 공통 환경변수입니다.

현재 대표적인 값:

```txt
CI
NODE_ENV
```

`globalEnv`에 포함된 값은 여러 Task의 Cache Hash에 영향을 줄 수 있으므로 모든 환경변수를 여기에 넣지 않습니다.

---

## 13.2 Task `env`

특정 Task의 결과에 영향을 주는 환경변수를 선언합니다.

예:

```txt
build
  WEB_APP_URL
  ADMIN_APP_URL
  DATABASE_URL
  AUTH_SESSION_*
  MAIL_*

test
  DATABASE_URL
  AUTH_SESSION_*
  MAIL_*
```

환경변수가 바뀌면 Task 결과도 달라질 수 있다면 `env` 대상인지 검토합니다.

---

## 13.3 `passThroughEnv`

Runtime에 값은 필요하지만 해당 Secret 값을 Cache Key에 포함시키고 싶지 않은 경우 사용합니다.

대표적인 예:

```txt
OAuth Client Secret
RESEND_API_KEY
```

개념:

```txt
env
  Runtime 전달
  +
  Cache Hash 영향

passThroughEnv
  Runtime 전달
  +
  Cache Hash에는 직접 포함하지 않음
```

Secret이라는 이유만으로 무조건 `passThroughEnv`를 사용하는 것은 아닙니다.

해당 값이 Task Output에 영향을 주는 방식도 함께 고려합니다.

---

## 13.4 `inputs`

환경 파일 변경 자체도 Task 결과에 영향을 줄 수 있습니다.

예:

```txt
build

.env*
apps/*/.env*
```

Test:

```txt
.env.test
.env.test.local
```

E2E:

```txt
.env.e2e.local
```

이를 통해 환경 파일 변경이 필요한 Task Cache와 연결됩니다.

---

# 14. `NEXT_PUBLIC_*`과 Turborepo

현재 보일러플레이트에는 공통 `NEXT_PUBLIC_*` 환경변수가 없습니다.

따라서 `NEXT_PUBLIC_APP_URL` 같은 별도의 Public App URL을 `turbo.json`에서 추적하지 않습니다.

향후 실제 `NEXT_PUBLIC_*` 값을 추가한다면 다음을 함께 확인합니다.

```txt
실제로 Browser에서 필요한가?

Secret이 아닌가?

어느 앱에서 사용하는가?

Build 결과에 영향을 주는가?

Turbo Task Env에 반영할 필요가 있는가?
```

Public Env 추가는 단순히 `.env`에 한 줄을 추가하는 작업으로 끝내지 않습니다.

---

# 15. CI 환경변수

CI에서는 실제 Production Secret 대신 Job에 필요한 테스트용 값을 사용합니다.

대표적인 환경:

```txt
Quality
Build
Integration
E2E
```

각 Job에는 자신이 실행하는 코드가 요구하는 환경변수만 제공합니다.

예:

```txt
Quality / Build

WEB_APP_URL
ADMIN_APP_URL
DATABASE_URL
DIRECT_URL
AUTH_SESSION_*
OAuth Dummy Credential
```

E2E에는 추가로:

```txt
WEB_E2E_*
ADMIN_E2E_*
E2E_AUTH_SECRET
```

등을 제공합니다.

CI Workflow에서 환경변수를 변경하면 `@repo/env`, `turbo.json`, Test Config와의 일치 여부도 확인합니다.

---

# 16. Production Secret

운영 환경의 Secret은 Deployment Platform에서 관리합니다.

예:

```txt
Database Credential

OAuth Client Secret

Mailer API Key

Storage Credential

Signing Key
```

운영 Secret을 다음 위치에 저장하지 않습니다.

```txt
Source Code
README
docs/*
Git Commit
Public Issue
Client Env
NEXT_PUBLIC_*
```

---

# 17. Secret Logging

Secret은 로그에 출력하지 않습니다.

금지:

```ts
console.info(serverEnv.RESEND_API_KEY);
console.log(process.env.DATABASE_URL);
```

오류 상황에서도 Secret 전체를 Error Message에 넣지 않습니다.

좋은 예:

```txt
Mailer provider configuration is invalid.

Database connection configuration is missing.
```

나쁜 예:

```txt
Invalid RESEND_API_KEY: re_...

Cannot connect to postgresql://user:password@...
```

필요한 경우 설정 여부만 기록합니다.

```txt
MAIL_PROVIDER=resend

Mailer credential configured=true
```

실제 값은 출력하지 않습니다.

---

# 18. Environment Validation

환경변수는 Zod를 통해 Runtime에서 검증합니다.

목적:

```txt
필수 값 누락 조기 발견

잘못된 URL 차단

숫자 문자열 Parsing

Enum 제한

조건부 필수 값 검증

Typed API 제공
```

예:

```txt
AUTH_SESSION_MAX_AGE_SECONDS
  string
    ↓
  positive integer

MAIL_PROVIDER
  console | resend

MAIL_PROVIDER=resend
  ↓
MAIL_FROM required
RESEND_API_KEY required
```

환경변수가 설정되어 있다는 사실만 검사하지 않고 실제 Runtime 요구사항을 Schema로 표현합니다.

---

# 19. 조건부 환경변수

Provider 기반 설정은 조건부 Validation을 사용할 수 있습니다.

예:

```txt
MAIL_PROVIDER=console
  ↓
RESEND_API_KEY 필요 없음


MAIL_PROVIDER=resend
  ↓
MAIL_FROM 필요
RESEND_API_KEY 필요
```

이 패턴은 향후 Storage, Analytics 등의 Provider 설정에도 적용할 수 있습니다.

단, 해당 기능이 실제로 추가되기 전에 미리 환경변수를 만들지는 않습니다.

# 20. 환경변수 추가 절차

새로운 환경변수를 추가할 때는 다음 순서로 판단합니다.

### 20.1 사용 범위 확인

```txt
Repository 공통인가?

특정 앱 전용인가?

Server인가?

Client인가?

Test 전용인가?
```

---

### 20.2 Schema 위치 결정

```txt
공통 Shared
→ packages/env/src/shared.ts

공통 Server
→ packages/env/src/server.ts

공통 Client
→ packages/env/src/client.ts

Web 전용 Server
→ apps/web/src/config/server-env.ts

Admin 전용 Server
→ apps/admin/src/config/server-env.ts

앱 전용 Client
→ apps/[app]/src/config/client-env.ts
```

---

### 20.3 Runtime 값 추가

필요한 환경에 값을 추가합니다.

```txt
.env.local
.env.test
.env.test.local
.env.e2e.local
CI
Deployment Platform
```

모든 환경에 반드시 같은 값이 필요한 것은 아닙니다.

실제로 해당 Runtime에서 필요한 곳에만 설정합니다.

---

### 20.4 Turborepo 검토

다음을 확인합니다.

```txt
globalEnv가 필요한가?

Task env에 들어가야 하는가?

passThroughEnv가 적절한가?

환경 파일이 inputs에 포함되어 있는가?
```

---

### 20.5 테스트 및 CI 검토

해당 값을 요구하는 코드가 Test 또는 CI에서 로드되는지 확인합니다.

필수 환경변수를 Schema에 추가했는데 CI에 값을 추가하지 않으면 Build나 Test가 즉시 실패할 수 있습니다.

```txt

Test Setup

turbo.json

CI

Deployment Environment

README / docs
```

Repository 내 잔여 참조는 다음과 같이 확인할 수 있습니다.

```bash

```


결과가 없다면 Source와 Git 관리 파일에서 참조가 모두 제거되었는지 확인할 수 있습니다.

# 22. `process.env` 직접 사용 기준

일반 애플리케이션 코드에서는 검증된 Env 객체를 사용합니다.

권장:

```ts
import { serverEnv } from "@/config/server-env";

const appUrl = serverEnv.WEB_APP_URL;
```

지양:

```ts
const appUrl = process.env.WEB_APP_URL;
```

단, Environment Schema 자체나 Tool Config처럼 **환경변수를 읽어서 검증 객체를 만드는 경계**에서는 `process.env`를 직접 사용할 수 있습니다.

대표적인 위치:

```txt
@repo/env

apps/*/src/config/*-env.ts

next.config.*

Vitest Environment Loader

Playwright Config

CI / Tooling
```

---

# 23. 환경변수와 `next.config.js`

`next.config.js`는 환경변수 검증 Package를 대신하지 않습니다.

다음과 같은 책임을 넣지 않는 것을 기본으로 합니다.

```txt
앱 전용 Env Schema 정의

Server Env를 Public Env로 변환

Secret을 Client에 주입

여러 앱의 환경변수 의미 조합
```

환경변수의 의미와 Validation은:

```txt
@repo/env

또는

apps/*/src/config
```

에서 담당합니다.

`next.config.js`에서는 Next.js 설정 자체에 필요한 값만 직접 사용합니다.

---

# 24. 환경변수와 Metadata

Next.js Metadata는 Server 영역에서 생성할 수 있으므로 Base URL을 위해 Public Env를 만들 필요가 없습니다.

예:

```ts
import { serverEnv } from "@/config/server-env";

export const metadata = {
  metadataBase: new URL(serverEnv.WEB_APP_URL),
};
```

Admin 역시:

```ts
metadataBase: new URL(serverEnv.ADMIN_APP_URL);
```

형태를 사용합니다.

```txt
Server에서 해결 가능한 설정
→ Server Env 유지
```

라는 Server First 원칙을 따릅니다.

# 28. 핵심 원칙

```txt
환경변수는 외부 입력으로 보고 검증한다.

공통 환경변수만 @repo/env에 둔다.

앱 전용 환경변수는 해당 앱 config에서 관리한다.

Server와 Client Env를 명확하게 분리한다.

Browser가 반드시 알아야 하는 값만 NEXT_PUBLIC_*으로 공개한다.

Secret은 항상 Server에 둔다.

앱 URL을 Server에서만 사용한다면 Public Env로 만들지 않는다.

검증된 Env 객체를 Runtime 코드에서 사용한다.

환경별 파일의 책임을 분리한다.

Test와 E2E 환경을 개발 환경과 분리한다.

Turborepo Strict Env 정책과 환경변수 변경을 함께 관리한다.

Secret을 코드, 로그, Client Bundle, 문서에 노출하지 않는다.

환경변수를 추가하거나 제거하면 CI와 배포 설정까지 함께 검토한다.
```
