# 문서 가이드

이 문서는 `boilerplate-turborepo`의 `docs/` 문서 체계와 각 문서의 책임을 설명합니다.

이 보일러플레이트는 단순한 프로젝트 초기 설정 모음이 아니라 다음과 같은 개발 기반을 함께 제공합니다.

```txt
Turborepo + pnpm Workspace
Next.js App Router
완화된 FSD 기반 앱 구조
Domain / Repository 기반 Backend Layering
공통 Design System
Auth / Storage / Mailer 등의 Infrastructure Package
Vitest / Playwright / Storybook
코드 생성기
프로젝트 초기화 및 Boundary 검사 Script
Claude Code 개발 환경
```

따라서 하나의 문서에 모든 규칙을 모으지 않고, 각 관심사별로 기준 문서를 분리하여 관리합니다.

---

## 1. 문서 작성 목적

`docs/`는 다음 질문에 답할 수 있어야 합니다.

```txt
이 프로젝트는 어떤 구조와 원칙으로 설계되어 있는가?

새 코드는 어디에 작성해야 하는가?

앱, Domain, Database, Package는 각각 어떤 책임을 가지는가?

각 계층은 어디까지 의존할 수 있는가?

새 앱이나 Package를 추가하려면 어떻게 해야 하는가?

테스트는 어떤 수준으로 나누고 어디에 작성해야 하는가?

보일러플레이트를 새 프로젝트에 적용하려면 무엇부터 해야 하는가?

프로젝트에서 제공하는 Generator와 Script는 어떻게 사용하는가?
```

문서는 실제 코드 구조와 규칙을 설명하는 기준으로 사용합니다.

코드와 문서가 다를 경우 문서를 그대로 유지하는 것이 아니라 현재 설계 의도를 확인한 뒤 둘 중 하나를 수정하여 다시 일치시킵니다.

## 4. AI 작업 시 문서 선택

AI와 작업할 때 `docs/`의 모든 문서를 항상 Context로 제공할 필요는 없습니다.

이 문서들은 전체를 한 번에 읽도록 만든 단일 매뉴얼이 아니라, 작업 종류에 따라 필요한 기준을 선택해서 사용하는 Reference Library입니다.

AI에게 제공할 문서는 다음 세 범위로 구분합니다.

```txt
Boilerplate Core
  프로젝트의 공통 Architecture와 구현 규칙

Project Core
  실제 서비스의 요구사항과 Business Context

Task Context
  현재 작업과 직접 관련된 전문 문서와 코드
```

AI가 올바른 구현을 만들기 위해서는 Boilerplate 규칙뿐 아니라 실제 프로젝트의 요구사항과 현재 구현 상태를 함께 이해해야 합니다.

---

### 4.1 기본 Boilerplate Context

일반적인 기능 구현에서 우선순위가 높은 문서는 다음과 같습니다.

```txt
01_아키텍처.md
08_도메인_레이어.md
09_Server_Actions.md
10_앱_구조.md
18_컨벤션.md
```

이 문서들은 다음과 같은 기본 판단에 사용합니다.

```txt
전체 Architecture와 책임 방향

Business Logic의 위치

Server Action의 책임

Entity / Feature / View의 위치

Naming / Import / Export 규칙
```

작업 성격에 따라 다음 문서를 추가합니다.

```txt
Package Dependency
  → 05_의존성_경계.md

Database / Repository
  → 07_데이터베이스.md

Design System
  → 11_디자인_시스템.md

Test
  → 12_테스트_전략.md

Storybook
  → 13_스토리북.md

Generator
  → 14_코드_생성기.md

Environment
  → 06_환경변수.md

Security / Operations
  → 17_보안_및_운영_기본정책.md

App / Domain / Package 확장
  → 19_확장_가이드.md
```

현재 작업과 직접 관계없는 문서를 기계적으로 모두 Context에 포함하지 않습니다.

---

### 4.2 실제 프로젝트 문서를 우선한다

이 보일러플레이트를 기반으로 실제 서비스를 개발하기 시작하면 Boilerplate 문서 외에 프로젝트 고유 문서가 추가될 수 있습니다.

예:

```txt
프로젝트 개요 / 기획서

요구사항

Business Policy / 운영 규칙

Data Model / ERD

화면 구조 / IA / User Flow

외부 연동

API 명세

구현 현황 / 우선순위
```

프로젝트에 따라 필요한 문서만 작성합니다.

AI 작업에서는 이러한 문서의 중요도가 Boilerplate 사용법보다 높을 수 있습니다.

특히 다음 정보는 구현 판단에 직접 영향을 줍니다.

```txt
무엇을 구현해야 하는가?
  → 요구사항

어떤 조건에서 어떤 동작을 해야 하는가?
  → Business Policy / 운영 규칙

어떤 데이터와 관계를 사용하는가?
  → Data Model / ERD

사용자가 어떤 흐름으로 기능을 사용하는가?
  → 화면 구조 / User Flow

어떤 외부 시스템과 연결되는가?
  → 외부 연동

현재 무엇이 이미 구현되어 있는가?
  → 구현 현황 / 우선순위
```

AI가 프로젝트 Architecture를 정확히 이해하더라도 Business Policy가 없다면 서비스 요구사항을 임의로 추측할 수 있습니다.

따라서 실제 기능 구현에서는 현재 작업과 관련된 프로젝트 고유 문서를 우선적으로 함께 제공합니다.

### 4.3 작업별 Context 구성

AI Context는 현재 작업에 필요한 문서 중심으로 구성합니다.

예를 들어 일반적인 App Mutation 기능을 구현한다면:

```txt
Project
  요구사항
  관련 Business Policy
  관련 Data Model
  현재 구현 현황

Boilerplate
  01_아키텍처.md
  08_도메인_레이어.md
  09_Server_Actions.md
  10_앱_구조.md
  12_테스트_전략.md
  18_컨벤션.md
```

Repository 작업이라면:

```txt
Project
  관련 요구사항
  관련 Business Policy
  Data Model / ERD

Boilerplate
  05_의존성_경계.md
  07_데이터베이스.md
  08_도메인_레이어.md
  12_테스트_전략.md
  18_컨벤션.md
```

UI 작업이라면:

```txt
Project
  요구사항
  화면 구조 / User Flow
  관련 Policy
```

### 4.4 AI Context의 우선순위

Context 수에 제한이 있다면 문서의 우선순위를 다음과 같이 판단합니다.

```txt
1. 현재 작업 요구사항

2. 관련 Business Policy

3. 현재 구현 상태

4. 관련 Data Model / 화면 구조 / 외부 연동

5. 작업에 직접 필요한 Boilerplate 전문 문서

6. 공통 Architecture와 Convention

7. 현재 작업과 직접 관련 없는 Reference
```

예를 들어 환불 기능을 구현하는 상황에서는:

```txt
환불 요구사항
환불 가능 조건
Order / Payment Data Model
현재 주문 및 결제 구현 상태
08_도메인_레이어.md
09_Server_Actions.md
10_앱_구조.md
12_테스트_전략.md
```

가:

```txt
14_코드_생성기.md
15_프로젝트_초기화.md
20_Claude_Code.md
```

보다 높은 우선순위를 가집니다.

### 4.5 Claude Code에서는 필요한 문서를 탐색한다

Claude Code처럼 Repository를 직접 탐색할 수 있는 환경에서는 모든 문서를 사전에 Context로 제공할 필요가 없습니다.

기본 흐름은 다음과 같습니다.

```txt
CLAUDE.md
  ↓
00_문서_가이드.md
  ↓
현재 작업 분류
  ↓
관련 docs/*
  ↓
관련 프로젝트 문서
  ↓
현재 코드
```

`CLAUDE.md`는 프로젝트 Architecture를 다시 정의하지 않고 Claude Code가 어떤 기준 문서를 확인해야 하는지 안내하는 진입점으로 사용합니다.

상세한 Claude Code 사용 방법은 `20_Claude_Code.md`에서 설명합니다.

### 4.6 제한된 AI Context를 사용하는 경우

ChatGPT Project와 같이 한 번에 제공할 수 있는 Project Source 수가 제한되어 있다면 Boilerplate 문서 전체를 등록하는 것보다 실제 프로젝트 문서를 위한 Context 공간을 남겨두는 것을 우선합니다.

권장 구성은 다음과 같습니다.

```txt
Boilerplate Core
  약 5~7개

Project Core
  약 7~10개

Current Task
  필요한 전문 문서와 자료
```

Boilerplate Core의 대표적인 구성:

```txt
01_아키텍처.md
05_의존성_경계.md
08_도메인_레이어.md
09_Server_Actions.md
10_앱_구조.md
12_테스트_전략.md
18_컨벤션.md
```

이 목록은 고정된 필수 목록이 아닙니다.

현재 작업과 프로젝트 특성에 따라 일부 문서를 제외하거나 다른 전문 문서로 교체합니다.

### 4.7 AI에게 문서를 제공하는 목적

AI에게 문서를 많이 제공하는 것 자체가 목적은 아닙니다.

목적은 AI가 다음 질문에 추측 없이 답할 수 있도록 필요한 Context를 제공하는 것입니다.

```txt
무엇을 만들어야 하는가?

어떤 Business Rule을 따라야 하는가?

현재 무엇이 구현되어 있는가?

어느 계층에 코드를 작성해야 하는가?

어떤 Dependency Boundary를 지켜야 하는가?

어떤 Convention을 따라야 하는가?

어떤 수준의 Test가 필요한가?
```

따라서 AI Context는 문서 개수가 아니라 **현재 작업에 필요한 판단 근거가 충분한가**를 기준으로 구성합니다.

## 13. 코드와 문서의 관계

문서는 실제 코드와 분리된 별도의 설계물이 아닙니다.

다음 원칙을 적용합니다.

```txt
현재 구현된 구조를 기준으로 작성한다.

아직 구현되지 않은 기능을 현재 제공되는 기능처럼 설명하지 않는다.

코드 구조가 변경되면 관련 문서를 함께 수정한다.

하나의 규칙은 하나의 기준 문서에서 정의한다.

다른 문서에서는 같은 규칙을 다시 정의하지 않고 기준 문서를 참조한다.
```

예:

```txt
Entity와 Feature의 경계
→ 10_앱_구조.md

Domain Service의 책임
→ 08_도메인_레이어.md

Repository의 책임
→ 07_데이터베이스.md

Story 작성 대상
→ 13_스토리북.md
```

## 14. README와 `docs/`의 역할

루트 `README.md`는 프로젝트의 첫 번째 진입점입니다.

README에는 다음 정도만 유지합니다.

```txt
프로젝트 소개
핵심 기술 스택
빠른 시작
주요 명령어
문서 링크
```

상세한 설계와 개발 규칙은 `docs/`에서 관리합니다.

각 Package의 `README.md`는 해당 Package를 독립적으로 사용할 때 필요한 간단한 사용법과 Public API를 중심으로 작성하고, 전체 아키텍처 규칙은 `docs/`의 기준 문서를 참조합니다.

## 15. 문서 유지 원칙

문서를 작성하거나 수정할 때 다음 원칙을 적용합니다.

```txt
실제 코드와 일치한다.

문서마다 하나의 명확한 책임을 가진다.

같은 규칙을 여러 문서에 중복 작성하지 않는다.

소스 코드를 그대로 복사하는 대신 구조와 의도를 설명한다.

왜 존재하는지 설명한다.

어디에서 수정해야 하는지 설명한다.

어떤 경우에 사용하는지 설명한다.

특정 서비스의 비즈니스 요구사항보다
재사용 가능한 보일러플레이트 규칙을 중심으로 작성한다.
```

문서의 목적은 코드의 모든 세부 내용을 기록하는 것이 아니라, 새로운 코드를 작성할 때 일관된 판단을 내릴 수 있는 기준을 제공하는 것입니다.
