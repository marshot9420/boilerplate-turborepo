# 아키텍처

이 문서는 `boilerplate-turborepo`의 전체 구조, 패키지 책임, 의존성 방향, 앱 계층, 백엔드 계층을 설명합니다.

---

## 1. 목표

이 보일러플레이트의 목표는 다음과 같습니다.

```txt
프로젝트 초기 세팅을 빠르게 끝낸다.
Next.js 앱 구조를 일관되게 유지한다.
사용자 앱과 관리자 앱의 공통 기반을 제공한다.
비즈니스 로직과 DB 접근 경계를 명확히 둔다.
폼, 검증, 에러, 로깅, 테스트, 설정을 표준화한다.
반복적인 파일 생성을 자동화한다.
과도한 패키지 분리는 피하되, 나중에 분리 가능한 구조로 시작한다.
```

핵심 방향은 다음입니다.

```txt
Turborepo
+ pnpm workspace
+ Next.js App Router
+ Server First
+ Native Form + Server Actions
+ 완화된 FSD
+ DDD-style Backend Layering
+ Zod Validation
+ Result Pattern
+ Vitest
+ Playwright
+ Storybook
+ 코드 생성기
+ 프로젝트 초기화 스크립트
```

## 3. 핵심 원칙

### 3.1 앱은 조립 계층이다

`apps/*`는 라우팅, 페이지 조립, 사용자 인터랙션 연결을 담당합니다.

앱에 두는 것:

```txt
Next.js route
page/layout/route handler
Server Action
앱별 환경변수 검증
앱별 constants
앱별 entity UI
앱별 feature UI
앱별 shared UI
앱별 type
앱별 view
```

앱에 두지 않는 것:

```txt
비즈니스 규칙
Prisma query
공통 error 처리
공통 validation helper
공통 인증/session 구현
공통 디자인 시스템 primitive
그 외 공통적으로 쓰이는 유틸 함수, 헬퍼 등
```

---

### 3.2 비즈니스 로직은 domain service에 둔다

기본 흐름은 다음입니다.

```txt
UI
 → Server Action
   → Domain Service
     → Repository
       → Prisma
```

각 계층은 자기 책임만 가져야 합니다.

```txt
UI
  화면 표시
  사용자 입력
  form submit

Server Action
  FormData 처리
  인증/권한 확인
  Zod validation
  service 호출
  revalidatePath / redirect

Domain Service
  비즈니스 규칙
  비즈니스 검증
  repository 조합
  Result 반환

Repository
  Prisma query
  DB 입출력
  Prisma error 변환

Prisma
  실제 DB 처리
```

---

### 3.3 DB 접근은 repository로 제한한다

Prisma는 `packages/database` 내부에서만 직접 사용합니다.

허용:

```txt
packages/database/src/**/*
```

금지:

```txt
apps/**/*
packages/domain/**/*
packages/design-system/**/*
packages/core/**/*
```

도메인 서비스는 DB가 필요할 때 repository 함수를 호출합니다.

---

### 3.4 Server First를 우선한다

기본 우선순위는 다음입니다.

```txt
1. Server Component
2. Server Action
3. URL Search Params
4. Client Component local state
5. Global client state
```

Client Component가 필요한 경우에만 `"use client"`를 사용합니다.

예:

```txt
useState/useEffect/useActionState/useFormStatus 사용
브라우저 이벤트 직접 처리
드롭다운, 모달, 토스트, 탭, 캐러셀 등 인터랙션 필요
```

---

### 3.5 Result Pattern을 기본으로 한다

예상 가능한 실패는 throw보다 `Result`로 표현합니다.

```txt
성공
  { ok: true, data }

실패
  { ok: false, error }
```

흐름:

```txt
Repository Result
 → Domain Service Result
 → Server Action ActionResult
 → UI 표시
```

---

### 3.6 처음부터 과도하게 쪼개지 않는다

이 프로젝트는 확장 가능성을 고려하지만, 처음부터 모든 것을 세부 패키지로 분리하지 않습니다.

원칙:

```txt
경계는 명확히 둔다.
반복이 충분히 생기기 전에는 성급하게 추상화하지 않는다.
작은 일회성 helper는 무리하게 분리하지 않는다.
나중에 분리 가능한 구조를 유지한다.
```

### 3.7 DTO는 한 곳에서 관리한다.

식별자 파라미터(예: UserIdParam), 목록 조회 필터링/정렬/검색 쿼리를 포함한 요청 DTO는 `@repo/domain`의 `[domain].schema.ts`에서 관리하고, 응답 DTO는 `[domain].dto.ts`에서 관리합니다. 요청/응답 DTO는 UI 계층부터 서비스 계층까지 공통적으로 호출하여 사용해야 합니다.

제약 조건, 제약 조건에 따른 에러 메시지는 `[domain].constant.ts`에서 상수 객체로 관리하며, 이는 input 에러 메시지 또한 포함합니다.

## 5. Apps 구조: 완화된 FSD

Next.js App Router의 `app/` 라우팅 구조를 중심에 두고, 그 주변에 완화된 FSD 구조를 배치합니다.

```txt
apps/[app]/src/
├─ actions/
├─ app/
├─ config/
├─ constants/
├─ entities/
├─ features/
├─ hooks/
├─ shared/
├─ types/
└─ views/
```

---

### 5.1 `app`

Next.js routing 전용입니다.

담당:

```txt
page.tsx
layout.tsx
route.ts
loading.tsx
error.tsx
not-found.tsx
route group
dynamic route
```

원칙:

```txt
page.tsx는 되도록 얇게 유지한다.
복잡한 UI 조립은 views로 넘긴다.
비즈니스 로직을 넣지 않는다.
Prisma를 직접 사용하지 않는다.
```

---

### 5.2 `views`

페이지 조립 단위입니다.

담당:

```txt
페이지 단위 레이아웃
feature/entity 조합
페이지에 필요한 데이터 조회 연결
empty/error/pagination 조립
```

원칙:

```txt
views는 페이지를 조립한다.
재사용 가능한 도메인 UI는 entities로 내린다.
사용자 행위 단위 UI는 features로 내린다.
기본적으로 Storybook story를 작성하지 않는다.
필요한 경우 단위 테스트는 작성한다.
```

---

### 5.3 `features`

사용자 행위 단위입니다.

예:

```txt
create-content-form
create-content-submit-button
update-content-form
delete-content-form
content-filter-form
logout-button
social-login-buttons
update-my-profile-form
delete-my-account-form
```

원칙:

```txt
사용자 액션 하나를 기준으로 나눈다.
Server Action을 호출할 수 있다.
useActionState/useFormStatus를 사용할 수 있다.
도메인 비즈니스 규칙은 넣지 않는다.
필요한 경우 테스트와 Storybook story를 함께 작성한다.
```

특정 feature 전용 커스텀 훅은 해당 feature 폴더에 둡니다.

```txt
features/content/create-content-form/
├─ create-content-form.tsx
├─ use-create-content-form.ts
├─ create-content-form.test.tsx
└─ index.ts
```

---

### 5.4 `entities`

도메인 모델 단위 UI/helper입니다.

예:

```txt
entities/content/
├─ lib/
└─ ui/

entities/user/
├─ lib/
└─ ui/
```

담당:

```txt
content-card
content-list
content-detail
content-pagination
content-status-badge
user-profile-card
user-info-list
user-table
user-role-badge
user-status-badge
도메인 표시용 formatter/helper
```

원칙:

```txt
특정 사용자 행위가 아니라 도메인 표시를 담당한다.
form submit 같은 action 중심 UI는 features에 둔다.
순수 표시 helper는 lib에 둔다.
컴포넌트 테스트와 Storybook story를 작성한다.
```

---

### 5.5 `actions`

Server Actions 위치입니다.

예:

```txt
actions/
├─ content/
│  ├─ __test__/
│  ├─ create-content.action.ts
│  ├─ update-my-content.action.ts
│  ├─ delete-my-content.action.ts
│  └─ index.ts
└─ user/
   ├─ __test__/
   ├─ update-my-profile.action.ts
   ├─ delete-my-account.action.ts
   └─ index.ts
```

원칙:

```txt
파일 하나당 Server Action 함수 하나를 둔다.
actions/index.ts는 두지 않는다.
도메인 디렉터리의 index.ts에서만 export를 모은다.
FormData 처리, 인증/권한, validation, service 호출만 담당한다.
비즈니스 로직을 넣지 않는다.
Prisma를 직접 호출하지 않는다.
```

---

### 5.6 `hooks`

앱 전체에서 재사용되는 범용 React hook만 둡니다.

예:

```txt
hooks/
├─ useMediaQuery.ts
├─ useDebounce.ts
├─ useOutsideClick.ts
└─ usePrevious.ts
```

원칙:

```txt
앱 전체에서 재사용되는 범용 hook만 둔다.
특정 domain, feature, form에 종속된 hook은 넣지 않는다.
feature 전용 hook은 해당 feature 폴더에 둔다.
여러 feature가 공유하는 domain hook은 features/[domain]/hooks 또는 entities/[domain]/hooks를 검토한다.
React hook이 아닌 순수 helper는 lib에 둔다.
```

---

### 5.7 `shared`

앱 내부에서만 공유되는 코드입니다.

담당:

```txt
header
footer
sidebar
main
auth-card
navigation-link
login-error-alert
앱 전용 공통 UI
앱 전용 hook
앱 전용 lib
```

원칙:

```txt
앱 내부 공통으로만 사용한다.
다른 앱에서도 필요해지면 design-system 또는 packages로 이동을 검토한다.
도메인 특화 UI는 entities/features에 둔다.
```

---

### 5.8 `config`

앱별 설정입니다.

담당:

```txt
client-env.ts
server-env.ts
```

원칙:

```txt
서버 환경변수와 클라이언트 환경변수를 분리한다.
클라이언트 환경변수는 NEXT_PUBLIC_만 허용한다.
앱마다 필요한 env를 앱 내부 config에서 검증한다.
공통 env helper는 @repo/env를 사용한다.
```

---

### 5.9 `constants`

앱별 상수입니다.

담당:

```txt
urls.constant.ts
navigation.constant.ts
```

원칙:

```txt
앱 라우트, 메뉴, 화면 상수 등을 둔다.
도메인 필드 상수는 packages/domain에 둔다.
```

## 6. 패키지 역할

### 6.1 `@repo/core`

가장 아래에 있는 순수 공통 기반입니다.

담당:

```txt
Result
AppError
ActionResult
validation helper
zod error mapper
pagination
search params
normalizer
logger
공통 타입
공통 유틸
```

원칙:

```txt
core는 다른 도메인을 모른다.
core는 database를 모른다.
core는 auth를 모른다.
core는 design-system을 모른다.
순수하고 재사용 가능한 기반 코드만 둔다.
```

---

### 6.2 `@repo/domain`

비즈니스 도메인 규칙의 중심입니다.

담당:

```txt
도메인 상수
Zod schema
Request Input 타입
Response DTO 타입
service
mapper
permission
domain error code
client/server export
```

원칙:

```txt
도메인 규칙은 domain service에 둔다.
DTO 변환은 mapper에서 처리한다.
권한 판단 helper는 permission에 둔다.
Zod schema는 domain에 둔다.
Response DTO는 domain에 둔다.
database model을 UI에 직접 노출하지 않는다.
```

Zod schema의 경우, Param(UserIdParam 등), 필터링 및 정렬 쿼리를 포함하여 유스케이스 별 모든 요청 DTO를 포함합니다.

DTO의 경우, TypeScript `interface`를 사용하여 모든 응답 DTO를 포함합니다.

Zod schema와 DTO는 도메인 계층에서 각 도메인 별로 `[domain].schema.ts`, `[domain].dto.ts` 파일에서 관리되어야 하며, 이는 서비스 계층에서부터 UI까지 공통 사용되고 다른 곳에 분산되어선 안 됩니다.

폼 입력 시 발생하는 input 에러 메시지와 서버 에러 메시지 및 제약 조건 등은 상수 객체인 `[domain].constant.ts`에서 관리되어야 합니다.

---

### 6.3 `@repo/database`

DB 접근 전용 패키지입니다.

담당:

```txt
Prisma schema
Prisma client
repository
transaction
Prisma error mapper
migration
script client
```

원칙:

```txt
database는 DB 접근만 담당한다.
repository는 Prisma query를 실행한다.
repository는 Prisma error를 AppError로 변환한다.
repository는 Response DTO를 반환하지 않는다.
repository는 DB model 또는 Prisma payload에 가까운 값을 반환한다.
business rule은 domain service에서 처리한다.
```

인증/인가 공통 패키지입니다.

```txt
OAuth profile 변환
```

원칙:

```txt

session 관련 세부 구현은 auth 내부에 둔다.
```

```txt
apps/*
```

```txt
apps/*
```

## 8. Backend Layering

전체 흐름은 다음입니다.

```txt
React UI
  ↓
Server Action
  ↓
Domain Service
  ↓
Database Repository
  ↓
Prisma
  ↓
Database
```

---

### 8.1 Server Action

위치:

```txt
apps/web/src/actions/[domain]/
apps/admin/src/actions/[domain]/
```

책임:

```txt
"use server" 선언
FormData 처리
인증/권한 확인
Zod validation
domain service 호출
ActionResult 반환
revalidatePath
redirect
```

하지 않는 것:

```txt
Prisma 직접 접근
복잡한 비즈니스 규칙 처리
DTO mapping
repository 직접 조합
도메인 정책 판단
```

---

### 8.2 Domain Service

위치:

```txt
packages/domain/src/[domain]/[domain].service.ts
```

책임:

```txt
비즈니스 규칙
비즈니스 검증
권한 검증
repository 호출
transaction 조합
DTO mapper 호출
Result 반환
```

하지 않는 것:

```txt
FormData 직접 처리
Next.js revalidate/redirect
React 상태 처리
UI message 결정
Prisma query 직접 작성
```

---

### 8.3 Repository

위치:

```txt
packages/database/src/[domain]/[domain].repository.ts
```

책임:

```txt
Prisma query
DB 입출력
Prisma error mapping
Result 반환
```

하지 않는 것:

```txt
비즈니스 정책 판단
Response DTO 반환
UI용 데이터 가공
권한 검증
Next.js API 사용
```

## 13. 확장 기준

### 13.1 새 도메인 추가

기본 순서:

```txt
1. packages/domain/src/[domain] 추가
2. packages/database/src/[domain] repository 추가
3. 필요한 Prisma model 추가
4. migration 생성
5. service 테스트 작성
6. repository 테스트 작성
7. apps/* actions 추가
8. entities/features/views 추가
9. component/action 테스트 작성
10. 필요한 Storybook story 작성
```

---

### 13.2 새 앱 추가

새 앱은 기존 앱 구조를 따릅니다.

```txt
apps/[app]/
├─ src/
│  ├─ actions/
│  ├─ app/
│  ├─ config/
│  ├─ constants/
│  ├─ entities/
│  ├─ features/
│  ├─ hooks/
│  ├─ shared/
│  └─ views/
├─ e2e/
├─ package.json
├─ next.config.js
├─ vitest.config.ts
├─ vitest.integration.config.ts
└─ playwright.config.ts
```

---

### 13.3 새 패키지 추가

새 패키지는 바로 만들지 않습니다.

추가를 검토할 수 있는 경우:

```txt
여러 앱/패키지에서 반복 사용된다.
독립적인 책임이 명확하다.
기존 패키지에 넣으면 의존성 방향이 깨진다.
외부 서비스나 인프라 책임이 독립적이다.
```

추후 분리 후보:

```txt
storage
mailer
analytics
feature-flags
observability
rate-limit
audit-log
queue
notification
```

현재는 필요해질 때까지 만들지 않습니다.
