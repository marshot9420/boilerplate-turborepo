# 아키텍처

이 문서는 `boilerplate-turborepo`의 전체 설계 방향과 주요 아키텍처 원칙을 설명합니다.

세부적인 파일 배치, Package별 책임, 테스트 작성 방법, 환경변수 관리, Tooling 사용법 등은 각각의 전문 문서에서 다룹니다.

이 문서의 목적은 다음 질문에 대한 상위 기준을 제공하는 것입니다.

```txt
이 보일러플레이트는 어떤 구조를 전제로 하는가?

앱과 Package는 어떤 관계를 가지는가?

UI, 비즈니스 규칙, 데이터베이스 접근은 어떻게 분리되는가?

Server와 Client의 경계는 어떻게 판단하는가?

새로운 기능이나 Package를 추가할 때 어떤 방향을 유지해야 하는가?
```

---

## 1. 목표

`boilerplate-turborepo`는 Next.js 기반 서비스를 빠르게 시작하면서도 프로젝트가 성장한 이후 구조가 무너지지 않도록 공통 개발 기반을 제공하는 것을 목표로 합니다.

주요 목표는 다음과 같습니다.

```txt
프로젝트 초기 설정 시간을 줄인다.

여러 Next.js 앱을 하나의 Workspace에서 일관되게 관리한다.

사용자 앱과 관리자 앱이 공통 기반을 공유할 수 있도록 한다.

UI, 비즈니스 규칙, 데이터 접근, Infrastructure의 경계를 명확히 한다.

환경변수, 인증, 에러 처리, 테스트, UI 기반 등의 반복 구성을 표준화한다.

반복적인 코드와 프로젝트 설정 작업을 자동화한다.

필요한 시점에 확장할 수 있으면서도 초기부터 과도하게 추상화하지 않는다.
```

핵심 기술 및 설계 방향은 다음과 같습니다.

```txt
Turborepo
+ pnpm Workspace
+ Next.js App Router
+ Server First
+ Native Form + Server Actions
+ 완화된 Feature-Sliced Design
+ Domain 중심 Backend Layering
+ Repository Pattern
+ Zod Validation
+ Result Pattern
+ 공통 Design System
+ 공통 Infrastructure Package
+ Vitest
+ Playwright
+ Storybook
+ Code Generator
+ Project Initialization Script
```

## 2. 설계 철학

이 보일러플레이트는 특정 설계 방법론을 엄격하게 구현하는 것을 목표로 하지 않습니다.

대신 각 방법론에서 프로젝트의 유지보수성과 확장성에 도움이 되는 원칙을 선택하여 사용합니다.

전체적인 기준은 다음과 같습니다.

```txt
앱은 조립한다.

도메인은 판단한다.

데이터베이스는 저장한다.

Infrastructure Package는 외부 시스템과 연결한다.

Design System은 도메인에 독립적인 UI 기반을 제공한다.

공통 기반 코드는 하위 계층에 둔다.

Server에서 해결할 수 있는 문제는 Server에서 처리한다.

사용하는 위치와 가까운 곳에 코드를 둔다.

실제 공유와 책임이 발생했을 때만 추상화하거나 승격한다.

계층과 Package의 경계는 명확하게 유지한다.
```

구조를 세분화하는 것 자체가 목적은 아닙니다.

새로운 추상화나 Package를 추가할 때는 해당 경계가 실제 책임을 표현하는지 먼저 판단합니다.

## 3. Workspace 구조

Repository는 Turborepo와 pnpm Workspace를 기반으로 구성합니다.

전체 구조는 다음과 같습니다.

```txt
boilerplate-turborepo/
├─ apps/
│  ├─ admin/
│  └─ web/
│
├─ packages/
│  ├─ auth/
│  ├─ core/
│  ├─ database/
│  ├─ design-system/
│  ├─ domain/
│  ├─ env/
│  ├─ mailer/
│  ├─ storage/
│  │
│  ├─ eslint-config/
│  ├─ playwright-config/
│  ├─ storybook-config/
│  ├─ typescript-config/
│  └─ vitest-config/
│
├─ tooling/
│  ├─ generators/
│  └─ scripts/
│
├─ docs/
├─ package.json
├─ pnpm-workspace.yaml
├─ turbo.json
└─ README.md
```

Workspace는 크게 네 영역으로 나눕니다.

```txt
apps
  실제 실행되는 Next.js 애플리케이션

packages
  여러 앱 또는 Package가 공유하는 기능과 기반

tooling
  프로젝트 개발 및 유지보수를 자동화하는 도구

docs
  프로젝트 구조와 개발 규칙을 정의하는 문서
```

세부 디렉터리 구조는 `03_프로젝트_구조.md`에서 다룹니다.

## 4. Apps와 Packages

### 4.1 Apps

`apps/*`는 최종 애플리케이션을 구성하는 조립 계층입니다.

현재 기본 앱은 다음과 같습니다.

```txt
apps/web
  사용자용 서비스

apps/admin
  관리자용 서비스
```

앱은 다음과 같은 책임을 가질 수 있습니다.

```txt
Next.js Route

Page / Layout

Route Handler

Server Action

화면 조립

사용자 인터랙션

앱 전용 UI

앱 전용 설정
```

비즈니스 규칙이나 공통 Infrastructure 구현을 앱 내부에 반복해서 구현하지 않습니다.

---

### 4.2 Packages

`packages/*`는 앱 외부에서 독립적인 책임을 가지는 공유 계층입니다.

크게 다음 종류로 구분합니다.

```txt
공통 기반
  core

Business / Data
  domain
  database

Application Infrastructure
  auth
  storage
  mailer
  env

UI
  design-system

공통 개발 설정
  eslint-config
  typescript-config
  vitest-config
  playwright-config
  storybook-config
```

Package별 세부 책임과 Public API 기준은 `04_패키지_구조.md`에서 설명합니다.

## 5. 앱 아키텍처

앱 내부에서는 Next.js App Router를 Routing Layer로 사용하고, UI 영역에는 완화된 Feature-Sliced Design 구조를 적용합니다.

큰 흐름은 다음과 같습니다.

```txt
app
  ↓
views
  ↓
features
  ↓
entities
  ↓
shared / design-system
```

각 계층의 개념은 다음과 같습니다.

```txt
app
  Route와 Next.js Framework Boundary

views
  페이지 또는 화면 단위 조립

features
  사용자가 수행하는 행위

entities
  Domain Object의 표현

shared
  앱 내부의 Domain 비종속 공통 코드

design-system
  여러 앱에서 공유 가능한 Domain 비종속 UI 기반
```

상위 계층은 필요한 하위 계층을 조합할 수 있지만, 하위 계층이 자신을 사용하는 상위 계층을 알지 못하도록 합니다.

예:

```txt
View → Feature

View → Entity

Feature → Entity

Entity → Design System
```

반대로 다음과 같은 방향은 피합니다.

```txt
Entity → Feature

Feature → View

Shared → Entity
```

Layer, Slice, Segment, Colocation 등 앱 내부의 상세 구조는 `10_앱_구조.md`에서 정의합니다.

## 6. Backend Layering

서버 기능은 다음 흐름을 기본으로 합니다.

```txt
React UI
  ↓
Server Action
  ↓
Domain Service
  ↓
Repository
  ↓
Prisma
  ↓
Database
```

각 계층은 다른 계층의 책임을 대신하지 않습니다.

---

### 6.1 Server Action

Server Action은 앱과 Domain Layer 사이의 Application Boundary입니다.

주요 흐름은 다음과 같습니다.

```txt
사용자 입력
  ↓
인증 및 기본 접근 경계 확인
  ↓
Request Validation
  ↓
Domain Service 호출
  ↓
ActionResult 변환
  ↓
필요한 Cache 갱신 또는 Navigation
```

구체적인 Resource Permission이나 Business Rule은 Domain에서 판단합니다.

Server Action에는 핵심 비즈니스 규칙이나 Prisma Query를 작성하지 않습니다.

상세한 작성 기준은 `09_서버_액션.md`에서 다룹니다.

---

### 6.2 Domain Service

Domain Service는 애플리케이션의 비즈니스 판단을 담당합니다.

```txt
비즈니스 규칙

비즈니스 검증

권한 정책

Repository 조합

Transaction 조합

Response DTO 구성
```

앱이나 UI가 동일한 비즈니스 규칙을 별도로 구현하지 않도록 Domain을 규칙의 중심으로 사용합니다.

Domain Layer의 구조와 DTO, Schema, Mapper, Permission 등의 세부 규칙은 `08_도메인_레이어.md`에서 설명합니다.

---

### 6.3 Repository

Repository는 데이터 저장소와 Domain 사이의 Persistence Boundary입니다.

```txt
Domain Service
  ↓
Repository
  ↓
Prisma
  ↓
Database
```

Prisma Query는 Database Package에 제한합니다.

Repository는 데이터베이스 입출력을 담당하고 비즈니스 정책을 결정하지 않습니다.

Database Layer와 Repository의 상세 기준은 `07_데이터베이스.md`에서 다룹니다.

---

## 7. Infrastructure Layer

모든 외부 시스템 접근을 Database Layer에 넣지 않습니다.

외부 시스템의 종류에 따라 독립적인 Infrastructure Boundary를 사용할 수 있습니다.

현재 대표적인 예는 다음과 같습니다.

```txt
auth
  OAuth와 Session

storage
  파일 저장소

mailer
  이메일 발송
```

예를 들어 파일 저장이 필요한 경우 기본적인 흐름은 다음과 같습니다.

```txt
App
  ↓
Storage
  ↓
Storage Provider
  ↓
External Storage
```

데이터베이스에 파일 메타데이터를 저장해야 한다면 별도의 Domain 흐름과 조합할 수 있습니다.

```txt
App
  ├─→ Storage
  │
  └─→ Domain Service
        ↓
      Repository
        ↓
      Database
```

Infrastructure Package가 Business Domain이나 UI를 직접 소유하지 않도록 합니다.

새로운 외부 서비스가 추가될 때도 기존 계층에 억지로 포함시키기보다 독립적인 책임이 있는지 판단합니다.

Infrastructure Package의 세부 책임은 `04_패키지_구조.md`, 의존성 방향은 `05_의존성_경계.md`를 따릅니다.

---

## 8. Server First

Next.js에서는 Server에서 처리할 수 있는 작업을 우선적으로 Server에 둡니다.

기본적인 판단 순서는 다음과 같습니다.

```txt
1. Server Component

2. Server Action

3. URL Search Params

4. Client Component Local State

5. Global Client State
```

Client Component는 Browser에서 실제 상태나 Interaction이 필요한 경우에 사용합니다.

예:

```txt
useState

useEffect

useActionState

useFormStatus

Browser API

Dialog

Dropdown

Toast

Carousel

Drag & Drop
```

Client Component가 필요하다는 이유만으로 Page 전체를 Client Component로 전환하지 않습니다.

가능한 한 Client Boundary를 실제 Interaction이 필요한 위치까지 낮춥니다.

Server First는 Client-side JavaScript를 금지하는 원칙이 아니라, Server와 Client 중 어느 쪽이 해당 책임을 가지는 것이 자연스러운지 먼저 판단하는 기준입니다.

---

## 9. Native Form과 Server Actions

일반적인 Form Mutation은 Browser의 Form 동작과 Next.js Server Action을 기본으로 사용합니다.

기본 흐름은 다음과 같습니다.

```txt
Form
  ↓
Server Action
  ↓
Domain Service
  ↓
Repository
```

필요한 경우 Client Component에서 다음과 같은 React 기능을 연결할 수 있습니다.

```txt
useActionState

useFormStatus
```

Client-side 상태관리나 별도의 API Layer를 모든 Mutation에 기본적으로 추가하지 않습니다.

복잡한 Client Interaction이나 별도의 HTTP API가 실제로 필요한 경우에만 추가합니다.

---

## 10. Domain 중심의 데이터 계약

앱과 Server Layer 사이에서 사용하는 Domain 관련 데이터 계약은 Domain Layer를 중심으로 관리합니다.

큰 구분은 다음과 같습니다.

```txt
Request
  Zod Schema

Response
  DTO

Business Constraint
  Domain Constant / Rule
```

UI가 Database Model이나 Prisma Payload에 직접 의존하지 않도록 합니다.

```txt
Database Model
  ↓
Mapper
  ↓
Response DTO
  ↓
App
```

이를 통해 Database Schema와 화면 표현 사이의 직접적인 결합을 줄입니다.

Schema, DTO, Constant의 구체적인 구성과 파일 규칙은 `08_도메인_레이어.md`에서 정의합니다.

## 11. Result와 Error 흐름

예상 가능한 Business Failure는 가능한 한 호출자가 명시적으로 구분할 수 있는 결과로 전달합니다.

개념적인 흐름은 다음과 같습니다.

```txt
Persistence / Infrastructure
  ↓
Domain Service
  ↓
Application Boundary
  ↓
UI
```

각 계층은 필요에 따라 자신이 이해할 수 있는 Error 또는 Result 형태로 변환합니다.

예:

```txt
Persistence Error
  ↓
Database Error Mapping
  ↓
Domain Result / Error
  ↓
ActionResult
  ↓
사용자에게 표시할 상태
```

모든 Error가 반드시 동일한 변환 단계를 거치는 것은 아닙니다.

예상 가능한 실패와 예상하지 못한 Runtime Error를 구분하고, 세부 처리 기준은 각 계층의 전문 문서를 따릅니다.

## 12. UI Layering

UI 구조는 개념적으로 다음 방향을 유지합니다.

```txt
Design System / App Shared
  ↓
Entity
  ↓
Feature
  ↓
View
  ↓
App Route
```

각 영역의 관심사는 다음과 같습니다.

```txt
Design System
  Domain에 독립적인 공통 UI 기반과 UI Infrastructure

App Shared
  하나의 App 안에서 공유하는 Domain 비종속 코드와 UI

Entity
  Domain Object 표현

Feature
  사용자 행위와 Interaction

View
  화면 단위 조립

App Route
  URL과 화면 연결
```

Design System이 특정 Business Domain을 알지 못하도록 유지합니다.

또한 Design System 내부에 별도의 `primitives` 계층을 Architecture 전제로 두지 않습니다.

Web과 Admin에서 필요한 공통 UI는 실제 책임과 사용 범위에 따라 Design System의 Public 영역에서 관리합니다.

App UI의 Layer / Slice / Segment 구조는 `10_앱_구조.md`, Design System의 실제 구조와 승격 기준은 `11_디자인_시스템.md`에서 설명합니다.

## 13. 의존성 방향

Workspace Dependency는 상위 조립 계층에서 하위 기반 계층으로 흐르는 것을 기본으로 합니다.

가장 중요한 방향은 다음과 같습니다.

```txt
Apps
  ↓
Runtime Packages

Domain
  ↓
Database / Core

Database
  ↓
Core / Env

Design System
  ↓
Domain 비종속 공통 기반
```

하위 Package가 자신을 사용하는 상위 App이나 Package를 다시 참조하지 않습니다.

특히 다음 방향은 허용하지 않습니다.

```txt
packages/* → apps/*
```

Package 사이의 정확한 허용 관계는 각 Package의 책임에 따라 다릅니다.

예를 들어 Auth, Mailer, Storage가 모두 같은 하위 Dependency 구조를 가져야 하는 것은 아닙니다.

따라서 정확한 Dependency Matrix와 Boundary 검사 기준은 `05_의존성_경계.md`에서만 정의합니다.

## 14. 공통 설정 중앙화

여러 Workspace에서 반복되는 개발 설정은 공통 Config Package로 관리합니다.

```txt
eslint-config

typescript-config

vitest-config

playwright-config

storybook-config
```

각 App과 Package는 가능한 한 공통 설정을 재사용하고 자신에게 필요한 최소한의 차이만 추가합니다.

이를 통해 다음을 줄입니다.

```txt
설정 중복

Tool Version 불일치

App별 설정 편차

설정 변경 지점의 분산
```

공통 설정의 실제 구성은 `02_기본설정.md`에서 설명합니다.

## 15. 테스트와 UI 문서화

Test와 Storybook은 Architecture를 보조하는 개발 기반으로 사용합니다.

Test는 책임과 실행 범위에 따라 다음과 같이 분리합니다.

```txt
Unit

Component

Integration

E2E
```

Storybook은 독립적으로 관찰하고 조작할 가치가 있는 UI의 상태와 계약을 확인하고 문서화하는 데 사용합니다.

아키텍처 문서에서는 세부 Test 대상이나 Story 작성 규칙을 정의하지 않습니다.

상세 기준은 다음 문서에서 관리합니다.

```txt
12_테스트_전략.md

13_스토리북.md
```

## 16. Tooling

반복적인 프로젝트 작업은 `tooling/*`에서 자동화합니다.

```txt
tooling/generators
  반복적인 코드 구조 생성

tooling/scripts
  프로젝트 초기화 및 유지보수 작업 자동화
```

Generator는 프로젝트의 현재 구조와 Convention을 반영해야 합니다.

프로젝트 구조가 변경되면 문서뿐 아니라 Generator의 생성 결과도 함께 검토합니다.


## 17. 확장 원칙

이 보일러플레이트는 새로운 App, Domain, Package, Infrastructure를 추가할 수 있도록 설계합니다.

하지만 미래의 가능성만으로 구조를 미리 만들지는 않습니다.

새로운 구조를 추가할 때는 다음을 확인합니다.

```txt
현재 위치에서 책임을 명확하게 표현할 수 있는가?

실제로 여러 위치에서 공유되는가?

독립적인 Business Concept나 외부 시스템 경계를 가지는가?

기존 구조에 포함하면 책임이나 Dependency 방향이 불명확해지는가?

새로운 경계를 만드는 것이 실제 유지보수 비용을 줄이는가?
```

기본 원칙은 다음과 같습니다.

```txt
먼저 colocate한다.

실제 공유가 발생하면 승격한다.

독립적인 책임이 생기면 분리한다.

경계를 분명히 하되 구조 자체를 목적으로 만들지 않는다.
```

새 App, Domain, Package 등을 추가하는 구체적인 판단 기준은 `19_확장_가이드.md`에서 다룹니다.

## 19. 핵심 원칙

이 보일러플레이트의 아키텍처를 가장 짧게 표현하면 다음과 같습니다.

```txt
앱은 조립한다.

도메인은 판단한다.

데이터베이스는 저장한다.

Infrastructure는 외부 시스템과 연결한다.

Design System은 Domain에 독립적인 UI 기반을 제공한다.

Core는 순수한 공통 기반을 제공한다.

Server에서 해결할 수 있는 것은 Server에서 처리한다.

공통 설정은 중앙화한다.

반복 작업은 Tooling으로 자동화한다.

코드는 사용하는 위치 가까이에 둔다.

실제 책임과 공유가 생겼을 때만 분리하거나 승격한다.

하위 계층은 자신을 사용하는 상위 계층을 알지 않는다.

구조는 확장을 가능하게 해야 하지만
확장을 예상하여 과도하게 복잡해져서는 안 된다.
```
