# 프로젝트 초기화

이 문서는 `boilerplate-turborepo`를 새로운 프로젝트의 시작점으로 사용할 때 필요한 초기 설정 절차를 설명합니다.

프로젝트 초기화의 기본 흐름은 다음과 같습니다.

```txt
Boilerplate Clone
  ↓
Project Identity 초기화
  ↓
Dependency 설치
  ↓
환경변수 설정
  ↓
Prisma Client 생성
  ↓
Database Schema 반영
  ↓
Seed
  ↓
프로젝트 검증
  ↓
개발 서버 실행
```

이 프로젝트는 Boilerplate에서 사용하는 기본 Project Name과 Workspace Package Scope를 실제 프로젝트에 맞게 변경할 수 있도록 초기화 Script를 제공합니다.

기본값:

```txt
Project Name
  boilerplate-turborepo

Workspace Package Scope
  @repo

Database Prefix
  boilerplate_turborepo

Session Cookie
  boilerplate_session
```

예를 들어 실제 프로젝트가 다음과 같다면:

```txt
Project Name
  athena-doctrine

Workspace Package Scope
  @athena
```

초기화 이후 관련 값은 다음과 같이 변경됩니다.

```txt
boilerplate-turborepo
  → athena-doctrine

@repo
  → @athena

boilerplate_turborepo
  → athena_doctrine

boilerplate_session
  → athena_doctrine_session
```

---

## 1. 기본 초기화 순서

새 프로젝트에서는 다음 순서를 기본으로 사용합니다.

```txt
1. Boilerplate Clone

2. pnpm init-project 실행

3. pnpm install

4. 환경변수 설정

5. Prisma Client 생성

6. Database Schema 반영

7. Seed 실행

8. 프로젝트 검증

9. 개발 서버 실행
```

예:

```bash
git clone <boilerplate-repository-url> athena-doctrine
cd athena-doctrine

pnpm init-project athena-doctrine --scope athena --remove-git

pnpm install
```

환경변수를 설정한 뒤:

```bash
pnpm db:generate
pnpm db:push
pnpm db:seed

pnpm check
pnpm test

pnpm dev
```

---

## 2. Boilerplate Clone

Boilerplate Repository를 Clone할 때 실제 프로젝트의 Directory 이름을 함께 지정하는 것을 권장합니다.

예:

```bash
git clone <boilerplate-repository-url> athena-doctrine
cd athena-doctrine
```

이 경우 실제 Directory 이름은 처음부터 다음과 같습니다.

```txt
athena-doctrine/
```

`pnpm init-project`는 현재 Repository Directory 자체를 Rename하지 않습니다.

따라서 다음 책임을 구분합니다.

```txt
git clone
  실제 Repository Directory 이름 결정

pnpm init-project
  Repository 내부 Project Identity 변경
```

---

## 3. `pnpm init-project`

`pnpm init-project`는 Boilerplate를 실제 프로젝트로 전환하기 위한 최초 초기화 명령입니다.

기본 형식:

```bash
pnpm init-project <project-name> [options]
```

예:

```bash
pnpm init-project mars
```

Project Name과 Workspace Package Scope가 서로 다르다면 `--scope`를 함께 사용합니다.

```bash
pnpm init-project athena-doctrine --scope athena
```

---

## 4. `init-project`는 `pnpm install` 전에 실행한다

`init-project`는 초기 Bootstrap 단계에서 사용할 수 있도록 Node에서 직접 실행됩니다.

따라서 기본 순서는 다음과 같습니다.

```txt
Clone
  ↓
pnpm init-project
  ↓
pnpm install
```

예:

```bash
git clone <boilerplate-repository-url> athena-doctrine
cd athena-doctrine

pnpm init-project athena-doctrine --scope athena

pnpm install
```

Project Name과 Package Scope가 변경된 이후 처음으로 Workspace Dependency를 설치하는 구조입니다.

---

## 5. Project Name과 Package Scope

Project Name과 Workspace Package Scope는 서로 다른 개념입니다.

예:

```txt
Project Name
  athena-doctrine

Workspace Package Scope
  @athena
```

이 경우 다음 명령을 사용합니다.

```bash
pnpm init-project athena-doctrine --scope athena
```

`--scope`를 생략하면 Project Name을 Package Scope의 기본값으로 사용합니다.

예:

```bash
pnpm init-project mars
```

결과:

```txt
Project Name
  mars

Workspace Package Scope
  @mars
```

Project Name과 Package Scope가 같다면 별도의 `--scope` 지정이 필요하지 않습니다.

---

## 6. `init-project`가 변경하는 값

`init-project`는 현재 Repository의 Project Identity를 읽고 새로운 값으로 치환합니다.

주요 변경 대상:

```txt
Project Name
Workspace Package Scope
Database Prefix
Session Cookie Name
```

예:

```bash
pnpm init-project athena-doctrine --scope athena
```

실행 전:

```txt
Project Name
  boilerplate-turborepo

Scope
  @repo

Database Prefix
  boilerplate_turborepo

Session Cookie
  boilerplate_session
```

실행 후:

```txt
Project Name
  athena-doctrine

Scope
  @athena

Database Prefix
  athena_doctrine

Session Cookie
  athena_doctrine_session
```

---

## 7. 현재 Project Name과 Scope 자동 감지

`init-project`는 기존 Project Name과 Package Scope를 고정값으로 가정하지 않습니다.

현재 Project Name은 Root `package.json`에서 확인합니다.

```txt
package.json
  ↓
name
```

현재 Package Scope는 `tooling/scripts/package.json`의 Package Name에서 확인합니다.

예:

```txt
@repo/scripts
  ↓
repo
```

따라서 Boilerplate를 이미 한 번 초기화한 이후 다시 실행하더라도 현재 값을 기준으로 변경할 수 있습니다.

예:

```txt
현재
  athena-doctrine
  @athena

변경
  new-project
  @new
```

명령:

```bash
pnpm init-project new-project --scope new
```

---

## 8. `--from-name`

현재 Project Name을 자동 감지하지 않고 직접 지정해야 하는 경우 사용할 수 있습니다.

```bash
pnpm init-project mars --from-name boilerplate-turborepo
```

기본적으로는 Root `package.json`에서 자동 감지하므로 일반적인 초기화에서는 사용할 필요가 없습니다.

---

## 9. `--from-scope`

현재 Package Scope를 직접 지정해야 하는 경우 사용할 수 있습니다.

```bash
pnpm init-project mars --from-scope repo --scope mars
```

기본적으로는 `tooling/scripts/package.json`에서 자동 감지하므로 일반적인 초기화에서는 사용할 필요가 없습니다.

---

## 10. `--dry-run`

실제 파일을 변경하기 전에 변경 범위를 확인하려면 `--dry-run`을 사용합니다.

예:

```bash
pnpm init-project athena-doctrine --scope athena --dry-run
```

`--dry-run`에서는 실제 파일을 수정하지 않습니다.

대신 다음 정보를 출력합니다.

```txt
변경될 Project Name
변경될 Scope
변경될 Database Prefix
변경될 Session Cookie
검사한 파일 수
변경 예정 파일 수
생성 예정 파일
삭제 예정 Directory
Git 제거 여부
```

새 프로젝트를 초기화할 때는 먼저 `--dry-run`으로 결과를 확인한 뒤 실제 명령을 실행해도 됩니다.

예:

```bash
pnpm init-project athena-doctrine --scope athena --dry-run

pnpm init-project athena-doctrine --scope athena --remove-git
```

---

## 11. Git History 처리

Boilerplate의 기존 Git History를 새 프로젝트에서 유지하지 않으려면 `--remove-git`을 사용합니다.

```bash
pnpm init-project athena-doctrine \
  --scope athena \
  --remove-git
```

이 경우 기존 `.git` Directory를 제거합니다.

초기화 후 새로운 Repository로 시작할 수 있습니다.

```bash
git init
git add .
git commit -m "chore: 프로젝트 초기화"
```

기존 Git History를 유지하려면:

```bash
pnpm init-project athena-doctrine \
  --scope athena \
  --keep-git
```

을 사용합니다.

`--remove-git`과 `--keep-git`은 동시에 사용할 수 없습니다.

두 옵션을 모두 생략하면 Interactive Terminal에서는 기존 `.git` Directory를 제거할지 확인합니다.

## 12. 생성물 정리

`init-project`는 기존 Boilerplate 작업 과정에서 남아 있을 수 있는 생성물을 정리합니다.

대표적인 대상:

```txt
.turbo
.next
dist
coverage
out
node_modules
```

초기화는 Dependency 설치 전에 수행하는 것을 기본으로 하므로 기존 `node_modules`가 존재하더라도 제거할 수 있습니다.

초기화 이후 새 Project Identity를 기준으로 다시 Dependency를 설치합니다.

```bash
pnpm install
```

---

## 13. Local Environment 파일 생성

`init-project`는 Local Environment 파일이 존재하지 않는 경우 Example 파일을 기반으로 생성합니다.

```txt
.env.example
  ↓
.env.local

.env.test.example
  ↓
.env.test.local

.env.e2e.example
  ↓
.env.e2e.local
```

생성 대상 파일이 이미 존재한다면 덮어쓰지 않습니다.

즉 기존:

```txt
.env.local
.env.test.local
.env.e2e.local
```

의 실제 Secret이나 개발 환경 설정은 보호됩니다.

---

## 14. `init-project`가 자동으로 하지 않는 작업

`init-project`는 Project Identity 초기화까지만 담당합니다.

다음 작업은 자동으로 수행하지 않습니다.

```txt
Dependency 설치
실제 Environment Secret 입력
Prisma Client 생성
Database Schema 반영
Migration 실행
Seed
Playwright Browser 설치
개발 서버 실행
```

이 작업들은 프로젝트 초기화 이후 명시적으로 수행합니다.

초기화 Script와 외부 Infrastructure 연결을 분리함으로써 실패 지점을 명확하게 유지합니다.

---

## 15. `pnpm install`

Project Identity 초기화가 끝나면 Workspace Dependency를 설치합니다.

```bash
pnpm install
```

이 시점에는 이미 Workspace Package Scope가 새로운 값으로 변경되어 있습니다.

예:

```txt
@repo/core
@repo/domain
@repo/database
```

가 초기화 과정에서:

```txt
@athena/core
@athena/domain
@athena/database
```

로 변경된 뒤 Dependency 설치가 진행됩니다.

---

## 16. `pnpm install` 이후 기본 작업

Dependency 설치 이후에는 다음 순서로 진행합니다.

```txt
1. Local Environment 확인

2. 실제 Environment 값 입력

3. Prisma Client 생성

4. Database Schema 반영

5. Seed

6. 코드 검증

7. 개발 서버 실행
```

## 17. Environment 설정

초기화 과정에서 생성된 `.env.local`을 확인합니다.

```txt
.env.local
```

Example 값 중 실제 Provider 정보가 필요한 항목을 채웁니다.

대표적으로 다음과 같은 값이 포함될 수 있습니다.

```txt
Database Connection
Authentication Secret
OAuth Provider
Application URL
Storage Provider
Mailer Provider
기타 외부 Infrastructure
```

Environment Variable의 실제 분류와 관리 기준은 `06_환경변수.md`를 따릅니다.

## 18. Test Environment

Unit 및 Integration Test에서 별도의 환경변수가 필요한 경우:

```txt
.env.test.local
```

을 설정합니다.

기본 Template:

```txt
.env.test.example
```

초기화 시 `.env.test.local`이 없다면 자동 생성됩니다.

Test Database를 사용하는 Integration Test가 있다면 실제 Test Database 연결 정보도 설정해야 합니다.

---

## 19. E2E Environment

Playwright E2E 환경은:

```txt
.env.e2e.local
```

을 사용합니다.

기본 Template:

```txt
.env.e2e.example
```

초기화 시 `.env.e2e.local`이 없다면 자동 생성됩니다.

E2E Test에서는 일반 개발 Database와 분리된 Database를 사용해야 합니다.

## 20. Database 초기화

환경변수를 준비한 뒤 Database를 초기화합니다.

기본 개발 환경에서는 다음 순서를 사용합니다.

```bash
pnpm db:generate
pnpm db:push
pnpm db:seed
```

---

## 21. `pnpm db:generate`

Prisma Schema를 기준으로 Prisma Client를 생성합니다.

```bash
pnpm db:generate
```

개념:

```txt
schema.prisma
  ↓
Prisma Client Generate
  ↓
Application / Repository에서 Prisma Type과 Client 사용 가능
```

Prisma Schema가 변경되었다면 다시 실행합니다.

---

## 22. `pnpm db:push`

현재 Prisma Schema를 개발 Database에 반영합니다.

```bash
pnpm db:push
```

새 프로젝트를 처음 실행할 때 Database가 비어 있다면 이 명령을 통해 현재 Schema를 반영할 수 있습니다.

개발 과정에서 Migration을 사용할 경우:

```bash
pnpm db:migrate
```

를 사용합니다.

Database 운영 및 Migration 정책은 `07_데이터베이스.md`를 따릅니다.

---

## 23. `pnpm db:seed`

Database Schema가 준비되면 초기 개발 데이터를 삽입합니다.

```bash
pnpm db:seed
```

실제 실행 대상:

```txt
tooling/scripts/src/seed.ts
```

Seed는 개발 환경에서 필요한 기본 데이터를 준비하기 위한 작업입니다.

예:

```txt
기본 관리자 계정
기본 설정 값
개발용 Domain Data
초기 Catalog Data
```

실제 Seed 내용은 프로젝트 요구사항에 맞게 수정합니다.

---

## 24. E2E Database 초기화

E2E 환경에서는 일반 개발 Database와 다른 환경을 사용합니다.

관련 명령:

```bash
pnpm db:e2e:generate
pnpm db:e2e:push
pnpm db:e2e:seed
```

일반적인 E2E 실행에서는 Root Script가 필요한 Database 준비를 함께 수행합니다.

```bash
pnpm test:e2e
```

내부 흐름:

```txt
db:e2e:push
  ↓
db:e2e:seed
  ↓
Playwright E2E
```

## 25. Integration Test Database

```bash
pnpm db:test:generate
pnpm db:test:push
pnpm db:test:migrate
```

실제 사용 범위는 `12_테스트_전략.md`와 `07_데이터베이스.md`를 따릅니다.

## 26. 프로젝트 검증

초기 설정과 Database 준비가 끝났다면 개발 서버를 실행하기 전에 프로젝트 상태를 검증합니다.

기본:

```bash
pnpm check
```

`pnpm check`는 현재 다음 검증을 순차적으로 수행합니다.

```txt
lint
  ↓
check:boundaries
  ↓
check-types
  ↓
format:check
```

각 명령을 개별적으로 실행할 수도 있습니다.

```bash
pnpm lint

pnpm check:boundaries

pnpm check-types

pnpm format:check
```

---

## 27. Unit Test

기본 테스트를 실행합니다.

```bash
pnpm test
```

초기화 과정에서 Project Name이나 Package Scope가 변경되었기 때문에 Import 경로나 Workspace Package 연결에 문제가 없는지 함께 확인할 수 있습니다.

---

## 28. Integration Test

필요한 Test Database가 준비되어 있다면 Integration Test도 실행할 수 있습니다.

```bash
pnpm test:integration
```

모든 프로젝트에서 최초 실행 전에 Integration Test를 반드시 실행해야 한다는 의미는 아닙니다.

Database와 관련된 초기 설정을 변경한 경우에는 실행하는 것을 권장합니다.

---

## 29. Playwright 설치

E2E Test를 사용할 프로젝트에서는 Playwright Browser를 설치합니다.

```bash
pnpm playwright:install
```

Playwright E2E를 바로 사용하지 않는다면 프로젝트 초기화 과정에서 반드시 실행할 필요는 없습니다.

---

## 30. 개발 서버 실행

초기 설정이 끝나면 개발 서버를 실행합니다.

```bash
pnpm dev
```

Turborepo를 통해 개발 Script가 있는 Workspace App과 Package Task가 실행됩니다.

일반적인 초기화 완료 상태:

```txt
Project Identity
  설정 완료

Workspace Dependency
  설치 완료

Environment
  설정 완료

Prisma Client
  생성 완료

Database Schema
  반영 완료

Seed
  완료

pnpm check
  통과

pnpm test
  통과
```

이후:

```bash
pnpm dev
```

를 실행합니다.

---

## 31. `pnpm setup:scope`

`pnpm setup:scope`는 새로운 프로젝트를 초기화하는 명령이 아닙니다.

이미 사용 중인 프로젝트의 Workspace Package Scope만 변경하기 위한 Maintenance Command입니다.

기본 형식:

```bash
pnpm setup:scope <scope-name>
```

예:

```bash
pnpm setup:scope athena
```

현재 Scope가:

```txt
@repo
```

라면:

```txt
@repo
  ↓
@athena
```

로 변경합니다.

---

## 32. 현재 Scope 자동 감지

`setup:scope`는 현재 Package Scope를 `tooling/scripts/package.json`에서 자동 감지합니다.

예:

```json
{
  "name": "@athena/scripts"
}
```

라면 현재 Scope를:

```txt
@athena
```

로 판단합니다.

따라서:

```bash
pnpm setup:scope eten
```

만 실행해도:

```txt
@athena
  ↓
@eten
```

으로 변경할 수 있습니다.

---

## 33. `setup:scope --from`

현재 Scope를 직접 지정해야 하는 경우 `--from`을 사용할 수 있습니다.

```bash
pnpm setup:scope eten --from athena
```

일반적인 경우에는 현재 Scope를 자동 감지하므로 필요하지 않습니다.

---

## 34. `setup:scope --dry-run`

실제 변경 전에 결과를 확인하려면:

```bash
pnpm setup:scope athena --dry-run
```

을 사용합니다.

실제 파일을 수정하지 않고 다음을 출력합니다.

```txt
현재 Scope
변경할 Scope
검사한 파일
변경 예정 파일
```

---

## 35. `init-project`와 `setup:scope`의 차이

두 명령의 책임은 명확히 구분합니다.

```txt
pnpm init-project

  새로운 Boilerplate Instance 초기화

  Project Name 변경
  Package Scope 변경
  Database Prefix 변경
  Session Cookie 변경
  Local Environment 파일 생성
  기존 생성물 정리
  Git History 처리
```

```txt
pnpm setup:scope

  기존 프로젝트 Package Scope 변경

  @old
    ↓
  @new
```

새로운 프로젝트를 시작할 때는:

```bash
pnpm init-project
```

를 사용합니다.

이미 운영하거나 개발 중인 프로젝트에서 Scope만 변경하려면:

```bash
pnpm setup:scope
```

를 사용합니다.

---

## 36. `setup:scope` 이후 작업

Workspace Package Scope가 변경되었다면 Dependency와 Workspace Link를 다시 확인합니다.

```bash
pnpm install
```

이후:

```bash
pnpm format
pnpm check
```

을 실행합니다.

필요하면 Test도 실행합니다.

```bash
pnpm test
```

---

## 37. Package Scope 변경 대상

Scope 변경은 Repository의 Source 및 설정 파일에 존재하는 기존 Workspace Scope를 새로운 Scope로 치환합니다.

예:

```txt
@repo/core
@repo/domain
@repo/database
@repo/design-system
```

변경:

```txt
@athena/core
@athena/domain
@athena/database
@athena/design-system
```

대상에는 다음 종류의 파일이 포함될 수 있습니다.

```txt
TypeScript
JavaScript
JSON
YAML
Markdown
Prisma
Environment
Dockerfile
기타 프로젝트 Text File
```

`.env.test*`, `.env.e2e*` 역시 같은 대상에 포함됩니다.

---

## 38. 처리하지 않는 Directory

초기화 및 Scope 변경 과정에서는 생성물이나 외부 Dependency Directory를 탐색하지 않습니다.

대표적인 제외 대상:

```txt
.git
.next
.turbo
coverage
dist
node_modules
out
```

이 영역의 파일을 직접 문자열 치환하지 않습니다.

---

## 39. `pnpm-lock.yaml`

`pnpm-lock.yaml`은 초기화 Script에서 직접 문자열 치환하지 않습니다.

Project Name과 Workspace Package Scope가 변경된 뒤:

```bash
pnpm install
```

을 실행하여 pnpm이 현재 Workspace 상태를 기준으로 Lockfile을 갱신하도록 합니다.

Lockfile을 단순 문자열 치환 대상으로 취급하지 않습니다.

## 43. Seed 이후 기본 절차

Seed까지 완료했다면 다음 순서를 권장합니다.

```bash
pnpm check
pnpm test
pnpm dev
```

필요하다면 Integration Test를 추가합니다.

```bash
pnpm test:integration
```

E2E까지 확인한다면:

```bash
pnpm playwright:install
pnpm test:e2e
```

전체 흐름:

```txt
pnpm db:seed
  ↓
pnpm check
  ↓
pnpm test
  ↓

  ↓
pnpm dev
```

## 46. 초기화 실패 시 확인 순서

초기화 과정에서 문제가 발생한다면 다음 순서로 확인합니다.

```txt
Node 버전

pnpm 버전

Project Name 형식

Scope Name 형식

환경변수 누락

Database 연결 정보

Prisma Client 생성 여부

Database Schema 반영 여부

Seed 실패 로그

Workspace Package Scope 변경 여부
```

현재 요구 버전은 Root `package.json`의 `engines`를 기준으로 합니다.

```txt

  >=11.6.0 <12

```

## 48. Package Scope 규칙

Package Scope 역시 다음 문자만 사용합니다.

```txt
소문자 영문
숫자
하이픈
```

입력할 때 `@`는 생략할 수 있습니다.

예:

```bash
pnpm init-project athena-doctrine --scope athena
```

내부에서는:

```txt
@athena
```

로 사용합니다.

`setup:scope`도 동일합니다.

```bash
pnpm setup:scope athena
```

## 49. 초기화 Script를 반복 실행할 때

`init-project`는 현재 Project Name과 Package Scope를 자동 감지합니다.

따라서 이미 초기화된 Repository에서도 현재 상태를 기준으로 다시 변경할 수 있습니다.

다만 `init-project`는 단순 Rename Utility가 아니라 다음 작업까지 포함합니다.

```txt
Local Env 생성
Generated Directory 정리
Git 처리
```

따라서 이미 개발 중인 프로젝트에서 단순히 Package Scope만 바꿀 목적이라면 `setup:scope`를 사용합니다.

다음 조건을 충족하면 기본 프로젝트 초기화가 완료된 것으로 봅니다.

```txt
Repository Directory가 실제 Project Name을 사용한다.

Root package.json의 name이 실제 Project Name을 사용한다.

Workspace Package가 실제 Package Scope를 사용한다.

Local Environment 파일이 준비되어 있다.

필수 Environment Variable이 설정되어 있다.

Prisma Client가 생성되어 있다.

개발 Database Schema가 준비되어 있다.

Seed가 정상 실행된다.

pnpm check가 통과한다.

기본 Test가 통과한다.

pnpm dev로 Application이 정상 실행된다.
```

## 53. 핵심 원칙

```txt
Boilerplate Clone 시 실제 프로젝트 Directory 이름을 지정한다.

Project Identity 초기화는 Dependency 설치 전에 수행한다.

Project Name과 Package Scope는 서로 독립적으로 설정할 수 있다.

--scope를 생략하면 Project Name을 기본 Scope로 사용한다.

현재 Project Name과 Scope는 Repository에서 자동 감지한다.

--from-name과 --from-scope는 필요한 경우에만 사용한다.

실제 변경 전에 --dry-run으로 결과를 확인할 수 있다.

새 Repository로 시작한다면 --remove-git을 사용할 수 있다.

init-project는 Project Identity 초기화를 담당한다.

setup:scope는 기존 프로젝트의 Package Scope 변경만 담당한다.

Local Environment 파일은 기존 파일을 덮어쓰지 않는다.

실제 Secret은 init-project가 자동으로 채우지 않는다.

Database 연결과 Seed는 Project Identity 초기화와 분리한다.

pnpm-lock.yaml은 직접 문자열 치환하지 않는다.

Project Name과 Scope 변경 후 pnpm install로 Workspace를 동기화한다.

Database 초기화는 db:generate → db:push → db:seed 순서를 기본으로 한다.

Seed 이후 pnpm check와 pnpm test로 프로젝트를 검증한다.

검증이 끝나면 pnpm dev로 개발을 시작한다.
```
