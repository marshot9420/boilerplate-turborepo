# 프로젝트 초기화

이 문서는 `boilerplate-turborepo`를 새로운 프로젝트의 시작점으로 사용할 때 필요한 초기 설정 절차를 설명합니다.

기본 흐름:

```txt
Boilerplate Clone
  ↓
Project Identity 초기화
  ↓
Dependency 설치
  ↓
Source Format 정리
  ↓
환경변수 설정
  ↓
Database 준비
  ↓
Seed
  ↓
프로젝트 검증
  ↓
개발 서버 실행
```

프로젝트를 처음 만드는 과정에 집중하며, Database 운영 정책이나 Test 전략 등의 세부 내용은 각각의 전문 문서를 따릅니다.

---

## 1. 기본 초기화 순서

먼저 [기본설정](./02_기본설정.md)의 Node.js와 pnpm을 준비합니다. `node --version`과 `pnpm --version`으로 고정 버전을 확인한 뒤 진행합니다.

새로운 프로젝트에서는 다음 순서를 권장합니다.

```bash
git clone <boilerplate-repository-url> athena-doctrine
cd athena-doctrine

node tooling/scripts/src/init-project.ts athena-doctrine \
  --scope athena \
  --dry-run

node tooling/scripts/src/init-project.ts athena-doctrine \
  --scope athena \
  --remove-git

pnpm install --no-frozen-lockfile
pnpm format
```

환경변수를 설정한 뒤:

```bash
pnpm db:generate
pnpm db:push
pnpm db:seed

pnpm check
pnpm test

pnpm dev
```

즉 기본 순서는 다음과 같습니다.

```txt
Clone
  ↓
init-project
  ↓
pnpm install --no-frozen-lockfile
  ↓
pnpm format
  ↓
Environment
  ↓
Database
  ↓
Seed
  ↓
Validation
  ↓
Development
```

## 2. Boilerplate Clone

Clone할 때 실제 프로젝트 Directory 이름을 함께 지정하는 것을 권장합니다.

```bash
git clone <boilerplate-repository-url> athena-doctrine
cd athena-doctrine
```

`node tooling/scripts/src/init-project.ts`는 Repository Directory 자체를 Rename하지 않습니다.

역할을 다음과 같이 구분합니다.

```txt
git clone
  실제 Directory 이름 결정

node tooling/scripts/src/init-project.ts
  Repository 내부 Project Identity 변경
```

---

## 3. `init-project` 실행

`node tooling/scripts/src/init-project.ts`는 Boilerplate를 실제 프로젝트로 전환하기 위한 최초 초기화 명령입니다.

기본 형식:

```bash
node tooling/scripts/src/init-project.ts <project-name> [options]
```

Project Name과 Workspace Package Scope가 같다면:

```bash
node tooling/scripts/src/init-project.ts mars
```

처럼 사용할 수 있습니다.

결과:

```txt
Project Name
  mars

Workspace Package Scope
  @mars
```

Project Name과 Package Scope가 다르다면 `--scope`를 지정합니다.

```bash
node tooling/scripts/src/init-project.ts athena-doctrine --scope athena
```

결과:

```txt
Project Name
  athena-doctrine

Workspace Package Scope
  @athena
```

`init-project`는 Node.js 기본 모듈만 사용하므로 Dependency 설치 전에 직접 실행할 수 있습니다.

pnpm 11은 Script 실행 전에 Dependency 상태를 검사하면서 자동 설치를 시도할 수 있습니다. 따라서 최초 설치 전에는 위의 Node 명령을 사용합니다. 설치가 끝난 Workspace에서는 루트 Alias인 `pnpm init-project <project-name> [options]`도 사용할 수 있습니다.

---

## 4. `init-project`의 변경 범위

`init-project`는 현재 Repository의 Project Identity를 감지하고 새로운 값으로 변경합니다.

주요 변경 대상:

```txt
Project Name
Workspace Package Scope
Project Name의 snake_case 표현
Session Cookie Name
```

Boilerplate 기본값에서:

```txt
boilerplate-turborepo
@repo
boilerplate_turborepo
boilerplate_session
```

다음 명령을 실행하면:

```bash
node tooling/scripts/src/init-project.ts athena-doctrine --scope athena
```

다음 형태로 변경됩니다.

```txt
athena-doctrine
@athena
athena_doctrine
athena_doctrine_session
```

현재 Project Name은 Root `package.json`에서, 현재 Package Scope는 `tooling/scripts/package.json`에서 자동 감지합니다.

일반적인 초기화에서는 기존 값을 직접 지정할 필요가 없습니다.

필요한 경우에만 다음 옵션을 사용할 수 있습니다.

```bash
node tooling/scripts/src/init-project.ts mars \
  --from-name boilerplate-turborepo \
  --from-scope repo \
  --scope mars
```

## 5. `init-project`가 함께 처리하는 작업

Project Identity 변경 외에도 다음 초기 작업을 수행합니다.

### Local Environment 파일

파일이 존재하지 않는 경우 Example을 기반으로 생성합니다.

```txt
.env.example
  → .env.local

.env.test.example
  → .env.test.local

.env.e2e.example
  → .env.e2e.local
```

Project Identity 치환은 위의 세 Example Environment 파일에만 적용합니다. 기존 `.env`, `.env.local`, `.env.test.local`, `.env.e2e.local`, `.env.production` 등 다른 Environment 파일은 내용을 읽거나 치환하지 않습니다.

이미 존재하는 Local Environment 파일은 덮어쓰지 않으므로, 초기화 전에 만들었다면 DB 이름과 Session Cookie Name 같은 프로젝트별 값은 직접 확인해야 합니다.

### 기존 생성물 정리

초기화 전에 남아 있을 수 있는 생성물을 정리합니다.

대표적인 대상:

```txt
node_modules
.turbo
.next
dist
coverage
out
```

초기화 이후 새로운 Project Identity를 기준으로 다시 Dependency를 설치합니다.

### Lockfile

`pnpm-lock.yaml`은 문자열 치환 대상으로 직접 수정하지 않습니다.

Project Name과 Package Scope를 변경한 뒤:

```bash
pnpm install --no-frozen-lockfile
pnpm format
```

을 실행하여 Lockfile과 Source Format을 현재 Workspace 상태에 맞춥니다. Scope 변경 직후에는 기존 Lockfile과 Manifest가 다르므로 첫 설치에 `--frozen-lockfile`을 사용하지 않습니다.

갱신된 `pnpm-lock.yaml`을 새 프로젝트에 포함하고, 이후 재설치나 CI에서는 다음 명령을 사용합니다.

```bash
pnpm install --frozen-lockfile
```

## 6. Dry Run과 Git History

실제 변경 전에 결과를 확인하려면 `--dry-run`을 사용합니다.

```bash
node tooling/scripts/src/init-project.ts athena-doctrine \
  --scope athena \
  --dry-run
```

`--dry-run`에서는 파일을 변경하지 않고 변경 예정 범위를 출력합니다.

새 프로젝트에서 Boilerplate의 기존 Git History를 제거하려면:

```bash
node tooling/scripts/src/init-project.ts athena-doctrine \
  --scope athena \
  --remove-git
```

을 사용합니다.

기존 History를 유지하려면:

```bash
node tooling/scripts/src/init-project.ts athena-doctrine \
  --scope athena \
  --keep-git
```

을 사용합니다.

`--remove-git`과 `--keep-git`은 동시에 사용할 수 없습니다.

기존 Git History를 제거했다면 초기화 이후 새로운 Repository를 시작할 수 있습니다.

```bash
git init
git add .
git commit -m "chore: 프로젝트 초기화"
```

Commit 규칙은 `18_컨벤션.md`를 따릅니다.

## 7. `init-project`가 하지 않는 작업

`init-project`는 Project Identity와 Local Bootstrap까지만 담당합니다.

다음 작업은 자동으로 수행하지 않습니다.

```txt
Dependency 설치

실제 Secret 입력

외부 Provider 연결

Prisma Client 생성

Database Schema 반영

Migration 실행

Seed

Test 실행

개발 서버 실행
```

초기화 Script와 실제 Infrastructure 설정을 분리하여 각 단계의 책임과 실패 원인을 명확하게 유지합니다.

## 8. Dependency와 Environment 설정

Project Identity 초기화가 끝나면 Dependency를 설치합니다.

```bash
pnpm install --no-frozen-lockfile
pnpm format
```

Package Scope가 바뀌면 Import 경로의 문자열 길이도 바뀌어 기존 줄바꿈이 Prettier 규칙과 달라질 수 있습니다. 따라서 첫 설치 직후 `pnpm format`을 실행한 다음 `pnpm check`로 검증합니다.

이후 생성된 Local Environment 파일을 확인하고 개발 환경에 필요한 값을 입력합니다. 생성은 값 설정과 외부 서비스 연결을 완료하지 않습니다.

```txt
.env.local

.env.test.local
.env.e2e.local
```

일반 개발 환경은 `.env.local`을 사용합니다.

각 파일의 `DATABASE_URL`과 `DIRECT_URL`을 같은 목적의 Database로 설정합니다. 개발·Integration Test·E2E Database는 서로 분리합니다. Test와 E2E는 데이터를 정리하므로 실제 사용자 데이터가 있는 Database를 지정하지 않습니다.

- `.env.local`: 개발 DB 연결과 세 OAuth Provider의 Client ID / Secret을 설정합니다. 실제 로그인에는 Provider 콘솔에서 발급한 값과 앱별 Callback 등록이 필요합니다. Callback 주소는 [Auth Package 안내](../packages/auth/README.md#oauth-callback-url)를 따릅니다.
- `.env.test.local`: Test 전용 DB를 설정합니다. Example의 OAuth 값은 외부 통신을 하지 않는 자동 검증용 가짜 값이므로 실제 OAuth Secret이 필요하지 않습니다.
- `.env.e2e.local`: E2E 전용 DB와 `E2E_AUTH_SECRET`을 설정합니다. OAuth 값과 인증 Session Fixture는 자동 검증용이며 실제 Provider 로그인을 검증하지 않습니다.

외부 로그인을 연결하기 전의 최소 실행·Build 검증에 사용할 가짜 OAuth 값과 기본 Console Mailer의 범위는 [로컬 검증과 외부 서비스 설정](./06_환경변수.md#95-로컬-검증과-외부-서비스-설정)을 따릅니다. 실제 로그인과 메일 발송은 발급받은 Credential로 별도 확인합니다. 환경변수의 분류, Server / Client Boundary, Secret 관리 기준도 같은 문서에서 관리합니다.

## 9. Database 초기화

먼저 [Database 문서의 로컬 개발 환경](./07_데이터베이스.md#171-로컬-postgresql-준비)에 따라 PostgreSQL과 개발·Test·E2E 전용 Database를 준비합니다. Example URL의 접속 계정·비밀번호·Port·DB 이름을 실제 준비한 환경과 일치시킵니다.

개발 환경의 필수 Environment Variable을 설정한 뒤 Schema를 반영합니다.

기본적인 최초 개발 환경에서는:

```bash
pnpm db:generate
pnpm db:push
pnpm db:seed
```

순서를 사용할 수 있습니다.

역할:

```txt
db:generate
  Prisma Client 생성

db:push
  현재 Prisma Schema를 개발 Database에 반영

db:seed
  초기 개발 데이터 삽입
```

위 `db:push`는 비어 있는 개발 전용 DB의 최초 Schema 준비에 사용합니다. 기존 운영 DB에 그대로 적용하지 않습니다. Migration, Test Database, E2E Database의 상세한 사용 기준은 [Database 문서](./07_데이터베이스.md)와 [Test 전략](./12_테스트_전략.md)을 따릅니다.

Seed의 관리자와 OAuth Account는 가짜 Provider 식별자를 사용하는 개발용 데이터입니다. `admin@example.com`이라는 Seed 이메일만으로 실제 소셜 로그인할 수 없습니다. 최초 실제 관리자를 준비하려면 Web에서 실제 Provider로 가입한 사용자를 확인한 뒤, 개발 DB의 해당 사용자에게 명시적으로 `ADMIN` 권한을 부여해야 합니다. 일반 OAuth 신규 가입은 `USER`이며, 같은 이메일만으로 Seed 계정에 연결되지 않습니다. 개발 환경에서는 `pnpm db:studio`로 본인이 관리하는 DB를 열어 해당 사용자 ID와 Provider 연결을 확인하고 `User.role`을 변경할 수 있습니다. 운영 관리자 권한 부여는 별도의 검토된 운영 절차로 관리합니다.

## 10. 프로젝트 검증과 개발 시작

Database와 Seed까지 준비되었다면 기본 검증을 수행합니다.

```bash
pnpm check
pnpm test
```

구매자 환경에서 전체 설치를 확인하려면 Test / E2E 전용 DB와 환경 설정을 준비한 뒤 다음도 실행합니다.

```bash
pnpm db:test:push
pnpm test:integration
pnpm exec playwright install chromium
pnpm test:e2e
pnpm build
```

`test:e2e`는 E2E 전용 DB의 Schema 반영과 Seed를 포함합니다. Chromium 실행에 필요한 OS 의존성은 사용하는 OS에 맞게 준비합니다. Browser 설정과 E2E 실행 정책은 [Test 전략](./12_테스트_전략.md)을 참고합니다.

검증의 책임과 평상시 변경 범위별 실행 기준은 [Test 전략](./12_테스트_전략.md)과 [개발 워크플로우](./16_개발_워크플로우.md)를 따릅니다.

기본 준비가 끝나면 개발 서버를 실행합니다.

```bash
pnpm dev
```

기본 개발 주소는 Web `http://localhost:3000`, Admin `http://localhost:3001`입니다. 두 Port를 다른 프로세스가 사용하지 않는지 확인합니다.

Production Build 결과를 확인하려면 개발 서버를 종료하고 별도 Terminal 두 개에서 각각 실행합니다.

```bash
pnpm --filter web start --port 3000
```

```bash
pnpm --filter admin start --port 3001
```

각 앱의 `start`는 `next start`이므로 Port를 지정해야 두 앱을 함께 실행할 수 있습니다. 앱 URL과 실제 Port가 일치해야 Callback과 Navigation도 일치합니다. Web 홈·콘텐츠 목록과 Admin 로그인 화면에 접속하고, 실제 OAuth를 설정했다면 로그인 및 권한까지 별도로 확인합니다.

## 11. `pnpm setup:scope`

`pnpm setup:scope`는 새로운 프로젝트를 초기화하는 명령이 아닙니다.

이미 존재하는 프로젝트에서 **Workspace Package Scope만 변경할 때** 사용합니다.

기본 형식:

```bash
pnpm setup:scope <scope-name>
```

예:

```bash
pnpm setup:scope athena
```

현재 Scope가:

```txt
@repo
```

라면:

```txt
@repo
  ↓
@athena
```

로 변경합니다.

현재 Scope는 `tooling/scripts/package.json`에서 자동 감지합니다.

필요한 경우 기존 Scope를 직접 지정할 수 있습니다.

```bash
pnpm setup:scope athena --from repo
```

실제 변경 전 확인:

```bash
pnpm setup:scope athena --dry-run
```

Scope 변경 후에는 Workspace 상태를 다시 동기화하고 검증합니다.

```bash
pnpm install --no-frozen-lockfile
pnpm format
pnpm check
```

필요하면 관련 Test도 실행합니다.

## 12. `init-project`와 `setup:scope`의 차이

두 명령은 목적이 다릅니다.

```txt
node tooling/scripts/src/init-project.ts

  새로운 Boilerplate Instance 초기화

  Project Name 변경
  Package Scope 변경
  Project Prefix 변경
  Session Cookie 변경
  Local Environment 파일 생성
  기존 생성물 정리
  Git History 처리
```

```txt
pnpm setup:scope

  기존 프로젝트의 Package Scope만 변경

  @old
    ↓
  @new
```

새로운 프로젝트를 시작한다면:

```bash
node tooling/scripts/src/init-project.ts <project-name>
```

를 사용합니다.

이미 개발 중인 프로젝트에서 Scope만 변경한다면:

```bash
pnpm setup:scope <scope-name>
```

를 사용합니다.

## 13. 초기화 완료 기준

다음 상태가 되면 기본 프로젝트 초기화가 완료된 것으로 봅니다.

```txt
Repository Directory가 실제 Project Name을 사용한다.

Root package.json이 실제 Project Name을 사용한다.

Workspace Package가 실제 Package Scope를 사용한다.

Dependency 설치가 완료되었다.

필수 Local Environment가 설정되었다.

Prisma Client가 생성되었다.

개발 Database Schema가 준비되었다.

Seed가 정상적으로 실행되었다.

pnpm check가 통과한다.

필요한 Test가 통과한다.

pnpm dev로 Application을 실행할 수 있다.
```

## 15. 빠른 시작

Project Name과 Package Scope가 다른 프로젝트를 새로 시작하는 전체 예:

```bash
git clone <boilerplate-repository-url> athena-doctrine
cd athena-doctrine

node tooling/scripts/src/init-project.ts athena-doctrine \
  --scope athena \
  --dry-run

node tooling/scripts/src/init-project.ts athena-doctrine \
  --scope athena \
  --remove-git

pnpm install --no-frozen-lockfile
pnpm format
```

`.env.local`에 필요한 값을 설정한 뒤:

```bash
pnpm db:generate
pnpm db:push
pnpm db:seed

pnpm check
pnpm test

pnpm dev
```

핵심 순서만 기억하면 다음과 같습니다.

```txt
Clone
  ↓
init-project
  ↓
install
  ↓
format
  ↓
env
  ↓
database
  ↓
seed
  ↓
check
  ↓
dev
```
