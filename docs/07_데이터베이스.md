# 데이터베이스

이 문서는 `boilerplate-turborepo`의 Database Layer 구조와 Prisma 사용 기준을 설명합니다.

Database Layer의 목적은 단순히 Prisma Client를 공통 Package로 옮기는 것이 아니라 다음 경계를 유지하는 것입니다.

```txt
App
  ↓
Domain Service
  ↓
Repository
  ↓
Prisma Client
  ↓
PostgreSQL
```

이 문서는 다음 질문에 대한 기준을 제공합니다.

```txt
Prisma Schema와 Migration은 어디에서 관리하는가?

Runtime Prisma Client와 Script Client는 왜 분리되어 있는가?

Repository는 어디까지 책임지는가?

Transaction은 어느 계층에서 결정하고 실행하는가?

개발, Integration Test, E2E Database는 어떻게 구분하는가?

Seed와 E2E Seed는 어떤 차이가 있는가?

앱과 Domain에서 Prisma를 직접 사용하면 왜 안 되는가?
```

Domain Layer의 세부 구조와 Service 책임은 `08_도메인_레이어.md`에서 설명합니다.

---

# 1. 기본 원칙

Database Layer의 기본 원칙은 다음과 같습니다.

```txt
Database는 데이터를 저장하고 조회한다.

비즈니스 규칙은 Domain이 판단한다.

Prisma는 @repo/database 내부 구현으로 취급한다.

앱과 Domain Service는 Prisma Query를 직접 작성하지 않는다.

Database 접근은 Repository를 통해 수행한다.

Transaction의 필요성은 Use Case가 결정한다.

Migration은 Database Schema 변경 이력이다.

Seed는 개발 편의를 위한 초기 데이터 구성이다.

Integration Test와 E2E는 개발 Database와 분리한다.
```

핵심 흐름:

```txt
App
 ↓
Domain Service
 ↓
Repository
 ↓
Prisma
 ↓
Database
```

역방향 의존성은 만들지 않습니다.

```txt
Database
  ✕ Domain Service를 호출하지 않음

Repository
  ✕ UI 상태를 판단하지 않음

Prisma
  ✕ App에서 직접 호출하지 않음
```

---

# 2. `@repo/database`

Database 기능은 다음 Package에서 관리합니다.

```txt
@repo/database
```

주요 책임:

```txt
Prisma Schema

Migration

Prisma Client

Script용 Prisma Client

Repository

Transaction

Database Error Mapping
```

현재 Public API는 책임별 Subpath로 분리되어 있습니다.

예:

```txt
@repo/database/client
@repo/database/errors
@repo/database/transaction

@repo/database/content
@repo/database/user
@repo/database/user-oauth-account
@repo/database/user-session
```

소비자는 가능한 한 Package의 Public API를 사용하고 `src/*` 내부 구현을 직접 참조하지 않습니다.

---

# 3. 전체 구조

Database Package는 개념적으로 다음과 같이 구성됩니다.

```txt
packages/database/
├─ prisma/
│  ├─ schema.prisma
│  └─ migrations/
│
├─ src/
│  ├─ client.ts
│  ├─ script-client.ts
│  ├─ transaction.ts
│  ├─ errors/
│  └─ [repository domains]/
│
├─ prisma.config.ts
├─ package.json
└─ ...
```

Repository는 Domain 또는 Persistence 대상에 따라 별도 영역으로 나눌 수 있습니다.

현재 예:

```txt
content
user
user-oauth-account
user-session
```

새로운 Model이 생겼다고 반드시 하나의 Repository Package 영역을 추가하는 것은 아닙니다.

조회와 저장 책임을 기준으로 구조를 결정합니다.

---

# 4. Prisma Schema

Prisma Schema는 Database 구조의 Source of Truth입니다.

관리 위치:

```txt
packages/database/prisma/schema.prisma
```

Schema에는 다음과 같은 Persistence 구조를 정의합니다.

```txt
Model

Field

Relation

Index

Unique Constraint

Database Mapping
```

Prisma Schema는 **저장 구조**를 표현합니다.

비즈니스 규칙 전체를 Prisma Schema에 표현하려고 하지 않습니다.

예:

```txt
적절함

email unique
외래키 관계
필수 Column
Database Index
데이터 타입


부적절함

관리자가 자기 자신을 차단할 수 없음
특정 상태에서만 수정 가능
현재 사용자만 주문 취소 가능
```

후자의 규칙은 Domain Layer의 책임입니다.

---

# 5. Schema 변경 기준

Database 구조 변경이 필요하면 먼저 Prisma Schema를 수정합니다.

대표적인 변경:

```txt
새 Model 추가

Field 추가 / 삭제

Relation 변경

Index 추가

Unique Constraint 변경

Column Type 변경
```

변경 후에는 목적에 따라 `db:push` 또는 Migration을 사용합니다.

Schema를 수정하고 Generated Client를 오래된 상태로 방치하지 않습니다.

---

# 6. Migration

Migration은 Database Schema 변경 이력을 관리합니다.

Migration은 다음 목적을 가집니다.

```txt
Schema 변경 이력 보존

환경 간 동일한 Schema 재현

운영 Database 변경 추적

Review 가능한 Database 변경 생성
```

Migration 파일은 Prisma가 관리하는 Migration Directory에 저장합니다.

```txt
packages/database/prisma/migrations/
```

Migration은 Source Code와 마찬가지로 Version Control 대상입니다.

---

## 6.1 `db:migrate`

개발 중 영속적인 Schema 변경 이력을 생성해야 할 때 사용합니다.

```bash
pnpm db:migrate
```

루트 명령은 `@repo/database`의 Prisma Migration 명령으로 연결됩니다.

기본적으로 다음 상황에 사용합니다.

```txt
실제 제품 Schema 변경

새로운 Model 추가

Column 변경

Constraint 변경

향후 배포 환경에서도 재현해야 하는 변경
```

---

## 6.2 `db:push`

현재 Prisma Schema를 Database에 직접 반영합니다.

```bash
pnpm db:push
```

Migration 이력을 생성하는 것과 목적이 다릅니다.

주로 다음과 같은 환경에서 사용할 수 있습니다.

```txt
초기 로컬 Database 구성

임시 개발 Database

Test Database

E2E Database
```

운영 Schema 변경 이력을 `db:push`만으로 관리하지 않습니다.

---

# 7. Prisma Client 생성

Prisma Schema 변경 후 Generated Client가 필요하면 다음 명령을 사용합니다.

```bash
pnpm db:generate
```

`@repo/database`에서는:

```txt
prisma generate
```

를 실행합니다.

Generated Client가 Schema와 일치하지 않으면 TypeScript Type과 실제 Database 구조가 어긋날 수 있으므로 Schema 변경 후 Client 생성 여부를 확인합니다.

CI에서도 Build와 Test 전에 필요한 Prisma Client를 생성합니다.

---

# 8. Runtime Prisma Client

일반 애플리케이션 Runtime에서는:

```txt
packages/database/src/client.ts
```

의 Prisma Client를 사용합니다.

Public API:

```ts
import { prisma } from "@repo/database/client";
```

다만 이 Public API가 존재한다는 것은 앱이나 Domain에서 자유롭게 직접 사용하라는 의미가 아닙니다.

주요 소비자는 Database Package 내부의 Repository입니다.

```txt
Repository
   ↓
prisma
```

---

## 8.1 Connection

Runtime Client는 PostgreSQL Adapter와 Connection Pool을 사용합니다.

개념:

```txt
DATABASE_URL
    ↓
pg Pool
    ↓
PrismaPg
    ↓
PrismaClient
```

현재 Pool은 제한된 Connection 수를 사용하도록 구성되어 있습니다.

이 값은 Deployment 환경과 Database Connection 정책에 영향을 줄 수 있으므로 단순히 성능을 높이기 위해 임의로 증가시키지 않습니다.

---

## 8.2 Development Singleton

개발 환경에서는 Hot Reload 과정에서 Prisma Client와 PostgreSQL Pool이 반복 생성되는 것을 줄이기 위해 `globalThis`에 Instance를 보관합니다.

개념:

```txt
Development

첫 Load
  ↓
Prisma / Pool 생성
  ↓
globalThis에 보관
  ↓
Hot Reload
  ↓
기존 Instance 재사용
```

Production에서는 Runtime Lifecycle에 맡깁니다.

이 패턴은 Business Logic이 아니라 Database Connection Lifecycle을 관리하기 위한 Infrastructure 구현입니다.

---

## 8.3 Prisma Logging

개발 환경에서는 Query, Warning, Error 등을 확인할 수 있도록 더 많은 Prisma Log를 사용할 수 있습니다.

Production에서는 불필요한 Query Log를 줄이고 Error 중심으로 제한합니다.

Database Log에 사용자 개인정보나 Credential을 별도로 추가하여 출력하지 않습니다.

---

# 9. Script Client

CLI Script와 Runtime Application은 실행 환경이 다릅니다.

따라서 Script용 Client를 별도로 제공합니다.

위치:

```txt
packages/database/src/script-client.ts
```

Public API:

```ts
import { disconnectScriptPrisma, scriptPrisma } from "@repo/database/script-client";
```

---

## 9.1 Runtime Client와의 차이

Runtime Client:

```txt
@repo/database/client

애플리케이션 실행 중 사용

@repo/env/server를 통한 환경변수 검증

Runtime Lifecycle에 맞춘 Client 관리
```

Script Client:

```txt
@repo/database/script-client

Seed 등 독립 Node.js Script에서 사용

process.env.DATABASE_URL을 직접 확인

Script 종료 시 명시적인 Disconnect 지원
```

Script는 Next.js Runtime이나 `server-only` 기반 앱 실행 환경과 동일하지 않으므로 별도의 Client 경계를 둡니다.

---

## 9.2 Script 종료

독립 실행 Script는 작업이 끝난 뒤 Connection을 정리해야 합니다.

```ts
await disconnectScriptPrisma();
```

이를 통해:

```txt
Prisma Client Disconnect

PostgreSQL Pool 종료
```

를 명시적으로 수행합니다.

Seed Script가 작업을 끝냈는데 Node.js Process가 Connection 때문에 종료되지 않는 상황을 방지할 수 있습니다.

---

# 10. Repository

Repository는 Domain과 Prisma 사이의 Persistence Boundary입니다.

흐름:

```txt
Domain Service
     ↓
Repository
     ↓
Prisma Client
     ↓
Database
```

Repository는 **데이터를 어떻게 조회하고 저장할 것인가**를 담당합니다.

---

## 10.1 Repository가 담당하는 것

대표적인 책임:

```txt
findById

findMany

create

update

delete

exists

count

Database Query 조건 구성

Pagination Query

Relation Include / Select

Persistence Model 반환

Prisma Error 변환
```

예:

```txt
findUserById

createUser

updateUserStatus

findUserSessionByTokenHash
```

---

## 10.2 Repository가 담당하지 않는 것

Repository에는 비즈니스 판단을 넣지 않습니다.

예:

```txt
관리자가 이 사용자를 차단할 수 있는가?

현재 상태에서 콘텐츠를 공개할 수 있는가?

사용자가 이 주문을 취소할 권한이 있는가?

어떤 상태 전이가 허용되는가?
```

이런 판단은 Domain Service 또는 Permission의 책임입니다.

---

## 10.3 잘못된 Repository 예

다음과 같은 형태는 피합니다.

```txt
blockUserIfAdminCanBlockTarget(...)

publishContentWhenAllowed(...)

cancelOrderIfOwnedByCurrentUser(...)
```

Repository Method 이름에 Business Rule이 들어가기 시작한다면 책임이 섞였는지 검토합니다.

Repository는 보다 Persistence 중심으로 유지합니다.

```txt
updateUserStatus(...)

updateContentStatus(...)

updateOrderStatus(...)
```

실행 여부는 Domain Service가 결정합니다.

---

# 11. Prisma를 직접 사용하지 않는 원칙

다음 계층에서는 Prisma Query를 직접 작성하지 않습니다.

```txt
apps/*

Server Action

View

Feature

Entity

Domain Service

Domain Permission
```

금지 예:

```ts
import { PrismaClient } from "@prisma/client";

const prisma = new PrismaClient();

await prisma.user.findUnique(...);
```

또는:

```ts
import { prisma } from "@repo/database/client";

await prisma.user.findMany(...);
```

를 App이나 Domain Service에서 직접 호출하는 것도 기본적으로 허용하지 않습니다.

---

## 11.1 올바른 흐름

```txt
App
 ↓
Domain Service
 ↓
User Repository
 ↓
Prisma
```

예:

```ts
const result = await getUserService(input);
```

Domain 내부에서는:

```txt
getUserService
  ↓
findUserById Repository
```

형태로 접근합니다.

---

## 11.2 이유

Prisma 직접 접근을 제한하는 이유는 다음과 같습니다.

```txt
Persistence 구현이 Domain으로 누출되는 것을 방지

Prisma Model과 Response DTO 분리

Query 중복 방지

Database 변경 영향 범위 축소

Repository Test 가능

Transaction 조립 위치 명확화

비즈니스 규칙과 저장 규칙 분리
```

특히 Prisma Model을 그대로 UI Response 계약으로 사용하는 구조를 피합니다.

```txt
Prisma Model
    ↓
Mapper
    ↓
Domain Response DTO
    ↓
App
```

DTO와 Mapper의 구체적인 기준은 `08_도메인_레이어.md`에서 설명합니다.

---

# 12. Transaction

공통 Transaction Helper는:

```txt
packages/database/src/transaction.ts
```

에서 제공합니다.

Public API:

```ts
import { transaction, type TransactionClient } from "@repo/database/transaction";
```

개념:

```ts
await transaction(async (database) => {
  // 여러 Repository 작업
});
```

---

## 12.1 Transaction Client

Transaction Callback 내부에서는 일반 Prisma Client 대신 Transaction Client를 사용합니다.

```txt
PrismaClient
   ↓
$transaction
   ↓
TransactionClient
```

Repository가 Transaction Client를 받을 수 있도록 구성하면 동일 Repository를 일반 Query와 Transaction 모두에서 재사용할 수 있습니다.

---

# 13. Transaction을 사용하는 경우

여러 Database 변경이 하나의 비즈니스 작업으로 함께 성공하거나 실패해야 할 때 Transaction을 사용합니다.

예:

```txt
User 생성
+
OAuth Account 생성
```

또는:

```txt
주문 생성
+
재고 변경
+
관련 기록 생성
```

이런 작업 중 일부만 성공하면 데이터 상태가 깨질 수 있습니다.

따라서:

```txt
모두 성공
→ Commit

하나라도 실패
→ Rollback
```

이 필요한 경우 Transaction을 사용합니다.

---

## 13.1 Transaction이 필요하지 않은 경우

단일 Query라고 해서 항상 Transaction Wrapper로 감싸지 않습니다.

예:

```txt
단일 조회

단일 Insert

독립적인 단일 Update
```

Transaction은 비용과 Connection 점유를 발생시키므로 실제 Atomicity가 필요한 경우에 사용합니다.

---

# 14. Transaction 책임 위치

**Transaction 필요 여부는 Repository가 아니라 Domain Service가 판단합니다.**

Repository는 개별 Database Operation을 제공합니다.

```txt
Repository A
  create(...)

Repository B
  update(...)
```

Domain Service가 Use Case를 조립합니다.

```txt
Domain Service
      ↓
transaction(...)
      ↓
Repository A
Repository B
```

이유:

```txt
어떤 작업들이 하나의 Atomic Unit인가?
```

라는 질문은 Persistence 기술이 아니라 비즈니스 Use Case에 의해 결정되기 때문입니다.

---

# 15. Repository와 Transaction

Transaction을 지원해야 하는 Repository는 Database Client를 주입받을 수 있도록 구성할 수 있습니다.

개념:

```txt
Repository
  database = prisma
```

일반 호출:

```txt
Repository(prisma)
```

Transaction 내부:

```txt
transaction(database => {
  Repository(database)
})
```

Repository가 직접 새로운 Prisma Client를 생성하지 않습니다.

---

# 16. Database Error

Prisma의 Raw Error를 App이나 UI까지 그대로 전달하지 않습니다.

기본 흐름:

```txt
Prisma Error
    ↓
Database Error Mapping
    ↓
Domain Error
    ↓
ActionResult
    ↓
UI
```

Database Package는 Persistence 관점의 오류를 정규화할 수 있습니다.

예:

```txt
Unique Constraint Violation

Record Not Found

Connection Error
```

사용자에게 어떤 메시지를 보여줄 것인지는 Database Layer가 결정하지 않습니다.

Error 흐름의 세부 기준은 `08_도메인_레이어.md`와 `09_Server_Actions.md`에서 다룹니다.

---

# 17. 개발 Database

로컬 개발에서는 개발 전용 PostgreSQL Database를 사용합니다.

일반적인 초기 흐름:

```txt
.env.local 구성
      ↓
DATABASE_URL
DIRECT_URL
      ↓
pnpm db:generate
      ↓
pnpm db:push 또는 db:migrate
      ↓
pnpm db:seed
      ↓
pnpm dev
```

Schema 변경 이력을 남겨야 하는 개발 작업에서는 Migration을 사용합니다.

단순 초기 Database 구성에서는 현재 Schema를 직접 반영하는 `db:push`를 사용할 수 있습니다.

---

# 18. Database 환경변수

Database 연결은 Server Environment를 사용합니다.

대표적인 값:

```txt
DATABASE_URL
DIRECT_URL
```

Runtime Prisma Client는 검증된:

```txt
@repo/env/server
```

의 값을 사용합니다.

Script Client는 Script Runtime에서 `DATABASE_URL`을 직접 읽습니다.

환경별 값 관리 기준은 `06_환경변수.md`에서 설명합니다.

---

# 19. Test Database

Integration Test는 개발 Database와 분리된 Database를 사용합니다.

목적:

```txt
개발 데이터 오염 방지

테스트 간 재현성 확보

Schema 변경 검증

실제 Repository와 PostgreSQL 통합 검증
```

Test Database용 명령:

```bash
pnpm db:test:generate
pnpm db:test:push
pnpm db:test:migrate
```

현재 Package Script에서는 Test Runtime으로 실행하기 위해:

```txt
NODE_ENV=test
```

를 사용합니다.

## 19.1 Integration Test 흐름

일반적인 흐름:

```txt
.env.test
.env.test.local
      ↓
Test DATABASE_URL
      ↓
db:test:generate
      ↓
db:test:push
      ↓
Integration Test
```

CI에서도 별도의 PostgreSQL Database를 준비하고 Test Schema를 반영한 뒤 Integration Test를 실행합니다.

# 20. E2E Database

E2E Test 역시 개발 및 Integration Test Database와 분리합니다.

개념:

```txt
Development DB

Integration Test DB

E2E DB
```

세 환경을 별도로 유지합니다.

E2E Database 관련 루트 명령:

```bash
pnpm db:e2e:generate
pnpm db:e2e:push
pnpm db:e2e:migrate
pnpm db:e2e:seed
```

E2E 명령은:

```txt
E2E=true
```

환경을 사용하여 E2E Runtime임을 명시합니다.

# 21. Seed

일반 개발 Seed는:

```bash
pnpm db:seed
```

를 사용합니다.

Seed의 목적은 로컬 개발에 필요한 기본 데이터를 재현 가능하게 만드는 것입니다.

예:

```txt
개발용 사용자

예제 콘텐츠

기본 Reference Data

개발 확인용 데이터
```

Seed는 Application Runtime의 일부가 아닙니다.

```txt
tooling/scripts
      ↓
scriptPrisma
      ↓
Database
```

형태의 독립 Script로 실행합니다.

---

# 22. Seed에 넣지 말아야 하는 것

일반 Seed는 다음 용도로 사용하지 않습니다.

```txt
Production Migration 대체

Production 운영 데이터 수정

실제 사용자 개인정보 삽입

테스트 한 케이스만을 위한 임시 데이터

실행할 때마다 결과가 무작위로 크게 변하는 데이터
```

가능하면 동일한 초기 상태를 반복해서 만들 수 있도록 구성합니다.

---

# 23. E2E Seed

E2E Seed는 일반 개발 Seed와 목적이 다릅니다.

실행:

```bash
pnpm db:e2e:seed
```

목적:

```txt
Playwright가 기대하는 고정된 사용자

로그인 Fixture

정해진 상태의 Domain Data

E2E Scenario 시작 상태
```

E2E Test가 Seed 데이터의 우연한 변화에 의존하지 않도록 가능한 한 결정적인 데이터를 생성합니다.

---

## 23.1 일반 Seed와 E2E Seed

```txt
Development Seed
  사람이 개발 화면을 확인하기 위한 데이터

E2E Seed
  자동화된 Scenario가 기대하는 고정 Fixture
```

따라서 두 Seed를 무조건 하나로 합치지 않습니다.

공유할 수 있는 저수준 Helper가 있다면 재사용할 수 있지만 목적과 데이터 계약은 구분합니다.

---

# 24. E2E 실행 흐름

루트 E2E 명령은 Database 준비를 포함합니다.

개념:

```txt
E2E Database 준비
      ↓
Schema 반영
      ↓
E2E Seed
      ↓
Next.js App 실행
      ↓
Playwright
```

이를 통해 E2E Test가 개발자의 현재 로컬 데이터 상태에 의존하지 않도록 합니다.

구체적인 Test 실행 정책은 `12_테스트_전략.md`에서 설명합니다.

# 25. Prisma Studio

개발 중 Database 상태를 확인할 때 다음 명령을 사용할 수 있습니다.

```bash
pnpm db:studio
```

Prisma Studio는 개발 및 디버깅 도구입니다.

Studio에서 데이터를 직접 수정했다고 해서 해당 변경이 Seed, Migration 또는 Application Logic에 반영되는 것은 아닙니다.

재현해야 하는 구조 변경:

```txt
Migration
```

재현해야 하는 초기 데이터:

```txt
Seed
```

로 각각 코드화합니다.

# 26. Prisma Config

Prisma CLI 관련 공통 설정은:

```txt
packages/database/prisma.config.ts
```

에서 관리합니다.

이 파일은 Prisma CLI가 Schema, Migration, Database Connection 등 필요한 설정을 해석하기 위한 진입점입니다.

Database CLI 동작을 변경해야 할 때는 다음을 함께 검토합니다.

```txt
prisma.config.ts

package.json의 db:* Script

환경변수 Loading

개발 / Test / E2E Database 흐름
```

CLI 설정을 앱 코드에 분산하지 않습니다.

# 27. Database Package Export

Database Package는 필요한 Persistence API만 명시적으로 export합니다.

현재 예:

```txt
@repo/database/client
@repo/database/errors
@repo/database/transaction

@repo/database/content
@repo/database/user
@repo/database/user-oauth-account
@repo/database/user-session
```

내부 파일 경로를 직접 참조하지 않습니다.

지양:

```ts
import ... from "@repo/database/src/user/user.repository";
```

권장:

```ts
import ... from "@repo/database/user";
```

Public API 정책의 전체 기준은 `04_패키지_구조.md`에서 설명합니다.

# 28. 새로운 Repository 추가 기준

새로운 Prisma Model이 추가되었다고 항상 즉시 별도 Repository를 만들지는 않습니다.

다음 질문을 기준으로 판단합니다.

```txt
어떤 Domain Use Case에서 사용되는가?

기존 Repository 책임에 포함되는가?

독립적인 조회 / 저장 책임이 있는가?

여러 Service에서 재사용되는 Persistence Operation인가?

별도의 Public API가 필요한가?
```

Repository 이름과 구조는 Database Table 이름을 기계적으로 복사하기보다 Persistence 책임을 표현해야 합니다.

# 29. Repository 변경 시 확인 사항

```txt

Migration

Generated Client

Repository Test

Integration Test

Transaction

E2E Seed

```

Database 구조 변경이 UI까지 직접 전파되지 않도록 계층을 유지합니다.

# 30. 테스트 기준

Database Package의 순수 Helper는 Unit Test로 검증할 수 있습니다.

실제 Repository Query는 가능한 한 실제 Test Database를 사용하는 Integration Test로 검증합니다.

```txt
Unit Test

Error Mapper
Pure Helper
Query와 무관한 Utility


Integration Test

Repository
Transaction
Constraint
Relation
실제 PostgreSQL 동작
```

Prisma 자체를 Mock하여 실제 Query 동작을 흉내 내는 테스트보다 Repository의 중요한 Persistence 동작은 Test Database를 통해 검증하는 것을 우선합니다.

세부 테스트 전략은 `12_테스트_전략.md`에서 설명합니다.

# 31. 변경 절차 예시

새로운 Persistence 구조를 추가할 때의 일반적인 흐름은 다음과 같습니다.

```txt
1. Domain 요구사항 확인

2. Prisma Schema 변경

3. Migration 생성 또는 개발 DB 반영

4. Prisma Client 생성

5. Repository 구현

6. Repository Integration Test

7. Domain Mapper / DTO / Service 연결

8. 필요한 Transaction 조합

9. 필요한 Seed / E2E Seed 수정

10. 전체 Test 및 Build
```

Database Schema부터 먼저 만들고 나중에 비즈니스 의미를 억지로 맞추는 방식은 피합니다.

# 32. 피해야 하는 구조

```txt
 ↓

```


```txt

 ↓
```


### Database에서 상위 계층 호출

```txt
 ↓

```

올바른 방향:

```txt

 ↓
Domain
 ↓
Repository
```

# 35. 핵심 원칙

```txt
Prisma Schema는 Database 저장 구조의 Source of Truth다.

Migration은 Schema 변경 이력을 관리한다.

Prisma Client는 @repo/database 내부 구현으로 취급한다.

App은 Prisma를 직접 사용하지 않는다.

Server Action은 Prisma를 직접 사용하지 않는다.

Domain Service는 Prisma를 직접 사용하지 않는다.

Database 접근은 Repository를 통해 수행한다.

Repository는 Persistence만 담당한다.

Business Rule은 Domain이 판단한다.

Transaction 필요 여부는 Domain Use Case가 결정한다.

Runtime Client와 Script Client의 책임을 분리한다.

Script는 종료 시 Database Connection을 정리한다.

개발, Integration Test, E2E Database를 분리한다.

Seed와 E2E Seed의 목적을 구분한다.

Database Error를 UI까지 그대로 노출하지 않는다.

Schema 변경 시 Migration, Repository, Test, Seed의 영향을 함께 검토한다.
```
