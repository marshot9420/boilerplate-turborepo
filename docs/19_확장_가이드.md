# 확장 가이드

이 문서는 `boilerplate-turborepo`를 기반으로 프로젝트의 규모와 기능이 커질 때 새로운 App, Domain, Workspace Package, Infrastructure Package, 공통 설정 및 Tooling을 어떤 기준으로 추가해야 하는지 설명합니다.

이 문서의 핵심은 **공통화 자체를 목표로 하지 않는 것**입니다.

기본 원칙:

```txt
가까운 곳에 둔다.

실제 책임이 생겼을 때 분리한다.

실제 공유가 발생했을 때 승격한다.

이름이 비슷하다는 이유만으로 합치지 않는다.

미래의 재사용 가능성만으로 Package를 만들지 않는다.

App은 조립한다.

Domain은 판단한다.

Database는 저장한다.

Infrastructure Package는 외부 시스템과 연결한다.

공통 기반은 아래 계층에 둔다.
```

프로젝트 확장은 다음 방향을 기본으로 합니다.

```txt
Component 내부
  ↓
Slice 내부
  ↓
App 내부 공통
  ↓
Workspace Package
```

처음부터 가장 높은 공통 계층에 코드를 두는 것이 아니라, 실제 사용 범위가 넓어질 때 필요한 만큼 승격합니다.

---

## 1. 확장의 기본 원칙

새로운 구조를 추가하기 전에 먼저 다음 질문을 확인합니다.

```txt
새로운 독립적인 책임이 생겼는가?

기존 책임에 포함시킬 수 없는가?

실제로 두 곳 이상에서 사용되는가?

같은 이름이 아니라 같은 의미와 정책을 공유하는가?

변경 이유가 기존 코드와 다른가?

독립적인 Public API가 필요한가?

Dependency Boundary를 별도로 관리할 가치가 있는가?
```

위 질문에 명확한 이유가 없다면 새로운 App이나 Package를 만드는 것보다 기존 위치에 두는 것을 우선합니다.

---

# 2. 확장 단위

이 Repository에서 주요 확장 단위는 다음과 같습니다.

```txt
App
  독립적인 사용자 경험과 Runtime

Domain
  독립적인 Business Concept

Workspace Package
  여러 Workspace가 공유하는 독립 책임

Infrastructure Package
  외부 시스템과 연결하는 기술적 책임

App 내부 Slice / Segment
  특정 App 안에서만 필요한 기능과 UI

Tooling
  Repository 개발 경험과 자동화

Config
  여러 Workspace가 공유하는 개발 설정
```

각 단위는 서로 다른 이유로 만들어집니다.

---

# 3. 새로운 App을 추가하는 기준

새로운 App은 단순히 새로운 Page가 필요하다는 이유로 만들지 않습니다.

App은 **독립적인 사용자 경험, 접근 정책, Runtime 또는 배포 단위**가 존재할 때 추가합니다.

예:

```txt
고객용 서비스

관리자 서비스

공개 콘텐츠 사이트

파트너 전용 서비스

독립적인 운영 Console
```

---

## 3.1 App 분리가 적절한 경우

다음 조건 중 여러 개가 성립한다면 새로운 App을 검토합니다.

```txt
사용자 집단이 명확하게 다르다.

Navigation 구조가 독립적이다.

Authentication 또는 Authorization 정책이 크게 다르다.

배포 주기나 운영 책임이 다르다.

Root Layout과 Metadata 정책이 독립적이다.

사용하는 UI Design Language가 크게 다르다.

환경변수 구성이 다르다.

독립적인 Domain 조합을 가진다.

하나의 App에 넣으면 Route와 Layout이 지나치게 복잡해진다.
```

예:

```txt
apps/web
  일반 사용자

apps/admin
  관리자
```

처럼 목적이 명확히 다르면 App 분리가 자연스럽습니다.

---

## 3.2 App을 추가하지 않는 경우

다음 이유만으로 App을 추가하지 않습니다.

```txt
Page가 많아졌다.

특정 Domain이 커졌다.

URL Prefix가 다르다.

일부 Layout이 다르다.

몇 개의 Component가 다르다.

Feature 수가 증가했다.
```

이 경우 먼저 다음 구조로 해결할 수 있는지 확인합니다.

```txt
Route Group

Layout

View Slice

Feature Slice

Entity Slice

App-local Shared
```

---

# 4. 새로운 App 추가 절차

예를 들어 새로운 `partner` App이 필요하다면 다음 순서로 진행합니다.

```txt
1. App의 사용자와 책임 정의

2. apps/partner 생성

3. package.json 작성

4. Next.js / TypeScript / ESLint 설정 연결

5. Environment 설정

6. Design System 사용 범위 결정

7. App 내부 Layer 구조 준비

8. Root Layout / Metadata 구성

9. 인증 및 접근 정책 구성

10. Turbo Task 확인

11. Test / E2E 환경 연결

12. Boundary 검사
```

---

## 4.1 기본 App 구조

필요한 Directory만 생성합니다.

예:

```txt
apps/partner/
├─ src/
│  ├─ app/
│  ├─ actions/
│  ├─ entities/
│  ├─ features/
│  ├─ views/
│  ├─ shared/
│  ├─ config/
│  ├─ constants/
│  ├─ hooks/
│  ├─ libs/
│  ├─ types/
│  └─ utils/
├─ package.json
├─ tsconfig.json
└─ next.config.ts
```

모든 Directory를 처음부터 생성할 필요는 없습니다.

```txt
책임이 생기면 만든다.
```

는 원칙을 유지합니다.

---

# 5. App 추가 시 Package Dependency

새로운 App은 기존 Architecture Boundary를 따릅니다.

개념적으로 App은 다음 Package를 사용할 수 있습니다.

```txt
@repo/core
@repo/domain
@repo/database
@repo/auth
@repo/design-system
@repo/env
Infrastructure Package
```

실제 허용 관계는 `05_의존성_경계.md`를 따릅니다.

App을 추가하면서 기존 Package가 새 App을 Import하게 만들지 않습니다.

```txt
Package
  → App

```

방향의 Dependency는 만들지 않습니다.

---

# 6. App 간 코드 공유

다음과 같은 직접 App 간 Import는 사용하지 않습니다.

```txt
apps/web
  ↓
apps/admin
```

예:

```ts
import { Something } from "../../../admin/src/...";
```

금지합니다.

두 App에서 같은 책임이 필요하다면 다음 중 하나를 판단합니다.

```txt
실제로 같은 책임인가?
  ↓
Workspace Package 후보

이름만 비슷하고 UX가 다른가?
  ↓
각 App에 유지
```

---

# 7. 새로운 Domain 추가 기준

Domain은 **독립적인 Business Concept와 규칙을 가진 대상**을 기준으로 추가합니다.

예:

```txt
user
order
payment
content
question
order-claim
```

Domain은 Database Table 단위와 동일하지 않습니다.

```txt
Prisma Model 하나
  ≠
반드시 Domain 하나
```

반대로 하나의 Domain이 여러 Persistence Model을 사용할 수도 있습니다.

---

## 7.1 Domain으로 분리할 가치가 있는 경우

다음과 같은 특성이 있다면 독립 Domain을 검토합니다.

```txt
독립적인 Business 용어가 있다.

고유한 상태 또는 Lifecycle이 있다.

독립적인 Rule이 있다.

독립적인 Permission이 있다.

별도의 Request / Response 계약이 필요하다.

여러 Use Case에서 반복적으로 등장한다.

다른 Domain과 구분되는 Error가 있다.
```

---

## 7.2 Domain을 추가하지 않는 경우

다음 이유만으로 Domain을 만들지 않습니다.

```txt
새 Prisma Model이 생겼다.

UI Component 하나가 생겼다.

상수 몇 개가 필요하다.

Helper 함수가 필요하다.

파일 수가 많아졌다.
```

기존 Domain의 하위 개념이라면 기존 Domain에 유지하는 편이 적절할 수 있습니다.

---

# 8. Domain Boundary 판단

두 개념을 하나의 Domain으로 둘지 나눌지 판단할 때 다음을 확인합니다.

```txt
같은 Business Lifecycle을 공유하는가?

같은 Permission 정책을 공유하는가?

하나 없이 다른 하나가 독립적으로 의미가 있는가?

변경 이유가 동일한가?

Use Case가 서로 강하게 결합되어 있는가?
```

예를 들어:

```txt
Order
OrderItem
```

이 강한 하나의 Aggregate 성격을 가진다면 반드시 별도 Domain으로 나눌 필요는 없습니다.

반면:

```txt
Order
Payment
```

처럼 Lifecycle과 외부 Provider 연동, 상태 규칙이 크게 다르다면 별도 Domain이 자연스러울 수 있습니다.

---

# 9. 새로운 Domain 추가 절차

기본적으로 Generator를 사용할 수 있습니다.

```bash
pnpm generate domain content
```

Persistence까지 필요한 경우:

```bash
pnpm generate domain content --repository
```

이후 실제 요구사항에 맞게 Scaffold를 수정합니다.

기본 흐름:

```txt
Business Concept 정의
  ↓
Domain Constant / Schema
  ↓
DTO
  ↓
Error
  ↓
Permission / Rule
  ↓
Mapper
  ↓
Service
  ↓
Test
```

Persistence가 있다면:

```txt
Prisma Model
  ↓
Prisma Client Generate
  ↓
Repository
  ↓
Repository Test
  ↓
Domain Service
```

구체적인 Domain 역할은 `08_도메인_레이어.md`를 따릅니다.

---

# 10. Domain Generator 결과는 고정 구조가 아니다

Generator가 다음 파일을 만들었다고 해서:

```txt
constant
dto
error
mapper
permission
schema
service
```

모두 영구적으로 유지해야 하는 것은 아닙니다.

필요 없는 파일:

```txt
삭제
```

책임이 커진 파일:

```txt
분리
```

합니다.

예:

```txt
order.service.ts
```

가 커진다면:

```txt
services/
├─ create-order.service.ts
├─ cancel-order.service.ts
└─ get-order-detail.service.ts
```

처럼 발전할 수 있습니다.

Generator는 시작점을 제공할 뿐 최종 구조를 결정하지 않습니다.

---

# 11. 새로운 Workspace Package 추가 기준

Workspace Package는 **Repository 여러 영역에서 공유되는 독립적인 책임과 Public API가 존재할 때** 추가합니다.

Package를 만드는 비용도 존재합니다.

```txt
package.json

Public Export

Dependency 관리

Boundary 관리

Build / Type Check

Test

문서

Version Compatibility
```

따라서 작은 Utility 하나를 공유하기 위해 Package를 추가하지 않습니다.

---

# 12. Package 추가를 검토할 조건

다음 조건이 여러 개 성립할 때 Package 승격을 검토합니다.

```txt
두 개 이상의 App 또는 Package에서 실제로 사용된다.

독립적인 책임을 설명할 수 있다.

Public API를 명확하게 정의할 수 있다.

Dependency 방향을 명확하게 제한할 수 있다.

App Context 없이도 의미가 있다.

독립적으로 Test할 가치가 있다.

앞으로 변경되는 이유가 사용하는 App과 다르다.
```

---

# 13. Package를 만들지 않는 경우

다음 상황에서는 Package로 승격하지 않는 것을 우선합니다.

```txt
한 App에서만 사용된다.

두 Component가 비슷해 보인다.

미래에 공유할 것 같다.

코드가 길다.

Directory가 커졌다.

파일 수가 많다.
```

코드 크기와 Package Boundary는 같은 문제가 아닙니다.

---

# 14. Workspace Package의 기본 구조

새 Runtime Package의 기본 형태:

```txt
packages/<name>/
├─ src/
│  ├─ index.ts
│  └─ ...
├─ package.json
└─ tsconfig.json
```

필요한 경우:

```txt
test
client.ts
server.ts
```

등의 Public Boundary를 추가합니다.

Package 구조는 실제 책임에 맞춰 결정합니다.

---

# 15. Package 이름

Workspace Package Scope는 프로젝트 초기화에서 설정된 값을 사용합니다.

Boilerplate 기본:

```txt
@repo/<package>
```

예:

```txt
@repo/core
@repo/domain
@repo/database
```

프로젝트 초기화 후:

```txt
@athena/core
@athena/domain
@athena/database
```

처럼 변경될 수 있습니다.

새 Package도 현재 Scope를 사용합니다.

---

# 16. Package Public API

Package 내부 구현을 사용하는 Workspace에 직접 노출하지 않습니다.

권장:

```ts
import { something } from "@repo/package";
```

또는 명시적인 Subpath:

```ts
import { something } from "@repo/package/server";
```

지양:

```ts
import { something } from "@repo/package/src/internal/something";
```

Public API는 `package.json`의 `exports`와 Public Entry를 통해 관리합니다.

---

# 17. Package Export

Package Public API에서는 명시적인 Named Export를 사용합니다.

권장:

```ts
export { something } from "./something";
export type { Something } from "./something";
```

지양:

```ts
export * from "./something";
```

Client / Server Boundary가 존재한다면:

```txt
client.ts
server.ts
```

를 구분할 수 있습니다.

Server 전용 Entry에서는:

```ts
import "server-only";
```

를 사용합니다.

세부 Convention은 `18_컨벤션.md`를 따릅니다.

---

# 18. Infrastructure Package란

Infrastructure Package는 **Business Rule을 결정하지 않고 외부 시스템과 연결하는 기술적 메커니즘**을 제공합니다.

예:

```txt
@repo/storage
@repo/mailer
```

확장 후보:

```txt
@repo/analytics
@repo/observability
@repo/rate-limit
```

다만 후보가 있다는 이유만으로 미리 만들지 않습니다.

---

# 19. Infrastructure Package 추가 기준

다음 조건을 만족할 때 Infrastructure Package를 검토합니다.

```txt
외부 Provider와 연결한다.

여러 App 또는 Domain Use Case에서 사용할 수 있다.

Provider-specific 코드를 Application에서 숨길 가치가 있다.

Secret 또는 Environment 접근이 필요하다.

Retry / Timeout / Error Mapping 같은 기술 정책이 있다.

Provider 교체 가능성을 Boundary로 관리할 가치가 있다.
```

---

# 20. Storage Package

Storage Package는 다음과 같은 책임을 가질 수 있습니다.

```txt
Upload Authorization

Object Key 생성

File 삭제

File Metadata 조회

Provider Error Mapping

Provider Client 초기화
```

Storage Package가 판단하지 않는 것:

```txt
이 사용자가 상품 이미지를 업로드할 수 있는가?

상품당 이미지가 몇 개인가?

프로필 이미지를 삭제할 수 있는가?
```

이런 판단은 Domain 또는 Application Use Case의 책임입니다.

구분:

```txt
Domain
  업로드 가능한가?

Storage
  실제로 어떻게 업로드하는가?
```

---

# 21. Mailer Package

Mailer Package는 다음 책임을 가질 수 있습니다.

```txt
Email Provider 연결

Email 발송

Provider Error Mapping

공통 Transport 설정
```

Mailer Package가 판단하지 않는 것:

```txt
언제 주문 완료 메일을 보낼 것인가?

누구에게 환불 알림을 보낼 것인가?

이 사용자가 알림 수신 대상인가?
```

이런 정책은 Domain 또는 Use Case에서 결정합니다.

구분:

```txt
Domain / Service
  왜, 언제, 누구에게 보낼 것인가?

Mailer
  어떻게 보낼 것인가?
```

---

# 22. Provider 이름을 Business 코드에 퍼뜨리지 않는다

예를 들어 Storage Provider가 변경될 가능성이 있다면 Business 코드 전체에서 Provider 이름을 직접 사용하지 않습니다.

지양:

```txt
createCloudflareProductImage
deleteCloudflareAvatar
```

Provider가 Business Meaning이 아니라면:

```txt
authorizeProductImageUpload
deleteStoredObject
```

등의 책임 중심 API를 검토합니다.

단, Provider-specific 기능 자체를 직접 사용하는 Package 내부에서는 Provider 이름을 사용할 수 있습니다.

---

# 23. Infrastructure Package와 Environment

Infrastructure Package가 공통 Secret을 필요로 한다면 `@repo/env`와의 Dependency가 필요한지 먼저 Architecture Boundary를 검토합니다.

단순히 Environment를 사용한다는 이유로 무조건 각 Package가 `process.env`를 직접 읽지 않습니다.

원칙:

```txt
Environment 접근 위치를 제한한다.

Secret Boundary를 명확하게 한다.

Client로 Provider Secret이 전달되지 않게 한다.
```

구체적인 기준은 `06_환경변수.md`와 `17_보안_및_운영_기본정책.md`를 따릅니다.

---

# 24. Infrastructure Package는 Business Domain을 모른다

Infrastructure Package에서 다음처럼 Domain 객체 자체에 강하게 결합하지 않습니다.

지양:

```ts
sendOrderRefundApprovedEmail(order: Order)
```

Infrastructure Package의 역할이 범용 메일 전송이라면 더 낮은 수준의 입력 계약을 가지는 편이 자연스럽습니다.

Business-specific Template 자체가 별도 책임으로 필요하다면 위치를 따로 판단합니다.

핵심은:

```txt
Infrastructure
  외부 연결 메커니즘

Domain
  Business 판단
```

을 섞지 않는 것입니다.

---

# 25. 앱 내부 코드와 Workspace Package 사이의 승격

코드는 기본적으로 사용하는 곳 가까이에 둡니다.

가장 작은 Scope에서 시작합니다.

```txt
Component
  ↓
Slice
  ↓
App
  ↓
Workspace
```

---

# 26. Component 내부 Colocation

하나의 Component에서만 사용하는 코드는 Component와 함께 둡니다.

예:

```txt
order-table/
├─ order-table.tsx
├─ order-table.test.tsx
├─ order-table-row.tsx
└─ order-table.utils.ts
```

이를 처음부터:

```txt
apps/admin/src/utils
```

로 올리지 않습니다.

---

# 27. Slice 내부 승격

같은 Slice의 여러 Component에서 사용된다면 Slice Segment로 올릴 수 있습니다.

예:

```txt
features/order/cancel-order/
├─ ui/
├─ hooks/
├─ lib/
└─ types/
```

판단:

```txt
Component 하나
  → Component와 colocate

같은 Slice의 여러 곳
  → Slice Segment
```

---

# 28. App 내부 승격

서로 다른 Slice가 사용하지만 하나의 App에만 필요한 경우 App-level 공통 영역으로 올릴 수 있습니다.

예:

```txt
apps/admin/src/shared
apps/admin/src/hooks
apps/admin/src/constants
apps/admin/src/libs
```

단순히 두 Slice에서 쓴다고 바로 Workspace Package로 올리지 않습니다.

---

# 29. Workspace Package 승격

두 개 이상의 App 또는 Package에서 실제로 공유되고, App Context와 분리 가능한 책임이라면 Workspace Package를 검토합니다.

예:

```txt
apps/web
        ↘
          공통 책임
        ↗
apps/admin
```

이때 다음을 확인합니다.

```txt
구현만 같은가?

정책도 같은가?

두 App이 항상 같이 변경되어야 하는가?

독립적인 Public API가 가능한가?
```

---

# 30. 코드 중복과 책임 공유를 구분한다

코드가 비슷하다는 사실만으로 공통화하지 않습니다.

예:

```txt
Admin ProductCard
Web ProductCard
```

가 이름과 일부 Markup이 비슷하더라도:

```txt
사용 목적
사용자
Interaction
Design
변경 이유
```

가 다르면 각각 유지하는 것이 적절할 수 있습니다.

반면 날짜 Formatting처럼 의미와 정책까지 동일하다면 공통화 후보가 될 수 있습니다.

---

# 31. 승격 판단 질문

코드를 상위 Scope로 올리기 전에 다음 질문을 사용합니다.

```txt
현재 두 곳 이상에서 사용되는가?

같은 책임인가?

같은 정책을 공유하는가?

같은 이유로 변경되는가?

하위 Context의 용어를 제거할 수 있는가?

상위 계층으로 옮겨도 API가 자연스러운가?

새 Dependency를 만드는 비용보다 이점이 큰가?
```

대부분 `아니다`라면 현재 위치에 유지합니다.

---

# 32. 잘못된 공통화 신호

다음과 같은 상황은 승격을 다시 검토해야 한다는 신호입니다.

```txt
공통 함수에 App 이름이 등장한다.

공통 Package에 Domain-specific 조건문이 계속 늘어난다.

옵션 Prop이 App별 차이를 처리하기 위해 계속 늘어난다.

boolean 옵션이 여러 개 생긴다.

Package가 여러 App 내부 구조를 알고 있다.

공통화를 유지하기 위해 분기문이 더 많아졌다.
```

예:

```txt
if (isAdmin) ...
if (isWeb) ...
if (isPartner) ...
```

가 공통 Component 안에서 계속 늘어난다면 실제로 공통 책임인지 다시 확인합니다.

---

# 33. 승격 이후 Dependency 방향

코드를 Package로 승격했다면 Package가 기존 App을 Import하지 않도록 합니다.

잘못된 구조:

```txt
apps/admin
  ↓
@repo/shared
  ↓
apps/admin
```

또는:

```txt
@repo/package
  ↓
apps/web
```

Package는 사용하는 App보다 낮은 계층에서 독립적으로 존재해야 합니다.

---

# 34. 새로운 공통 설정 Package

Repository 여러 영역에서 같은 Tool 설정을 반복한다면 Config Package를 만들 수 있습니다.

예:

```txt
eslint-config
typescript-config
storybook-config
vitest-config
```

Config Package의 목적은 다음과 같습니다.

```txt
개발 설정의 중복 제거

Repository-wide 기본값 제공

App / Package별 차이를 최소 Override로 표현
```

---

# 35. 공통 설정으로 승격하는 기준

다음 조건을 확인합니다.

```txt
여러 Workspace에서 동일한 설정을 반복하고 있는가?

설정이 프로젝트 전체 정책인가?

개별 Workspace에서 Override할 수 있어야 하는가?

공통화 후 설정이 더 이해하기 쉬워지는가?
```

한 Workspace에서만 사용하는 설정이라면 해당 Workspace에 유지합니다.

---

# 36. 공통 설정은 지나치게 강제하지 않는다

공통 Config는 기본값을 제공하는 역할입니다.

예:

```txt
Base TypeScript Config
  ↓
Next.js Config 확장

Base Vitest Config
  ↓
React Test Config
  ↓
Integration Config
```

모든 Workspace가 동일한 Runtime을 가진다고 가정하지 않습니다.

예를 들어:

```txt
Node Package
React Package
Next.js App
Tooling Script
```

는 서로 다른 설정이 필요할 수 있습니다.

---

# 37. Tooling 추가 기준

Tooling은 개발자가 반복하는 Repository-level 작업을 자동화할 때 추가합니다.

예:

```txt
Generator

Boundary Checker

Project Initialization

Seed Script

Cleanup Script

Repository Validation
```

다음 조건이 있다면 Tooling 추가를 검토합니다.

```txt
동일 작업을 자주 반복한다.

수동 작업에서 실수가 자주 발생한다.

여러 파일을 동시에 변경해야 한다.

Architecture Convention을 반복 적용한다.

명령어 하나로 표현할 가치가 있다.
```

---

# 38. Tooling으로 만들지 않는 경우

다음 경우에는 Script를 추가하지 않는 것을 우선합니다.

```txt
한 번만 수행할 작업

실행 순서가 계속 바뀌는 실험적 작업

자동화보다 수동 작업이 더 명확한 작업

특정 개발자 Local Environment에만 필요한 작업
```

Tooling도 유지보수 대상이므로 자동화 자체가 항상 이점은 아닙니다.

---

# 39. Tooling 위치

Repository-level Script:

```txt
tooling/scripts
```

Code Scaffold Generator:

```txt
tooling/generators
```

공통 개발 설정:

```txt
tooling/<config-package>
```

등으로 역할을 분리합니다.

기존 Tooling의 책임과 겹치는 새 Package를 만들기 전에 기존 위치에 추가할 수 있는지 먼저 확인합니다.

---

# 40. 새로운 Generator 추가

새로운 반복 Scaffold가 필요하다면 Generator 추가를 검토할 수 있습니다.

현재:

```txt
domain
component
entity
feature
view
```

가 존재합니다.

새 Generator를 만들 기준:

```txt
동일한 Directory 구조를 반복 생성한다.

Naming Convention을 반복 적용한다.

Test / Story / Barrel을 함께 만들어야 한다.

수동 생성 실수가 자주 발생한다.
```

Generator 상세 기준은 `14_코드_생성기.md`를 따릅니다.

---

# 41. Generator보다 기존 Generator 확장을 우선할 수 있다

새로운 Generator 종류를 추가하기 전에 기존 Generator Option으로 표현하는 것이 더 자연스러운지 확인합니다.

예:

```txt
Domain + Repository
```

를 별도:

```txt
repository generator
```

로 만들기보다:

```bash
pnpm generate domain order --repository
```

처럼 기존 Domain Generator의 책임 확장으로 표현할 수 있습니다.

기준은 두 작업이 하나의 생성 Context에 자연스럽게 속하는지입니다.

---

# 42. 새로운 Root Script 추가

루트 `package.json`에 Script를 추가할 때는 Repository 사용자가 자주 호출해야 하는 Command인지 확인합니다.

Root에 적합한 예:

```txt
dev
build
check
test
generate
db:*
init-project
```

특정 Package 내부에서만 의미가 있다면 Package Script로 유지하는 편이 좋습니다.

---

# 43. Root Script는 내부 구현을 숨긴다

개발자가 자주 쓰는 명령은 Root Script를 통해 간단한 Public Command를 제공합니다.

예:

```bash
pnpm db:seed
```

내부:

```txt
@repo/scripts seed
```

사용자는 내부 Package 위치를 외울 필요가 없습니다.

Root Script는 Repository 개발 경험의 Public API처럼 취급합니다.

---

# 44. 새로운 Dependency 추가

공통 Package나 Tooling을 추가하면서 새로운 Dependency가 필요하다면 다음을 확인합니다.

```txt
기존 Dependency로 해결 가능한가?

실제 Runtime Dependency인가?

Dev Dependency인가?

한 Package만 필요한가?

여러 Workspace가 같은 Version을 사용해야 하는가?

pnpm Catalog 대상인가?
```

Repository 전체가 같은 Version을 공유할 가치가 있는 Dependency는 Catalog 사용을 검토합니다.

기본 Package 관리 기준은 `02_기본설정.md`를 따릅니다.

---

# 45. Dependency는 필요한 Package에만 추가한다

Root에 모든 Dependency를 넣지 않습니다.

예:

```txt
Mailer Provider SDK
  → mailer Package

Storage SDK
  → storage Package

Zod
  → 실제 사용하는 Package

Playwright
  → E2E Tooling
```

Dependency 위치가 실제 책임을 나타내도록 합니다.

---

# 46. Infrastructure Provider 추가

예를 들어 Storage에 새로운 Provider를 추가한다면 먼저 기존 `storage` Package 책임 안에 들어가는지 확인합니다.

```txt
@repo/storage
├─ provider-a
└─ provider-b
```

처럼 같은 책임의 구현 교체라면 기존 Package 내부 확장이 자연스러울 수 있습니다.

반대로 완전히 다른 Infrastructure 책임이라면 새 Package를 검토합니다.

---

# 47. Provider 선택과 Business Logic

Provider 선택은 가능한 한 Server Configuration 또는 Infrastructure Boundary에서 결정합니다.

Client가 다음 값을 임의로 결정하도록 하지 않습니다.

```txt
paymentProvider

storageProvider

mailerProvider
```

Business 또는 운영 설정으로 결정해야 하는 값은 Server에서 결정합니다.

---

# 48. 새로운 Cross-cutting Package

다음과 같은 Cross-cutting 기능은 별도 Package 후보가 될 수 있습니다.

```txt
observability

rate-limit

analytics

audit-log
```

하지만 각각 책임이 크게 다릅니다.

예:

```txt
observability
  Trace / Metric / Error Reporting 메커니즘

rate-limit
  요청 제한 메커니즘

analytics
  Product Event 전달

audit-log
  Business 주요 행위 기록
```

이름이 Infrastructure처럼 보인다는 이유만으로 모두 같은 방식으로 설계하지 않습니다.

---

# 49. Audit Log 주의

Audit Log는 외부 Provider Adapter만의 문제가 아닐 수 있습니다.

```txt
누가
언제
무엇을
왜 변경했는가
```

라는 Business 의미가 강하다면 Domain / Database 책임과 연결될 수 있습니다.

따라서 모든 확장 후보를 무조건 Infrastructure Package로 분류하지 않습니다.

---

# 50. 새로운 Package 추가 절차

새 Package가 필요하다고 결정했다면 다음 순서를 권장합니다.

```txt
1. 책임 정의

2. Package 이름 결정

3. Dependency 방향 결정

4. Public API 설계

5. package.json 작성

6. TypeScript / ESLint 설정 연결

7. 구현

8. Test 추가

9. exports 설정

10. Boundary Checker 반영 여부 확인

11. 관련 문서 갱신
```

---

# 51. Boundary Checker 갱신

새 Runtime Package가 추가되면 `check:boundaries`가 해당 Package의 의존 관계를 알고 있어야 하는지 확인합니다.

예:

```txt
@repo/storage
@repo/mailer
```

같은 Package를 추가했다면:

```txt
누가 이 Package를 Import할 수 있는가?

이 Package는 무엇을 Import할 수 있는가?
```

를 명시해야 할 수 있습니다.

새 Package를 추가하고 Boundary 검사를 그대로 두어 사실상 모든 의존성을 허용하는 상태를 만들지 않습니다.

Architecture에 영향을 주는 확장이라면 관련 문서를 함께 갱신합니다.

```txt

```

모든 문서를 항상 수정하는 것이 아니라 실제 변경된 정책과 관련된 문서만 갱신합니다.

# 53. App 추가 체크리스트

독립된 Routing / Layout이 필요한가?

독립적인 배포 단위가 필요한가?

기존 App Route Group으로 해결할 수 없는가?

Test

Dependency Boundary
```

를 확인합니다.

# 54. Domain 추가 체크리스트

고유한 Rule이 있는가?

고유한 Lifecycle이 있는가?

기존 Domain의 일부로 보는 것이 더 자연스럽지 않은가?

```

# 55. Workspace Package 추가 체크리스트

독립적인 책임인가?

App Context 없이 사용할 수 있는가?

Dependency Boundary가 명확한가?

# 56. Infrastructure Package 추가 체크리스트

# 57. 승격 체크리스트

App 내부 코드를 Workspace Package로 올리기 전에:

```txt
두 App 이상에서 실제 사용되는가?

같은 코드뿐 아니라 같은 정책인가?

같은 이유로 변경되는가?

App-specific 이름을 제거할 수 있는가?

Public API가 자연스러운가?

Dependency가 단순해지는가?
```

하나라도 불분명하다면 기존 App에 유지하는 것이 더 안전할 수 있습니다.

---

# 58. Tooling 추가 체크리스트

```txt
반복 작업인가?

자동화 가치가 충분한가?

사람이 수동으로 할 때 오류가 발생하기 쉬운가?

기존 Script나 Generator로 해결할 수 없는가?

명령의 Input과 Output이 명확한가?

실패 시 Repository를 중간 상태로 만들 가능성은 없는가?
```

Tooling을 추가했다면:

```txt
Root Script가 필요한가?

Help가 필요한가?

Dry Run이 필요한가?

기존 파일 보호가 필요한가?

문서화가 필요한가?
```

도 확인합니다.

# 59. Config 추가 체크리스트

```txt
여러 Workspace가 실제 같은 설정을 사용하는가?

기본값과 Override를 분리할 수 있는가?

Runtime이 다른 Workspace까지 억지로 묶고 있지 않은가?

설정 Package의 Dependency가 과도하지 않은가?
```

공통 설정이 실제 설정을 더 복잡하게 만든다면 각 Workspace에 유지하는 편이 낫습니다.

# 60. 확장을 위한 권장 사고 순서

새로운 코드가 필요할 때 다음 순서로 판단합니다.

```txt
1. 기존 책임 안에 둘 수 있는가?
   → 그렇다면 기존 위치에 둔다.

2. Component 하나에서만 사용하는가?
   → colocate한다.

3. 같은 Slice 여러 곳에서 사용하는가?
   → Slice Segment로 올린다.

4. 같은 App 여러 Slice에서 사용하는가?
   → App-level 공통 영역을 검토한다.

5. 여러 App에서 실제 동일한 책임을 공유하는가?
   → Workspace Package를 검토한다.

6. 외부 Provider 연결 자체가 독립 책임인가?
   → Infrastructure Package를 검토한다.

7. 반복 개발 작업인가?
   → Tooling / Generator를 검토한다.

8. 여러 Workspace가 같은 개발 설정을 공유하는가?
   → Config Package를 검토한다.
```

# 61. 피해야 할 확장 방식

다음 방식은 지양합니다.

```txt
미래에 필요할 것 같아서 Package를 미리 만든다.

모든 Helper를 공통 Package로 이동한다.

두 Component가 비슷하다는 이유로 하나로 합친다.

모든 Domain에 같은 파일 구조를 강제한다.

새 Prisma Model마다 Domain을 하나 만든다.

새 Route마다 App을 하나 만든다.

App끼리 Source를 직접 Import한다.

Package가 App 코드를 Import한다.

Infrastructure Package에서 Business Rule을 판단한다.

Provider SDK를 여러 App에서 직접 사용한다.

Root package.json에 모든 Dependency를 몰아넣는다.

새 Tooling을 만들면서 기존 Script와 역할을 중복시킨다.

Config를 공통화한 뒤 Workspace별 예외 설정이 더 많아진다.
```

# 62. 확장의 목표

좋은 확장은 Directory나 Package 수를 늘리는 것이 아닙니다.

좋은 확장의 결과는 다음과 같습니다.

```txt
책임이 더 명확하다.

Dependency 방향이 단순하다.

변경 영향 범위가 줄어든다.

공유되는 정책이 한 곳에서 관리된다.

App-specific 코드가 독립적으로 발전할 수 있다.

외부 Provider 변경이 Business Code 전체로 전파되지 않는다.

새로운 개발자가 코드 위치를 예측할 수 있다.

새 기능을 추가할 때 기존 구조를 무너뜨리지 않는다.
```

반대로 구조를 추가했는데:

```txt
어디에 코드를 둬야 하는지 더 어려워졌다.

Package 간 Import가 복잡해졌다.

설정 파일이 더 많아졌다.

분기와 Adapter만 증가했다.

Public API가 무엇인지 알기 어렵다.
```

면 확장이 과도했을 가능성이 있습니다.

# 64. 핵심 원칙

```txt
가장 가까운 위치에서 시작한다.

실제 공유가 발생한 뒤 승격한다.

미래의 재사용 가능성만으로 Package를 만들지 않는다.

코드 중복과 책임 공유를 구분한다.

새 App은 독립적인 사용자 경험이나 Runtime Boundary가 있을 때 만든다.

Page가 많다는 이유만으로 App을 분리하지 않는다.

새 Domain은 독립적인 Business Concept와 Rule을 기준으로 만든다.

Prisma Model과 Domain을 1:1로 보지 않는다.

Workspace Package는 독립적인 책임과 Public API가 있을 때 만든다.

App끼리 직접 Import하지 않는다.

Package가 App을 Import하지 않는다.

Infrastructure Package는 외부 시스템 연결 메커니즘을 담당한다.

Infrastructure Package에서 Business Rule을 판단하지 않는다.

Storage는 어떻게 저장하는지를 담당한다.

Domain은 무엇을 저장할 수 있는지를 판단한다.

Mailer는 어떻게 발송하는지를 담당한다.

Domain은 언제 누구에게 발송할지를 판단한다.

Provider-specific 코드를 Business Code 전체에 퍼뜨리지 않는다.

Component 전용 코드는 Component에 colocate한다.

Slice 내부 공유는 Slice Segment로 승격한다.

App 내부 공유는 App-level 공통 영역을 먼저 검토한다.

여러 App에서 같은 책임과 정책을 공유할 때 Workspace Package를 검토한다.

공통화 후 분기와 옵션이 더 많아진다면 공통화를 다시 검토한다.

새 Runtime Package를 추가하면 Dependency Boundary도 확인한다.

공통 Config는 실제 반복되는 Repository-wide 설정을 기준으로 만든다.

Runtime이 다른 Workspace에 하나의 Config를 억지로 강제하지 않는다.

Tooling은 반복 작업과 수동 오류를 줄일 때 추가한다.

기존 Tooling으로 해결할 수 있다면 새로운 Tool을 만들지 않는다.

Root Script는 Repository 사용자가 자주 사용하는 Public Command에 집중한다.

Dependency는 실제 사용하는 Package에 추가한다.

새 구조를 추가하면 관련 문서도 함께 갱신한다.

확장의 목적은 구조를 늘리는 것이 아니라 책임과 변경 경계를 더 명확하게 만드는 것이다.
```
