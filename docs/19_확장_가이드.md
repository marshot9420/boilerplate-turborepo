# 확장 가이드

이 문서는 `boilerplate-turborepo`를 기반으로 프로젝트를 확장할 때 새로운 App, Domain, Workspace Package, Infrastructure Package, Config, Tooling을 어떤 기준으로 추가할지 설명합니다.

확장의 핵심 원칙은 **구조를 미리 만들지 않고 실제 책임과 공유가 발생했을 때 필요한 만큼 분리하고 승격하는 것**입니다.

```txt
가까운 곳에 둔다.

실제 책임이 생겼을 때 분리한다.

실제 공유가 발생했을 때 승격한다.

코드가 비슷하다는 이유만으로 공통화하지 않는다.

미래의 재사용 가능성만으로 Package를 만들지 않는다.

새로운 구조는 기존 Dependency Boundary를 유지해야 한다.
```

기본적인 승격 방향:

```txt
Component
  ↓
Slice
  ↓
App
  ↓
Workspace Package
```

---

## 1. 확장 단위

이 Repository에서 주요 확장 단위는 다음과 같습니다.

```txt
App
  독립적인 사용자 경험과 Runtime

Domain
  독립적인 Business Concept와 Rule

Workspace Package
  여러 Workspace가 공유하는 독립 책임

Infrastructure Package
  외부 시스템 연결 메커니즘

Config Package
  여러 Workspace가 공유하는 개발 설정

Tooling
  Repository-level 개발 자동화
```

새로운 구조를 만들기 전에 먼저 기존 책임 안에서 해결할 수 있는지 확인합니다.

---

## 2. 새로운 App

새 App은 단순히 Page나 Feature가 많아졌다는 이유로 추가하지 않습니다.

다음과 같은 독립성이 존재할 때 검토합니다.

```txt
사용자 집단이 다르다.

Navigation과 Layout이 독립적이다.

Authentication / Authorization 정책이 크게 다르다.

독립적인 배포 또는 운영 단위가 필요하다.

환경변수 구성이 다르다.

사용하는 Domain 조합이나 UI 성격이 크게 다르다.
```

예:

```txt
apps/web
  일반 사용자

apps/admin
  관리자
```

반대로 다음 정도의 차이라면 기존 App 내부 구조를 먼저 사용합니다.

```txt
Route Group

Layout

View

Feature

Entity

App-local Shared
```

새 App을 만들면서 다른 App의 Source를 직접 Import하지 않습니다.

```txt
apps/web
  → apps/admin

apps/admin
  → apps/web
```

와 같은 의존성은 만들지 않습니다.

두 App에서 같은 책임이 실제로 필요하다면 Workspace Package 승격 여부를 검토합니다.

---

## 3. App 추가 절차

새 App이 필요하다고 판단했다면 다음을 확인합니다.

```txt
1. 사용자와 책임 정의

2. apps/<app> 생성

3. package.json과 Workspace 설정

4. Next.js / TypeScript / ESLint 연결

5. Environment 설정

6. App 내부 구조 구성

7. Root Layout / Metadata

8. Authentication / Authorization

9. Design System 연결

10. Test / E2E 환경

11. Turbo Task

12. Dependency Boundary
```

App 내부 Directory는 처음부터 모두 만들지 않습니다.

필요한 책임이 생길 때 추가합니다.

구체적인 App 구조는 `10_앱_구조.md`를 따릅니다.

---

## 4. 새로운 Domain

Domain은 **독립적인 Business Concept와 Rule**을 기준으로 추가합니다.

예:

```txt
user
order
payment
content
question
order-claim
```

Domain과 Database Model은 동일한 개념이 아닙니다.

```txt
Prisma Model 하나
  ≠
Domain 하나
```

하나의 Domain이 여러 Persistence Model을 사용할 수도 있습니다.

새 Domain을 검토할 기준:

```txt
독립적인 Business 용어가 있는가?

고유한 Lifecycle이나 상태가 있는가?

독립적인 Rule이나 Permission이 있는가?

다른 개념과 변경 이유가 다른가?

독립된 Use Case로 설명할 수 있는가?
```

다음 이유만으로 Domain을 추가하지 않습니다.

```txt
Prisma Model이 하나 생겼다.

파일 수가 많아졌다.

상수나 Helper가 필요하다.

UI Component가 하나 생겼다.
```

---

## 5. Domain 추가 절차

새 Domain은 Generator로 시작할 수 있습니다.

```bash
pnpm generate domain <domain-name>
```

Persistence까지 함께 필요하다면:

```bash
pnpm generate domain <domain-name> --repository
```

Generator 결과는 시작점입니다.

```txt
생성
  ↓
실제 Business Requirement 반영
  ↓
필요 없는 Scaffold 제거
  ↓
필요한 Rule / Service 추가
```

Domain의 실제 역할과 파일 구성은 `08_도메인_레이어.md`, Persistence는 `07_데이터베이스.md`를 따릅니다.

## 6. 새로운 Workspace Package

Workspace Package는 **여러 Workspace가 공유하는 독립적인 책임과 명확한 Public API가 존재할 때** 추가합니다.

다음 조건을 검토합니다.

```txt
실제로 두 곳 이상에서 사용되는가?

같은 구현뿐 아니라 같은 의미와 정책을 공유하는가?

App Context 없이도 책임을 설명할 수 있는가?

독립적인 Public API를 만들 수 있는가?

Dependency 방향을 명확하게 제한할 수 있는가?

Package로 분리했을 때 변경 영향 범위가 더 명확해지는가?
```

다음 이유만으로 Package를 만들지 않습니다.

```txt
코드가 길다.

Directory가 커졌다.

두 Component가 비슷하다.

Helper를 공유하고 싶다.

나중에 다른 App에서도 쓸 것 같다.
```

Package를 추가하는 것은 새로운 Boundary와 유지보수 책임을 만드는 일입니다.

---

## 7. Workspace Package 추가 절차

새 Package가 필요하다면 다음 순서를 권장합니다.

```txt
1. 책임 정의

2. Package 이름 결정

3. Dependency 방향 결정

4. Public API 설계

5. package.json 작성

6. TypeScript / ESLint 설정 연결

7. 구현과 Test

8. package.json exports 구성

9. check:boundaries 반영 여부 확인

10. 관련 문서 갱신
```

기본 형태:

```txt
packages/<name>/
├─ src/
│  ├─ index.ts
│  └─ ...
├─ package.json
└─ tsconfig.json
```

필요한 경우에만:

```txt
client.ts
server.ts
test
```

등을 추가합니다.

## 8. Package Public API와 Dependency

다른 Workspace에서는 Package의 공개 Entry를 통해 Import합니다.

권장:

```ts
import { something } from "@repo/package";
```

또는 명시적인 Subpath:

```ts
import { something } from "@repo/package/server";
```

지양:

```ts
import { something } from "@repo/package/src/internal/something";
```

Public API에서는 명시적인 Named Export를 사용합니다.

```ts
export { something } from "./something";
export type { Something } from "./something";
```

Wildcard Export는 사용하지 않습니다.

```ts
export * from "./something";
```

Server-only Entry가 필요하다면:

```ts
import "server-only";
```

를 사용합니다.

세부 규칙은 `18_컨벤션.md`를 따릅니다.

새 Runtime Package를 추가했다면 `05_의존성_경계.md`와 `check:boundaries`도 함께 확인합니다.

## 9. Infrastructure Package

Infrastructure Package는 **Business Rule을 판단하지 않고 외부 시스템과 연결하는 기술적 메커니즘**을 제공합니다.

현재 대표적인 예:

```txt
@repo/storage
@repo/mailer
```

추가 후보는 프로젝트 요구사항에 따라 달라질 수 있습니다.

예:

```txt
analytics
observability
rate-limit
```

후보가 있다는 이유만으로 미리 만들지 않습니다.

Infrastructure Package를 검토할 기준:

```txt
외부 Provider와 연결하는 독립 책임인가?

여러 App이나 Use Case에서 사용되는가?

Provider-specific 코드를 App에서 숨길 가치가 있는가?

Secret이나 Environment 접근이 필요한가?

Timeout / Retry / Error Mapping 같은 기술 정책이 있는가?

Provider 변경을 별도 Boundary로 관리할 가치가 있는가?
```

---

## 10. Infrastructure와 Business Rule의 경계

Infrastructure는 **어떻게 수행하는가**를 담당합니다.

Business Layer는 **왜, 언제, 누가 수행할 수 있는가**를 판단합니다.

예:

```txt
Domain
  이 사용자가 이미지를 업로드할 수 있는가?

Storage
  실제 파일을 어떻게 저장하는가?
```

```txt
Domain / Service
  언제 누구에게 Email을 보내는가?

Mailer
  Email을 어떻게 발송하는가?
```

Infrastructure Package에 Domain-specific Business Rule을 넣지 않습니다.

예를 들어 범용 Mailer Package가 다음과 같이 특정 Domain 객체에 직접 결합되는 구조는 신중하게 검토합니다.

```ts
sendOrderRefundApprovedEmail(order);
```

Provider-specific 이름도 Business Code 전체에 퍼뜨리지 않습니다.

Provider 자체가 Business Meaning이 아니라면 책임 중심 API를 우선합니다.

```txt
authorizeProductImageUpload

deleteStoredObject
```

Provider 선택이나 Secret 관리 기준은 `06_환경변수.md`와 `17_보안_및_운영_기본정책.md`를 따릅니다.

## 11. 앱 내부 코드의 승격

코드는 기본적으로 사용하는 위치 가까이에 둡니다.

```txt
Component
  ↓
Slice
  ↓
App
  ↓
Workspace Package
```

판단 기준:

```txt
하나의 Component만 사용
  → Component와 colocate

같은 Slice의 여러 코드에서 사용
  → Slice Segment

여러 Slice가 사용하지만 한 App에서만 필요
  → App-level 공통 영역

여러 App에서 같은 책임과 정책을 공유
  → Workspace Package 후보
```

두 곳에서 사용된다는 사실만으로 바로 Package로 올리지 않습니다.

---

## 12. 공통화와 중복을 구분한다

코드가 비슷한 것과 책임이 같은 것은 다릅니다.

예:

```txt
Admin ProductCard

Web ProductCard
```

두 Component가 비슷하더라도:

```txt
사용 목적

Interaction

Design

사용자

변경 이유
```

가 다르다면 각각 유지하는 편이 자연스러울 수 있습니다.

Workspace Package로 승격하기 전에 다음을 확인합니다.

```txt
같은 책임인가?

같은 정책을 공유하는가?

같은 이유로 변경되는가?

App-specific Context를 제거할 수 있는가?

Public API가 자연스러운가?

새 Dependency를 만드는 것보다 이점이 큰가?
```

공통화를 유지하기 위해 다음과 같은 분기가 계속 늘어난다면 경계를 다시 검토합니다.

```txt
isAdmin

isWeb

isPartner

여러 boolean option

Domain-specific condition
```

공통화가 오히려 복잡성을 증가시키고 있다는 신호일 수 있습니다.

## 13. Config Package

여러 Workspace가 동일한 개발 설정을 반복한다면 공통 Config Package를 검토합니다.

예:

```txt
eslint-config

typescript-config

vitest-config

storybook-config
```

추가 기준:

```txt
여러 Workspace에서 실제 같은 설정을 사용하는가?

Repository-wide 기본 정책인가?

Workspace별 Override가 명확한가?

공통화한 뒤 설정이 더 단순해지는가?
```

모든 Workspace가 같은 Runtime을 가진다고 가정하지 않습니다.

```txt
Next.js App

React Package

Node Package

Tooling Script
```

는 서로 다른 설정이 필요할 수 있습니다.

공통 Config는 기본값을 제공하고 필요한 차이는 명시적으로 확장합니다.

---

## 14. Tooling

Tooling은 반복적인 Repository-level 작업을 자동화할 때 추가합니다.

예:

```txt
Generator

Boundary Checker

Project Initialization

Seed

Cleanup

Repository Validation
```

새 Tooling을 검토할 기준:

```txt
반복적으로 수행하는 작업인가?

수동 작업에서 실수가 발생하기 쉬운가?

여러 파일을 일관되게 변경해야 하는가?

Architecture Convention을 반복 적용하는가?

명확한 Input과 Output을 가진 Command로 표현할 수 있는가?
```

다음 경우에는 자동화하지 않는 것을 우선합니다.

```txt
한 번만 필요한 작업

아직 절차가 안정되지 않은 실험

자동화보다 수동 작업이 더 명확한 작업

특정 개발자의 Local 환경에만 필요한 작업
```

기존 Tooling의 책임으로 해결할 수 있다면 새로운 Tool을 만들지 않습니다.

## 15. Generator와 Root Script 확장

새 Generator를 만들기 전에 기존 Generator를 확장할 수 있는지 확인합니다.

예:

```bash
pnpm generate domain order --repository
```

처럼 동일한 생성 Context라면 새로운 `repository` Generator를 만드는 것보다 기존 Domain Generator의 Option이 자연스러울 수 있습니다.

새 Generator가 적절한 경우:

```txt
같은 Directory 구조를 반복 생성한다.

Naming Convention을 반복 적용한다.

Test / Story / Export를 함께 생성해야 한다.

수동 작업에서 같은 실수가 반복된다.
```

Generator 상세 기준은 `14_코드_생성기.md`를 따릅니다.

Root `package.json`에는 Repository 사용자가 자주 호출하는 Command를 둡니다.

예:

```txt
dev
build
check
test
generate
db:*
init-project
```

특정 Package에서만 의미가 있는 Command는 해당 Package Script에 유지합니다.

## 16. Dependency 추가

새 Package나 Tooling을 추가하면서 Dependency가 필요하다면 다음을 확인합니다.

```txt
기존 Dependency로 해결할 수 있는가?

Runtime Dependency인가?

Dev Dependency인가?

어느 Package에서 실제 사용하는가?

여러 Workspace가 같은 Version을 공유해야 하는가?

pnpm Catalog 대상인가?
```

Dependency는 실제 사용하는 Workspace에 추가합니다.

예:

```txt
Storage Provider SDK
  → storage Package

Mailer Provider SDK
  → mailer Package

Playwright
  → E2E 관련 Tooling

Zod
  → 실제 사용하는 Package
```

모든 Dependency를 Root에 몰아넣지 않습니다.

Package와 Catalog 관리 기준은 `02_기본설정.md`를 따릅니다.

## 17. 확장 후 확인

Architecture에 영향을 주는 확장이 끝났다면 다음을 확인합니다.

```txt
책임이 명확한가?

Dependency 방향이 기존 Architecture와 맞는가?

새 Package의 Public API가 명확한가?

App 간 직접 Import가 생기지 않았는가?

Package가 App을 Import하지 않는가?

Server / Client Boundary가 올바른가?

필요한 Test가 있는가?

check:boundaries가 새 구조를 반영하는가?

관련 문서가 현재 구조와 일치하는가?
```

새 구조를 추가했다고 해서 모든 문서를 수정할 필요는 없습니다.

실제로 영향을 받은 문서만 갱신합니다.

## 18. 확장 판단 순서

새 코드나 구조가 필요할 때 다음 순서로 판단합니다.

```txt
1. 기존 책임 안에서 해결할 수 있는가?
   → 기존 위치에 둔다.

2. 하나의 Component에서만 사용하는가?
   → colocate한다.

3. 같은 Slice에서 공유되는가?
   → Slice Segment를 사용한다.

4. 같은 App의 여러 Slice에서 공유되는가?
   → App-level 공통 영역을 검토한다.

5. 여러 App에서 같은 책임과 정책을 공유하는가?
   → Workspace Package를 검토한다.

6. 외부 시스템 연결 자체가 독립적인 책임인가?
   → Infrastructure Package를 검토한다.

7. 반복 개발 작업인가?
   → Tooling / Generator를 검토한다.

8. 여러 Workspace가 같은 개발 설정을 공유하는가?
   → Config Package를 검토한다.
```

## 19. 피해야 할 확장

다음 방식은 지양합니다.

```txt
미래에 필요할 것 같아서 Package를 미리 만든다.

모든 Helper를 공통 Package로 이동한다.

두 Component가 비슷하다는 이유로 합친다.

모든 Domain에 동일한 파일 구조를 강제한다.

새 Prisma Model마다 Domain을 만든다.

새 Route마다 App을 만든다.

App끼리 Source를 직접 Import한다.

Package가 App을 Import한다.

Infrastructure Package에서 Business Rule을 판단한다.

Provider SDK를 여러 App에서 직접 사용한다.

모든 Dependency를 Root에 추가한다.

기존 Tooling과 같은 책임의 새 Tool을 만든다.

공통 Config 때문에 Workspace별 예외 설정이 더 많아진다.
```

## 21. 핵심 원칙

```txt
가장 가까운 위치에서 시작한다.

실제 책임이 생겼을 때 분리한다.

실제 공유가 발생한 뒤 승격한다.

코드 중복과 책임 공유를 구분한다.

새 App은 독립적인 사용자 경험이나 Runtime Boundary가 있을 때 만든다.

새 Domain은 독립적인 Business Concept와 Rule을 기준으로 만든다.

Prisma Model과 Domain을 1:1로 보지 않는다.

Workspace Package는 독립적인 책임과 Public API가 있을 때 만든다.

App끼리 Source를 직접 Import하지 않는다.

Package가 App을 Import하지 않는다.

Infrastructure Package는 외부 시스템 연결 메커니즘을 담당한다.

Infrastructure Package에서 Business Rule을 판단하지 않는다.

Provider-specific 코드를 Business Code 전체에 퍼뜨리지 않는다.

Component 전용 코드는 colocate한다.

App 내부에서 해결할 수 있는 공유는 먼저 App 내부에 둔다.

여러 App에서 같은 책임과 정책을 공유할 때 Package 승격을 검토한다.

공통화 때문에 분기와 옵션이 늘어난다면 경계를 다시 검토한다.

공통 Config는 실제 반복되는 설정을 기준으로 만든다.

Tooling은 반복 작업과 수동 오류를 줄일 때 추가한다.

기존 Tooling으로 해결할 수 있다면 새 Tool을 만들지 않는다.

새 Runtime Package를 추가하면 Dependency Boundary도 확인한다.

확장의 목적은 구조를 늘리는 것이 아니라 책임과 변경 경계를 더 명확하게 만드는 것이다.
```
