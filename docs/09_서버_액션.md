# 서버 액션

이 문서는 `boilerplate-turborepo`에서 Next.js Server Action이 담당하는 책임과 구현 기준을 설명합니다.

Server Action은 Client와 Domain Layer 사이의 **Application Boundary**입니다.

기본 흐름은 다음과 같습니다.

```txt
Client UI
   ↓
Server Action
   ↓
Domain Service
   ↓
Repository
   ↓
Database
```

Server Action의 목적은 비즈니스 로직을 구현하는 것이 아니라 다음 책임을 조합하는 것입니다.

```txt
인증

FormData 해석

입력 정규화

Zod Validation

Domain Service 호출

Domain Result → ActionResult 변환

필요한 Cache 무효화

Navigation 처리
```

Domain의 비즈니스 규칙은 `08_도메인_레이어.md`, Database 접근은 `07_데이터베이스.md`에서 설명합니다.

---

# 1. 기본 원칙

Server Action의 기본 원칙은 다음과 같습니다.

```txt
Server Action은 얇게 유지한다.

FormData와 HTTP/UI 입력을 Domain 입력으로 변환한다.

구조적 Validation은 Zod로 처리한다.

비즈니스 Validation은 Domain Service에 맡긴다.

인증은 Action 진입 시점에 확인한다.

세부 인가는 Domain에서 판단한다.

Prisma Query를 직접 작성하지 않는다.

비즈니스 상태 전이를 직접 판단하지 않는다.

예상 가능한 결과는 ActionResult로 반환한다.

Cache 무효화와 Client UI 갱신의 책임을 구분한다.
```

---

# 2. Server Action의 위치

Server Action은 앱 계층에 둡니다.

개념적인 구조:

```txt
apps/[app]/src/
├─ actions/
├─ features/
├─ views/
└─ app/
```

예:

```txt
actions/
└─ user/
   ├─ update-user.action.ts
   └─ withdraw-user.action.ts
```

Action은 특정 앱의 인증 Context, Form 입력, URL 구조, Cache 정책 등을 알고 있으므로 `@repo/domain`에 두지 않습니다.

---

# 3. Server Action의 역할

Server Action은 다음 질문에 답합니다.

```txt
누가 요청했는가?

입력 데이터는 어떤 형태인가?

입력 구조가 유효한가?

어떤 Domain Service를 호출해야 하는가?

Domain 결과를 UI에 어떤 형태로 전달할 것인가?

성공 후 어떤 Server Cache를 무효화해야 하는가?

성공 후 Navigation이 필요한가?
```

반대로 다음 질문에는 답하지 않습니다.

```txt
현재 상태에서 이 작업이 가능한가?

이 사용자가 이 Resource를 수정할 권한이 있는가?

어떤 상태 전이가 허용되는가?

여러 DB 변경 중 무엇을 Transaction으로 묶어야 하는가?
```

이것은 Domain의 책임입니다.

---

# 4. 기본 실행 흐름

Mutation Action의 일반적인 흐름은 다음과 같습니다.

```txt
Server Action 호출
      ↓
Authentication
      ↓
FormData 읽기
      ↓
입력 정규화
      ↓
Zod Validation
      ↓
Domain Service 호출
      ↓
Domain Result 처리
      ↓
필요한 revalidatePath
      ↓
ActionResult 반환
```

Navigation이 필요한 Action이라면 마지막 단계에서 `redirect`를 사용할 수 있습니다.

---

# 5. Authentication

Server Action은 신뢰할 수 없는 외부 진입점으로 취급합니다.

UI에서 버튼을 숨겼다고 해서 Action이 보호되는 것은 아닙니다.

따라서 보호된 Action은 실행 초기에 인증을 확인합니다.

예:

```txt
일반 사용자 Action
→ requireUser(...)

관리자 Action
→ requireAdmin(...)
```

개념:

```ts
"use server";

export async function updateProfileAction(formData: FormData) {
  const actor = await requireUser();

  // ...
}
```

인증 결과를 Client에서 전달받아 신뢰하지 않습니다.

지양:

```txt
FormData
  role=ADMIN

FormData
  currentUserId=...
```

와 같은 값을 권한의 근거로 사용하지 않습니다.

---

# 6. Authentication과 Authorization

인증과 인가를 구분합니다.

```txt
Authentication
  누구인가?

Authorization
  이 사람이 이 작업을 할 수 있는가?
```

Server Action은 일반적으로 **인증 및 거친 접근 경계**를 확인합니다.

예:

```txt
로그인 필요

관리자 계정 필요
```

구체적인 Resource 권한은 Domain이 판단합니다.

예:

```txt
이 관리자가 이 사용자를 차단할 수 있는가?

현재 사용자가 이 주문의 소유자인가?

현재 사용자가 이 콘텐츠를 수정할 수 있는가?
```

기본 흐름:

```txt
Server Action
  requireAdmin()
       ↓
Domain Service
  canBlockUser(...)
```

---

# 7. 인증 및 인가 순서

일반적인 순서는 다음과 같습니다.

```txt
1. Authentication

2. FormData Parsing

3. Zod Validation

4. Domain Service 호출

5. Domain Permission / Rule 판단

6. Persistence
```

Resource 기반 Permission은 검증된 ID와 실제 Database Resource가 필요하므로 Domain Service에서 처리합니다.

Server Action에서 같은 Permission을 다시 구현하지 않습니다.

---

# 8. FormData

HTML Form에서 호출되는 Action은 `FormData`를 Application 입력으로 받습니다.

Server Action은 이를 Domain Request 형태로 변환합니다.

예:

```ts
const input = {
  userId: formData.get("userId"),
  displayName: formData.get("displayName"),
};
```

이 단계에서는 아직 값이 신뢰할 수 있다고 가정하지 않습니다.

```txt
FormData
   ↓
unknown input
   ↓
Schema Validation
   ↓
Validated Request
```

---

# 9. FormData를 Domain으로 넘기지 않는다

Domain Service가 다음과 같은 입력을 직접 받지 않도록 합니다.

```ts
updateUserService(formData);
```

`FormData`는 Web Platform의 입력 형식이며 Domain 계약이 아닙니다.

올바른 흐름:

```txt
FormData
   ↓
Server Action
   ↓
Request Object
   ↓
Zod
   ↓
Domain Service
```

Domain Service는 명확한 Type을 받습니다.

```ts
updateUserService(actor, request);
```

---

# 10. FormData 정규화

HTML Form은 모든 입력을 Domain에서 원하는 Type으로 보내지 않습니다.

대표적인 차이:

```txt
빈 Input
→ ""

number Input
→ string

checkbox
→ 존재 / 미존재

multiple Input
→ 여러 Value

File Input
→ File
```

따라서 필요한 경우 Server Action 또는 Schema 입력 단계에서 정규화합니다.

예:

```txt
""
→ undefined
```

숫자는 Schema에서:

```txt
z.coerce.number()
```

등으로 변환할 수 있습니다.

---

# 11. `Object.fromEntries(formData)` 사용 기준

단순한 Flat Form에서는 사용할 수 있습니다.

```ts
const input = Object.fromEntries(formData);
```

하지만 다음 입력에서는 주의합니다.

```txt
동일한 name을 가진 여러 값

checkbox group

multiple select

File upload
```

이 경우:

```ts
formData.getAll("ids");
```

등을 명시적으로 사용합니다.

공통 Action 실행 흐름은 `@repo/core/action`의 `executeFormAction`을 사용할 수 있습니다.
단순 Flat Form은 기본적으로 `Object.fromEntries(formData.entries())`로 해석하며, 복수 값이나 별도 구조가 필요한 Form은 `parseFormData`를 전달합니다.

```ts
import { executeFormAction } from "@repo/core/action";
import { parseJsonFormDataValues } from "@repo/core/parse";

const result = await executeFormAction({
  actionName: "order-claim.create",
  schema: CreateOrderClaimRequest,
  formData,
  parseFormData: (formData) => ({
    ...Object.fromEntries(formData.entries()),
    items: parseJsonFormDataValues(formData, "items"),
  }),
  handler: createOrderClaimService,
});
```

`parseFormData`는 Raw Input 구조를 해석하는 역할만 가지며, Validation과 Business Rule을 대신하지 않습니다.

FormData 변환 방식은 실제 Form 구조가 드러나도록 작성하는 것을 우선합니다.

---

# 12. Zod Validation

Server Action에서는 Domain Request Schema를 사용하여 구조적 입력을 검증합니다.

예:

```txt
UUID

문자열 길이

Enum

URL

number

required / optional
```

개념:

```ts
const parsed = UpdateUserRequestSchema.safeParse(input);

if (!parsed.success) {
  // Validation ActionResult 반환
}
```

Validation 성공 후에만 Domain Service를 호출합니다.

```txt
Raw Input
   ↓
Zod
   ↓
Validated DTO
   ↓
Domain Service
```

---

# 13. Zod Validation과 Business Validation

Server Action의 Zod Validation과 Domain Validation을 혼동하지 않습니다.

```txt
displayName이 50자 이하인가?
→ Zod

이 사용자의 이름을 현재 변경할 수 있는가?
→ Domain


orderId가 UUID인가?
→ Zod

이 주문을 현재 사용자가 취소할 수 있는가?
→ Domain
```

Server Action에 Database 조회가 필요한 Validation을 작성하지 않습니다.

지양:

```txt
Action
  ↓
DB 조회
  ↓
상태 판단
  ↓
Service 호출
```

권장:

```txt
Action
  ↓
Schema
  ↓
Service
  ↓
Repository + Rule
```

---

# 14. Domain Service 호출

입력이 검증되었다면 Domain Service를 호출합니다.

개념:

```ts
const result = await updateUserService(actor, parsed.data);
```

Server Action은 Domain Service가 어떤 Prisma Query를 사용하는지 알 필요가 없습니다.

```txt
Action
  Domain Service API만 앎

Domain Service
  Repository API를 앎

Repository
  Prisma를 앎
```

---

# 15. Server Action에 Business Logic을 작성하지 않는다

다음 코드는 Action에 두지 않습니다.

```ts
if (user.status === "BLOCKED") {
  // ...
}

if (order.status !== "PAID") {
  // ...
}

if (actor.id === targetUser.id) {
  // ...
}
```

이러한 판단은:

```txt
Domain Service

Permission

Rule
```

의 책임입니다.

UI와 Action에서 비즈니스 규칙을 복제하면 여러 경로에서 규칙이 달라질 수 있습니다.

---

# 16. Server Action에서 Prisma를 사용하지 않는다

Server Action에서는 다음 패턴을 사용하지 않습니다.

```ts
import { prisma } from "@repo/database/client";

await prisma.user.update(...);
```

또는:

```ts
import { updateUser } from "@repo/database/user";

await updateUser(...);
```

처럼 Repository를 Action이 직접 호출하는 것도 기본적으로 피합니다.

올바른 방향:

```txt
Server Action
      ↓
Domain Service
      ↓
Repository
      ↓
Prisma
```

---

# 17. `ActionResult`

Server Action에서 Client가 처리할 수 있는 예상 가능한 결과는 `ActionResult`로 반환합니다.

개념적인 역할:

```txt
성공

Validation 실패

Domain 실패

사용자에게 전달 가능한 오류
```

흐름:

```txt
Domain Result
      ↓
Server Action
      ↓
ActionResult
      ↓
Form / Dialog / Hook
```

`ActionResult`의 목적은 Client가 Exception Message를 분석하지 않고 Action 결과를 명시적으로 처리하게 하는 것입니다.

---

# 18. Domain `Result`와 `ActionResult`

두 Result의 책임은 다릅니다.

```txt
Domain Result
  Business Use Case 결과

ActionResult
  UI / Form이 소비하는 Action 결과
```

예:

```txt
Domain
  USER_NOT_FOUND

       ↓ Action

ActionResult
  작업 대상 사용자를 찾을 수 없습니다.
```

Domain Error의 내부 구조를 Client에 그대로 노출하지 않아도 됩니다.

Server Action은 Application Boundary에서 적절한 Action Result로 변환합니다.

---

# 19. 예상하지 못한 Error

다음은 일반적인 Business Failure가 아닙니다.

```txt
Database Connection 장애

Provider 장애

프로그램 버그

예상하지 못한 Exception
```

이러한 오류의 Stack Trace나 내부 메시지를 Client에 그대로 반환하지 않습니다.

지양:

```ts
return {
  error: error.message,
};
```

특히 Error Message에 다음 정보가 포함될 수 있습니다.

```txt
Database URL

SQL

Token

API Credential

내부 File Path
```

Client에는 안전한 일반 오류를 반환하고 상세 오류는 Server Logging 정책에 따라 처리합니다.

---

# 20. `revalidatePath`

Mutation으로 인해 Server Cache가 더 이상 유효하지 않다면 `revalidatePath`를 사용할 수 있습니다.

예:

```txt
사용자 정보 변경

목록 항목 생성 / 삭제

상태 변경

관리자 데이터 수정
```

개념:

```ts
revalidatePath("/users");
```

`revalidatePath`의 책임은:

```txt
Next.js Server Cache 무효화
```

입니다.

Client UI 이벤트를 처리하기 위한 API가 아닙니다.

---

# 21. `revalidatePath`를 호출하는 위치

해당 Mutation으로 인해 어떤 Server Path의 Cache가 무효화되어야 하는지 Action이 알고 있다면 성공 이후 Action에서 처리할 수 있습니다.

흐름:

```txt
Domain Mutation 성공
      ↓
revalidatePath(...)
      ↓
ActionResult
```

실패한 Mutation에서는 성공을 전제로 하는 Cache 무효화를 실행하지 않습니다.

---

# 22. `router.refresh()`

`router.refresh()`는 Client Router의 현재 Route를 다시 요청하여 화면을 동기화하기 위한 Client 책임입니다.

따라서 Server Action 내부에서는 호출하지 않습니다.

```txt
Server Action
  ✕ router.refresh()
```

기본적인 책임은 다음과 같습니다.

```txt
Server
  revalidatePath
  Cache 정책

Client
  router.refresh
  현재 화면 갱신
```

---

# 23. `router.refresh()`의 소유자

`router.refresh()`는 해당 Mutation의 **Client 상호작용을 소유한 Feature**가 호출합니다.

예:

```txt
UpdateUserDialog

DeleteContentDialog

BlockUserButton

UpdateProfileForm

해당 Form Action Hook
```

예를 들어 Dialog 기반 작업이라면:

```txt
Dialog
  ↓
Form 제출
  ↓
Server Action
  ↓
성공
  ↓
Dialog 닫기
  ↓
router.refresh()
```

형태를 사용할 수 있습니다.

---

# 24. Design System Primitive가 `router.refresh()`를 호출하지 않는다

다음과 같은 범용 Component에는 Navigation 책임을 넣지 않습니다.

```txt
@repo/design-system Button

@repo/design-system Dialog

@repo/design-system Form

@repo/design-system Input
```

지양:

```txt
Button
  onClick
    → router.refresh()
```

범용 Primitive는 어떤 Domain Mutation이 발생했는지 알지 못합니다.

올바른 위치:

```txt
Feature
└─ BlockUserButton
      ↓
   router.refresh()
```

또는:

```txt
Feature
└─ DeleteUserDialog
      ↓
   router.refresh()
```

즉 문서에서 말하는 `Button`이나 `Dialog`는 **Feature 수준의 구체적인 상호작용 Component**를 의미합니다.

---

# 25. Form Hook이 후처리를 소유할 수도 있다

Form Logic을 Hook으로 분리한 경우 성공 후 Client Side Effect를 Hook이 담당할 수도 있습니다.

예:

```txt
useUpdateProfileFormAction
  ↓
Action 성공 감지
  ↓
Toast
  ↓
router.refresh()
```

중요한 것은 특정 파일 이름이 아니라 책임입니다.

```txt
Mutation을 시작하고
그 결과에 따라 Client UI를 변경하는 계층
```

이 Client 후처리를 소유합니다.

---

# 26. `revalidatePath`와 `router.refresh()`의 차이

둘은 같은 기능이 아닙니다.

```txt
revalidatePath
  Server Cache 무효화

router.refresh
  현재 Client Route 새로고침
```

따라서 다음과 같이 생각합니다.

```txt
Server Data Cache가 낡았는가?
→ revalidatePath 검토

현재 화면에서 변경 결과를 즉시 다시 받아야 하는가?
→ router.refresh 검토
```

항상 둘을 동시에 호출해야 하는 것은 아닙니다.

필요한 책임만 사용합니다.

---

# 27. Client UI 후처리

다음 작업은 일반적으로 Server Action이 아니라 Client Feature의 책임입니다.

```txt
Dialog 닫기

Toast 표시

router.refresh()

Client State 초기화

Focus 이동

Modal 상태 변경
```

예:

```txt
Action 성공
   ↓
Feature
   ├─ Toast
   ├─ Dialog Close
   └─ router.refresh()
```

이렇게 하면 Server Action이 특정 UI Component의 존재를 알 필요가 없습니다.

---

# 28. `redirect`

Action 성공 이후 사용자를 다른 Route로 이동시키는 것이 Use Case 흐름 자체의 일부라면 `redirect`를 사용할 수 있습니다.

예:

```txt
생성 완료
→ 생성된 Resource 상세 페이지

로그인 완료
→ returnTo

탈퇴 완료
→ 홈
```

개념:

```ts
redirect("/somewhere");
```

`redirect`는 단순한 Client Toast나 Dialog 상태 변경과 달리 Server Navigation Control Flow입니다.

---

# 29. `redirect`와 `ActionResult`

성공 후 Client가 처리해야 할 UI 후처리가 많다면 `ActionResult` 반환이 적합합니다.

```txt
성공
→ Toast
→ Dialog 닫기
→ refresh
```

반대로 성공하면 즉시 다른 Route로 이동하는 흐름이라면 `redirect`가 자연스러울 수 있습니다.

```txt
성공
→ 상세 페이지로 이동
```

한 Action에 불필요하게 두 방식을 섞지 않습니다.

---

# 30. `redirect` 사용 시 주의

`redirect()`는 일반적인 함수 반환과 동일하게 취급하지 않습니다.

따라서 광범위한 `try/catch`로 감싸고 이를 일반 Error로 변환하지 않도록 주의합니다.

개념적으로:

```txt
Domain 처리
 ↓
필요한 Cache 무효화
 ↓
redirect
```

순서를 유지합니다.

Navigation Control Flow와 예상 가능한 Domain Failure를 구분합니다.

---

# 31. Action 이름

Server Action은 어떤 Application 작업을 수행하는지 이름으로 드러냅니다.

예:

```txt
createContentAction

updateProfileAction

deleteUserAction

blockUserAction
```

Domain Service와 구분하기 위해:

```txt
...Action
```

Suffix를 사용합니다.

파일 예:

```txt
create-content.action.ts
update-profile.action.ts
```

상세 Naming Convention은 `18_컨벤션.md`에서 정의합니다.

---

# 32. Action의 크기

Action이 다음처럼 길어지기 시작한다면 책임을 다시 검토합니다.

```txt
수십 줄의 상태 분기

여러 Repository 호출

복잡한 계산

Domain Permission 구현

Prisma Query

Provider API 호출
```

정상적인 Action은 대체로 다음 흐름을 읽는 것만으로 이해할 수 있어야 합니다.

```txt
Authenticate
Parse
Validate
Call Service
Map Result
Revalidate / Redirect
```

# 33. Server Action 예시

일반적인 Mutation Action은 공통 실행 Helper를 사용하여 다음처럼 구성할 수 있습니다.

```ts
"use server";

import { revalidatePath } from "next/cache";

import { executeFormAction } from "@repo/core/action";
import { UpdateUserRequestSchema } from "@repo/domain/user/client";
import { updateUserService } from "@repo/domain/user/server";

export async function updateUserAction(_previousState: unknown, formData: FormData) {
  const actor = await requireAdmin();

  const result = await executeFormAction({
    actionName: "user.update",
    schema: UpdateUserRequestSchema,
    formData,
    handler: (input) => updateUserService(actor, input),
    successMessage: "사용자 정보가 수정되었습니다.",
  });

  if (result.ok) {
    revalidatePath("/users");
  }

  return result;
}
```

`executeFormAction`은 다음 공통 흐름을 담당합니다.

```txt
FormData Parsing
  ↓
Zod Validation
  ↓
Domain Result → ActionResult 변환
  ↓
공통 Logging / Unexpected Error 처리
```

복수 값, 배열, JSON Field 등 기본 Flat Form 변환으로 표현할 수 없는 입력은 `parseFormData`로 명시적으로 구성합니다.

Authentication, Cache Revalidation, Redirect와 같은 Application 책임은 각 Server Action이 소유합니다.

---

# 34. Action이 하지 않는 일

위 예시의 Action에는 다음 코드가 없습니다.

```txt
prisma.user.findUnique

prisma.user.update

actor.id === user.id 판단

User 상태 전이 판단

Response DTO Mapping

Transaction 구성
```

모두 하위 Domain / Database Layer에서 처리합니다.

---

# 35. Server Action Test의 목적

Server Action Test는 Domain Business Logic을 다시 검증하는 테스트가 아닙니다.

Action Boundary가 올바르게 동작하는지를 검증합니다.

주요 대상:

```txt
Authentication

FormData Parsing

Input Normalization

Zod Validation

Domain Service 호출

ActionResult Mapping

Cache Revalidation

Redirect
```

---

# 36. 인증 테스트

보호된 Action에서는 인증 경계를 검증합니다.

예:

```txt
인증되지 않은 사용자
→ Action 실행 차단

일반 사용자가 Admin Action 호출
→ 차단

인증 성공
→ Domain Service 호출
```

Domain Permission 자체의 복잡한 경우의 수는 Domain Test에서 검증합니다.

---

# 37. Validation 테스트

잘못된 입력에서는:

```txt
Validation 실패

Domain Service 호출 안 됨

적절한 ActionResult 반환
```

을 확인합니다.

예:

```txt
빈 필수 필드

잘못된 UUID

허용되지 않은 Enum

길이 초과
```

Schema 자체의 모든 세부 경우를 Action Test에서 다시 반복할 필요는 없습니다.

Action이 Validation Boundary를 제대로 사용하는지를 확인합니다.

---

# 38. Domain Service 호출 테스트

유효한 입력에서는 Domain Service가 올바른 Request와 Actor를 받는지 검증합니다.

```txt
Authentication Actor

Validated Request

필요한 Context
```

Service 내부 Business Rule까지 Action Test에서 다시 구현하여 검증하지 않습니다.

---

# 39. ActionResult 테스트

Domain Service 결과에 따라 올바른 ActionResult가 반환되는지 확인합니다.

대표적인 경우:

```txt
Service 성공
→ 성공 ActionResult

예상 가능한 Domain 실패
→ 실패 ActionResult

Validation 실패
→ Validation ActionResult
```

Server 내부 Exception 정보가 그대로 Client 결과로 노출되지 않는지도 중요합니다.

---

# 40. `revalidatePath` 테스트

Mutation 성공 시 Cache 무효화가 필요한 Action이라면 다음을 검증합니다.

```txt
성공
→ revalidatePath 호출

실패
→ 불필요한 revalidatePath 호출 없음
```

어떤 Path를 무효화해야 하는지도 Action 책임에 포함된 경우 검증합니다.

---

# 41. `router.refresh()`는 Action Test 대상이 아니다

`router.refresh()`는 Client Feature의 책임이므로 Server Action Test에서는 검증하지 않습니다.

대신 해당 Feature 또는 Hook Test에서 검증할 수 있습니다.

예:

```txt
DeleteDialog

Action 성공
→ Dialog Close
→ router.refresh()
```

따라서 테스트 경계도 구현 책임과 동일합니다.

```txt
Server Action Test
  revalidatePath

Feature / Hook Test
  router.refresh
```

---

# 42. Redirect 테스트

Redirect를 사용하는 Action은 성공한 경우 올바른 Navigation이 발생하는지를 검증합니다.

동시에 실패 상황에서는 예상하지 않은 Redirect가 일어나지 않아야 합니다.

Redirect 구현의 Control Flow 특성을 고려하여 테스트합니다.

---

# 43. Mock 기준

Server Action Test에서는 Action 아래의 책임을 분리하기 위해 필요한 Dependency를 Mock할 수 있습니다.

대표적으로:

```txt
Authentication Guard

Domain Service

Next Cache API

Next Navigation API
```

반면 Prisma를 Mock하여 Action Test에서 Database 동작을 흉내 내지 않습니다.

Action이 Prisma를 직접 사용하면 안 되기 때문입니다.

Repository와 Database 동작은 Integration Test에서 검증합니다.

---

# 44. 테스트 중복을 피한다

각 계층의 테스트 책임은 다음과 같이 구분합니다.

```txt
Schema Test
  구조적 Validation

Domain Test
  Business Rule / Permission / Service

Repository Integration Test
  실제 Persistence

Server Action Test
  Application Boundary

Feature Test
  Client 후처리

E2E
  전체 사용자 흐름
```

하나의 Business Rule을 모든 계층에서 반복 검증하지 않습니다.

---

# 45. Server Action 추가 절차

새로운 Action을 추가할 때 다음 순서로 검토합니다.

```txt
1. 어떤 Domain Service를 호출하는가?

2. 인증이 필요한가?

3. 어떤 Actor Context가 필요한가?

4. FormData를 어떻게 Request로 변환하는가?

5. 사용할 Zod Schema가 있는가?

6. Domain Result를 어떤 ActionResult로 변환하는가?

7. Cache 무효화가 필요한가?

8. redirect가 필요한가?

9. Client에서 router.refresh가 필요한가?

10. Dialog / Form / Button 중 누가 성공 후처리를 소유하는가?

11. Action Boundary Test가 필요한가?
```

---

# 46. Mutation 후처리 책임 요약

Mutation의 성공 이후 처리를 다음처럼 구분합니다.

```txt
Server Action
├─ Domain Service 호출
├─ revalidatePath
└─ redirect 필요 시 수행


Client Feature
├─ Toast
├─ Dialog Close
├─ router.refresh
├─ Local State Reset
└─ 기타 UI Side Effect
```

이 경계를 유지하면 Action과 UI가 서로의 구현 세부사항을 알 필요가 없습니다.

---

# 47. 예시: Dialog Mutation

관리자 차단 Dialog를 예로 들면:

```txt
BlockUserDialog
      ↓
blockUserAction
      ↓
blockUserService
      ↓
Repository
      ↓
Database
```

성공 이후:

```txt
blockUserAction
  → 성공 ActionResult

BlockUserDialog
  → 성공 감지
  → Dialog 닫기
  → Toast
  → router.refresh()
```

Server Action이:

```txt
어떤 Dialog가 열려 있는가?

어떤 Toast를 보여줄 것인가?

현재 Client Router를 새로고침할 것인가?
```

를 알지 않습니다.

---

# 48. 예시: Redirect 기반 Form

생성 후 상세 페이지로 이동하는 Form이라면:

```txt
CreateForm
    ↓
createContentAction
    ↓
Domain Service
    ↓
성공
    ↓
revalidatePath(...)
    ↓
redirect(detailUrl)
```

처럼 Server Navigation으로 완료할 수도 있습니다.

이 경우 동일한 성공 흐름에 불필요한:

```txt
router.refresh()
```

를 추가하지 않습니다.

# 51. 핵심 원칙

```txt
Server Action은 Client와 Domain 사이의 Application Boundary다.

Action은 얇게 유지한다.

인증은 Action 진입 시 확인한다.

세부 인가는 Domain에서 판단한다.

FormData는 Action에서 Domain Request로 변환한다.

FormData를 Domain에 직접 넘기지 않는다.

Zod는 입력 구조를 검증한다.

Business Validation은 Domain이 담당한다.

Action은 Domain Service를 호출한다.

Action은 Repository를 직접 호출하지 않는다.

Action은 Prisma Query를 작성하지 않는다.

예상 가능한 결과는 ActionResult로 변환한다.

예기치 않은 Server Error를 Client에 그대로 노출하지 않는다.

revalidatePath는 Server Cache 무효화 책임이다.

router.refresh는 Client 화면 동기화 책임이다.

router.refresh는 Mutation을 소유한 Feature 수준의 Dialog, Form, Action Button 또는 Hook에서 수행한다.

범용 Design System Primitive는 router.refresh를 알지 않는다.

Toast와 Dialog Close도 Client Feature의 책임이다.

Navigation 자체가 성공 흐름이라면 redirect를 사용한다.

Action Test는 Boundary를 검증하고 Domain Business Logic을 중복 테스트하지 않는다.
```
