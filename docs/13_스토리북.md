# 스토리북

이 문서는 `boilerplate-turborepo`에서 Storybook을 사용하는 기준과 Story 작성 대상을 정의합니다.

Storybook의 목적은 모든 React Component에 Story를 만드는 것이 아닙니다.

다음과 같이 **독립적으로 관찰하고 조작할 가치가 있는 UI의 상태와 계약을 문서화하는 것**이 목적입니다.

```txt
UI 상태 확인
Component API 탐색
Visual Variant 비교
Interaction 확인
Accessibility 점검
공통 UI 사용 예시 제공
```

Storybook은 자동화 테스트를 대체하지 않습니다.

```txt
Storybook
  UI를 독립적으로 보고 탐색

Component Test
  기대 동작을 자동 검증

E2E Test
  실제 Application 흐름을 검증
```

전체 테스트 기준은 `12_테스트_전략.md`에서 설명합니다.

---

## 1. 기본 원칙

Story 작성의 기본 원칙은 다음과 같습니다.

```txt
독립적으로 렌더링할 가치가 있는 UI에 Story를 작성한다.

모든 Component에 Story를 강제하지 않는다.

Business Logic 자체를 Storybook에서 검증하지 않는다.

Server Runtime에 강하게 의존하는 Component는 억지로 Story로 만들지 않는다.

대표적인 상태와 Variant를 Story로 표현한다.

Controls는 의미 있는 Props만 조작할 수 있게 한다.

Accessibility Addon은 기본적인 접근성 문제를 조기에 발견하는 데 사용한다.

Story title은 실제 UI Layer와 구조를 반영한다.

Storybook을 실제 Application을 복제하는 공간으로 만들지 않는다.
```

---

## 2. Storybook 구성

Storybook 공통 설정은 다음 Package에서 관리합니다.

```txt
@repo/storybook-config
```

현재 Runtime에 따라 두 설정을 구분합니다.

```txt
@repo/storybook-config/nextjs
  Next.js App

@repo/storybook-config/react
  @repo/design-system
```

각각 사용하는 Framework는 다음과 같습니다.

```txt
Next.js App
  @storybook/nextjs-vite

Design System
  @storybook/react-vite
```

App과 일반 React Package의 Runtime 차이를 공통 설정에서 구분합니다.

---

## 3. Storybook 공통 설정의 책임

`@repo/storybook-config`는 다음과 같은 공통 설정을 담당합니다.

```txt
Story 검색 경로
Storybook Framework
Addon
Vite 설정
공통 Preview 설정
```

현재 기본 Addon은 다음과 같습니다.

```txt
@storybook/addon-docs
@storybook/addon-a11y
```

각 App의 `.storybook`에서는 App에 필요한 Alias 등 최소한의 설정만 추가합니다.

---

## 4. App Storybook

`apps/admin`, `apps/web`은 Next.js 기반 Storybook 설정을 사용합니다.

개념:

```txt
@repo/storybook-config/nextjs
              ↓
apps/*/.storybook/main.ts
              ↓
App Story
```

App 설정에서는 해당 App의 Source Alias를 Storybook에서도 동일하게 사용할 수 있도록 구성합니다.

예:

```txt
@
→ apps/[app]/src
```

Story 때문에 Production Import 구조를 별도로 만들지 않습니다.

---

## 5. Design System Storybook

`@repo/design-system`은 일반 React Storybook 설정을 사용합니다.

```txt
@repo/storybook-config/react
```

Design System은 Next.js Runtime을 전제로 하지 않으므로 다음 Framework를 사용합니다.

```txt
@storybook/react-vite
```

Story에서도 Package의 실제 Public UI Contract를 중심으로 작성합니다.

---

## 6. Story 작성 대상

Story 작성 여부는 Component 종류와 독립적인 UI 가치에 따라 판단합니다.

우선적으로 Story를 검토하는 대상은 다음과 같습니다.

```txt
Design System Component
Entity UI
Feature UI
Shared UI
다양한 Visual State를 가진 Component
여러 곳에서 재사용되는 Component
사용 방법을 UI로 확인하는 것이 유용한 Component
```

---

## 7. Design System Story

Design System Component는 Story 작성 우선순위가 높습니다.

Design System의 목적 자체가 여러 UI에서 재사용할 Presentation Contract를 제공하는 것이기 때문입니다.

향후 예:

```txt
Web Button
Web Dialog

Admin Button
Admin Table

ThemeToggleButton
```

Story에서는 실제 Component가 지원하는 범위에서 다음 상태를 확인할 수 있습니다.

```txt
기본 상태
주요 Variant
Disabled
Error
Loading
크기
Theme
중요 Interaction
```

존재하지 않는 Variant를 Storybook을 위해 새로 만들지 않습니다.

---

## 8. Design System Utility에는 Story를 작성하지 않는다

다음과 같은 코드는 Story 대상이 아닙니다.

```txt
form-error.utils.ts
form.utils.ts
theme.utils.ts
cn
Type Definition
Constant
```

이들은 필요한 경우 Unit Test로 검증합니다.

```txt
Presentation Component
→ Story 후보

Pure Logic
→ Unit Test 후보
```

---

## 9. Entity Story

Entity는 Business Object를 표현하는 UI입니다.

예:

```txt
MemberStatusBadge
OrderStatusBadge
ContentCard
MemberTable
```

Entity Story는 실제 Page 전체를 재현하는 것이 아니라 **해당 Business Object의 표현 상태**를 보여주는 데 집중합니다.

대표적인 Story 대상:

```txt
상태별 표현
데이터가 모두 존재하는 상태
Optional 값이 없는 상태
Empty State
긴 텍스트
여러 Row
```

실제로 해당 Component가 처리하는 상태만 작성합니다.

---

## 10. Entity Story에서 Business Logic을 구현하지 않는다

Story 안에서 Domain Service나 Repository를 호출하지 않습니다.

지양:

```txt
Story
 ↓
Domain Service
 ↓
Database
```

Story Data는 해당 UI Contract를 설명할 수 있는 명시적인 Fixture로 구성합니다.

```txt
Story Fixture
     ↓
Entity Component
```

Storybook은 Persistence 통합 환경이 아닙니다.

---

## 11. Feature Story

Feature는 사용자 Interaction을 포함하므로 독립적인 UI 검토 가치가 있을 때 Story를 작성합니다.

예:

```txt
Form
Dialog
Action Button
Interactive Filter
Upload UI
```

대표적으로 다음 상태를 Story로 표현할 수 있습니다.

```txt
기본 상태
Pending
Validation Error
Server Error
Disabled
Dialog Open
```

다만 실제 Component가 외부에서 해당 상태를 표현할 수 있는 경우에 한합니다.

---

## 12. 모든 Feature에 Story를 강제하지 않는다

Feature가 다음 Runtime에 강하게 의존한다면 Story 가치가 낮을 수 있습니다.

```txt
실제 Server Action
복잡한 Router Context
Authentication Runtime
Database State
Page 전체 Context
```

이 경우 Story를 위해 Production Architecture를 왜곡하지 않습니다.

다음 테스트가 더 적절할 수 있습니다.

```txt
Component Test
Integration Test
E2E
```

Story가 유용한 경우에만 작성합니다.

---

## 13. Server Action과 Story

Story에서 실제 Server Action을 실행하는 구조를 기본으로 하지 않습니다.

Feature Component가 Action을 직접 다루더라도 Story에서는 필요한 UI 상태를 독립적으로 표현할 수 있는지를 먼저 검토합니다.

Story의 목적은 다음이 아닙니다.

```txt
실제 Mutation 수행
```

목적은 다음에 가깝습니다.

```txt
Mutation UI 상태 확인
```

실제 Server Action 연결은 Component Test 또는 E2E에서 검증합니다.

---

## 14. Shared UI Story

App의 `shared`에 위치한 도메인 독립 UI도 반복 사용되고 독립적인 Presentation 책임이 있다면 Story를 작성할 수 있습니다.

예:

```txt
App Layout UI
Empty State
App Navigation UI
공통 Feedback UI
```

단순 Helper나 Layout Wrapper라는 이유만으로 Story를 만들지는 않습니다.

---

## 15. Story 존재 여부와 승격은 별개다

Story가 여러 곳에서 사용된다고 해서 Workspace Design System으로 승격하는 것은 아닙니다.

승격 기준은 `10_앱_구조.md`와 `11_디자인_시스템.md`를 따릅니다.

```txt
한 App에서만 공유
→ App Shared

Web 전체 Design Language
→ @repo/design-system/web 검토

Admin 전체 Design Language
→ @repo/design-system/admin 검토
```

Story 존재 여부는 Architecture 승격 기준이 아닙니다.

---

## 16. 기본적으로 Story를 작성하지 않는 대상

다음 대상은 기본적으로 Story를 작성하지 않습니다.

```txt
Page
Server Component 중심 View
Server Action
Domain Service
Repository
Schema
DTO
Mapper
Permission
Rule
Utility
Hook 자체
Type
Constant
Config
```

UI를 렌더링하지 않는 코드는 Storybook 대상이 아닙니다.

---

## 17. View Story

`views`는 Page 조립 단위이므로 기본적으로 Story를 작성하지 않습니다.

View는 다음 Dependency를 포함하기 쉽습니다.

```txt
Server Data
Search Params
Authentication
여러 Entity / Feature
Page Context
```

따라서 View 전체보다 내부 Entity와 Feature에 Story를 작성하는 것을 우선합니다.

다만 View 자체에 독립적으로 확인해야 할 중요한 Presentation State가 있다면 예외적으로 Story를 추가할 수 있습니다.

---

## 18. Page Story

Next.js `page.tsx`에는 Story를 작성하지 않는 것을 기본으로 합니다.

Page는 다음과 같은 App Router 책임을 갖기 때문입니다.

```txt
Route Entry
params / searchParams
Metadata
View 연결
```

Page 동작은 E2E에서 검증하는 편이 더 적절합니다.

---

## 19. Hook Story

Hook 자체를 Story로 만들지는 않습니다.

예:

```txt
useActionResultEffect
useFormInteractionState
useMediaQuery
useTheme
```

Hook은 필요한 경우 Unit 또는 React Test로 검증합니다.

Hook의 사용 결과가 중요한 UI Component가 있다면 해당 Component Story를 작성합니다.

예:

```txt
useTheme
  ↓
ThemeToggleButton
  ↓
Story
```

---

## 20. Story 파일 위치

Story는 기본적으로 대상 Component와 가까이 둡니다.

예:

```txt
member-status-badge/
├─ member-status-badge.tsx
├─ member-status-badge.test.tsx
└─ member-status-badge.stories.tsx
```

현재 Component 구조에 맞게 동일 Directory에 배치합니다.

Story 전용 중앙 Directory로 모든 Story를 이동하지 않습니다.

---

## 21. Story 파일 네이밍

기본 파일 이름:

```txt
*.stories.tsx
```

예:

```txt
button.stories.tsx
member-status-badge.stories.tsx
block-member-dialog.stories.tsx
```

React Component Story는 기본적으로 `.tsx`를 사용합니다.

---

## 22. `meta` 선언

Story의 `meta`는 명시적인 Type Annotation을 사용하는 것을 기본으로 합니다.

```ts
const meta: Meta<typeof Component> = {
  title: "...",
  component: Component,
};

export default meta;
```

이 형태를 기본 Style로 사용합니다.

---

## 23. Story Type

Story Object는 다음과 같이 정의합니다.

```ts
type Story = StoryObj<typeof meta>;
```

Story별로 필요한 `args`, `render`, `parameters` 등을 지정합니다.

Component API를 Story 전용 Wrapper 때문에 불필요하게 변경하지 않습니다.

---

## 24. App Story Title

App Story에서는 **App 이름을 Prefix로 반복하지 않습니다.**

예를 들어 `apps/admin`의 Storybook 안에서 다음과 같이 작성하지 않습니다.

```txt
Admin/Entities/Member/MemberStatusBadge
```

권장:

```txt
Entities/Member/MemberStatusBadge
```

Storybook 자체가 이미 Admin App Context이므로 `Admin`을 다시 붙일 필요가 없습니다.

---

## 25. App Story Title 구조

App Layer를 기준으로 다음 Prefix를 사용합니다.

```txt
Entities
Features
Shared
```

예:

```txt
Entities/Member/MemberStatusBadge

Entities/Order/OrderSummary

Features/Member/BlockMemberDialog

Features/User/UpdateProfileForm

Shared/Layout/Shell

Shared/Feedback/EmptyState
```

`Views`는 기본 Story 대상이 아니므로 일반적인 Story Title Prefix로 사용하지 않습니다.

---

## 26. Slice와 Story Title

App Story Title은 가능하면 다음 구조를 반영합니다.

```txt
Layer / Slice / Component
```

예:

```txt
Entities/User/UserProfileDetail

Features/Content/PublishContentDialog
```

Slice 내부의 실제 `ui` Segment 이름은 Sidebar에 반복하지 않습니다.

지양:

```txt
Entities/User/UI/UserProfileDetail
```

권장:

```txt
Entities/User/UserProfileDetail
```

`ui`는 File Structure Segment이지 Storybook 정보 구조의 핵심 개념은 아닙니다.

---

## 27. Design System Story Title

Design System Storybook은 하나의 Package 안에 여러 UI Context가 존재할 수 있으므로 `Web`, `Admin` 등의 영역을 Story Title에 표현할 수 있습니다.

예:

```txt
Web/Button

Web/Dialog

Admin/Button

Admin/Table

Theme/ThemeToggleButton
```

실제 Design System 구조가 구현된 시점에 해당 영역을 사용합니다.

아직 구현되지 않은 Component를 Story Title 규칙만을 위해 만들지 않습니다.

---

## 28. Form과 Toast Story

`form`의 Pure Utility는 Story 대상이 아닙니다.

향후 실제 공통 Form Component가 추가된다면 Story를 작성할 수 있습니다.

```txt
Form/...
```

`ToastProvider` 자체는 단순 Provider이므로 Story 가치가 낮을 수 있습니다.

Toast Presentation을 독립적으로 확인할 UI가 실제로 필요할 때 Story를 추가합니다.

Story 수를 채우기 위해 별도의 Demo Component를 만들지 않습니다.

---

## 29. Story 이름

Story 이름은 UI 상태를 표현합니다.

예:

```ts
export const Default: Story = {};

export const Disabled: Story = {};

export const Error: Story = {};

export const Empty: Story = {};
```

상태의 의미가 명확하다면 간결한 이름을 사용합니다.

---

## 30. Story를 너무 세분화하지 않는다

모든 Prop 조합을 개별 Story로 만들지 않습니다.

예를 들어:

```txt
size
×
variant
×
disabled
×
loading
```

의 모든 조합을 Story로 만들 필요는 없습니다.

대표적인 계약과 중요한 Edge State를 선택합니다.

예:

```txt
Default
Secondary
Destructive
Disabled
Loading
```

실제 Component API에 존재하는 상태만 작성합니다.

---

## 31. `args`

Component Props로 표현 가능한 상태는 `args`를 우선 사용합니다.

예:

```ts
export const Default: Story = {
  args: {
    children: "저장",
  },
};
```

이를 통해 Story와 Controls가 동일한 Component Contract를 사용하도록 합니다.

---

## 32. `render`

단순 `args`만으로 표현할 수 없는 상태에 `render`를 사용합니다.

예:

```txt
Stateful Interaction
여러 Component 조합
Wrapper가 필요한 Context
Controlled State
```

Story마다 불필요한 Wrapper Component를 만들지 않습니다.

---

## 33. Story 전용 Wrapper

Component가 Context Provider를 필요로 한다면 Storybook Decorator 또는 최소한의 Story Wrapper를 사용할 수 있습니다.

예:

```txt
Theme Provider
Form Context
필요한 Client Context
```

하지만 Story를 실행하기 위해 실제 Application 전체를 재현하지 않습니다.

---

## 34. Story Fixture

Story Data는 읽기 쉽고 의도를 알 수 있는 고정값을 사용합니다.

예:

```ts
const MEMBER = {
  id: "00000000-0000-4000-8000-000000000001",
  displayName: "홍길동",
};
```

Random Data Generator를 기본으로 사용하지 않습니다.

Story를 열 때마다 내용이 바뀌면 Visual 비교와 Debugging이 어려워집니다.

---

## 35. 실제 개인정보를 사용하지 않는다

Story Fixture에는 실제 사용자 정보나 Production Data를 사용하지 않습니다.

사용 가능한 예:

```txt
example.com
가상의 이름
고정 UUID
테스트용 Sample Data
```

Production Database를 Storybook에서 조회하지 않습니다.

---

## 36. Controls

Controls는 Component의 Public Props를 Storybook에서 조작하여 상태를 탐색하기 위한 기능입니다.

다음과 같은 Prop에 유용합니다.

```txt
variant
size
disabled
label
placeholder
boolean option
enum 형태 Prop
```

Controls의 목적은 **실제 Component API를 탐색하는 것**입니다.

---

## 37. Controls를 위한 가짜 Prop을 만들지 않는다

Storybook Controls에서 편하게 조작하기 위해 Production Component API에 Story 전용 Prop을 추가하지 않습니다.

지양:

```txt
storyMode
mockError
forceOpenForStory
```

Story에서만 필요한 상태는 Story Wrapper나 `render`에서 처리합니다.

---

## 38. 의미 없는 Controls는 숨긴다

다음과 같은 Prop은 Controls에서 직접 조작하는 가치가 낮을 수 있습니다.

```txt
복잡한 Callback
ReactNode
Internal Object
Framework Context
Function
```

필요하면 `argTypes`를 통해 Control을 비활성화합니다.

Storybook UI에 모든 Props를 억지로 노출하지 않습니다.

---

## 39. Callback

Callback Prop은 실제 Side Effect 대신 Storybook에서 Interaction을 확인할 수 있는 형태로 구성합니다.

Story에서 실제 Server Action이나 Database Mutation을 호출하지 않습니다.

```txt
onClick
  → Interaction 확인

onSubmit
  → UI Contract 확인
```

실제 Business Mutation은 Test와 Application에서 검증합니다.

---

## 40. Accessibility Addon

공통 Storybook 설정은 다음 Addon을 사용합니다.

```txt
@storybook/addon-a11y
```

Accessibility Addon은 Story 렌더링 결과에서 기본적인 접근성 문제를 조기에 발견하는 보조 도구입니다.

대표적으로 다음 문제를 확인하는 데 유용합니다.

```txt
Accessible Name
ARIA
색상 대비
Label
잘못된 Role
기본적인 HTML 접근성
```

---

## 41. Accessibility는 Addon만으로 완료되지 않는다

Accessibility Addon이 오류를 표시하지 않는다고 해서 Component가 완전히 접근 가능하다는 의미는 아닙니다.

다음 항목은 Component Test나 별도 검토가 필요할 수 있습니다.

```txt
Keyboard Navigation
Focus 이동
Dialog Focus Management
실제 Screen Reader 경험
복잡한 Interaction
```

Storybook A11y는 자동 점검 도구이지 접근성 품질의 유일한 기준이 아닙니다.

---

## 42. A11y 오류를 무조건 비활성화하지 않는다

Accessibility Addon에서 오류가 발생하면 먼저 Component 자체의 문제인지 확인합니다.

지양:

```txt
오류 발생
→ Rule Disable
```

정말 의도적인 예외이고 해결할 수 없는 명확한 이유가 있을 때만 예외 설정을 검토합니다.

---

## 43. Theme Story

Theme Runtime이 구현되면 Light / Dark 상태를 Storybook에서 확인할 수 있도록 구성합니다.

예:

```txt
Web Light
Web Dark
Admin Light
Admin Dark
```

Story마다 색상 값을 직접 다시 정의하지 않고 Design System의 실제 Semantic Token과 Theme Style을 사용합니다.

---

## 44. Storybook Styles

Design System Storybook은 Story용 Style Entry를 통해 실제 Token과 Theme를 사용합니다.

현재 기준:

```txt
tokens.css
storybook.css
```

Storybook 전용 스타일이 Production Design Token과 별개의 디자인 체계를 만들지 않도록 합니다.

---

## 45. Story와 Component Test

Story가 있다고 Component Test가 불필요해지는 것은 아닙니다.

예:

```txt
Story
  Disabled 상태를 눈으로 확인

Component Test
  Disabled 상태에서 Click Callback이 실행되지 않음을 자동 검증
```

둘은 목적이 다릅니다.

---

## 46. Story와 E2E

Story에서는 독립 UI를 확인합니다.

E2E에서는 실제 Application 흐름을 확인합니다.

예:

```txt
BlockMemberDialog Story
  Dialog UI와 상태 확인

Members E2E
  실제 회원 차단
  ↓
  화면 갱신 확인
```

Story에서 E2E 환경을 재현하지 않습니다.

---

## 47. Story와 Domain Rule

Story Fixture는 특정 Domain State를 표현할 수 있지만 Domain Rule 자체를 Story에서 검증하지 않습니다.

예:

```txt
OrderStatusBadge
  PAID Story
  CANCELED Story
```

는 적절합니다.

반면:

```txt
PAID에서는 주문 취소가 가능한가?
```

라는 Business Rule 검증은 Domain Unit Test의 책임입니다.

---

## 48. Story 작성 판단 순서

새로운 UI Component를 구현할 때 다음 순서로 판단합니다.

```txt
1. 독립적인 Presentation 책임이 있는가?

2. 여러 상태를 눈으로 비교할 가치가 있는가?

3. 재사용되는 Component인가?

4. Component API 사용 예시가 유용한가?

5. Server Runtime 없이 의미 있게 렌더링할 수 있는가?

6. Story보다 Component Test나 E2E가 더 적절하지 않은가?
```

Story가 유용하다면 작성합니다.

---

## 49. Story를 우선 작성할 대상

우선순위를 정한다면 다음과 같습니다.

```txt
1. Design System Component

2. 재사용되는 Entity UI

3. 복잡한 Interactive Feature UI

4. App Shared UI

5. 독립적인 Visual State가 중요한 기타 UI
```

Story 개수를 채우는 것이 목표는 아닙니다.

---

## 50. Story를 작성하지 않는 판단도 정상이다

새 Component를 만들었지만 다음에 해당한다면 Story를 만들지 않는 것이 정상입니다.

```txt
Page 전용 조립 Component

단순 Wrapper

Server Data에 강하게 의존

시각적으로 독립된 계약이 없음
```

Story가 없다는 것을 자동으로 문서화 부족으로 판단하지 않습니다.

---

## 51. Story 유지보수

Component API가 변경되면 관련 Story도 함께 수정합니다.

다음을 방치하지 않습니다.

```txt
존재하지 않는 Prop 사용

Deprecated Variant

실제 UI와 다른 Fixture

삭제된 Component Story

깨진 Story
```

Story는 Component 사용 계약의 일부로 유지합니다.

---

## 52. Component 제거

Component가 제거되었다면 Story도 함께 제거합니다.

```txt
Source 제거
 ↓
Test 검토
 ↓
Story 제거
 ↓
Public Export 검토
```

향후 다시 사용할 가능성이 있다는 이유로 사용되지 않는 Story를 남겨두지 않습니다.

---

## 53. Storybook Build

Storybook은 개발 중 UI를 탐색하는 도구이지만 Build 가능한 상태도 유지해야 합니다.

Design System:

```bash
pnpm --filter @repo/design-system build-storybook
```

각 App에 Storybook Build Script가 있다면 해당 Workspace에서도 동일하게 검증할 수 있습니다.

Storybook Build 실패는 다음 문제를 발견할 수 있습니다.

```txt
잘못된 Import

깨진 Story

누락된 CSS

Alias 오류

Browser에서 사용할 수 없는 Server Dependency

삭제된 Public API 사용
```

---

## 54. Storybook과 Server / Client Boundary

Storybook은 Browser 기반 UI Runtime입니다.

따라서 Story 대상 Component가 다음과 같은 Server Dependency를 직접 요구한다면 구조를 검토합니다.

```txt
server-only

Database

Secret

Server Env

Node.js 전용 API
```

Entity나 Feature가 UI Component이면서 Server Dependency와 강하게 결합되어 있다면 Client / Server 책임이 제대로 분리되었는지 확인합니다.

---

## 55. Story 작성 시 Import

Story는 실제 Production Component와 동일한 Import Boundary를 유지합니다.

App 내부에서는 현재 App 구조를 따릅니다.

예:

```ts
import MemberStatusBadge from "./member-status-badge";
```

또는 필요한 App Public API를 사용합니다.

Workspace Package의 내부 Source Path를 우회하지 않습니다.

지양:

```ts
import Button from "@repo/design-system/src/admin/button";
```

실제 Public API가 있다면 이를 사용합니다.

```ts
import { Button } from "@repo/design-system/admin";
```

---

## 56. Story와 Mock

Story에서 Mock은 외부 의존성을 실제로 실행하지 않기 위해 사용할 수 있습니다.

대표적인 대상:

```txt
Server Action

Router

External API

시간 의존 데이터
```

다만 Story가 Production Logic의 가짜 구현을 재현하는 공간이 되지 않도록 합니다.

Mock은 필요한 UI 상태를 만드는 최소한의 경계로만 사용합니다.

---

## 57. Story 상태를 만들기 어려운 경우

특정 상태의 Story를 만들기 위해 Production Component를 지나치게 수정해야 한다면 Story 작성 자체를 다시 검토합니다.

다음과 같은 상황은 신호가 될 수 있습니다.

```txt
Story 전용 Prop이 여러 개 필요

실제 App 전체 Context를 복제해야 함

Server Runtime 대부분을 Mock해야 함

Database Fixture까지 필요
```

이 경우 Component Test나 E2E가 더 적합할 수 있습니다.

---

## 58. Storybook과 Generator

Component Generator가 Story 생성 옵션을 지원한다면 Story 파일은 이 문서의 규칙을 따라야 합니다.

예:

```txt
pnpm generate ... --story
```

Generator가 Story를 생성한다고 해서 해당 UI에 Story가 반드시 필요하다는 의미는 아닙니다.

Story 옵션은 **Story 작성 가치가 있는 Component에 선택적으로 사용**합니다.

Generator 상세 기준은 `14_코드_생성기.md`에서 설명합니다.

---

## 59. Story title과 실제 디렉터리 구조

Story title은 File System을 한 글자도 빠짐없이 복제하는 것이 목적이 아닙니다.

예를 들어 실제 구조가:

```txt
entities/
└─ user/
   └─ ui/
      └─ user-profile-detail/
```

이라도 Story title은:

```txt
Entities/User/UserProfileDetail
```

이면 충분합니다.

Storybook Sidebar에서는 개발자가 **UI가 어느 Layer와 Slice에 속하는지 빠르게 이해하는 것**을 우선합니다.

---

## 60. 현재 Storybook 구조의 기본 방향

현재 Boilerplate의 Storybook 책임은 다음처럼 정리합니다.

```txt
apps/admin
  Next.js Storybook
  Entities / Features / Shared UI

apps/web
  Next.js Storybook
  Entities / Features / Shared UI

@repo/design-system
  React Storybook
  Web / Admin / Theme 등의 공통 UI
```

각 App의 Story title에는 App 이름을 반복하지 않습니다.

Design System은 하나의 Package에서 여러 UI Context를 다룰 수 있으므로 필요한 경우 `Web`, `Admin`, `Theme` 등의 Prefix를 사용할 수 있습니다.

## 62. 핵심 원칙

```txt
Storybook은 독립적인 UI 상태와 사용 계약을 탐색하는 공간이다.

모든 Component에 Story를 강제하지 않는다.

Design System Component는 Story 작성 우선순위가 높다.

Entity는 Business Object의 표현 상태를 Story로 보여줄 수 있다.

Feature는 독립적인 Interaction UI 가치가 있을 때 Story를 작성한다.

Shared UI도 재사용성과 독립적인 Presentation 책임이 있을 때 Story를 작성한다.

View와 Page는 기본적으로 Story를 작성하지 않는다.

Server Action, Domain, Repository, Utility에는 Story를 작성하지 않는다.

Hook 자체보다 Hook을 사용하는 UI Component에 Story를 작성한다.

App Story title에는 Admin, Web 같은 App 이름을 Prefix로 붙이지 않는다.

App Story title은 Layer / Slice / Component 구조를 따른다.

ui Segment 이름은 Story title에서 생략한다.

Design System Storybook에서는 Web / Admin / Theme Context를 Prefix로 사용할 수 있다.

Story의 대표 상태만 작성하고 모든 Prop 조합을 나열하지 않는다.

Props로 표현 가능한 상태는 args를 우선한다.

복잡한 상태에만 render와 Wrapper를 사용한다.

Controls를 위해 Production API를 왜곡하지 않는다.

Accessibility Addon은 접근성 문제를 조기에 발견하는 보조 도구다.

Storybook A11y 결과만으로 접근성이 완성되었다고 판단하지 않는다.

Story에서 실제 Database나 Production Server Action을 실행하지 않는다.

Story Fixture는 고정되고 가상의 데이터를 사용한다.

Storybook은 Component Test와 E2E를 대체하지 않는다.

Component가 제거되면 Story도 함께 제거한다.

Story를 위해 Production Architecture를 복잡하게 만들지 않는다.
```
