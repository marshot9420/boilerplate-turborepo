# 코드 생성기

이 문서는 `boilerplate-turborepo`에서 제공하는 코드 Generator의 사용 방법과 생성 규칙을 설명합니다.

Generator는 반복적인 디렉터리 생성, 기본 파일 작성, 테스트 파일 작성, Barrel Export 갱신 등의 작업을 자동화하기 위해 사용합니다.

목적은 다음과 같습니다.

```txt
반복적인 파일 생성 비용을 줄인다.
프로젝트 구조를 일관되게 유지한다.
파일과 Component Naming을 통일한다.
테스트와 Story의 기본 골격을 빠르게 만든다.
Barrel Export 누락을 줄인다.
새로운 Domain과 UI Slice의 시작점을 표준화한다.
```

Generator가 생성한 코드는 완성된 기능이 아닙니다.

```txt
Generator
  → 반복되는 기본 Scaffold 생성

개발자
  → 실제 요구사항에 맞게 구현
  → 필요 없는 파일 제거
  → 필요한 Segment 추가
  → 테스트와 Story 보완
```

---

## 1. 실행 방법

루트에서 다음 명령을 사용합니다.

```bash
pnpm generate <type> <name> [options]
```

예:

```bash
pnpm generate domain content

pnpm generate component empty-state --target all --category feedback

pnpm generate entity order-status-badge --app admin --domain order

pnpm generate feature update-profile --app web --domain user --ui update-profile-form

pnpm generate view order-list-view --app admin --domain order
```

루트의 `generate` Script는 내부적으로 `@repo/generators`를 실행합니다.

```txt
pnpm generate
  ↓
@repo/generators
  ↓
tooling/generators/src/cli.ts
  ↓
각 Generator
```

---

## 2. 제공 Generator

현재 제공하는 Generator는 다음과 같습니다.

```txt
domain
component
entity
feature
view
```

역할:

```txt
domain
  packages/domain의 Domain Scaffold 생성

component
  @repo/design-system의 공통 UI Component 생성

entity
  apps/*의 Entity UI 생성

feature
  apps/*의 Feature Slice와 UI 생성

view
  apps/*의 View Slice 생성
```

# 3. 공통 Naming 규칙

Generator 입력값은 프로젝트 Naming Convention에 맞게 정규화됩니다.

예:

```txt
orderClaim
order_claim
order claim
order-claim
```

은 필요한 위치에 따라 다음 형태로 변환됩니다.

```txt
파일 / 디렉터리
  order-claim

Component / Type
  OrderClaim

변수
  orderClaim

상수
  ORDER_CLAIM
```

기본 규칙:

```txt
파일명
  kebab-case

디렉터리명
  kebab-case

React Component
  PascalCase

Type / Interface
  PascalCase

함수
  camelCase

Domain Constant
  CONSTANT_CASE
```

Generator를 사용한 뒤 임의로 다른 Naming Convention으로 변경하지 않습니다.

# 4. 기존 파일 처리

Generator는 기존 코드를 무조건 덮어쓰는 용도로 사용하지 않습니다.

기본 원칙:

```txt
이미 존재하는 파일을 보호한다.
기존 Export를 보존한다.
새 Export를 추가할 때 기존 구조와 정렬 규칙을 유지한다.
```

Generator마다 기존 파일 처리 방식은 다를 수 있으므로 실행 로그를 확인합니다.

Generator 실행 후에는 생성된 파일뿐 아니라 갱신된 `index.ts`, `client.ts`, `server.ts`, `package.json`도 함께 확인합니다.

---

# 5. `domain`

새로운 Business Domain의 기본 Scaffold를 생성합니다.

기본 사용법:

```bash
pnpm generate domain <name>
```

예:

```bash
pnpm generate domain content
```

---

## 5.1 기본 생성 결과

```bash
pnpm generate domain content
```

을 실행하면 기본적으로 다음 Domain 구조를 생성합니다.

```txt
packages/domain/src/content/
├─ test/
│  ├─ content.mapper.test.ts
│  ├─ content.permission.test.ts
│  └─ content.schema.test.ts
├─ content.constant.ts
├─ content.dto.ts
├─ content.error.ts
├─ content.mapper.ts
├─ content.permission.ts
├─ content.schema.ts
├─ content.service.ts
├─ client.ts
└─ server.ts
```

각 파일의 기본 역할:

```txt
content.constant.ts
  Domain 상수

content.dto.ts
  Response DTO

content.error.ts
  Domain Error Code

content.schema.ts
  Zod Schema
  Request Input
  Query Type

content.mapper.ts
  Domain Response Mapper

content.permission.ts
  Permission Scaffold

content.service.ts
  Domain Service Scaffold

client.ts
  Client-safe Public API

server.ts
  Server-only Public API

test/
  Domain Unit Test
```

생성되는 역할 파일은 개발 시작을 빠르게 하기 위한 Scaffold입니다.

실제 Domain에서 필요하지 않은 역할은 제거할 수 있습니다.

반대로 실제 책임이 커지면 다음과 같이 분리할 수 있습니다.

```txt
services/
rules/
schemas/
dto/
```

Generator가 만든 최초 구조를 영구적인 고정 구조로 간주하지 않습니다.

---

## 5.2 Domain Public API

`client.ts`는 Browser에서도 사용할 수 있는 API만 공개합니다.

대표적으로:

```txt
constant
DTO type
schema
schema input type
query type
```

를 공개합니다.

Public API는 Wildcard Export를 사용하지 않고 명시적인 Named Export를 사용합니다.

예:

```ts
export { ORDER_CLAIM_ITEM } from "./order-claim-item.constant";
export type { OrderClaimItemDetailResponse, OrderClaimItemResponse } from "./order-claim-item.dto";
```

실제 Formatter와 Lint Rule에 따라 한 줄에 들어갈 수 있는 Export는 한 줄로 정리될 수 있습니다.

`server.ts`는 다음처럼 Server 전용 API를 공개합니다.

```txt
error
mapper
permission
service
```

그리고 파일 첫 줄에서 Server Boundary를 명시합니다.

```ts
import "server-only";
```

`client.ts`, `server.ts` 모두 `export *`를 사용하지 않습니다.

---

## 5.3 `--repository`

Persistence가 필요한 Domain에서는 Repository를 함께 생성할 수 있습니다.

```bash
pnpm generate domain content --repository
```

`--repository`를 사용하면 기본 Domain Scaffold에 추가하여 다음 구조를 생성합니다.

```txt
packages/database/src/content/
├─ content.repository.ts
├─ content.repository.test.ts
├─ content.repository.integration.test.ts
└─ index.ts
```

역할:

```txt
content.repository.ts
  Prisma 기반 Repository Scaffold

content.repository.test.ts
  Repository Adapter Unit Test

content.repository.integration.test.ts
  실제 Test Database 기반 Integration Test Scaffold

index.ts
  Repository Public API
```

그리고 `packages/database/package.json`의 Public Export도 추가합니다.

예:

```json
{
  "exports": {
    "./content": "./src/content/index.ts"
  }
}
```

---

## 5.4 Repository 옵션을 분리한 이유

모든 Domain이 Persistence를 필요로 하는 것은 아닙니다.

따라서:

```bash
pnpm generate domain content
```

은 Domain Scaffold만 생성하고,

```bash
pnpm generate domain content --repository
```

은 Database Layer까지 함께 생성합니다.

경계:

```txt
domain
  Business Domain 생성

--repository
  Persistence 책임까지 추가
```

`--repository`는 Domain 내부의 작은 역할을 On/Off하는 옵션이 아니라 **다른 Package인 `@repo/database`까지 생성 범위를 확장하는 옵션**입니다.

---

## 5.5 Repository 생성 전제

Repository Template은 Prisma Model을 기준으로 생성됩니다.

따라서 실제 작업에서는 해당 Domain의 Prisma Model이 준비되어 있어야 합니다.

예:

```txt
Prisma Model 정의
  ↓
Prisma Client Generate
  ↓
pnpm generate domain product --repository
  ↓
생성된 Repository를 실제 Model에 맞게 수정
```

Generator가 만든 CRUD 함수가 해당 Domain의 최종 Repository 계약이라는 의미는 아닙니다.

필요 없는 CRUD는 제거하고 실제 Use Case에 필요한 Query를 추가합니다.

---

## 5.6 Domain Test

Domain Unit Test는 Domain Slice 내부의 `test/`에 둡니다.

```txt
packages/domain/src/content/
└─ test/
   ├─ content.mapper.test.ts
   ├─ content.permission.test.ts
   ├─ content.schema.test.ts
   └─ content.service.test.ts
```

Repository를 포함한 경우 기본 Service 구현이 함께 생성되므로 Service Test도 추가될 수 있습니다.

테스트의 최종 범위는 `12_테스트_전략.md`를 따릅니다.

Generator가 만든 Placeholder Test를 그대로 유지해야 하는 것은 아닙니다.

실제 Domain Rule에 맞게 수정합니다.

# 6. `component`

`component` Generator는 `@repo/design-system`의 공통 UI Component를 생성합니다.

사용법:

```bash
pnpm generate component <name> --target <target> --category <category>
```

예:

```bash
pnpm generate component empty-state --target all --category feedback

pnpm generate component phone-input --target web --category inputs

pnpm generate component field --target admin --category form
```

---

## 6.1 `--target`

생성 대상을 지정합니다.

```txt
web
admin
all
```

예:

```bash
pnpm generate component button --target web --category actions
```

```bash
pnpm generate component table --target admin --category data-display
```

```bash
pnpm generate component empty-state --target all --category feedback
```

`all`은 동일한 역할의 Component를 Web과 Admin 양쪽에 생성할 때 사용합니다.

---

## 6.2 `--category`

Design System 내부 Category를 지정합니다.

예:

```txt
actions
feedback
form
inputs
layouts
navigation
data-display
```

실제 Category는 현재 Design System 구조에 맞게 선택합니다.

예:

```bash
pnpm generate component empty-state --target web --category feedback
```

개념적인 생성 위치:

```txt
packages/design-system/src/web/feedback/empty-state/
```

Admin:

```txt
packages/design-system/src/admin/feedback/empty-state/
```

---

## 6.3 생성 결과

Component Generator는 대상 Component를 독립적인 Component Directory에 생성합니다.

개념:

```txt
packages/design-system/src/web/feedback/
└─ empty-state/
   ├─ empty-state.tsx
   ├─ empty-state.test.tsx
   ├─ empty-state.stories.tsx
   └─ index.ts
```

실제 Generator가 관리하는 Public Export도 함께 갱신합니다.

Generator가 만든 Component에는 Business Domain Logic을 넣지 않습니다.

```txt
허용
  UI
  Styling
  Accessibility
  Interaction
  Generic Props

금지
  Order
  Product
  User
  Payment
  Domain Permission
  Server Action
```

Design System의 책임은 `11_디자인_시스템.md`를 따릅니다.

---

## 6.4 `all`

`--target all`은 Web과 Admin 양쪽에 동일한 이름의 Component 시작점을 생성하기 위한 옵션입니다.

```bash
pnpm generate component empty-state --target all --category feedback
```

개념:

```txt
packages/design-system/src/
├─ web/
│  └─ feedback/
│     └─ empty-state/
└─ admin/
   └─ feedback/
      └─ empty-state/
```

두 Component가 이후 동일한 구현을 유지해야 한다는 의미는 아닙니다.

Web과 Admin의 Design Language가 달라지면 각자 독립적으로 발전할 수 있습니다.

# 7. `entity`

`entity` Generator는 앱에서 Business Object를 표현하는 Entity UI를 생성합니다.

사용법:

```bash
pnpm generate entity <name> --app <app> --domain <domain>
```

예:

```bash
pnpm generate entity order-status-badge --app admin --domain order
```

```bash
pnpm generate entity product-card --app web --domain product
```

---

## 7.1 `--app`

대상 Application을 지정합니다.

```txt
web
admin
```

예:

```bash
pnpm generate entity user-status-badge --app admin --domain user
```

---

## 7.2 `--domain`

Entity가 속하는 Domain Slice를 지정합니다.

```bash
pnpm generate entity order-status-badge --app admin --domain order
```

여기서:

```txt
Layer
  entities

Slice
  order

Segment
  ui

Component
  order-status-badge
```

가 됩니다.

---

## 7.3 생성 결과

예:

```bash
pnpm generate entity order-status-badge --app admin --domain order
```

개념적인 결과:

```txt
apps/admin/src/entities/order/
└─ ui/
   └─ order-status-badge/
      ├─ order-status-badge.tsx
      ├─ order-status-badge.test.tsx
      ├─ order-status-badge.stories.tsx
      └─ index.ts
```

그리고 필요한 상위 Barrel Export도 현재 앱 구조에 맞게 갱신합니다.

예:

```txt
order-status-badge/index.ts
        ↓
entities/order/ui/index.ts
        ↓
entities/order/index.ts
        ↓
entities/index.ts
```

실제 Generator가 관리하는 Export 단계까지만 자동 갱신합니다.

---

## 7.4 Entity의 책임

Entity Generator는 다음 성격의 UI에 사용합니다.

```txt
Status Badge
Summary
Card
Table
Detail
Information
List Item
```

기준:

```txt
도메인 객체를 표시한다.
사용자 행위 자체를 구현하지 않는다.
Server Action을 직접 조립하는 Feature 역할을 맡지 않는다.
```

예:

```txt
OrderStatusBadge
ProductCard
UserSummary
PaymentTable
```

# 8. `feature`

`feature` Generator는 사용자가 수행하는 행위 단위의 Feature Slice를 생성합니다.

사용법:

```bash
pnpm generate feature <name> --app <app> --domain <domain> --ui <ui-name>
```

예:

```bash
pnpm generate feature update-profile \
  --app web \
  --domain user \
  --ui update-profile-form
```

```bash
pnpm generate feature register-order \
  --app web \
  --domain order \
  --ui register-order-dialog
```

```bash
pnpm generate feature logout \
  --app admin \
  --domain auth \
  --ui logout-button
```

---

## 8.1 `--app`

대상 App을 지정합니다.

```txt
web
admin
```

---

## 8.2 `--domain`

Feature가 속하는 Domain Namespace를 지정합니다.

예:

```txt
features/user/update-profile
features/order/register-order
features/auth/logout
```

---

## 8.3 `--ui`

Feature에서 최초로 생성할 UI Component 이름을 지정합니다.

예:

```bash
pnpm generate feature update-profile \
  --app web \
  --domain user \
  --ui update-profile-form
```

개념적인 구조:

```txt
apps/web/src/features/user/update-profile/
├─ ui/
│  └─ update-profile-form/
│     ├─ update-profile-form.tsx
│     ├─ update-profile-form.test.tsx
│     ├─ update-profile-form.stories.tsx
│     └─ index.ts
└─ index.ts
```

---

## 8.4 Feature의 책임

Feature는 사용자 행위를 기준으로 만듭니다.

예:

```txt
create-product
update-profile
delete-user
logout
register-order
publish-content
```

Feature 안에서 가능한 것:

```txt
Form
Button
Dialog
사용자 입력
Client Validation
useActionState
useFormStatus
Server Action 연결
Toast
Dialog Close
router.refresh()
```

Feature 안에 넣지 않는 것:

```txt
Domain Business Rule
Repository
Prisma Query
Page 전체 조립
순수 Entity 표시만 담당하는 UI
```

---

## 8.5 Segment 확장

Generator는 최초 UI Scaffold를 생성하지만 Feature가 성장하면 필요한 Segment를 추가합니다.

예:

```txt
features/order/register-order/
├─ ui/
├─ hooks/
├─ lib/
├─ constants/
├─ types/
└─ index.ts
```

모든 Segment를 미리 만들지 않습니다.

실제 책임이 생길 때 추가합니다.

---

# 9. `view`

`view` Generator는 페이지 또는 화면 단위의 View Slice를 생성합니다.

사용법:

```bash
pnpm generate view <name> --app <app> --domain <domain>
```

예:

```bash
pnpm generate view order-list-view --app admin --domain order

pnpm generate view order-detail-view --app admin --domain order

pnpm generate view my-profile-view --app web --domain user
```

---

## 9.1 `--app`

View가 생성될 대상 Application을 지정합니다.

```txt
web
admin
```

---

## 9.2 `--domain`

View가 속하는 Domain Namespace를 지정합니다.

예:

```bash
pnpm generate view order-list-view --app admin --domain order
```

결과 구조는 다음 방향을 따릅니다.

```txt
apps/admin/src/views/order/order-list-view/
```

---

## 9.3 생성 결과

View는 View Slice와 최초 UI Scaffold를 생성합니다.

개념:

```txt
apps/admin/src/views/order/order-list-view/
├─ ui/
│  └─ order-list-view.tsx
└─ index.ts
```

실제 View 구현이 커지면:

```txt
views/order/order-list-view/
├─ ui/
│  ├─ order-list-view.tsx
│  └─ order-list-view-content.tsx
├─ hooks/
├─ lib/
├─ constants/
├─ types/
└─ index.ts
```

처럼 필요한 Segment를 추가합니다.

---

## 9.4 View에는 Story를 기본 생성하지 않는다

View는 페이지 조립 단위이므로 Storybook Story를 기본 작성 대상으로 보지 않습니다.

```txt
Entity
  독립적인 표시 UI
  → Story 작성 가치 높음

Feature
  독립적인 Interaction UI
  → Story 작성 가능

View
  Page Context와 여러 Layer 조립
  → Story 기본 제외
```

Storybook 기준은 `13_스토리북.md`를 따릅니다.

# 10. 앱 구조와 Generator

App UI Generator는 `10_앱_구조.md`에서 정의한 다음 구조를 따릅니다.

```txt
Layer
  ↓
Slice
  ↓
Segment
```

Entity:

```txt
entities
  ↓
domain
  ↓
ui
  ↓
component
```

Feature:

```txt
features
  ↓
domain
  ↓
feature
  ↓
ui
```

View:

```txt
views
  ↓
domain
  ↓
view
  ↓
ui
```

예:

```txt
apps/admin/src/
├─ entities/
│  └─ order/
│     └─ ui/
│        └─ order-status-badge/
│
├─ features/
│  └─ order/
│     └─ update-shipping-status/
│        └─ ui/
│
└─ views/
   └─ order/
      └─ order-detail-view/
         └─ ui/
```

Generator는 이 Layer 구조를 우회하는 별도 디렉터리 체계를 만들지 않습니다.

# 11. Colocation 원칙

Generator가 생성한 Slice 안에서 Component 전용 코드는 가능한 한 Component와 가까이 둡니다.

예:

```txt
update-profile-form/
├─ update-profile-form.tsx
├─ update-profile-form.test.tsx
├─ update-profile-form.stories.tsx
└─ use-update-profile-form.ts
```

이 Hook이 같은 Feature 내 여러 UI에서 사용되기 시작하면:

```txt
update-profile/
├─ ui/
└─ hooks/
   └─ use-update-profile-form.ts
```

로 승격할 수 있습니다.

Generator 결과가 이후 구조 변경을 금지하는 것은 아닙니다.

# 12. 테스트 생성

Generator가 테스트 파일을 만드는 경우 테스트 종류는 해당 Layer의 책임을 따릅니다.

```txt
Domain
  Unit Test

Repository
  Unit Test
  Integration Test

Design System Component
  Component Test

Entity
  Component Test

Feature
  Component Test

View
  필요한 경우 Component Test
```

테스트 파일 Naming:

```txt
*.test.ts
*.test.tsx
*.integration.test.ts
*.integration.test.tsx
```

Repository Integration Test는 실제 Test Database를 사용하는 방향으로 확장합니다.

전체 기준은 `12_테스트_전략.md`를 따릅니다.

# 13. Story 생성

Story가 생성되는 UI Generator는 `13_스토리북.md`의 규칙을 따라야 합니다.

App Story title은 App 이름을 Prefix로 붙이지 않습니다.

예:

```txt
Entities/Order/OrderStatusBadge

Features/User/UpdateProfileForm
```

지양:

```txt
Admin/Entities/Order/OrderStatusBadge

Web/Features/User/UpdateProfileForm
```

App Storybook 자체가 이미 어느 App인지 알고 있기 때문입니다.

View는 기본 Story 작성 대상이 아닙니다.

# 14. Barrel Export

Generator는 Component 파일만 만드는 것이 아니라 필요한 Public API도 함께 갱신합니다.

기본 원칙:

```txt
Public API를 명시한다.

기존 Export를 제거하지 않는다.

새 Export를 추가한다.

프로젝트 Lint / Formatter 결과와 동일한 형태를 생성한다.

Named Export를 사용한다.

불필요한 export *를 생성하지 않는다.
```

Domain의:

```txt
client.ts
server.ts
```

와 Database의:

```txt
index.ts
```

도 같은 원칙을 따릅니다.

App의 Entity / Feature / View Barrel도 각 Layer의 현재 Export Convention을 따릅니다.

# 15. 생성 후 확인

Generator 실행 후 바로 Business Logic 구현을 시작하기 전에 생성 결과를 확인합니다.

기본 확인 항목:

```txt
생성 위치가 올바른가?

Layer / Slice / Segment가 올바른가?

파일명이 kebab-case인가?

Component 이름이 PascalCase인가?

Public Export가 추가되었는가?

Client / Server Export Boundary가 올바른가?

필요한 테스트가 생성되었는가?

Story title이 앱 이름 없이 시작하는가?

불필요한 파일이 있다면 제거했는가?
```

그리고 구현을 완료한 뒤 일반 Repository 검증을 수행합니다.

```bash
pnpm lint
pnpm check-types
pnpm test
```

Integration Test가 변경되었다면 해당 테스트도 실행합니다.

# 16. Generator는 Architecture를 대신하지 않는다

Generator가 특정 파일을 생성했다는 이유만으로 그 파일이 반드시 필요한 것은 아닙니다.

예를 들어 Domain Generator가:

```txt
constant
dto
error
mapper
permission
schema
service
```

를 생성하더라도 실제 Domain에서 `permission`이 필요 없다면 제거할 수 있습니다.

반대로 새로운 책임이 생기면 Generator가 만들지 않은 파일을 추가할 수 있습니다.

```txt
rule
validator
Domain 전용 normalizer
Domain 전용 formatter
transaction helper
```

이 목록의 `normalizer`, `formatter`는 특정 Domain의 의미를 가지는 책임입니다.
도메인에 독립적인 입력 정규화나 출력 Formatter는 각각 `@repo/core/input`, `@repo/core/format`의 책임을 우선 검토합니다.

Generator는 다음을 제공합니다.

```txt
좋은 시작점
```

하지만 다음을 결정하지는 않습니다.

```txt
실제 Business Requirement
최종 Domain Model
최종 Use Case
최종 UI 구조
```

# 18. 새로운 Generator 추가

새로운 Generator가 실제 반복 작업을 충분히 줄일 수 있을 때 추가합니다.

Generator 개수를 늘리는 것 자체가 목적은 아닙니다.

추가를 검토할 기준:

```txt
동일한 구조를 반복해서 수동 생성하고 있다.

파일 위치와 Naming 실수가 반복된다.

여러 파일과 Barrel Export를 동시에 갱신해야 한다.

정해진 Architecture Pattern을 반복해서 구현한다.

생성 결과를 일반화할 수 있다.
```

반대로 한두 번만 필요한 구조라면 Generator를 만들지 않습니다.

---

## 18.1 Generator 파일 추가

예를 들어 새로운 `action` Generator가 필요하다면:

```txt
tooling/generators/src/generators/
└─ action.generator.ts
```

를 추가합니다.

기본 구조:

```ts
interface GenerateActionParams {
  name: string;
  args: string[];
}

export async function generateAction({ name, args }: GenerateActionParams) {
  // 1. options parse
  // 2. input validation
  // 3. naming normalize
  // 4. output path resolve
  // 5. template build
  // 6. file write
  // 7. barrel export update
}
```

Generator 내부에서는 가능한 한 다음 순서를 유지합니다.

```txt
Input
  ↓
Option Parsing
  ↓
Validation
  ↓
Naming Normalization
  ↓
Path Resolution
  ↓
Template 생성
  ↓
File 생성
  ↓
Export 갱신
  ↓
Log
```

---

## 18.2 Generator 등록

`generators/index.ts`에서 새 Generator를 공개합니다.

개념:

```ts
export { generateAction } from "./action.generator";
```

그리고 `availableGenerators`에도 추가합니다.

```txt
domain
component
entity
feature
view
action
```

---

## 18.3 CLI 연결

`cli.ts`에서 새 Generator를 호출할 수 있도록 연결합니다.

개념:

```ts
if (type === "action") {
  await generateAction({
    name,
    args,
  });

  return;
}
```

Help의 Example과 Option 설명도 함께 추가합니다.

Generator 구현만 추가하고 CLI Help를 갱신하지 않는 상태를 만들지 않습니다.

---

## 18.4 입력 검증

새 Generator는 잘못된 입력으로 잘못된 디렉터리를 만들지 않아야 합니다.

확인 대상:

```txt
필수 옵션 누락

지원하지 않는 App

지원하지 않는 Target

빈 Domain 이름

잘못된 Path 이름

지원하지 않는 Option

Option Value 누락

예상하지 못한 Positional Argument
```

가능하면 파일을 만들기 전에 입력 검증을 완료합니다.

---

## 18.5 파일 생성 안전성

Generator는 기존 코드를 조용히 파괴해서는 안 됩니다.

기본 원칙:

```txt
기존 파일 존재 여부를 확인한다.

Overwrite를 지원한다면 명시적인 옵션이 필요하다.

Barrel Export는 기존 Export를 보존한다.

동일 Export를 중복 추가하지 않는다.

Package Export는 기존 값을 덮어쓰지 않는다.
```

여러 파일을 생성하는 Generator에서는 일부 파일만 생성된 상태에서 실패할 가능성도 고려합니다.

---

## 18.6 Template 규칙

Generator Template도 실제 프로젝트 코드와 같은 Convention을 사용합니다.

```txt
Prettier 결과와 맞는 구조

ESLint Rule과 맞는 Import / Export 순서

Named Export Convention

Type-only Import / Export

kebab-case 파일명

PascalCase Component

현재 Package Scope인 @repo 사용
```

Generator가 만든 코드를 저장하자마자 Formatter가 대규모로 다시 쓰는 상태는 피합니다.

특히 Export Template은 실제 저장 후 코드 형태를 기준으로 작성합니다.

# 19. Generator를 변경할 때

프로젝트 Architecture가 변경되면 Generator도 함께 수정해야 합니다.

예:

```txt

→ entity / feature / view Generator 수정

Design System 구조 변경

→ domain Generator 수정

Storybook title 규칙 변경
```


```bash
pnpm generate component status-badge \
  --target admin \
  --category feedback
```

처럼 추가할 수 있습니다.

# 22. 핵심 원칙

```txt
Generator는 반복 작업을 줄이기 위한 도구다.

Generator는 현재 Architecture와 Convention을 따라야 한다.

Generator가 Architecture를 새로 정의해서는 안 된다.

생성된 코드는 완성 구현이 아니라 Scaffold다.

기본 Scaffold는 반복 작업을 충분히 줄일 수 있도록 제공한다.

필요 없는 생성 파일은 제거할 수 있다.

필요한 책임이 생기면 구조를 확장할 수 있다.

Domain과 Persistence는 --repository 옵션으로 경계를 나눈다.

Domain Unit Test는 Domain Slice의 test/에 둔다.

Repository는 Unit Test와 Integration Test를 구분한다.

Design System Component는 web/admin 책임에 맞게 생성한다.

Entity는 도메인 표현 UI를 생성한다.

Feature는 사용자 행위 단위로 생성한다.

View는 페이지 조립 단위로 생성한다.

App UI Generator는 Layer / Slice / Segment 구조를 따른다.

Public API는 현재 Named Export Convention을 따른다.

Generator Template은 실제 Formatter와 Lint 결과에 맞아야 한다.

기존 파일과 Export를 조용히 덮어쓰지 않는다.

새 Generator는 반복 가치가 충분할 때만 추가한다.

Generator를 수정하면 관련 문서와 Convention도 함께 갱신한다.
```
