# 앱 구조

이 문서는 `apps/*` 내부의 디렉터리 구조와 각 계층의 책임을 정의합니다.

프로젝트의 앱은 Next.js App Router를 중심으로 구성하며, UI와 사용자 인터랙션 영역에는 완화된 Feature-Sliced Design(FSD) 구조를 적용합니다.

이 문서의 목적은 모든 코드를 세세하게 분리하는 것이 아니라 다음 기준을 명확히 하는 것입니다.

```txt
어떤 코드를 어디에 둘 것인가
어떤 단위로 Slice를 나눌 것인가
Slice 내부 코드를 언제 Segment로 분리할 것인가
각 Layer가 어떤 Layer를 참조할 수 있는가
앱 내부 공통 코드와 패키지 공통 코드를 어떻게 구분할 것인가
```

---

## 1. 기본 원칙

앱은 서비스의 라우팅과 UI를 조립하는 계층입니다.

기본 흐름은 다음과 같습니다.

```txt
app
  ↓
views
  ↓
features
  ↓
entities
  ↓
shared / design-system
```

백엔드 흐름은 별도의 계층을 사용합니다.

```txt
UI
  ↓
Server Action
  ↓
Domain Service
  ↓
Repository
  ↓
Database
```

앱 내부 UI 구조와 백엔드 계층은 서로 다른 책임을 가집니다.

```txt
apps/*
  라우팅
  페이지 조립
  사용자 인터랙션
  앱 전용 UI
  Server Action 연결

packages/domain
  비즈니스 규칙
  요청/응답 Schema
  Domain Service

packages/database
  DB 접근
  Repository

packages/design-system
  도메인에 종속되지 않는 UI 기반
```

---

## 2. 기본 디렉터리 구조

각 앱은 기본적으로 다음 구조를 사용합니다.

```txt
apps/[app]/
├─ src/
│  ├─ actions/
│  ├─ app/
│  ├─ config/
│  ├─ constants/
│  ├─ entities/
│  ├─ features/
│  ├─ hooks/
│  ├─ libs/
│  ├─ shared/
│  ├─ types/
│  ├─ utils/
│  └─ views/
│
├─ e2e/
├─ package.json
├─ next.config.ts
├─ vitest.config.ts
├─ vitest.integration.config.ts
└─ playwright.config.ts
```

앱마다 모든 디렉터리를 반드시 가질 필요는 없습니다.

사용되는 책임이 있을 때만 해당 디렉터리를 둡니다.

---

## 3. Layer, Slice, Segment

완화된 FSD 구조에서는 UI 영역을 다음 세 단계로 구분합니다.

```txt
Layer
  → Slice
    → Segment
```

예:

```txt
entities/
└─ order/
   ├─ ui/
   ├─ hooks/
   ├─ lib/
   ├─ constants/
   └─ types/
```

여기서:

```txt
entities
  Layer

order
  Slice

ui / hooks / lib / constants / types
  Segment
```

각 Layer마다 Slice의 기준은 다릅니다.

```txt
entities
  도메인 단위

features
  사용자 행위 단위

views
  페이지 또는 화면 단위
```

---

## 4. Segment

Slice 내부에서는 필요에 따라 다음 Segment를 사용할 수 있습니다.

```txt
ui
hooks
lib
constants
types
```

모든 Slice가 모든 Segment를 가져야 하는 것은 아닙니다.

예를 들어 UI만 존재하는 Entity라면 다음 구조로 충분합니다.

```txt
entities/order/
└─ ui/
   └─ order-status-badge/
      ├─ order-status-badge.tsx
      ├─ order-status-badge.test.tsx
      ├─ order-status-badge.stories.tsx
      └─ index.ts
```

다음과 같은 빈 디렉터리는 만들지 않습니다.

```txt
entities/order/
├─ ui/
├─ hooks/
├─ lib/
├─ constants/
└─ types/
```

`hooks`, `lib`, `constants`, `types`가 실제로 필요해질 때 추가합니다.

---

### 4.1 `ui`

React UI 컴포넌트를 둡니다.

예:

```txt
entities/order/ui/
├─ order-table/
├─ order-summary/
└─ order-status-badge/
```

컴포넌트 단위 디렉터리를 기본으로 사용합니다.

```txt
order-status-badge/
├─ order-status-badge.tsx
├─ order-status-badge.test.tsx
├─ order-status-badge.stories.tsx
└─ index.ts
```

컴포넌트 내부에서만 사용하는 작은 코드가 있다면 같은 디렉터리에 colocate할 수 있습니다.

예:

```txt
order-table/
├─ order-table.tsx
├─ order-table-column.tsx
├─ order-table.test.tsx
├─ order-table.stories.tsx
└─ index.ts
```

### 4.1.1 Component와 하위 Component 구조

하나의 Component에 종속되는 하위 Component가 독립적인 Component 단위를 가질 정도로 커졌다면 부모 Component Directory 아래에 별도의 Component Directory를 둘 수 있습니다.

예:

```txt
entities/domain/ui/
└─ domain-table/
   ├─ domain-table.tsx
   ├─ domain-table.test.tsx
   ├─ domain-table.stories.tsx
   ├─ index.ts
   │
   └─ domain-table-item/
      ├─ domain-table-item.tsx
      ├─ domain-table-item.test.tsx
      ├─ domain-table-item.stories.tsx
      └─ index.ts
```

이 구조에서:

```txt
DomainTable
  부모 Component

DomainTableItem
  DomainTable에 종속된 하위 Component
```

로 봅니다.

하위 Component를 부모 Component Directory에 두는 기준은 다음과 같습니다.

```txt
부모 Component의 구현을 위해 존재한다.

현재 부모 Component 또는 그 하위 Component에서만 사용한다.

독립적인 Slice-level UI로 사용할 의미가 없다.

부모 Component와 함께 변경되는 경우가 대부분이다.
```

예:

```txt
DomainTable
  ↓
DomainTableItem

Navigation
  ↓
NavigationItem

Filter
  ↓
FilterOption

CardList
  ↓
CardListItem
```

단순히 JSX가 분리되었다는 이유만으로 별도의 Directory를 만들 필요는 없습니다.

작은 내부 Component라면 부모 Component Directory에 파일만 colocate할 수 있습니다.

예:

```txt
domain-table/
├─ domain-table.tsx
├─ domain-table-header.tsx
├─ domain-table.test.tsx
└─ index.ts
```

하위 Component가 자체적인 Test, Story, 여러 내부 파일 등 독립적인 Component 구조를 가질 필요가 생겼을 때 별도 Directory로 분리합니다.

---

#### 하위 Component의 승격

하위 Component의 사용 범위가 넓어지면 실제 공유 범위에 맞게 승격합니다.

예를 들어 처음에는:

```txt
entities/domain/ui/
└─ domain-table/
   └─ domain-table-item/
```

처럼 `DomainTable`에서만 사용하던 `DomainTableItem`이 이후 같은 Slice의 다른 UI에서도 사용된다면:

```txt
entities/domain/ui/
├─ domain-table/
└─ domain-table-item/
```

처럼 Slice의 `ui` 바로 아래로 승격할 수 있습니다.

기본 판단:

```txt
부모 Component에서만 사용
  → 부모 Component Directory 내부

같은 Component Family에서만 사용
  → 가장 가까운 공통 부모 Component Directory 내부

같은 Slice의 여러 독립 Component에서 사용
  → Slice의 ui로 승격

여러 Slice에서 사용
  → App 공통 영역 검토

여러 App에서 동일한 책임으로 사용
  → Workspace Package 검토
```

즉 Component 계층 역시 전체 Colocation 원칙과 동일하게:

```txt
가장 가까운 사용 범위에 둔다.
        ↓
공유 범위가 넓어질 때 승격한다.
```

를 따릅니다.

---

#### Public API

부모 Component에 종속된 하위 Component는 기본적으로 Slice의 Public API로 직접 노출하지 않습니다.

예:

```txt
entities/domain/ui/domain-table/
├─ domain-table.tsx
├─ domain-table-item/
└─ index.ts
```

`domain-table/index.ts`:

```ts
export { default as DomainTable } from "./domain-table";
```

`DomainTableItem`이 `DomainTable`의 내부 구현이라면 상위 Barrel까지 Export하지 않습니다.

```txt
entities/domain
  → DomainTable 공개
  → DomainTableItem 비공개
```

하위 Component가 외부에서도 직접 사용할 수 있는 독립적인 UI Contract가 되었다면 부모 내부에 계속 두기보다 적절한 범위로 승격한 뒤 Public API 노출을 검토합니다.

따라서:

```txt
Directory 계층
  Component 소유 관계 표현

Public API
  외부 사용 가능 범위 표현
```

으로 구분합니다.

---

#### 중첩 깊이

하위 Component 안에 다시 하위 Component를 둘 수도 있지만 깊은 Directory 구조 자체를 목표로 하지 않습니다.

예:

```txt
parent/
└─ child/
   └─ grand-child/
```

가 실제 소유 관계를 정확하게 표현한다면 사용할 수 있습니다.

다만 중첩이 계속 깊어진다면 다음을 다시 확인합니다.

```txt
하위 Component가 이미 독립적인 책임을 가지는가?

같은 Slice의 다른 UI에서도 사용할 가능성이 실제로 생겼는가?

부모 Component가 너무 많은 책임을 가지고 있는가?

별도의 Component 또는 Slice-level UI로 승격하는 편이 자연스러운가?
```

디렉터리 깊이를 기계적으로 제한하지 않지만, 소유 관계보다 구조적 복잡성이 커지지 않도록 합니다.

---

### 4.2 `hooks`

같은 Slice 내부의 여러 구성요소에서 공유하는 React Hook을 둡니다.

Hook 파일은 `use` 접두사와 camelCase를 사용합니다.

예:

```txt
features/order/cancel-order/
├─ ui/
└─ hooks/
   └─ useCancelOrder.ts
```

다음 코드는 `hooks`에 두지 않습니다.

```txt
순수 formatter
문자열 변환 함수
날짜 계산 helper
일반 validation helper
React 상태를 사용하지 않는 함수
```

이러한 코드는 `lib`을 사용합니다.

---

### 4.3 `lib`

같은 Slice 내부의 여러 구성요소에서 사용하는 Slice 전용 순수 코드 또는 내부 구현을 둡니다.

예:

```txt
entities/order/lib/
├─ format-order-number.ts
└─ get-order-display-name.ts
```

가능한 대상:

```txt
Slice 전용 formatter
Slice 전용 mapper
Slice 전용 normalizer
display helper
UI 전용 계산 함수
adapter
```

여기서 `normalizer`는 해당 App Slice의 표현이나 입력에만 필요한 로컬 책임을 의미합니다.
여러 Workspace에서 공통으로 사용하는 도메인 독립 입력 정규화는 `@repo/core/input`을 사용합니다.

`lib`은 해당 Slice 내부 구현이라는 점이 중요합니다.

앱 전반에서 사용하는 외부 라이브러리 초기화나 앱 수준 Library Integration은 루트 `libs`에 둡니다.

앱 전체에서 사용하는 일반적인 순수 Utility는 루트 `utils`에 둡니다.

비즈니스 규칙은 `lib`에 두지 않습니다.

예:

```txt
주문 취소 가능 여부 판단
재고 차감 정책
환불 가능 수량 계산
권한 판단
```

이러한 규칙은 `packages/domain`에서 처리합니다.

---

### 4.4 `constants`

같은 Slice 내부의 여러 구성요소에서 공유하는 상수를 둡니다.

예:

```txt
entities/order/constants/
└─ order-table.constant.ts
```

컴포넌트 하나에서만 사용하는 상수는 별도의 Segment로 분리하지 않습니다.

도메인의 실제 정책이나 필드 제한 값은 앱의 `constants`가 아니라 `packages/domain`에서 관리합니다.

---

### 4.5 `types`

같은 Slice 내부의 여러 파일에서 공유하는 TypeScript 타입을 둡니다.

예:

```txt
views/order/order-list-view/
├─ ui/
└─ types/
   └─ order-list-view.type.ts
```

컴포넌트 하나에서만 사용하는 Props 타입은 컴포넌트 파일에 colocate합니다.

단순히 타입이 존재한다는 이유만으로 별도의 `types` Segment를 만들지 않습니다.

## 5. Colocation과 승격

코드는 가능한 한 실제 사용하는 위치 가까이에 둡니다.

기본 기준은 다음과 같습니다.

```txt
한 컴포넌트에서만 사용
→ 해당 컴포넌트와 colocate
→ 독립적인 Component 구조가 필요하면 부모 Component Directory 아래에 하위 Component Directory로 구성

같은 Slice의 여러 독립 Component에서 사용
→ Slice Segment로 승격

앱의 여러 Slice에서 사용
→ 앱 공통 영역으로 이동 검토

여러 앱에서 사용
→ packages/*로 이동 검토
```

예를 들어 `CancelOrderDialog`에서만 사용하는 helper라면:

```txt
features/order/cancel-order/
└─ ui/
   └─ cancel-order-dialog/
      ├─ cancel-order-dialog.tsx
      └─ get-cancel-order-message.ts
```

로 둘 수 있습니다.

이 helper가 이후 여러 UI에서 사용된다면:

```txt
features/order/cancel-order/
├─ ui/
│  ├─ cancel-order-dialog/
│  └─ cancel-order-form/
└─ lib/
   └─ get-cancel-order-message.ts
```

로 승격합니다.

처음부터 재사용을 예상하여 과도하게 분리하지 않습니다.

## 6. `app`

`app`은 Next.js App Router의 Routing Layer입니다.

위치:

```txt
apps/[app]/src/app/
```

담당:

```txt
page.tsx
layout.tsx
route.ts
loading.tsx
error.tsx
not-found.tsx
route group
dynamic route
metadata
```

기본 원칙:

```txt
라우팅을 담당한다.
페이지 파일은 가능한 한 얇게 유지한다.
복잡한 화면 조립은 views에 위임한다.
비즈니스 규칙을 직접 처리하지 않는다.
Prisma를 직접 호출하지 않는다.
```

---

## 7. `views`

View는 페이지 또는 화면 단위의 조립 계층입니다.

위치:

```txt
apps/[app]/src/views/
```

Slice 기준:

```txt
페이지 또는 화면 단위
```

기본 구조:

```txt
views/[domain]/[view]/
├─ ui/
├─ hooks/
├─ lib/
├─ constants/
├─ types/
└─ index.ts
```

필요한 Segment만 사용합니다.

예:

```txt
views/order/
├─ order-list-view/
│  ├─ ui/
│  │  ├─ order-list-view.tsx
│  │  └─ order-list-view-content.tsx
│  └─ index.ts
│
└─ order-detail-view/
   ├─ ui/
   │  ├─ order-detail-view.tsx
   │  └─ order-detail-view-content.tsx
   └─ index.ts
```

View가 담당할 수 있는 것:

```txt
페이지에 필요한 데이터 조회 연결
Entity와 Feature 조립
페이지 수준 레이아웃
검색 조건 처리
Pagination 조립
Empty/Error 상태 조립
페이지 수준 권한에 따른 표시 결정
```

View가 담당하지 않는 것:

```txt
도메인 비즈니스 규칙
DB 직접 접근
재사용 가능한 Entity UI 구현
사용자 행위 자체의 구현
공통 디자인 시스템 구현
```

---

## 8. `features`

Feature는 사용자가 수행하는 행위 단위의 UI와 Client Logic을 담당합니다.

위치:

```txt
apps/[app]/src/features/
```

Slice 기준:

```txt
사용자 행위
```

도메인별 namespace를 먼저 두고 그 아래 Feature Slice를 배치합니다.

```txt
features/[domain]/[feature]/
```

예:

```txt
features/order/
├─ cancel-order/
├─ update-shipping-status/
└─ request-refund/
```

Feature 내부 구조:

```txt
features/order/cancel-order/
├─ ui/
│  ├─ cancel-order-dialog/
│  └─ cancel-order-form/
├─ hooks/
│  └─ useCancelOrder.ts
├─ lib/
├─ constants/
├─ types/
└─ index.ts
```

필요한 Segment만 생성합니다.

Feature가 담당할 수 있는 것:

```txt
form
button
dialog
사용자 입력
useActionState
useFormStatus
Client Validation
Server Action 호출
사용자 인터랙션 상태
성공/실패 UI 연결
```

Feature에 넣지 않는 것:

```txt
도메인 표시만 담당하는 UI
페이지 전체 조립
비즈니스 규칙
Repository
Prisma query
```

---

## 9. `entities`

Entity는 앱에서 도메인 객체를 표현하는 UI 계층입니다.

위치:

```txt
apps/[app]/src/entities/
```

Slice 기준:

```txt
도메인
```

예:

```txt
entities/
├─ order/
├─ payment/
├─ product/
├─ question/
└─ user/
```

기본 구조:

```txt
entities/[domain]/
├─ ui/
├─ hooks/
├─ lib/
├─ constants/
├─ types/
└─ index.ts
```

필요한 Segment만 사용합니다.

예:

```txt
entities/order/
├─ ui/
│  ├─ order-status-badge/
│  ├─ order-table/
│  ├─ order-summary/
│  └─ order-amount-summary/
└─ lib/
   └─ format-order-number.ts
```

Entity가 담당하는 것:

```txt
도메인 정보 표시
도메인 목록
상세 정보
Badge
Table
Card
Summary
도메인 표시용 formatter
```

Entity가 담당하지 않는 것:

```txt
사용자 행위
Server Action 호출
폼 제출
페이지 전체 조립
비즈니스 정책 판단
```

Entity에서 Server Action을 직접 import하지 않습니다.

---

## 10. `actions`

Server Action을 둡니다.

위치:

```txt
apps/[app]/src/actions/
```

도메인 단위로 구성합니다.

```txt
actions/
├─ order/
├─ payment/
├─ product/
└─ user/
```

기본 원칙:

```txt
파일 하나당 Server Action 하나를 둔다.
도메인 단위 index.ts에서 public action을 export한다.
루트 actions/index.ts는 기본적으로 두지 않는다.
```

Server Action의 책임:

```txt
FormData 처리
인증 확인
인가 확인
Request validation
Domain Service 호출
ActionResult 변환
revalidatePath
redirect
```

Server Action이 하지 않는 것:

```txt
Prisma 직접 호출
복잡한 비즈니스 규칙
Repository 직접 조합
UI 렌더링
```

Feature는 필요한 Server Action을 참조할 수 있습니다.

Entity는 Server Action을 참조하지 않습니다.

---

## 11. `shared`

`shared`에는 한 앱 안에서 여러 도메인과 화면이 공유하는 앱 전용 코드를 둡니다.

위치:

```txt
apps/[app]/src/shared/
```

예:

```txt
shared/
├─ ui/
│  ├─ header/
│  ├─ sidebar/
│  └─ page-container/
├─ hooks/
└─ lib/
```

가능한 대상:

```txt
앱 Header
앱 Footer
Sidebar
앱 Navigation
앱 전용 Layout UI
로그인 공통 UI
여러 화면이 공유하는 앱 전용 UI
```

도메인 특화 코드는 `shared`에 두지 않습니다.

예:

```txt
OrderStatusBadge
ProductTable
UserSummary
```

등은 `entities`에 둡니다.

여러 앱에서 동일한 코드가 필요해지면 `shared` 간 복사보다 적절한 `packages/*`로 이동할 수 있는지 검토합니다.

---

## 12. 루트 `hooks`

위치:

```txt
apps/[app]/src/hooks/
```

앱 전반에서 여러 Slice가 공유하는 범용 React Hook만 둡니다.

Hook 파일은 camelCase를 사용합니다.

예:

```txt
hooks/
├─ useDebounce.ts
├─ useMediaQuery.ts
├─ useOutsideClick.ts
└─ usePrevious.ts
```

특정 Feature에 종속된 Hook은 Feature에 둡니다.

```txt
features/user/update-profile/hooks/
└─ useUpdateProfile.ts
```

특정 Entity에 종속된 Hook은 Entity에 둡니다.

```txt
entities/product/hooks/
└─ useProductDisplay.ts
```

Hook이 여러 도메인과 화면에서 재사용되는 경우에만 루트 `hooks`로 승격합니다.

---

## 13. 루트 `libs`

위치:

```txt
apps/[app]/src/libs/
```

앱 전반에서 사용하는 Library Integration 및 앱 수준 기반 구현을 둡니다.

`libs`는 단순 Utility 모음이 아닙니다.

주로 외부 라이브러리 또는 특정 기술과 앱 사이의 연결 계층으로 사용합니다.

예:

```txt
libs/
├─ analytics/
├─ query-client/
├─ monitoring/
└─ browser-storage/
```

가능한 대상:

```txt
외부 라이브러리 초기화
라이브러리별 Client 생성
앱 전용 Adapter
앱 수준 Provider 지원 코드
브라우저 저장소 Wrapper
외부 SDK 연결
앱 전용 Infrastructure Helper
```

예를 들어 다음과 같은 코드가 해당할 수 있습니다.

```txt
TanStack Query의 QueryClient 생성
앱 전용 Analytics Client 초기화
브라우저 Storage Adapter
앱 전용 외부 SDK 설정
```

다음 코드는 `libs`에 두지 않습니다.

```txt
단순 문자열 변환 함수
날짜 formatter
배열 helper
도메인 비즈니스 규칙
React UI
컴포넌트 전용 helper
```

구분 기준:

```txt
특정 외부 Library 또는 Infrastructure와 연결된다
→ libs

앱 전체에서 사용하는 일반적인 순수 함수다
→ utils

특정 Slice 내부에서만 사용한다
→ 해당 Slice의 lib
```

여러 앱에서 동일한 Library Integration이 필요해지고 책임이 명확하게 독립된다면 별도 `packages/*`로 분리하는 것을 검토합니다.

---

## 14. 루트 `utils`

위치:

```txt
apps/[app]/src/utils/
```

앱 전반에서 사용할 수 있는 도메인 비종속 순수 Utility 함수를 둡니다.

예:

```txt
utils/
├─ format-file-size.ts
├─ normalize-search-param.ts
├─ parse-number.ts
└─ sleep.ts
```

가능한 대상:

```txt
문자열 처리
숫자 처리
배열 처리
URL 처리
Search Params 처리
브라우저와 무관한 작은 순수 Helper
앱 전반에서 반복되는 일반 변환 함수
```

기본 원칙:

```txt
React에 의존하지 않는다.
특정 도메인에 의존하지 않는다.
특정 Feature나 View에 의존하지 않는다.
상태를 가지지 않는다.
가능한 한 순수 함수로 작성한다.
```

다음 코드는 루트 `utils`에 두지 않습니다.

```txt
주문 금액 계산
환불 가능 여부 판단
사용자 권한 판단
Product 전용 formatter
Feature 하나에서만 사용하는 helper
외부 SDK 초기화
```

이러한 코드는 각각 적절한 Domain, Slice `lib`, 또는 루트 `libs`에 둡니다.

---

## 15. `lib`, `libs`, `utils` 구분

이 세 위치는 목적이 다릅니다.

```txt
Slice의 lib
  특정 Slice 내부에서 공유하는 구현

루트 libs
  앱 수준 Library / Infrastructure Integration

루트 utils
  앱 전체에서 사용하는 도메인 비종속 순수 Utility
```

예:

```txt
entities/order/lib/format-order-number.ts
  Order Entity 내부에서 사용하는 표시용 helper

libs/query-client/
  TanStack Query Client 초기화 및 설정

utils/format-file-size.ts
  앱 여러 영역에서 사용하는 일반 Utility
```

공유 범위를 이유로 코드를 무조건 루트로 올리지 않습니다.

우선 사용하는 위치와 가까운 곳에 두고 실제 공유 범위가 넓어질 때 승격합니다.

---

## 16. 루트 `constants`

위치:

```txt
apps/[app]/src/constants/
```

앱 전체에서 사용하는 앱 전용 상수를 둡니다.

예:

```txt
constants/
├─ navigation.constant.ts
└─ urls.constant.ts
```

가능한 대상:

```txt
앱 URL

앱 화면 설정
앱 전용 UI 상수
```

도메인 규칙과 관련된 상수는 `packages/domain`에 둡니다.

## 17. 루트 `types`

```txt
apps/[app]/src/types/
```

앱 전체의 여러 Layer에서 공유해야 하는 앱 전용 타입만 둡니다.

단순히 여러 파일에서 사용할 가능성이 있다는 이유만으로 타입을 루트로 이동하지 않습니다.

기본 우선순위는 다음과 같습니다.

```txt
파일 내부
→ 컴포넌트 디렉터리
→ Slice types
→ 앱 루트 types
→ packages/*
```

가능한 한 사용하는 위치와 가까운 곳에 둡니다.

## 18. `config`

위치:

```txt
apps/[app]/src/config/
```

앱 실행 환경과 관련된 설정을 둡니다.

예:

```txt
config/
├─ client-env.ts
└─ server-env.ts
```

기본 원칙:

```txt
환경변수 Schema는 앱별로 정의한다.
Server Env와 Client Env를 분리한다.
Client Env는 NEXT_PUBLIC_ 환경변수만 노출한다.
공통 Env helper는 packages/env를 사용한다.
```

## 19. Layer 의존성 방향

UI Layer는 기본적으로 아래 방향으로만 의존합니다.

```txt
app
 ↓
views
 ↓
features
 ↓
entities
 ↓
shared
 ↓
design-system
```

상위 Layer가 필요한 하위 Layer를 건너뛰어 직접 사용하는 것은 허용합니다.

예:

```txt
View → Entity
View → Shared
Feature → Shared
App → Entity
```

중요한 것은 반대 방향의 의존성을 만들지 않는 것입니다.

### 허용

```txt
app
  → views
  → features
  → entities
  → shared
  → hooks
  → libs
  → utils
  → design-system

views
  → features
  → entities
  → shared
  → hooks
  → libs
  → utils
  → design-system

features
  → entities
  → shared
  → hooks
  → libs
  → utils
  → design-system
  → actions

entities
  → shared
  → hooks
  → libs
  → utils
  → design-system

shared
  → hooks
  → libs
  → utils
  → design-system
```

### 금지

```txt
entities → features
entities → views
entities → actions

features → views

shared → entities
shared → features
shared → views

hooks → entities
hooks → features
hooks → views

libs → entities
libs → features
libs → views

utils → entities
utils → features
utils → views

design-system → apps/*
```

루트 `hooks`, `libs`, `utils`는 앱 내부의 기반 코드이므로 특정 Entity, Feature, View를 알지 못해야 합니다.

---

## 20. 같은 Layer 내부 의존성

같은 Layer의 서로 다른 Slice 간 직접 의존은 가능한 한 피합니다.

예:

```txt
entities/order
  → entities/payment
```

이러한 의존이 반드시 필요한 경우 다음을 먼저 검토합니다.

```txt
View에서 두 Entity를 조립할 수 없는가
Feature에서 조립할 수 없는가
공통되는 표현을 더 아래 계층으로 분리할 수 없는가
실제로 하나의 도메인 Slice로 보는 것이 맞지 않은가
```

같은 Layer 간 의존성을 절대적으로 금지하지는 않지만, 암묵적인 Slice 결합이 증가하지 않도록 주의합니다.

---

## 21. 도메인 Namespace

Feature와 View는 이름 충돌과 구조 확장을 고려해 도메인 Namespace를 사용합니다.

Feature:

```txt
features/order/cancel-order/
features/order/update-shipping-status/
features/user/update-profile/
```

View:

```txt
views/order/order-list-view/
views/order/order-detail-view/
views/user/user-list-view/
```

Entity는 도메인 자체가 Slice이므로 별도의 한 단계가 필요하지 않습니다.

```txt
entities/order/
entities/user/
entities/product/
```

다음 구조는 사용하지 않습니다.

```txt
entities/order/order/
```

---

## 22. 디렉터리를 만들지 않는 기준

미래에 사용할 가능성만으로 디렉터리를 만들지 않습니다.

예를 들어 다음 Entity가 있다고 가정합니다.

```txt
entities/order/
└─ ui/
   └─ order-status-badge/
```

현재 Hook, Helper, Constant, 공유 Type이 없다면 다음은 만들지 않습니다.

```txt
hooks/
lib/
constants/
types/
```

이 원칙은 앱 루트의 `hooks`, `libs`, `utils`에도 동일하게 적용합니다.

실제로 해당 책임의 코드가 존재할 때만 디렉터리를 둡니다.

---

## 23. 파일을 분리하지 않는 기준

다음 코드는 기본적으로 사용하는 파일과 가까이 둡니다.

```txt
컴포넌트 하나에서만 사용하는 Props
컴포넌트 하나에서만 사용하는 상수
컴포넌트 하나에서만 사용하는 작은 Helper
Feature 하나의 UI에서만 사용하는 Local Type
```

이를 이유 없이 다음처럼 분해하지 않습니다.

```txt
user-status-badge/
├─ user-status-badge.tsx
├─ user-status-badge.type.ts
├─ user-status-badge.constant.ts
├─ user-status-badge.lib.ts
└─ index.ts
```

분리는 실제 재사용이나 책임 분리가 발생했을 때 수행합니다.

---

## 24. `index.ts`

`index.ts`는 Slice 또는 컴포넌트의 Public API를 정의할 때 사용합니다.

외부에서는 가능한 한 내부 파일 경로가 아니라 Public API를 사용합니다.

예:

```txt
entities/order/ui/order-status-badge/
├─ order-status-badge.tsx
└─ index.ts
```

```ts
export { default as OrderStatusBadge } from "./order-status-badge";
```

상위에서도 필요한 Public API만 명시적으로 노출하는 것을 기본으로 합니다.

불필요한 내부 구현까지 외부로 export하지 않습니다.

`index.ts`의 구체적인 Export 방식과 파일 네이밍 규칙은 컨벤션 문서에서 정의합니다.

## 25. Design System과 App UI의 경계

Design System은 비즈니스 도메인을 모릅니다.

예:

```txt
Button
Input
Select
Dialog
Table
Badge
Pagination
```

등은 Design System에 둘 수 있습니다.

다음과 같은 컴포넌트는 App Entity 또는 Feature에 둡니다.

```txt
OrderStatusBadge
PaymentStatusBadge
UserTable
ProductSummary
CancelOrderDialog
CreateProductForm
```

구분 기준:

```txt
도메인을 몰라도 의미가 성립한다
→ design-system

특정 도메인을 표현한다
→ entities

특정 사용자 행위를 수행한다
→ features
```

## 26. Server Component와 Client Component

Server First를 기본 원칙으로 합니다.

우선순위:

```txt
1. Server Component
2. Server Action
3. URL Search Params
4. Client Component Local State
5. Global Client State
```

다음과 같은 경우 Client Component를 사용합니다.

```txt
useState
useEffect
useActionState
useFormStatus
브라우저 API
클릭/드래그 등의 Client Interaction
Dialog
Dropdown
Toast
Carousel
```

Client Component가 필요하다는 이유만으로 상위 View 전체에 `"use client"`를 적용하지 않습니다.

가능한 한 Client Boundary를 필요한 UI까지 내려놓습니다.

---

## 27. 데이터 조회

페이지 단위 데이터 조회는 기본적으로 View에서 조립합니다.

```txt
page.tsx
  ↓
OrderListView
  ↓
Domain Service
```

Page는 Route Parameter 또는 Search Params를 View에 전달하는 정도로 유지합니다.

View는 필요한 Domain Service를 호출하고 결과에 따라 Entity와 Feature를 조립할 수 있습니다.

Client Component가 단순 조회를 위해 불필요하게 API Route를 호출하지 않도록 Server Component를 우선합니다.

## 29. 새로운 코드를 추가할 때 판단 순서

새 코드를 작성할 때는 다음 순서로 판단합니다.

```txt
1. Next.js Route 자체인가?
   → app

2. 페이지 또는 화면 전체를 조립하는가?
   → views

3. 사용자가 수행하는 행위인가?
   → features

4. 도메인 객체를 표현하는가?
   → entities

5. 앱 내부 여러 도메인에서 공유하는 UI인가?
   → shared

6. 앱 전체에서 공유하는 React Hook인가?
   → hooks

7. 외부 Library 또는 Infrastructure와 앱을 연결하는가?
   → libs

8. 앱 전체에서 사용하는 도메인 비종속 순수 함수인가?
   → utils

9. 앱 전체에서 사용하는 상수 또는 타입인가?
   → constants / types

10. 도메인과 무관하며 여러 앱에서 공유하는 UI인가?
    → design-system

11. 비즈니스 규칙인가?
    → packages/domain

12. DB 접근인가?
    → packages/database
```

---

## 30. 새로운 Segment를 추가할 때 판단 순서

Slice 내부에 코드가 추가될 때는 다음 순서로 판단합니다.

```txt
1. 하나의 컴포넌트에서만 사용하는가?
   → 컴포넌트와 colocate

2. 같은 Slice의 여러 UI가 공유하는 React Hook인가?
   → hooks

3. 같은 Slice의 여러 파일이 공유하는 순수 함수인가?
   → lib

4. 같은 Slice의 여러 파일이 공유하는 상수인가?
   → constants

5. 같은 Slice의 여러 파일이 공유하는 Type인가?
   → types

6. 다른 Slice에서도 공유하기 시작했는가?
   → 앱 공통 영역으로 승격 검토

7. 다른 앱에서도 공유하는가?
   → packages/*로 승격 검토
```

## 31. 피해야 하는 구조

### 31.1 모든 코드를 앱 루트로 올리기

피합니다.

```txt
hooks/
libs/
utils/
types/
constants/
```

에 도메인별 코드가 무분별하게 쌓이지 않도록 합니다.

공유되지 않는 코드는 가능한 한 해당 Slice 가까이에 둡니다.

### 31.2 `lib`, `libs`, `utils`를 같은 용도로 사용하기

피합니다.

```txt
Slice 전용 코드
→ lib

앱 수준 Library Integration
→ libs

앱 수준 범용 순수 함수
→ utils
```

각 책임을 명확히 구분합니다.

### 31.3 작은 컴포넌트까지 과도하게 분해하기

피합니다.

```txt
component/
├─ component.tsx
├─ component.type.ts
├─ component.constant.ts
├─ component.helper.ts
├─ component.hook.ts
└─ index.ts
```

각 파일이 실제로 독립적인 책임을 가지지 않는다면 한 파일에 함께 두는 편이 낫습니다.

### 31.4 Feature에 비즈니스 규칙 넣기

비즈니스 정책은 Domain에서 처리합니다.

Feature는 Domain에서 결정된 결과를 UI와 사용자 행위에 연결합니다.

### 31.5 Entity에서 Action 호출하기

피합니다.

```txt
Entity
  → Server Action
```

사용자 행위가 필요한 순간 Feature로 분리합니다.

### 31.6 View를 재사용 컴포넌트 저장소로 사용하기

여러 화면에서 재사용되는 도메인 UI라면 Entity 또는 Feature로 이동합니다.

View는 화면 조립에 집중합니다.

## 33. 최종 원칙

앱 구조에서 가장 중요한 기준은 다음과 같습니다.

```txt
app은 Route를 연결한다.

view는 화면을 조립한다.

feature는 사용자의 행위를 구현한다.

entity는 도메인을 표현한다.

shared는 앱 내부의 도메인 비종속 공통 UI를 제공한다.

hooks는 앱 전반에서 공유하는 범용 React Hook을 제공한다.

libs는 앱과 외부 Library 또는 Infrastructure의 연결을 담당한다.

utils는 앱 전반에서 공유하는 도메인 비종속 순수 함수를 제공한다.

design-system은 여러 앱이 사용할 수 있는 UI 기반을 제공한다.

business rule은 domain에 둔다.

database access는 database package에 둔다.
```

Slice와 Segment는 코드를 많이 나누기 위한 규칙이 아닙니다.

```txt
사용하는 위치 가까이에 둔다.
필요해졌을 때만 분리한다.
공유 범위가 넓어질 때만 승격한다.
하위 계층이 상위 계층을 참조하지 않는다.
```

이 원칙을 우선합니다.
