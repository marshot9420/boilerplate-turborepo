# 기본설정

이 문서는 `boilerplate-turborepo`의 공통 개발 환경과 Tool 설정 정책을 설명합니다.

설정 파일의 전체 내용을 복제하는 것이 아니라 다음 내용을 중심으로 다룹니다.

```txt
어떤 설정을 공통으로 관리하는가

왜 해당 설정을 사용하는가

어디에서 변경해야 하는가

각 앱과 Package가 공통 설정을 어떻게 재사용하는가
```

개별 기능의 구체적인 사용법은 각 전문 문서에서 다룹니다.

---

## 1. 기본 원칙

이 Repository의 개발 환경과 Tool 설정은 가능한 한 중앙에서 관리합니다.

기본 원칙은 다음과 같습니다.

```txt
Node.js와 pnpm의 기준 버전을 명확히 한다.

공통 외부 의존성 버전은 pnpm Catalog로 중앙화한다.

반복되는 TypeScript, ESLint, Vitest 등의 설정은 Package로 분리한다.

각 Workspace는 공통 설정을 가져와 최소한의 차이만 추가한다.

Turborepo는 Workspace 전체 Task 실행과 Cache를 관리한다.

설정 파일과 실제 사용 Package의 책임을 분리한다.

특정 앱에만 필요한 설정은 해당 앱에 유지한다.
```

설정을 공통화한다는 이유만으로 모든 설정을 하나의 파일에 넣지는 않습니다.

```txt
Workspace 전체 정책
→ Repository Root

여러 Workspace가 공유하는 Tool 설정
→ packages/*-config

특정 앱 또는 Package만 필요한 설정
→ 해당 Workspace
```

## 2. Runtime 및 Package Manager

### 2.1 Node.js

기준 Node.js 버전은 `.nvmrc`에서 관리합니다.

현재 기준:

```txt
24.16.0
```

루트 `package.json`의 `engines`에서도 허용 범위를 제한합니다.

```txt
Node.js
>= 24.16.0 < 25
```

`.nvmrc`는 로컬 개발 환경에서 사용할 구체적인 버전을 지정하고, `engines`는 프로젝트가 허용하는 Runtime 범위를 정의합니다.

기본 원칙:

```txt
새로운 Major Node.js 버전으로 자동 이동하지 않는다.

Node.js 버전을 변경할 때는
.nvmrc와 package.json의 engines를 함께 검토한다.

CI와 배포 환경도 가능한 한 같은 Major 버전을 사용한다.
```

---

### 2.2 pnpm

Package Manager는 pnpm을 사용합니다.

루트 `package.json`의 `packageManager`가 실제 프로젝트 기준 버전을 정의합니다.

현재 기준:

```txt
pnpm 11.9.0
```

`engines`에서는 다음 범위를 허용합니다.

```txt
pnpm
>= 11.6.0 < 12
```

Node.js와 마찬가지로 pnpm Major 버전 변경은 의도적으로 수행합니다.

---

## 3. pnpm Workspace

Workspace 구성과 pnpm 공통 정책은 루트 `pnpm-workspace.yaml`에서 관리합니다.

Workspace 대상은 다음과 같습니다.

```txt
apps/*
packages/*
tooling/*
```

구조:

```txt
apps
  실행 가능한 애플리케이션

packages
  공유 Package 및 공통 설정 Package

tooling
  Generator와 Script
```

---

## 4. pnpm Catalog

공통 외부 의존성 버전은 pnpm Catalog를 사용해 중앙화합니다.

예:

```yaml
catalog:
  next: 16.2.0
  react: ^19.2.0
  react-dom: ^19.2.0
  typescript: 5.9.2
  vitest: ^4.1.8
  zod: ^4.4.3
```

각 Workspace에서는 실제 버전을 직접 반복하지 않고 다음과 같이 참조합니다.

```json
{
  "dependencies": {
    "next": "catalog:",
    "react": "catalog:",
    "react-dom": "catalog:"
  }
}
```

이 방식의 목적은 다음과 같습니다.

```txt
Workspace마다 같은 Package 버전을 반복하지 않는다.

공통 의존성 버전 변경 지점을 하나로 만든다.

앱과 Package 사이의 의존성 버전 차이를 줄인다.

버전 Upgrade 시 변경 범위를 쉽게 파악한다.
```

Catalog에는 주로 여러 Workspace가 공통으로 사용하는 외부 Package를 등록합니다.

예:

```txt
Framework
  next
  react
  react-dom

Language / Validation
  typescript
  zod

Testing
  vitest
  @playwright/test
  @testing-library/*

Storybook
  storybook
  @storybook/*

Styling
  tailwindcss
  clsx
  tailwind-merge

Infrastructure
  prisma
  @prisma/client
  dotenv
```

모든 Dependency를 반드시 Catalog에 등록할 필요는 없습니다.

하나의 Package에서만 사용되는 라이브러리까지 무조건 중앙화하지 않습니다.

## 5. pnpm 정책

pnpm의 공통 설치 정책도 `pnpm-workspace.yaml`에서 관리합니다.

현재 주요 설정은 다음과 같습니다.

```txt
engineStrict
  engines 조건을 만족하지 않으면 설치를 제한

autoInstallPeers
  필요한 Peer Dependency를 자동으로 설치

strictPeerDependencies
  Peer Dependency 충돌을 설치 실패로 강제할지 결정
```

현재 기준:

```yaml
engineStrict: true
autoInstallPeers: true
strictPeerDependencies: false
```

이 정책은 Workspace 전체에서 동일하게 적용합니다.

---

### 5.1 Build Script 허용

의존성 설치 과정에서 Build Script 실행이 필요한 Package는 명시적으로 관리합니다.

현재 예:

```txt
@prisma/engines
esbuild
prisma
sharp
unrs-resolver
```

관련 설정은 `allowBuilds`에서 관리합니다.

Build Script가 필요한 새로운 Dependency를 추가했다면 설치 오류를 우회하기보다 해당 Script가 실제로 필요한지 먼저 확인한 뒤 정책을 수정합니다.

---

### 5.2 Release Age 예외

일부 Package는 pnpm의 Release Age 정책 적용에서 제외할 수 있습니다.

현재 Turborepo Platform Binary와 `turbo`의 특정 버전이 예외 목록에 포함되어 있습니다.

이 설정은 일반적인 Dependency 버전 관리 수단으로 사용하지 않습니다.

특정 Toolchain 설치를 위해 필요한 경우에만 예외를 추가합니다.

## 7. Turborepo

Turborepo는 Workspace 전체의 Task 실행, 의존성 순서, Cache를 관리합니다.

설정 위치:

```txt
turbo.json
```

주요 역할:

```txt
Task Dependency
Task Cache
Persistent Task
Build Output
Workspace 간 실행 순서
환경변수와 Cache 관계
```

---

### 7.1 Task Dependency

상위 Workspace의 Task를 실행하기 전에 의존 Package의 동일 Task가 먼저 실행되어야 하는 경우 `dependsOn`을 사용합니다.

대표적인 구조:

```txt
build
  → ^build

lint
  → ^lint

check-types
  → ^check-types

test
  → ^test
```

`^`는 현재 Workspace가 의존하는 다른 Workspace의 Task를 먼저 실행한다는 의미로 사용합니다.

이를 통해 Package를 먼저 검증하거나 Build한 뒤 앱 Task를 실행할 수 있습니다.

---

### 7.2 Cache

결과를 재사용할 수 있는 Task는 Turborepo Cache를 활용합니다.

예:

```txt
build
test
test:coverage
```

반대로 실행할 때마다 실제 동작해야 하거나 상태를 유지하는 Task는 Cache를 사용하지 않습니다.

예:

```txt
dev
test:watch
test:integration
test:e2e
clean
```

---

### 7.3 Persistent Task

종료되지 않고 계속 실행되는 개발용 Task는 `persistent`로 구성합니다.

대표적인 예:

```txt
dev
test:watch
test:integration:watch
test:e2e:ui
```

---

### 7.4 Build Output

Build 결과 중 Cache 대상으로 관리할 디렉터리는 `outputs`에서 정의합니다.

Next.js 앱은 일반적으로 다음 결과를 대상으로 합니다.

```txt
.next/**
```

Next.js 자체 Cache처럼 별도 재사용 가치가 낮거나 충돌 가능성이 있는 경로는 제외할 수 있습니다.

---

### 7.5 환경변수

Task 결과에 영향을 주는 환경변수는 Turborepo가 인식할 수 있도록 관리합니다.

현재 `turbo.json`에는 앱 URL, Database, 인증, OAuth, E2E 관련 환경변수 등이 등록되어 있습니다.

환경변수 이름이나 관리 정책 자체는 `06_환경변수.md`에서 다룹니다.

`turbo.json`에서는 다음 관점만 책임집니다.

```txt
어떤 환경변수가 Task 결과에 영향을 주는가

환경변수 변경이 Cache에 반영되어야 하는가
```

## 8. TypeScript

공통 TypeScript 설정은 `@repo/typescript-config`에서 관리합니다.

위치:

```txt
packages/typescript-config/
```

Public Config:

```txt
base.json
nextjs.json
node-library.json
react-library.json
test.json
```

각 Workspace는 자신의 Runtime 성격에 맞는 Config를 `extends`합니다.

---

### 8.1 `base.json`

모든 TypeScript Workspace의 공통 기반입니다.

주요 정책:

```txt
strict
noUncheckedIndexedAccess
isolatedModules
ESNext Module
Bundler Module Resolution
ES2022 Target
JSON Module 지원
```

기본 방향은 엄격한 타입 검사를 유지하는 것입니다.

Workspace별 이유 없이 TypeScript Strictness를 완화하지 않습니다.

---

### 8.2 `nextjs.json`

Next.js 앱에서 사용합니다.

추가되는 주요 환경:

```txt
DOM
DOM.Iterable
Next.js TypeScript Plugin
JSX preserve
noEmit
```

사용 대상:

```txt
apps/web
apps/admin
```

앱별 `tsconfig.json`은 이 설정을 기반으로 앱에 필요한 Alias나 Type만 추가합니다.

---

### 8.3 `react-library.json`

React 기반 내부 Package에서 사용합니다.

대표 대상:

```txt
@repo/design-system
```

주요 특징:

```txt
react-jsx
DOM Library
noEmit
```

Next.js에 직접 의존하지 않는 React Package를 위한 설정입니다.

---

### 8.4 `node-library.json`

Node.js 환경에서 실행되는 Package와 Tooling에 사용합니다.

예:

```txt
일부 Infrastructure Package
tooling/*
공통 설정 Package
```

주요 특징:

```txt
Node.js Type
DOM 없음
noEmit
```

---

### 8.5 `test.json`

독립적인 테스트 설정이 필요한 경우 사용하는 공통 TypeScript Config입니다.

Vitest Global과 Node.js Type을 기본적으로 사용할 수 있도록 구성합니다.

테스트 전략 자체는 `12_테스트_전략.md`에서 설명합니다.

## 9. ESLint

공통 ESLint 설정은 `@repo/eslint-config`에서 관리합니다.

위치:

```txt
packages/eslint-config/
```

Public Config:

```txt
base
nextjs
react-internal
node
test
```

ESLint Flat Config를 사용합니다.

---

### 9.1 Base Config

모든 환경에 공통으로 적용할 코드 품질 규칙을 정의합니다.

주요 정책:

```txt
TypeScript Recommended Rule

명시적인 any 제한

사용하지 않는 Import 제거

사용하지 않는 변수 검사

Type-only Import 정리

Import 순서

중복 Import 방지

Export 정렬

Turborepo 환경변수 검사

Prettier와 충돌하는 Format Rule 비활성화
```

코드 Formatting 자체는 ESLint보다 Prettier가 담당합니다.

---

### 9.2 Import 규칙

Import는 크게 다음 그룹으로 구분합니다.

```txt
Node.js Built-in

외부 Package

Workspace Package
  @repo/*

앱 내부 Alias
  @/*

상대 경로
```

구체적인 코드 작성 규칙은 `18_컨벤션.md`에서 관리합니다.

ESLint Config는 해당 규칙을 실제 코드에서 검사하는 역할을 합니다.

---

### 9.3 Next.js Config

Next.js 앱에는 다음 규칙이 추가됩니다.

```txt
React
React Hooks
Next.js Recommended
Core Web Vitals
Browser Global
Service Worker Global
```

Next.js Config 파일이나 Vitest Config처럼 Node.js에서 실행되는 설정 파일은 별도의 Node Global을 사용합니다.

---

### 9.4 React Internal Config

Next.js가 아닌 React Package에 사용합니다.

대표 대상:

```txt
@repo/design-system
```

React와 React Hooks 규칙은 적용하지만 Next.js 전용 규칙은 포함하지 않습니다.

---

### 9.5 Node Config

Node.js Runtime을 사용하는 Package 및 Tooling에 사용합니다.

Browser Global을 추가하지 않고 Node.js Global을 기준으로 검사합니다.

---

### 9.6 Test Config

테스트 파일에는 Vitest, Node, Browser Global을 사용할 수 있도록 설정합니다.

테스트에서 현실적으로 필요한 경우를 고려하여 일부 Production Rule은 완화될 수 있습니다.

구체적인 Test 작성 기준은 `12_테스트_전략.md`에서 정의합니다.

## 10. Prettier

코드 Formatting은 Repository Root의 Prettier 설정을 사용합니다.

관련 파일:

```txt
.prettierrc
.prettierignore
```

루트 명령어:

```bash
pnpm format
pnpm format:check
```

역할:

```txt
Prettier
  코드 Formatting

ESLint
  코드 품질 및 구조 검사
```

두 Tool이 동일한 Formatting Rule을 경쟁해서 적용하지 않도록 `eslint-config-prettier`를 사용합니다.

Tailwind CSS Class 정렬은 `prettier-plugin-tailwindcss`에서 처리합니다.

Formatting Style의 세부 기준은 `.prettierrc`를 Source of Truth로 사용하며 문서에 전체 설정 값을 반복하지 않습니다.

### 11.4 Test Environment

공통 Test Setup은 Workspace Root의 테스트 환경변수를 읽습니다.

기본 대상:

```txt
.env.test
.env.test.local
```

테스트 실행 시:

```txt
NODE_ENV=test
```

를 사용합니다.

앱별 테스트에서는 현재 실행 중인 Workspace를 기준으로 필요한 App URL을 구성할 수 있습니다.

환경변수 관리의 전체 기준은 `06_환경변수.md`에서 다룹니다.

### 11.5 `server-only`

Vitest 환경에서는 Next.js의 `server-only` Package를 직접 해석하면서 발생할 수 있는 문제를 피하기 위해 테스트용 Alias를 사용합니다.

이 Alias는 Production Runtime 동작을 구현하기 위한 것이 아니라 Test Runtime을 위한 Compatibility Layer입니다.

실행 환경에 따라 기본 정책이 달라집니다.

로컬:

```txt
기존 개발 서버 재사용 가능
기본 Worker 사용
List Reporter
```

CI:

```txt
전용 Web Server 실행
Retry 사용
Worker 제한
GitHub Reporter 사용
```

E2E 실패 분석을 위해 필요에 따라 다음 결과를 남깁니다.

```txt
Trace
Screenshot
Video
HTML Report
```

구체적인 E2E 작성 기준은 `12_테스트_전략.md`에서 다룹니다.

### 12.2 E2E 환경변수

Playwright는 일반 개발 환경과 E2E 환경을 구분해서 읽습니다.

기본 흐름:

```txt
.env.local
  ↓
.env.e2e.local
```

E2E 전용 설정은 기존 값을 Override할 수 있습니다.

환경변수 파일별 책임은 `06_환경변수.md`에서 설명합니다.

## 13. Storybook

공통 Storybook 설정은 `@repo/storybook-config`에서 관리합니다.

위치:

```txt
packages/storybook-config/
```

제공 Config:

```txt
nextjs
react
preview
```

---

### 13.1 Next.js Storybook

Next.js 앱은 다음 Config를 사용합니다.

```txt
@repo/storybook-config/nextjs
  ↓
@storybook/nextjs-vite
```

대상:

```txt
apps/web
apps/admin
```

`@storybook/nextjs-vite`는 앱의 Next.js Runtime 특성을 Storybook 환경에서 지원합니다.

Story에서 사용하는 Type 역시 공통 Config Package를 통해 가져옵니다.

예:

```ts
import type { Meta, StoryObj } from "@repo/storybook-config/nextjs";
```

---

### 13.2 React Storybook

Next.js에 종속되지 않는 React Package는 React Vite Config를 사용합니다.

현재 대표 대상:

```txt
@repo/design-system
```

구조:

```txt
@repo/storybook-config/react
  ↓
@storybook/react-vite
```

Story에서 사용하는 Type:

```ts
import type { Meta, StoryObj } from "@repo/storybook-config/react";
```

Next.js 앱과 React Package의 Storybook Framework를 억지로 하나로 통일하지 않습니다.

```txt
Next.js App
→ @storybook/nextjs-vite

React Package
→ @storybook/react-vite
```

공통화하는 것은 Framework 자체가 아니라 프로젝트에서 사용하는 설정 진입점입니다.

---

### 13.3 공통 Preview

공통 Preview는 다음과 같은 Storybook 전체 기본값을 관리합니다.

```txt
Controls
Accessibility
공통 Parameter
```

각 앱 또는 Package의 `.storybook/preview.tsx`는 이를 기반으로 자신에게 필요한 설정만 추가합니다.

예:

```txt
apps/*
  App Global CSS
  Next.js Navigation Parameter
  Toast Provider

design-system
  Design System Storybook CSS
  Theme Wrapper
  Toast Provider
```

Story 작성 대상과 Story 구조는 `13_스토리북.md`에서 다룹니다.

## 14. 공통 Config Package

현재 공통 개발 설정은 다음 Package에서 관리합니다.

```txt
@repo/typescript-config
@repo/eslint-config
@repo/vitest-config
@repo/playwright-config
@repo/storybook-config
```

각 Config Package의 목적은 동일합니다.

```txt
설정 중복을 줄인다.

Workspace 간 정책 차이를 줄인다.

설정 변경 지점을 중앙화한다.

새로운 Workspace가 기존 프로젝트 규칙을 쉽게 재사용하게 한다.
```

각 Workspace는 공통 Config를 그대로 복제하지 않습니다.

예:

```txt
apps/web
  → Next.js용 TypeScript
  → Next.js용 ESLint
  → React Vitest
  → Next.js Storybook
  → Next.js Playwright

apps/admin
  → 동일한 앱 기반 설정 재사용

packages/design-system
  → React Library TypeScript
  → React Internal ESLint
  → React Vitest
  → React Storybook
```

Workspace 고유 설정이 필요한 경우 공통 Config를 확장합니다.

## 15. 설정 변경 기준

새로운 Tool 또는 설정을 추가할 때는 다음 순서로 판단합니다.

```txt
1. 하나의 Workspace에서만 필요한가?
   → 해당 Workspace에 둔다.

2. 여러 Workspace에서 동일하게 사용하는가?
   → 공통 Config Package를 검토한다.

3. 외부 Dependency 버전을 여러 Workspace가 공유하는가?
   → pnpm Catalog에 등록한다.

4. Workspace Task 실행과 Cache에 영향을 주는가?
   → turbo.json을 검토한다.

5. Runtime 또는 Package Manager 정책인가?
   → Root package.json / pnpm-workspace.yaml을 검토한다.
```

공통화 자체를 목표로 설정을 분리하지 않습니다.

실제 중복 또는 공통 정책이 존재할 때 중앙화합니다.

## 17. 최종 원칙

공통 설정의 핵심 원칙은 다음과 같습니다.

```txt
Runtime 버전은 명시적으로 관리한다.

공통 외부 Dependency 버전은 Catalog로 중앙화한다.

Workspace Dependency는 workspace:*를 사용한다.

공통 Tool 설정은 Config Package로 재사용한다.

각 Workspace에는 필요한 차이만 남긴다.

Turborepo는 Task 실행과 Cache를 담당한다.

TypeScript는 엄격한 타입 검사를 기본으로 한다.

ESLint는 코드 품질과 구조를 검사한다.

Prettier는 Formatting을 담당한다.

Vitest는 Unit / Component / Integration Test 기반을 제공한다.

Playwright는 E2E 실행 기반을 제공한다.

Storybook Framework는 실행 환경에 맞게 구분한다.

설정 파일 전체를 문서에 복제하지 않는다.

문서에는 설정의 목적과 변경 지점을 기록한다.
```
