# 컨벤션

이 문서는 `boilerplate-turborepo` 전반에서 사용하는 코드 작성 규칙을 정의합니다.

이 문서에서는 다음 내용을 다룹니다.

```txt
파일 및 디렉터리 Naming
변수 및 함수 Naming
Component / Hook Naming
Action / Service / Repository Naming
Schema / DTO / Constant Naming
Import / Export
Barrel Export
Test / Story Naming
Commit 규칙
```

다음과 같은 Architecture 자체의 책임은 이 문서에서 반복해서 설명하지 않습니다.

```txt
Package 구조
Dependency Boundary
Domain Layer 역할
Server Action 책임
App Layer / Slice / Segment 구조
Design System 책임
Test 전략
Storybook 작성 기준
```

해당 내용은 각각의 전문 문서를 따릅니다.

```txt
04_패키지_구조.md
05_의존성_경계.md
08_도메인_레이어.md
09_서버_액션.md
10_앱_구조.md
11_디자인_시스템.md
12_테스트_전략.md
13_스토리북.md
14_코드_생성기.md
```

---

## 1. 기본 원칙

코드의 이름은 짧게 쓰는 것보다 **역할과 의미를 정확하게 표현하는 것**을 우선합니다.

기본 원칙:

```txt
이름만 보고 역할을 추론할 수 있어야 한다.

줄임말을 습관적으로 사용하지 않는다.

같은 개념에는 같은 용어를 사용한다.

다른 책임에는 다른 동사를 사용한다.

계층의 책임과 함수 이름이 일치해야 한다.

create, get 같은 범용 동사를 습관적으로 붙이지 않는다.

Public API에서는 모호한 이름보다 구체적인 이름을 사용한다.

파일명과 Export 이름만으로 코드의 위치와 책임을 추론할 수 있게 한다.
```

특히 다음과 같은 이름을 피합니다.

```txt
data
item
value
result
temp
obj
info
util
helper
manager
handler
process
doSomething
getSomething
createSomething
```

문맥상 의미가 명확한 좁은 Scope에서는 `result`, `value` 등의 일반적인 이름을 사용할 수 있지만, Scope가 넓거나 여러 값이 동시에 존재한다면 구체적인 이름을 사용합니다.

---

# 2. 파일명

파일과 디렉터리 이름은 기본적으로 `kebab-case`를 사용합니다.

예:

```txt
user.repository.ts
user.repository.test.ts
user.repository.integration.test.ts

user.constant.ts
user.schema.ts
user.permission.ts
user.error.ts
user.service.ts
user.mapper.ts
user.dto.ts

create-product.action.ts

order-status-badge.tsx
order-status-badge.test.tsx
order-status-badge.stories.tsx

update-profile-form.tsx
update-profile-form.test.tsx
update-profile-form.stories.tsx
```

디렉터리도 동일합니다.

```txt
order-claim
order-status-badge
update-profile
update-profile-form
```

---

# 3. Hook 파일명

Custom Hook은 함수 이름과 동일하게 `camelCase`를 사용합니다.

```txt
useMediaQuery.ts
useActionResultEffect.ts
useFormInteractionState.ts
useUpdateProfileForm.ts
```

Hook 파일에서 하나의 대표 Hook을 Default Export하는 경우에도 파일명은 해당 Hook 이름과 동일하게 유지합니다.

---

# 4. React Component Naming

React Component 이름은 `PascalCase`를 사용합니다.

```tsx
export default function OrderStatusBadge() {
  // ...
}
```

Props Type도 Component 이름을 기준으로 작성합니다.

```tsx
interface OrderStatusBadgeProps {
  status: OrderStatus;
}
```

다음처럼 지나치게 일반적인 이름을 사용하지 않습니다.

```txt
Component
Container
Wrapper
Content
Item
Row
```

단, 상위 Component 이름과 결합하여 의미가 명확하다면 사용할 수 있습니다.

```txt
OrderDetailContent
ProductTableRow
UserProfileContent
```

---

# 5. Component Export

React Component는 기본적으로 `default export`를 사용합니다.

```tsx
interface OrderStatusBadgeProps {
  status: OrderStatus;
}

export default function OrderStatusBadge({ status }: OrderStatusBadgeProps) {
  // ...
}
```

Barrel에서는 Named Export로 공개합니다.

```ts
export { default as OrderStatusBadge } from "./order-status-badge";
```

따라서 사용하는 쪽에서는:

```tsx
import { OrderStatusBadge } from "@/entities/order";
```

처럼 사용합니다.

---

# 6. `forwardRef`

`forwardRef`를 사용하는 Component는 변수 형태로 정의할 수 있습니다.

```tsx
"use client";

import { forwardRef } from "react";

interface InputProps {
  // ...
}

const Input = forwardRef<HTMLInputElement, InputProps>(({ ...props }, ref) => {
  return <input ref={ref} {...props} />;
});

Input.displayName = "Input";

export default Input;
```

Public Export 규칙은 일반 Component와 같습니다.

```ts
export { default as Input } from "./input";
```

# 7. 함수명 기본 규칙

함수 이름은 기본적으로 `camelCase`를 사용합니다.

```txt
formatUserDate
normalizeBlankStringToUndefined
resolveFieldError
parseSearchParams
buildSessionCookie
loadPlaywrightEnv
```

함수 이름은 다음 구조를 우선합니다.

```txt
동사 + 대상 + 필요한 한정어
```

예:

```txt
formatOrderDate
resolveUserDisplayName
normalizeSearchKeyword
parseOrderListQuery
buildSessionCookie
loadTestEnvironment
```

---

# 8. 동사를 의미에 맞게 사용한다

함수 이름의 첫 동사는 함수가 실제로 무엇을 하는지 표현해야 합니다.

같은 종류의 작업에 같은 동사를 사용합니다.

---

## 8.1 `build`

여러 입력을 조합하여 **새로운 메모리상의 값이나 구조를 구성**할 때 사용합니다.

```txt
buildSessionCookie
buildOrderFixture
buildPaginationItems
buildRequestHeaders
```

예:

```ts
function buildSessionCookie(token: string) {
  return {
    name: "session",
    value: token,
  };
}
```

단순 객체를 만드는 Helper에 습관적으로 `create`를 사용하지 않습니다.

지양:

```txt
createSessionCookie
createTestUser
createMockOrder
```

권장:

```txt
buildSessionCookie
buildUserFixture
buildOrderFixture
```

---

## 8.2 `define`

설정, 선언적 구조, 고정된 Definition을 구성할 때 사용합니다.

```txt
defineNextAppE2EConfig
defineNavigationGroups
defineTableColumns
```

특히 Config Factory에서 단순히 객체를 반환한다는 이유로 `createConfig`라고 하지 않습니다.

지양:

```txt
createNextAppE2EConfig
createConfig
```

권장:

```txt
defineNextAppE2EConfig
defineConfig
```

---

## 8.3 `resolve`

여러 후보나 상태를 고려하여 **최종 값을 결정**할 때 사용합니다.

```txt
resolveWorkspaceRoot
resolveFieldError
resolveUserDisplayName
resolveRedirectUrl
resolveSortDirection
```

예:

```txt
환경변수
기본값
현재 상태
여러 후보
```

중 하나를 판단해서 최종 결과를 내는 함수에 적합합니다.

---

## 8.4 `normalize`

입력을 동일한 의미의 **정규화된 형태로 변환**할 때 사용합니다.

```txt
normalizeBlankStringToUndefined
normalizeEmail
normalizeSearchKeyword
normalizePhoneNumber
```

의미 자체를 바꾸는 변환에는 사용하지 않습니다.

---

## 8.5 `parse`

문자열, `FormData`, Search Params 등 Raw Input을 구조화된 값으로 해석할 때 사용합니다.

```txt
parseSearchParams
parseFormData
parseSortDirection
parseDateInput
```

`parse` 결과는 입력을 해석한 결과라는 의미를 가집니다.

---

## 8.6 `load`

파일, 환경, 외부 Resource 등에서 값을 읽어오는 작업에 사용합니다.

```txt
loadTestEnv
loadPlaywrightEnv
loadFixture
```

단순 객체 Property 접근에는 사용하지 않습니다.

---

## 8.7 `map`

한 구조를 다른 구조로 대응시키거나 Collection을 Mapping하는 책임에 사용합니다.

```txt
mapPrismaError
mapValidationErrors
mapOrderItems
```

Domain Mapper의 대표적인 단일 변환 함수는 `to...`를 우선할 수 있습니다.

```txt
toUserResponse
toOrderDetailResponse
```

---

## 8.8 `format`

값을 사람이 읽거나 출력하기 위한 표현으로 변환할 때 사용합니다.

```txt
formatCurrency
formatOrderDate
formatPhoneNumber
```

`format` 결과는 Presentation 성격을 가집니다.

---

## 8.9 `required`

필수 값을 읽고, 존재하지 않으면 실패하는 작은 Utility에 사용할 수 있습니다.

예:

```ts
function requiredEnv(key: string): string {
  const value = process.env[key]?.trim();

  if (!value) {
    throw new Error(`${key} is required`);
  }

  return value;
}
```

이 경우:

```txt
getRequiredEnv
```

보다:

```txt
requiredEnv
```

처럼 의미를 직접 표현합니다.

---

# 9. Boolean 함수

Boolean을 반환하는 함수는 반환 의미에 따라 다음 Prefix를 사용합니다.

```txt
is
has
can
should
```

예:

```txt
isAdmin
isPublished
hasFieldErrors
hasPermission
canUpdateOrder
canDeleteQuestion
shouldShowNavigation
```

---

## 9.1 `is`

현재 상태나 성질을 표현합니다.

```txt
isActive
isValid
isPublished
isGeneratorType
```

---

## 9.2 `has`

무엇인가를 가지고 있는지를 표현합니다.

```txt
hasFieldErrors
hasPermission
hasNextPage
```

---

## 9.3 `can`

행위 가능 여부를 나타냅니다.

주로 Permission이나 Rule에서 사용합니다.

```txt
canUpdateUser
canDeleteOrder
canPublishContent
```

---

## 9.4 `should`

렌더링이나 실행 여부 등 정책적인 결정을 표현할 때 사용합니다.

```txt
shouldShowPagination
shouldRefreshPage
```

---

# 10. `create` 남용 금지

`create`는 아무 값이나 새로 만든다는 뜻으로 사용하지 않습니다.

이 프로젝트에서 `create`는 기본적으로 **실제 생성 Use Case 또는 Persistence 생성 작업**을 의미합니다.

사용하기 적절한 예:

```txt
createUserAction
createUserService
createUserRepository
```

이 경우 실제로:

```txt
새로운 User Resource를 생성한다.
Database에 새로운 Row를 생성한다.
```

라는 의미가 있습니다.

반면 다음과 같은 Helper에서는 `create`를 사용하지 않습니다.

지양:

```txt
createMockUser
createTestOrder
createConfig
createCookie
createOptions
createColumns
```

권장:

```txt
buildUserFixture
buildOrderFixture
defineConfig
buildSessionCookie
resolveOptions
defineColumns
```

---

# 11. `get` 남용 금지

`get` 역시 단순히 값을 반환한다는 이유만으로 사용하지 않습니다.

다음처럼 사용하지 않습니다.

```txt
getConfig
getOptions
getWorkspaceRoot
getDisplayName
getFormattedDate
getRequiredEnv
```

실제 의미에 맞는 이름을 사용합니다.

```txt
resolveConfig
resolveOptions
resolveWorkspaceRoot
resolveDisplayName
formatDate
requiredEnv
```

---

## 11.1 `get`을 사용하는 경우

`get`은 Application Use Case 수준에서 **조회 행위 자체가 함수의 의미인 경우** 사용할 수 있습니다.

예:

```txt
getUserByIdService
getUsersService
getOrderDetailService
getDashboardSummaryService
```

이 경우 `get`은 단순 Getter가 아니라:

```txt
Application의 조회 Use Case
```

를 의미합니다.

이미 의미가 명확하게 정립된 Public Utility API에서도 사용할 수 있습니다.

예:

```txt
getFieldError
getFormError
```

따라서 `get` 자체를 금지하는 것이 아니라 **아무 생각 없이 모든 조회성 Helper에 붙이는 것을 금지**합니다.

---

# 12. 계층별 동사 규칙

같은 동사라도 Layer에 따라 의미가 달라질 수 있으므로 계층별 기준을 따릅니다.

---

# 13. Server Action Naming

Server Action은 **Mutation Use Case**를 기준으로 이름을 작성합니다.

형식:

```txt
<useCase><Domain>Action
```

예:

```txt
createProductAction
registerOrderAction
updateProfileAction
publishContentAction
deleteQuestionAction
cancelOrderAction
withdrawOrderClaimAction
```

실제 행위를 가장 잘 표현하는 동사를 사용합니다.

다음처럼 CRUD 단어를 기계적으로 맞추지 않습니다.

```txt
create
register
publish
cancel
withdraw
archive
restore
approve
reject
```

는 서로 다른 Business Meaning을 가질 수 있습니다.

예:

```txt
publishContentAction
```

을 단순히:

```txt
updateContentAction
```

으로 표현하지 않습니다.

---

## 13.1 Action과 Service 동사 일치

같은 Use Case를 나타내는 Action과 Service는 같은 핵심 동사를 사용합니다.

```txt
createProductAction
createProductService
```

```txt
publishContentAction
publishContentService
```

```txt
cancelOrderAction
cancelOrderService
```

지양:

```txt
registerOrderAction
createOrderService
```

둘이 실제로 같은 Use Case라면 같은 용어를 사용합니다.

---

## 13.2 조회 Action

일반적인 조회를 위한 Server Action은 작성하지 않습니다.

조회 흐름은 Server Component에서 Domain Service를 직접 사용합니다.

따라서 다음 형태는 기본적으로 만들지 않습니다.

```txt
getUsersAction
getOrderDetailAction
getProductsAction
```

Server Action의 자세한 책임은 `09_서버_액션.md`를 따릅니다.

---

# 14. Service Naming

Service는 Application Use Case 단위로 이름을 작성합니다.

형식:

```txt
<useCase><Domain>Service
```

예:

```txt
createUserService
updateUserProfileService
publishContentService
cancelOrderService

getUserByIdService
getUsersService
getOrderDetailService
getDashboardSummaryService
```

Service에는 단순 CRUD보다 Business Meaning이 있는 이름을 우선합니다.

예:

```txt
approveRefundService
```

가 의미상 맞다면:

```txt
updateRefundService
```

라고 하지 않습니다.

---

# 15. 조회 Service Naming

조회 Service에서는 `get`을 사용할 수 있습니다.

```txt
getUserByIdService
getUsersService
getOrderDetailService
```

조회 대상이나 조건을 이름에서 구분할 가치가 있다면 명시합니다.

```txt
getPublishedContentsService
getQuestionsForAdminService
getMyOrdersService
```

단, Query 조건을 함수 이름에 끝없이 나열하지 않습니다.

지양:

```txt
getAllActivePublishedContentsOrderedByCreatedAtDescService
```

Query Object로 표현할 수 있는 세부 조건은 Parameter로 전달합니다.

---

# 16. Repository Naming

Repository는 Persistence 작업을 표현합니다.

Repository 함수의 기본 동사:

```txt
create
find
update
delete
count
upsert
```

필요한 경우 Domain 의미에 맞는 동사를 추가할 수 있습니다.

```txt
softDelete
hardDelete
increment
decrement
replace
```

---

## 16.1 조회 Repository는 `find`

Repository 조회에서는 기본적으로 `get`보다 `find`를 사용합니다.

```txt
findUserByIdRepository
findUserByEmailRepository
findOrdersRepository
findPurchasedProductsRepository
```

이유:

```txt
Repository
  Persistence에서 조건에 맞는 값을 찾음

Service
  Application Use Case로 값을 조회함
```

의 차이를 이름에서도 드러내기 위함입니다.

---

## 16.2 Null 가능 조회

대상을 찾지 못할 수 있는 Repository는 `find`가 자연스럽습니다.

```ts
findUserByIdRepository(
  userId: string,
): Promise<User | null>
```

Service에서 `null`을 Domain Failure로 변환할 수 있습니다.

---

## 16.3 목록 + Count

Pagination 등을 위해 목록과 전체 개수를 함께 반환한다면 의미를 이름에 포함할 수 있습니다.

```txt
findUsersAndCountRepository
findOrdersAndCountRepository
findPurchasedProductsAndCountRepository
```

단순히 모든 조회에 `AndCount`를 붙이지 않습니다.

실제로 Count를 함께 반환할 때만 사용합니다.

---

## 16.4 Update

```txt
updateUserRepository
updateOrderRepository
```

ID가 함수 Signature상 명확한 경우 불필요하게 `ById`를 반복하지 않아도 됩니다.

다만 여러 조회 Key가 존재하여 구분이 필요하다면 명시합니다.

```txt
updateUserByIdRepository
updateUserByExternalIdRepository
```

프로젝트 안에서는 같은 종류의 Repository에 일관된 방식을 사용합니다.

---

## 16.5 Delete

삭제 방식이 하나뿐이면:

```txt
deleteUserRepository
```

를 사용할 수 있습니다.

Soft Delete와 Hard Delete가 모두 존재한다면 명확하게 구분합니다.

```txt
softDeleteUserRepository
hardDeleteUserRepository
```

---

# 17. Repository 내부 Helper

Repository 내부의 Private Helper에도 습관적으로 `get`이나 `create`를 붙이지 않습니다.

예:

```txt
resolveUserListWhere
resolveUserListOrderBy
buildUserListWhere
buildUserListOrderBy
```

Prisma Query Object를 구성한다면 `build`가 자연스럽습니다.

예:

```ts
function buildUserListWhere(query: UserListQueryInput): Prisma.UserWhereInput {
  // ...
}
```

기존의:

```txt
userListFilterQuery
setQueryOrderBy
```

같은 이름보다 함수의 동작을 명확하게 표현합니다.

특히 단순히 Object를 반환하면서 `set`을 사용하지 않습니다.

`set`은 외부 상태를 실제로 변경하는 의미가 있을 때 사용합니다.

---

# 18. Schema Naming

Zod Schema 값은 `PascalCase`를 사용합니다.

예:

```txt
UserIdParam
UserListQuerySchema
CreateUserRequest
UpdateUserProfileRequest
```

---

## 18.1 Request

Mutation Input Schema:

```txt
CreateUserRequest
UpdateUserProfileRequest
PublishContentRequest
CancelOrderRequest
```

Type:

# 19. DTO Naming

DTO를 포함한 Type과 Interface는 `PascalCase`를 사용합니다.

응답 DTO에는 `Response`를 붙입니다.

```txt
UserResponse
UserDetailResponse
OrderResponse
OrderDetailResponse
```

목록의 각 Row가 동일한 DTO라면 불필요하게 `ListItemResponse`를 만들지 않습니다.

예:

```ts
interface UserResponse {
  // ...
}
```

목록 응답 자체에 Pagination Metadata가 필요하다면 별도의 Response를 만들 수 있습니다.

```ts
interface UserListResponse {
  users: UserResponse[];
  totalCount: number;
}
```

DTO를 만들지 여부와 Domain Layer의 책임은 `08_도메인_레이어.md`를 따릅니다.

# 20. Mapper Naming

Domain Mapper 함수는 `to<Destination>` 형태를 우선합니다.

```txt
toUserResponse
toUserDetailResponse
toOrderResponse
toOrderDetailResponse
```

이름에 Source를 반복하지 않습니다.

지양:

```txt
mapUserToUserResponse
convertUserToUserResponse
```

권장:

```txt
toUserResponse
```

# 21. Permission Naming

Permission 함수는 `can`으로 시작합니다.

```txt
canReadUser
canCreateUser
canUpdateUser
canDeleteUser
```

Business Use Case가 더 구체적이라면 해당 행위를 사용합니다.

```txt
canPublishContent
canCancelOrder
canApproveRefund
```

Actor Type:

```txt
UserPermissionActor
OrderPermissionActor
```

# 22. Rule Naming

Business Rule이 Boolean을 반환한다면 의미에 따라:

```txt
can
is
has
```

등을 사용합니다.

판정 결과 자체가 Boolean이 아닌 경우 실제 의미를 표현합니다.

예:

```txt
calculateRefundableQuantity
resolveNextOrderStatus
```

단순히:

```txt
getRefundableQuantity
```

라고 하지 않습니다.

```ts
export const URLS = {} as const;
export const NAVIGATION_ITEMS = {} as const;
```

Domain Constant는 Domain 이름을 사용합니다.


# 24. Domain Validation Constant

Domain의 Field Constraint가 여러 위치에서 공유된다면 Constant에서 관리할 수 있습니다.

예:

```ts
export const USER = {
  NICKNAME: {
    KR: "닉네임",
    MIN_LENGTH: 2,
    MAX_LENGTH: 30,
    REQUIRED_MESSAGE: "닉네임을 입력해 주세요.",
    MIN_MESSAGE: "닉네임은 2글자 이상이어야 합니다.",
    MAX_MESSAGE: "닉네임은 30자 이하이어야 합니다.",

```

이 값은 필요에 따라 다음에서 공유할 수 있습니다.

```txt
Zod Schema

```

# 26. 변수는 값의 의미를 표현한다

함수의 반환값을 무조건 `data`라고 하지 않습니다.

지양:

```ts
const data = await findUserByIdRepository(userId);
```

권장:

```ts
const user = await findUserByIdRepository(userId);
```

여러 결과가 있을 경우에도 의미를 표현합니다.

```ts
const orderCount = ...

```

# 27. `result`

`result`는 바로 다음 줄에서 검사되는 좁은 Scope에서는 사용할 수 있습니다.

예:

```ts
const result = UserIdParam.safeParse(input);

if (!result.success) {
  // ...
}
```

하지만 한 함수 안에 여러 Result가 있다면 구체적으로 작성합니다.

```txt
validationResult

```

# 28. `options`

```ts
function generateDomain(options: GenerateDomainOptions) {}
```

하지만 여러 설정 값을 단순히 묶었다는 이유로 전부 `options`라고 부르지는 않습니다.

```txt
config
query
params
filters
preferences
```

중 실제 의미를 사용합니다.

# 30. Import 기본 규칙

Import는 프로젝트 ESLint와 Formatter 결과를 기준으로 작성합니다.

일반적인 그룹:

```txt
Node / Framework / External
Workspace Package
App Alias
Relative Import
```

예:

```ts
import { randomUUID } from "node:crypto";

import { z } from "zod";

```

실제 순서와 빈 줄은 현재 ESLint / Formatter 규칙을 우선합니다.

# 31. Type-only Import

Runtime에서 사용하지 않는 Type은 `import type`을 사용합니다.

```ts
import type { User } from "@prisma/client";
```

같은 Module에서 Runtime Value와 Type을 함께 Import하는 경우 현재 Formatter 규칙에 맞게 작성합니다.

예:

```ts
import { z, type ZodType } from "zod";
```

또는 규칙에 따라 분리합니다.

---

# 32. App Import

App 내부 Layer Public API가 존재하면 Barrel을 사용합니다.

예:

```tsx
import { OrderStatusBadge } from "@/entities/order";
import { UpdateOrderStatusForm } from "@/features/order";
import { OrderDetailView } from "@/views/order";
```

다른 Slice 내부 구현 파일을 Deep Import하지 않습니다.

지양:

```tsx
import OrderStatusBadge from "@/entities/order/ui/order-status-badge/order-status-badge";
```

---

# 33. 같은 Slice 내부 Import

같은 Slice 내부에서는 필요한 경우 Relative Import를 사용할 수 있습니다.

예:

```ts
import { ORDER_ERROR_CODE } from "./order.error";
```

무조건 자기 자신의 Barrel을 다시 Import하지 않습니다.

지양:

```ts
import { ORDER_ERROR_CODE } from ".";
```

이는 순환 의존성이나 불필요한 간접 참조를 만들 수 있습니다.

---

# 34. Package Import

Workspace Package는 Package Public API를 통해 Import합니다.

권장:

```ts
import { success } from "@repo/core/result";
import { UserIdParam } from "@repo/domain/user/client";
import { getUserByIdService } from "@repo/domain/user/server";
```

지양:

```ts
import { getUserByIdService } from "../../../packages/domain/src/user/user.service";
```

Package의 내부 Source Path를 직접 참조하지 않습니다.

# 35. Export 기본 규칙

Public API는 가능한 한 **Named Export를 명시적으로 작성**합니다.

지양:

```ts
export * from "./user.service";
```

권장:

```ts
export { getUserByIdService } from "./user.service";
```

Type:

```ts
export type { UserResponse } from "./user.dto";
```

# 36. Type Export 순서

같은 Module에서 Type과 Runtime Value를 모두 Export한다면 현재 프로젝트의 Lint 결과에 맞춰 Type Export를 먼저 둘 수 있습니다.

예:

```ts
export type { OrderClaimItemErrorCode } from "./order-claim-item.error";
export { ORDER_CLAIM_ITEM_ERROR_CODE } from "./order-claim-item.error";
```

Schema 역시 현재 Formatter / Lint 결과를 그대로 따릅니다.

```ts
export type {
  CreateOrderClaimItemRequestInput,
  OrderClaimItemIdParamInput,
  OrderClaimItemListQuery,
  OrderClaimItemListSortKey,
  UpdateOrderClaimItemRequestInput,
} from "./order-claim-item.schema";
export {
  CreateOrderClaimItemRequest,
  OrderClaimItemIdParam,
  OrderClaimItemListSortKeys,
  UpdateOrderClaimItemRequest,
} from "./order-claim-item.schema";
```

Generator Template 역시 이 결과와 동일해야 합니다.

# 37. 한 줄 Export

짧은 Export는 Formatter가 허용하는 경우 한 줄로 작성합니다.

```ts
export { ORDER_CLAIM_ITEM } from "./order-claim-item.constant";
```

```ts
export type { OrderClaimItemErrorCode } from "./order-claim-item.error";
```

불필요하게:

```ts
export { ORDER_CLAIM_ITEM } from "./order-claim-item.constant";
```

형태를 Generator에서 강제로 만들지 않습니다.

최종 기준은 Repository의 실제 Formatter / Lint 결과입니다.

# 39. Barrel Export

Domain Package처럼 Client / Server Boundary가 필요한 경우 `client.ts`를 사용합니다.

# 44. Wildcard Export

Public Barrel에서는 기본적으로 다음을 사용하지 않습니다.

```ts
export * from "./...";
```

이유:

```txt
Public API 범위가 암묵적이 됨
의도하지 않은 Export가 외부에 노출될 수 있음
이름 충돌을 발견하기 어려움
Client / Server Boundary를 검토하기 어려움
```

따라서 Export 대상은 명시합니다.

# 53. Commit 기본 형식

Commit Message는 다음 구조를 사용합니다.

```txt
<type>: <summary>
```

예:

```txt
feat: 주문 취소 기능 추가
fix: 주문 상세 조회 시 nullable 처리 수정
refactor: 도메인 generator repository 옵션 분리
docs: 코드 생성기 문서 추가
test: 주문 repository integration test 추가
chore: pnpm catalog 의존성 정리
```

필요할 때 Scope를 사용할 수 있습니다.

```txt
<type>(<scope>): <summary>
```

예:

```txt
feat(order): 주문 취소 기능 추가
fix(auth): 세션 만료 처리 수정
refactor(generator): domain generator export 구조 정리
```

Scope 사용 여부는 Commit 단위에서 의미가 있을 때만 선택합니다.

---

# 54. Commit Type

기본 Type은 다음과 같습니다.

```txt
feat
fix
refactor
docs
test
chore
build
ci
perf
style
revert
```

---

## 54.1 `feat`

사용자 또는 개발자가 사용할 새로운 기능을 추가합니다.

```txt
feat: 회원 차단 기능 추가
feat: entity generator 추가
```

---

## 54.2 `fix`

기존 동작의 오류를 수정합니다.

```txt
fix: 주문 상세 조회 시 사용자 정보 누락 수정
```

---

## 54.3 `refactor`

기능의 외부 동작을 바꾸지 않고 구조를 개선합니다.

```txt
refactor: server action validation 흐름 정리
refactor: domain generator repository 생성을 옵션으로 분리
```

---

## 54.4 `docs`

문서만 변경합니다.

```txt
docs: 테스트 전략 문서 추가
docs: 컨벤션 문서 재정비
```

---

## 54.5 `test`

Production 동작 변경 없이 Test를 추가하거나 수정합니다.

```txt
test: user repository integration test 추가
```

---

## 54.6 `chore`

기능, Bug Fix, Build 자체가 아닌 유지보수 작업에 사용합니다.

```txt
chore: 사용하지 않는 의존성 제거
chore: generator help 문구 정리
```

---

## 54.7 `build`

Build System이나 Dependency 구성 변경에 사용합니다.

```txt
build: pnpm workspace catalog 설정 변경
```

---

## 54.8 `ci`

CI Workflow 변경에 사용합니다.

```txt
ci: integration test job 추가
```

---

## 54.9 `perf`

외부 동작은 동일하지만 성능을 개선합니다.

```txt
perf: 주문 목록 query 최적화
```

---

## 54.10 `style`

Formatting 등 동작이나 구조에 영향을 주지 않는 코드 스타일 변경에 사용합니다.

```txt
style: import 정렬
```

단순 Formatting을 `refactor`로 분류하지 않습니다.

---

## 54.11 `revert`

기존 Commit을 되돌릴 때 사용합니다.

```txt
revert: 주문 캐시 정책 변경 되돌림
```

---

# 55. Commit Summary

Summary는 변경 내용을 짧고 명확하게 작성합니다.

권장:

```txt
feat: 주문 취소 기능 추가
```

지양:

```txt
feat: 기능 추가
fix: 수정
chore: 작업
```

Summary만 읽어도 무엇을 변경했는지 알 수 있어야 합니다.

---

# 56. Commit Message 언어

Commit Summary는 이 프로젝트에서 일관되게 한국어를 사용할 수 있습니다.

Type과 Scope는 영문 Convention을 유지합니다.

```txt
feat(order): 주문 취소 기능 추가
```

기술적 이름은 원래 표기를 유지합니다.

```txt
refactor(generator): Domain Generator export 구조 정리
```

# 57. Commit 단위

Commit은 가능한 한 하나의 논리적인 변경 단위를 나타냅니다.

좋은 예:

```txt
1. Domain Generator repository 옵션 추가
2. Generator 테스트 수정
3. 문서 갱신
```

이 셋이 하나의 변경 목적에 속한다면 하나의 Commit으로 묶을 수도 있습니다.

반대로 다음처럼 관계없는 작업을 한 Commit에 섞지 않습니다.

```txt
주문 취소 구현
+
Storybook Button 색상 수정
+
README 오탈자 수정
```

---

# 58. Commit과 Formatting

Formatting만 변경된 파일이 대규모로 섞이지 않도록 합니다.

기능 수정 전에 전체 Repository를 무의미하게 Format하지 않습니다.

Generator나 Lint Rule 수정으로 인해 Formatting이 광범위하게 변경되어야 한다면 별도의 Commit으로 분리하는 것을 검토합니다.

# 59. Commit 전에 확인

Commit 전 최소한 현재 변경 범위에 필요한 검증을 수행합니다.

대표적으로:

```bash
pnpm lint
pnpm check-types
pnpm test
```

Integration Test가 관련되었다면:


도 실행합니다.

전체 검증 명령은 `16_개발_워크플로우.md`에서 정의합니다.

# 60. 이름을 결정하는 순서

새로운 함수나 변수를 만들 때 다음 순서로 이름을 결정합니다.

```txt
1. 이 코드의 계층은 어디인가?

2. 실제 책임은 무엇인가?

3. Business Use Case인가?
   → create / publish / cancel / approve 등

4. Persistence 작업인가?
   → create / find / update / delete

5. 값을 조합하는가?
   → build

6. 최종 후보를 결정하는가?
   → resolve

7. Raw Input을 해석하는가?
   → parse

8. 동일 의미의 형태를 정규화하는가?
   → normalize

9. 출력용 표현으로 바꾸는가?
   → format

10. 외부 Source에서 읽는가?
    → load

11. Boolean 상태인가?
    → is / has / can / should
```

아무 동사도 정확히 맞지 않는다면 `create`나 `get`을 임시로 붙이지 말고 함수의 책임부터 다시 확인합니다.

# 63. 금지해야 할 기계적인 Naming

다음 Pattern을 습관적으로 생성하지 않습니다.

```txt
create + 아무 Helper
get + 아무 값
set + 객체 생성
handle + 일반 Utility
process + 모호한 작업
manage + 모호한 책임
helper + 아무 함수
util + 아무 파일
```

예:

```txt
processUserData
manageOrder
userHelper
orderUtil
getData
createData
```

이런 이름이 필요해졌다면 책임이 아직 충분히 분해되지 않았을 가능성이 높습니다.

# 64. 일관성이 우선이다

동일한 개념을 Repository 안에서:

```txt
findUserByIdRepository
```

라고 부르고 다른 Domain에서는 특별한 이유 없이:

```txt
getOrderByIdRepository
```

라고 부르지 않습니다.

동일 계층과 동일 책임에는 동일한 Naming Pattern을 적용합니다.

다만 Business Language가 다른 경우에는 Business Meaning을 우선합니다.

```txt
publish
archive
cancel
withdraw
approve
reject
```

같은 동사를 단순 CRUD로 치환하지 않습니다.

# 65. Generator와 Convention

`pnpm generate`가 생성하는 코드도 이 문서의 Convention을 따라야 합니다.

Generator가 생성한 직후:

```txt
Lint
Formatter
```

가 대규모로 코드를 다시 변경한다면 Generator Template을 수정합니다.

특히 다음을 일치시킵니다.

```txt
파일명
디렉터리명
Import 순서
Named Export
Type-only Export
Barrel 구조
Test 위치
Story 파일명
```

Generator 상세 기준은 `14_코드_생성기.md`를 따릅니다.

# 66. Architecture 설명과 Convention의 경계

이 문서는 다음과 같은 질문에 답합니다.

```txt
이 파일은 무엇이라고 이름 짓는가?
이 함수에는 어떤 동사를 쓰는가?
어떻게 Import / Export하는가?
Test 파일 이름은 무엇인가?
Commit Message는 어떻게 작성하는가?
```

다음 질문은 이 문서의 책임이 아닙니다.

```txt
Entity와 Feature의 차이는 무엇인가?
Domain Service는 어떤 책임을 가지는가?
Server Action에 Business Logic을 넣어도 되는가?
Repository가 어느 Package를 Import할 수 있는가?
Story를 어떤 Component에 작성하는가?
```

이런 내용은 각각의 Architecture 전문 문서를 따릅니다.

# 68. 핵심 원칙

```txt
파일과 디렉터리는 기본적으로 kebab-case를 사용한다.

Custom Hook 파일은 Hook 이름과 동일한 camelCase를 사용한다.

Component와 Type은 PascalCase를 사용한다.

변수와 함수는 camelCase를 사용한다.

상수는 UPPER_SNAKE_CASE를 사용한다.

Component는 기본적으로 default export하고 Barrel에서 named export한다.

Public API는 명시적인 named export를 사용한다.

Type은 export type을 사용한다.

Public Barrel에서는 export *를 기본적으로 사용하지 않는다.

client.ts에는 Browser-safe API만 공개한다.

server.ts에는 server-only를 선언하고 Server API만 공개한다.

Domain Unit Test는 Domain Slice의 test/에 둔다.

Unit Test는 *.test.ts 또는 *.test.tsx를 사용한다.

Integration Test는 *.integration.test.ts 또는 *.integration.test.tsx를 사용한다.

Playwright E2E는 *.spec.ts를 사용한다.

Story는 *.stories.tsx를 사용한다.

변수와 함수 이름에 의미 없는 줄임말을 사용하지 않는다.

create는 실제 생성 Use Case나 Persistence 생성 작업에 사용한다.

get은 Application 조회 Use Case 등 의미가 명확할 때 사용한다.

단순 객체 생성에는 build를 사용한다.

설정 Definition에는 define을 사용한다.

최종 값을 결정할 때 resolve를 사용한다.

Raw Input 해석에는 parse를 사용한다.

형태 정규화에는 normalize를 사용한다.

출력 표현에는 format을 사용한다.

외부 Resource 읽기에는 load를 사용한다.

Boolean 함수는 is / has / can / should를 사용한다.

Repository 조회는 기본적으로 find를 사용한다.

Action과 Service의 같은 Use Case는 같은 핵심 동사를 사용한다.

Business Meaning이 있는 동사를 단순 CRUD로 바꾸지 않는다.

Mock Function에는 mock Prefix를 사용할 수 있다.

테스트 Fixture Builder에는 build...Fixture를 사용한다.

Commit은 <type>: <summary> 형식을 기본으로 사용한다.

Commit 하나에는 가능한 한 하나의 논리적인 변경 목적을 담는다.

Generator Template도 실제 Lint / Formatter 결과와 동일한 Convention을 따른다.

Convention 문서에는 Architecture 자체의 설명을 중복하지 않는다.
```
