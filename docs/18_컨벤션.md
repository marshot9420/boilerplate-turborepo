# 컨벤션

이 문서는 `boilerplate-turborepo` 전반에서 사용하는 코드 표현과 Naming 규칙을 정의합니다.

주요 대상:

```txt
파일 / 디렉터리 Naming

Component / Hook Naming

변수 / 함수 Naming

Action / Service / Repository Naming

Schema / DTO / Mapper / Permission / Rule Naming

Constant Naming

Import / Export

Public API / Barrel

Test / Story / Fixture Naming

Commit 규칙
```

Architecture 자체의 책임은 이 문서에서 다시 정의하지 않습니다.

다음 내용은 각각의 전문 문서를 따릅니다.

## 1. 기본 원칙

이름은 짧은 것보다 **역할과 의미를 정확하게 표현하는 것**을 우선합니다.

```txt
이름만 보고 역할을 추론할 수 있어야 한다.

같은 개념에는 같은 용어를 사용한다.

다른 책임에는 다른 동사를 사용한다.

Layer의 책임과 함수 이름이 일치해야 한다.

줄임말을 습관적으로 사용하지 않는다.

create, get 같은 범용 동사를 습관적으로 사용하지 않는다.

Public API에서는 모호한 이름보다 구체적인 이름을 사용한다.

같은 Layer와 같은 책임에는 같은 Naming Pattern을 사용한다.

Business Language가 존재한다면 단순 CRUD보다 Business Meaning을 우선한다.
```

다음과 같은 지나치게 넓은 이름은 필요한 경우에만 사용합니다.

```txt
data
item
value
result
temp
obj
info
util
helper
manager
handler
process
```

좁은 Scope에서 의미가 충분히 명확한 `result`, `value`, `options` 등은 사용할 수 있습니다.

## 2. 파일과 디렉터리 Naming

파일과 디렉터리는 기본적으로 `kebab-case`를 사용합니다.

예:

```txt
user.repository.ts
user.repository.test.ts
user.repository.integration.test.ts

user.constant.ts
user.schema.ts
user.permission.ts
user.error.ts
user.service.ts
user.mapper.ts
user.dto.ts

create-product.action.ts

order-status-badge.tsx
order-status-badge.test.tsx
order-status-badge.stories.tsx

update-profile-form.tsx
```

디렉터리:

```txt
order-claim
order-status-badge
update-profile
update-profile-form
```

Custom Hook 파일은 예외적으로 Hook 함수 이름과 동일한 `camelCase`를 사용합니다.

```txt
useMediaQuery.ts
useActionResultEffect.ts
useFormInteractionState.ts
useUpdateProfileForm.ts
```

## 3. Component와 Hook Naming

React Component는 `PascalCase`를 사용합니다.

```tsx
interface OrderStatusBadgeProps {
  status: OrderStatus;
}

export default function OrderStatusBadge({ status }: OrderStatusBadgeProps) {
  // ...
}
```

Props Type은 Component 이름을 기준으로 작성합니다.

```txt
OrderStatusBadge
→ OrderStatusBadgeProps
```

지나치게 일반적인 이름은 피합니다.

```txt
Component
Container
Wrapper
Content
Item
Row
```

다만 상위 개념과 결합하여 의미가 명확하면 사용할 수 있습니다.

```txt
OrderDetailContent
ProductTableRow
UserProfileContent
```

Custom Hook은 `use`로 시작합니다.

```txt
useMediaQuery
useActionResultEffect
useUpdateProfileForm
```

---

## 4. Component Export

React Component는 기본적으로 `default export`를 사용합니다.

```tsx
export default function OrderStatusBadge() {
  // ...
}
```

Component Directory 또는 Slice의 Public API에서는 Named Export로 공개합니다.

```ts
export { default as OrderStatusBadge } from "./order-status-badge";
```

소비 코드는 Public API를 사용합니다.

```tsx
import { OrderStatusBadge } from "@/entities/order";
```

`forwardRef` 등 함수 선언이 적합하지 않은 Component도 최종적으로는 동일한 방식으로 `default export`할 수 있습니다.

```tsx
"use client";

import { forwardRef } from "react";

const Input = forwardRef<HTMLInputElement, InputProps>((props, ref) => {
  return <input ref={ref} {...props} />;
});

Input.displayName = "Input";

export default Input;
```

## 5. 변수와 함수 Naming

변수와 함수는 기본적으로 `camelCase`를 사용합니다.

함수는 다음 형태를 우선합니다.

```txt
동사 + 대상 + 필요한 한정어
```

예:

```txt
formatOrderDate

resolveUserDisplayName

normalizeSearchKeyword

parseOrderListQuery

buildSessionCookie

loadTestEnvironment
```

변수도 값의 의미를 표현합니다.

지양:

```ts
const data = await findUserByIdRepository(userId);
```

권장:

```ts
const user = await findUserByIdRepository(userId);
```

여러 결과가 존재한다면 더 구체적으로 작성합니다.

```txt
validationResult
serviceResult
actionResult

orderCount
filteredUsers
normalizedKeyword
```

## 6. 함수 동사 Convention

함수의 첫 동사는 실제 동작을 표현해야 합니다.

### `build`

여러 입력을 조합하여 새로운 메모리상의 값이나 구조를 구성합니다.

```txt
buildSessionCookie
buildUserFixture
buildPaginationItems
buildRequestHeaders
buildOrderWhere
```

단순 객체 생성 Helper에 습관적으로 `create`를 사용하지 않습니다.

---

### `define`

설정이나 선언적 Definition을 구성합니다.

```txt
defineNextAppE2EConfig
defineNavigationGroups
defineTableColumns
defineConfig
```

단순 Config Factory를 의미 없이 `createConfig`라고 하지 않습니다.

---

### `execute`

이미 정의된 작업이나 처리 흐름을 실제로 실행합니다.

```txt
executeFormAction
executeCommand
executeMigration
```

값이나 설정을 구성하는 `build`, `define`과 구분하며, 실제 Resource 생성 의미가 없는 실행 Wrapper에 `create`를 사용하지 않습니다.

---

### `resolve`

여러 후보나 상태를 고려하여 최종 값을 결정합니다.

```txt
resolveWorkspaceRoot
resolveFieldError
resolveUserDisplayName
resolveRedirectUrl
resolveSortDirection
```

---

### `normalize`

같은 의미를 유지하면서 정규화된 형태로 변환합니다.

```txt
normalizeBlankStringToUndefined
normalizeEmail
normalizeSearchKeyword
normalizePhoneNumber
```

---

### `parse`

Raw Input을 구조화된 값으로 해석합니다.

```txt
parseSearchParams
parseFormData
parseSortDirection
parseDateInput
```

---

### `load`

파일, 환경 또는 외부 Resource에서 값을 읽어옵니다.

```txt
loadTestEnv
loadPlaywrightEnv
loadFixture
```

---

### `map` / `to`

구조를 다른 구조로 대응시키는 일반적인 변환에는 `map`을 사용할 수 있습니다.

```txt
mapPrismaError
mapValidationErrors
mapOrderItems
```

Domain Mapper의 대표적인 Response 변환은 `to<Destination>`을 우선합니다.

```txt
toUserResponse
toOrderDetailResponse
```

---

### `format`

사람이 읽거나 화면에 출력하기 위한 표현으로 변환합니다.

```txt
formatCurrency
formatOrderDate
formatPhoneNumber
```

---

### `required`

필수 값을 읽고 존재하지 않으면 실패하는 작은 Utility에서 사용할 수 있습니다.

```txt
requiredEnv
```

단순히:

```txt
getRequiredEnv
```

라고 하지 않습니다.

---

### Boolean

Boolean을 반환하는 함수는 의미에 따라 다음 Prefix를 사용합니다.

```txt
is
  상태나 성질

has
  보유 여부

can
  행위 가능 여부

should
  실행 또는 표현 여부
```

예:

```txt
isPublished

hasFieldErrors

canCancelOrder

shouldShowPagination
```

## 7. `create`와 `get`

`create`와 `get` 자체를 금지하지는 않습니다.

다만 실제 의미가 있을 때 사용합니다.

### `create`

실제 Resource 생성 Use Case 또는 Persistence 생성 작업에 사용합니다.

```txt
createUserAction
createUserService
createUserRepository
```

다음과 같은 단순 Helper에는 다른 동사를 우선합니다.

```txt
createMockUser
→ buildUserFixture

createSessionCookie
→ buildSessionCookie

createConfig
→ defineConfig
```

### `get`

Application 수준의 조회 Use Case에는 사용할 수 있습니다.

```txt
getUserByIdService
getUsersService
getOrderDetailService
getDashboardSummaryService
```

이미 의미가 정립된 Utility에서도 사용할 수 있습니다.

```txt
getFieldError
getFormError
```

단순히 값을 반환한다는 이유만으로 모든 Helper에 `get`을 붙이지 않습니다.

```txt
getWorkspaceRoot
→ resolveWorkspaceRoot

getDisplayName
→ resolveDisplayName

getFormattedDate
→ formatDate
```

## 8. Server Action과 Service Naming

Server Action과 Domain Service는 **Use Case**를 기준으로 이름을 작성합니다.

형식:

```txt
<useCase><Domain>Action

<useCase><Domain>Service
```

예:

```txt
createProductAction
createProductService

publishContentAction
publishContentService

cancelOrderAction
cancelOrderService
```

Business Meaning이 있다면 CRUD 이름으로 단순화하지 않습니다.

```txt
publishContentAction

approveRefundService

cancelOrderService

withdrawOrderClaimAction
```

같은 Use Case를 나타내는 Action과 Service는 같은 핵심 동사를 사용합니다.

지양:

```txt
registerOrderAction
createOrderService
```

둘이 같은 Use Case라면 같은 용어를 선택합니다.

일반적인 조회를 위한 Server Action은 만들지 않습니다.

```txt
getUsersAction
getOrderDetailAction
getProductsAction
```

조회 Service는 `get`을 사용할 수 있습니다.

```txt
getUserByIdService
getUsersService
getPublishedContentsService
getQuestionsForAdminService
getMyOrdersService
```

Server Action 자체의 책임은 `09_서버_액션.md`, Service 책임은 `08_도메인_레이어.md`를 따릅니다.

## 9. Repository Naming

Repository는 Persistence 작업을 표현합니다.

기본 동사:

```txt
create
find
update
delete
count
upsert
```

필요하면 의미에 따라:

```txt
softDelete
hardDelete
increment
decrement
replace
```

등을 사용할 수 있습니다.

조회에는 기본적으로 `find`를 사용합니다.

```txt
findUserByIdRepository

findUserByEmailRepository

findOrdersRepository

findPurchasedProductsRepository
```

Service의:

```txt
getUserByIdService
```

와 Repository의:

```txt
findUserByIdRepository
```

를 구분합니다.

대상을 찾지 못할 수 있는 조회에도 `find`가 자연스럽습니다.

```ts
function findUserByIdRepository(userId: string): Promise<User | null> {
  // ...
}
```

목록과 Count를 실제로 함께 반환한다면 이름에 표현할 수 있습니다.

```txt
findUsersAndCountRepository
findOrdersAndCountRepository
```

Update와 Delete는 필요한 수준에서 Query Key나 삭제 방식을 명확히 합니다.

```txt
updateUserRepository

updateUserByExternalIdRepository

deleteUserRepository

softDeleteUserRepository

hardDeleteUserRepository
```

Repository 내부 Query Object Builder에도 동일한 동사 규칙을 적용합니다.

```txt
buildUserListWhere
buildUserListOrderBy
```

외부 상태를 실제로 변경하지 않는 함수에 `set`을 사용하지 않습니다.

## 10. Schema와 DTO Naming

Zod Schema 값과 DTO Type은 `PascalCase`를 사용합니다.

### Schema Factory

재사용 가능한 Schema Factory는 반환하는 Schema의 역할이 드러나도록 `<meaning>Schema` 형태를 사용합니다.

```txt
requiredStringSchema
optionalStringSchema
nullableStringSchema
optionalNumberSchema
optionalIntegerSchema
optionalBooleanSchema
optionalDateSchema
optionalEnumSchema
formBooleanSchema
```

구현 라이브러리를 함수 이름의 Prefix로 사용하지 않습니다.

지양:

```txt
zRequiredString
zOptionalString
zOptionalInt
```

권장:

```txt
requiredStringSchema
optionalStringSchema
optionalIntegerSchema
```

`Int`와 같이 불필요한 축약어보다 `Integer`처럼 의미가 명확한 이름을 우선합니다.

### Request

Mutation Input Schema:

```txt
CreateUserRequest
UpdateUserProfileRequest
PublishContentRequest
CancelOrderRequest
```

Input Type:

```txt
CreateUserRequestInput
UpdateUserProfileRequestInput
```

### Param

```txt
UserIdParam
OrderIdParam

UserIdParamInput
OrderIdParamInput
```

### Query

```txt
UserListQuerySchema
OrderListQuerySchema

UserListQueryInput
OrderListQueryInput
```

### Sort Key

Collection 값은 의미에 맞는 복수형을 사용합니다.

```ts
export const UserListSortKeys = ["EMAIL", "STATUS", "CREATED_AT"] as const;

export type UserListSortKey = (typeof UserListSortKeys)[number];
```

### DTO

Response DTO에는 `Response`를 사용합니다.

```txt
UserResponse
UserDetailResponse
OrderResponse
OrderDetailResponse
```

목록 항목이 기존 DTO와 동일하다면 불필요하게 `ListItemResponse`를 새로 만들지 않습니다.

Pagination Metadata 등을 포함한 별도 계약이 필요하면:

```txt
UserListResponse
```

처럼 구분할 수 있습니다.

DTO 사용 여부 자체는 `08_도메인_레이어.md`를 따릅니다.

## 11. Mapper, Permission, Rule Naming

Domain Mapper의 대표적인 변환 함수는:

```txt
to<Destination>
```

형태를 우선합니다.

```txt
toUserResponse
toUserDetailResponse
toOrderResponse
toOrderDetailResponse
```

지양:

```txt
mapUserToUserResponse
convertUserToUserResponse
```

Permission 함수는 `can`을 사용합니다.

```txt
canReadUser
canCreateUser
canUpdateUser
canDeleteUser

canPublishContent
canCancelOrder
canApproveRefund
```

Actor Type은 Domain과 역할을 드러냅니다.

```txt
UserPermissionActor
OrderPermissionActor
```

Rule이 Boolean을 반환한다면 의미에 따라:

```txt
can
is
has
```

를 사용할 수 있습니다.

Boolean이 아니라면 실제 계산이나 결정의 의미를 사용합니다.

```txt
calculateRefundableQuantity

resolveNextOrderStatus
```

## 12. Constant Naming

상수는 기본적으로 `UPPER_SNAKE_CASE`를 사용합니다.

```ts
export const USER = {} as const;

export const PRODUCT_IMAGE = {} as const;

export const URLS = {} as const;

export const NAVIGATION_ITEMS = {} as const;
```

Domain Constant는 Domain 이름을 사용합니다.

```txt
USER

ORDER

PAYMENT

ORDER_CLAIM
```

Field Constraint가 여러 위치에서 실제로 공유된다면 Domain Constant로 관리할 수 있습니다.

```ts
export const USER = {
  NICKNAME: {
    KR: "닉네임",
    MIN_LENGTH: 2,
    MAX_LENGTH: 30,
  },
} as const;
```

모든 Field에 기계적으로 Constraint Object를 만들지는 않습니다.

변수는 `camelCase`를 사용하고 의미 없는 줄임말을 피합니다.

지양:

```txt

prd
cfg
opts
res
req
err
idx
cnt
```

권장:

```txt
user
product
config
options
response
request
error
index
count
```

일반적으로 통용되는 기술적 약어는 사용할 수 있습니다.

```txt

dto
html
css
```

Event Handler는 필요에 따라 `handle`을 사용합니다.

## 14. Import 규칙

Import 순서는 Repository의 ESLint와 Formatter 결과를 기준으로 합니다.

일반적인 그룹:

```txt
Node / Framework / External

Workspace Package

App Alias

Relative Import
```

예:

```ts
import { randomUUID } from "node:crypto";

import { z } from "zod";

import type { AppError } from "@repo/core/errors";
import { failure, success } from "@repo/core/result";

import { URLS } from "@/constants";

import { ORDER_ERROR_CODE } from "./order.error";
```

Runtime에서 사용하지 않는 Type은 `import type`을 사용합니다.

```ts
import type { User } from "@prisma/client";
```

Value와 Type을 같은 Module에서 가져올 경우 현재 Lint / Formatter 결과를 따릅니다.

```ts
import { z, type ZodType } from "zod";
```

## 15. App과 Package Import

다른 Slice나 Layer를 사용할 때는 Public API를 사용합니다.

```tsx
import { OrderStatusBadge } from "@/entities/order";

import { UpdateOrderStatusForm } from "@/features/order";

import { OrderDetailView } from "@/views/order";
```

다른 Slice의 내부 구현을 Deep Import하지 않습니다.

지양:

```tsx
import OrderStatusBadge from "@/entities/order/ui/order-status-badge/order-status-badge";
```

같은 Slice 내부에서는 Relative Import를 사용할 수 있습니다.

```ts
import { ORDER_ERROR_CODE } from "./order.error";
```

자기 자신의 Barrel을 다시 Import하지 않습니다.

```ts
// 지양
import { ORDER_ERROR_CODE } from ".";
```

Workspace Package는 Package Public API를 통해 Import합니다.

```ts
import { success } from "@repo/core/result";

import { UserIdParam } from "@repo/domain/user/client";

import { getUserByIdService } from "@repo/domain/user/server";
```

Package의 내부 Source Path를 직접 참조하지 않습니다.

## 16. Export와 Public API

Public API는 명시적인 Named Export를 사용합니다.

지양:

```ts
export * from "./user.service";
```

권장:

```ts
export { getUserByIdService } from "./user.service";

export type { UserResponse } from "./user.dto";
```

짧은 Export는 Formatter 결과에 따라 한 줄로 유지합니다.

```ts
export { ORDER_CLAIM_ITEM } from "./order-claim-item.constant";

export type { OrderClaimItemErrorCode } from "./order-claim-item.error";
```

`index.ts`는 Public API Boundary가 필요한 위치에서 사용합니다.

대표적인 대상:

```txt
Component Directory

Slice Public API

Package Subpath Public API

App Layer Public API
```

모든 Directory에 기계적으로 만들지 않습니다.

Barrel의 목적:

```txt
Public API를 제한한다.

Deep Import를 방지한다.

내부 구조 변경의 영향을 줄인다.

Layer / Slice Boundary를 유지한다.
```

App-level 공통 영역도 필요한 경우 Public API를 가질 수 있습니다.

```txt
config
constants
hooks
shared
types
```

---

### `client.ts`

Client / Server Boundary가 필요한 Package에서는 Browser-safe API만 공개합니다.

```ts
export { USER } from "./user.constant";

export type { UserResponse } from "./user.dto";

export type { UserIdParamInput } from "./user.schema";
export { UserIdParam } from "./user.schema";
```

Server-only Module을 Export하지 않습니다.

### `server.ts`

Server 전용 Public API를 공개합니다.

```ts
import "server-only";

export type { UserErrorCode } from "./user.error";
export { USER_ERROR_CODE } from "./user.error";

export { toUserResponse } from "./user.mapper";

export type { UserPermissionActor } from "./user.permission";
export { canReadUser } from "./user.permission";

export { getUserByIdService } from "./user.service";
```

Public Barrel에서는 기본적으로 `export *`를 사용하지 않습니다.

## 17. Test, Story, Fixture Naming

Vitest 일반 Test:

```txt
*.test.ts
*.test.tsx
```

Integration Test:

```txt
*.integration.test.ts
*.integration.test.tsx
```

Playwright E2E:

```txt
*.spec.ts
```

Storybook:

```txt
*.stories.tsx
```

파일의 실제 위치와 Test Level 선택은 `12_테스트_전략.md`, Story 작성 대상은 `13_스토리북.md`를 따릅니다.

Test Fixture Builder는:

```txt
build<Domain>Fixture
```

형태를 사용합니다.

```txt
buildUserFixture
buildOrderFixture
buildProductFixture
```

지양:

```txt
createMockUser
createMockOrder
getMockUser
```

실제 Mock Function이나 Mocked API에는 `mock` Prefix를 사용할 수 있습니다.

```txt
mockFindUserByIdRepository

mockLoggerError

mockCreate

mockUpdate
```

일반 Domain Fixture 자체에는 `mock`을 붙이지 않습니다.

재현 가능한 Test에서는 고정된 날짜와 ID를 우선합니다.

```ts
const now = new Date("2026-01-01T00:00:00.000Z");
```

Randomness 자체가 Test 대상이 아니라면 불필요한 Random Fixture를 만들지 않습니다.

## 18. Commit Convention

Commit Message의 기본 형식:

```txt
<type>: <summary>
```

필요한 경우 Scope를 사용할 수 있습니다.

```txt
<type>(<scope>): <summary>
```

예:

```txt
feat: 주문 취소 기능 추가

fix(auth): 세션 만료 처리 수정

refactor(generator): Domain Generator export 구조 정리

docs: 테스트 전략 문서 수정

test: 주문 repository integration test 추가
```

기본 Type:

```txt
feat
  새로운 기능

fix
  기존 동작 오류 수정

refactor
  외부 동작을 바꾸지 않는 구조 개선

docs
  문서 변경

test
  Production 동작 변경 없는 Test 작업

chore
  일반 유지보수

build
  Build System 또는 Dependency 구성

ci
  CI Workflow

perf
  성능 개선

style
  Formatting 등 동작에 영향 없는 스타일 변경

revert
  기존 Commit 되돌림
```

Summary는 무엇을 변경했는지 알 수 있도록 작성합니다.

지양:

```txt
feat: 기능 추가

fix: 수정

chore: 작업
```

Commit Summary에는 한국어를 사용할 수 있으며 Type과 Scope는 영문 Convention을 유지합니다.

```txt
feat(order): 주문 취소 기능 추가
```

Commit은 가능한 한 하나의 논리적인 변경 목적을 나타냅니다.

관계없는 변경을 한 Commit에 섞지 않습니다.

대규모 Formatting 변경도 실제 기능 변경과 불필요하게 섞지 않습니다.

Commit 전 검증 범위는 `16_개발_워크플로우.md`를 따릅니다.

## 19. Generator와 Convention

`pnpm generate`가 생성하는 코드도 이 문서의 Convention을 따라야 합니다.

```txt

디렉터리명

Component Export

Import 순서

Named Export

Type-only Export

Barrel 구조

Test 파일명

Story 파일명
```

Generator가 생성한 직후 Lint나 Formatter가 같은 부분을 반복적으로 대규모 수정한다면 Generator Template을 수정합니다.

## 21. 핵심 원칙

```txt
파일과 디렉터리는 기본적으로 kebab-case를 사용한다.

Custom Hook 파일은 Hook 이름과 동일한 camelCase를 사용한다.

Component와 Type은 PascalCase를 사용한다.

변수와 함수는 camelCase를 사용한다.

상수는 UPPER_SNAKE_CASE를 사용한다.

Component는 기본적으로 default export하고 Public Barrel에서 named export한다.

함수 이름은 실제 동작을 표현하는 동사를 사용한다.

단순 객체 구성에는 build를 사용한다.

설정 Definition에는 define을 사용한다.

정의된 작업이나 처리 흐름의 실행에는 execute를 사용한다.

최종 값을 결정할 때 resolve를 사용한다.

Raw Input 해석에는 parse를 사용한다.

동일 의미의 형태 정규화에는 normalize를 사용한다.

Presentation 변환에는 format을 사용한다.

외부 Resource를 읽을 때 load를 사용한다.

Boolean 함수는 is / has / can / should를 사용한다.

create는 실제 생성 Use Case나 Persistence 생성에 사용한다.

get은 Application 조회 Use Case 등 의미가 명확할 때 사용한다.

같은 Use Case의 Action과 Service는 같은 핵심 동사를 사용한다.

Repository 조회에는 기본적으로 find를 사용한다.

Business Meaning이 있는 동사를 단순 CRUD로 치환하지 않는다.

Domain Mapper는 to<Destination> 형태를 우선한다.

Permission은 can으로 시작한다.

Public API는 명시적인 Named Export를 사용한다.

Runtime에서 사용하지 않는 Type은 import type / export type을 사용한다.

다른 Slice와 Package는 Public API를 통해 사용한다.

같은 Slice 내부에서는 Relative Import를 사용할 수 있다.

Public Barrel에서는 export *를 기본적으로 사용하지 않는다.

client.ts에는 Browser-safe API만 공개한다.

server.ts에는 Server-only API만 공개한다.

일반 Test는 *.test.ts[x]를 사용한다.

Integration Test는 *.integration.test.ts[x]를 사용한다.

Playwright E2E는 *.spec.ts를 사용한다.

Story는 *.stories.tsx를 사용한다.

Fixture Builder에는 build...Fixture를 사용한다.

실제 Mock에는 mock Prefix를 사용할 수 있다.

Commit은 <type>: <summary> 형식을 기본으로 사용한다.

Commit 하나에는 가능한 한 하나의 논리적인 변경 목적을 담는다.

Generator Output도 실제 Convention과 일치해야 한다.

Convention 문서에서는 Architecture 자체의 책임을 다시 정의하지 않는다.
```
