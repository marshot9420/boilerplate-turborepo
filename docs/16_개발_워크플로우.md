# 개발 워크플로우

이 문서는 `boilerplate-turborepo`에서 일상적인 개발 작업에 사용하는 주요 명령어와 기능 구현의 기본 흐름을 설명합니다.

이 문서의 목적은 다음과 같습니다.

```txt
어떤 명령어를 언제 사용하는지 빠르게 확인한다.

기능 구현 전후의 기본 작업 순서를 통일한다.

Database, Test, Generator를 개발 흐름에서 언제 사용하는지 정리한다.

변경 범위에 맞는 검증 방법을 선택한다.
```

각 계층의 상세한 책임이나 Test 정책은 이 문서에서 다시 정의하지 않습니다.

관련 전문 문서를 함께 참고합니다.

```txt
05_의존성_경계.md
07_데이터베이스.md
08_도메인_레이어.md
09_서버_액션.md
10_앱_구조.md
12_테스트_전략.md
13_스토리북.md
14_코드_생성기.md
18_컨벤션.md
22_구현_안전성.md
```

## 1. 기본 개발 흐름

일반적인 기능 개발은 다음 흐름을 기준으로 합니다.

```txt
Issue / 요구사항 확인
  ↓
현재 구현과 영향 범위 확인
  ↓
필요한 계층 결정
  ↓
하위 책임부터 구현
  ↓
Application UI 연결
  ↓
관련 Test
  ↓
필요한 Story
  ↓
전체 검증
  ↓
실제 Application 확인
  ↓
Commit / PR
```

모든 기능이 모든 계층을 필요로 하는 것은 아닙니다.

예:

```txt
단순 UI 변경
  → UI
  → Component Test
  → 필요한 Story
  → 검증
```

```txt
Persistence가 필요한 Mutation
  → Prisma / Repository
  → Domain
  → Server Action
  → Feature / View
  → Test
  → 검증
```

핵심은 **현재 요구사항에 필요한 계층만 변경하는 것**입니다.

### 1.1 Issue 작성 원칙

Issue는 구현 결과를 미리 설명하는 문서가 아니라 **실제로 해결해야 하는 문제와 완료 조건을 정의하는 문서**입니다.

Issue에서는 다음 내용을 구분합니다.

```txt
현재 문제 또는 배경
  왜 이 작업이 필요한가?

목표
  어떤 상태를 달성해야 하는가?

작업 범위
  이번 Issue에서 다루는 영역은 어디까지인가?

완료 조건
  어떤 결과가 충족되면 완료로 판단할 수 있는가?

검증 항목
  완료 여부를 어떻게 확인할 것인가?
```

구현 방법 자체가 요구사항이 아니라면 특정 Package, Layer, Library, 함수 구조를 불필요하게 고정하지 않습니다. 구현자가 현재 Architecture와 Source를 확인한 뒤 적절한 방법을 선택할 수 있어야 합니다.

반대로 이미 결정된 Architecture나 기술적 제약이 있다면 명시적으로 작성합니다.

예:

```txt
기존 Database Constraint를 유지해야 한다.

외부 Provider API Contract를 변경할 수 없다.

현재 Public API와 하위 호환성을 유지해야 한다.
```

Issue에는 현재 문제와 직접 관계없는 작업을 함께 포함하지 않습니다. 하나의 Issue가 서로 독립적인 여러 변경 이유를 가진다면 별도 Issue로 분리할지 검토합니다.

완료 조건과 검증 항목은 실제 완료 여부를 판단할 수 있도록 Checklist로 작성합니다.

```txt
[ ] 요구된 Behavior가 충족되었다.

[ ] 의도한 작업 범위가 반영되었다.

[ ] 필요한 검증을 수행했다.
```

Issue 제목의 Type과 대소문자 규칙은 `18_컨벤션.md`를 따릅니다.

Repository의 `.github/ISSUE_TEMPLATE/*`는 작업 유형별 시작 형식을 제공하며, 공통 작성 원칙의 Source of Truth는 이 절입니다.

### 1.2 Pull Request 작성 원칙

Issue와 Pull Request의 역할을 다음처럼 구분합니다.

```txt
Issue
  무엇을 해결해야 하는가

Pull Request
  실제로 무엇을 변경했는가
```

PR 본문에는 현재 Diff에 실제로 구현된 내용만 작성합니다. Issue의 배경과 요구사항 전체를 그대로 반복하지 않고, 변경 결과와 Reviewer가 알아야 하는 구현 정보를 중심으로 정리합니다.

기본적으로 다음 내용을 구분합니다.

```txt
설명
  이번 PR이 실제로 변경한 결과

변경 사항
  주요 구현과 영향 영역

구조적 판단
  중요한 설계 결정 또는 의도적으로 선택한 구현 방향

검증
  실제로 실행하고 결과를 확인한 항목

제외 범위 / 후속 작업
  의도적으로 포함하지 않은 내용과 별도 작업이 필요한 항목

관련 Issue
  해결하거나 연결하는 Issue
```

구조적 판단이 단순하거나 별도 설명이 필요 없다면 형식적으로 내용을 만들지 않습니다.

검증 항목은 실제로 수행한 명령과 확인만 작성하거나 Check합니다. 실행하지 않은 Test나 검증을 완료한 것처럼 표시하지 않습니다.

현재 PR에서 제외한 범위와 아직 필요한 후속 작업은 완료된 변경과 명확하게 구분합니다. 관련 Issue는 `Closes #...`, `Fixes #...` 또는 Repository에서 사용하는 연결 방식으로 명시합니다.

PR 제목의 Type과 대소문자 규칙은 `18_컨벤션.md`를 따릅니다.

실제 작성 시 `.github/PULL_REQUEST_TEMPLATE.md`를 사용하며, 공통 작성 원칙의 Source of Truth는 이 절입니다.

## 2. 주요 명령어

| ------------------- | ----------------------------- |
| 개발 서버           | `pnpm dev`                    |

| Lint                | `pnpm lint`                   |

| Dependency Boundary | `pnpm check:boundaries`       |
| 전체 정적 검증      | `pnpm check`                  |
| 일반 Test           | `pnpm test`                   |
| Test Watch          | `pnpm test:watch`             |

## 3. 개발 서버와 Build

전체 Workspace의 개발 환경을 실행합니다.

```bash
pnpm dev
```

특정 Workspace만 실행해야 한다면 pnpm Filter를 사용할 수 있습니다.

```bash
pnpm --filter <workspace-name> dev
```

실제 Workspace Name은 해당 `package.json`을 기준으로 합니다.

Production Build 확인:

```bash
pnpm build
```

Build는 특히 다음과 같은 변경에서 확인할 가치가 있습니다.

```txt
App Router

Next.js Config

Environment

Package Export

Server / Client Boundary

Build Configuration

Deployment 관련 변경
```

작은 내부 로직 수정마다 반드시 Build를 실행할 필요는 없습니다.

## 4. 정적 검증

개별 검증 명령:

```bash
pnpm lint
pnpm check:boundaries
pnpm check-types
pnpm format:check
```

Lint 자동 수정:

```bash
pnpm lint:fix
```

Formatting 적용:

```bash
pnpm format
```

기능 구현이 끝난 뒤에는 일반적으로 다음 명령을 사용합니다.

```bash
pnpm check
```

현재 `pnpm check`는 다음 검증을 순차적으로 수행합니다.

```txt
lint
  ↓
check:boundaries
  ↓
check-types
  ↓
format:check
```

Dependency Boundary의 상세 기준은 `05_의존성_경계.md`를 따릅니다.

## 5. Test

일반 Test:

```bash
pnpm test
```

개발 중 반복 실행:

```bash
pnpm test:watch
```

Coverage 확인:

```bash
pnpm test:coverage
```

실제 Infrastructure Boundary를 검증해야 한다면:

```bash
pnpm test:integration
```

Watch Mode:

```bash
pnpm test:integration:watch
```

Browser User Flow 검증:

```bash
pnpm test:e2e
```

필요한 경우:

```bash
pnpm test:e2e:ui
pnpm test:e2e:headed
```

새로운 개발 환경에서 Playwright Browser가 없다면:

```bash
pnpm playwright:install
```

을 실행합니다.

현재 일반적인 `pnpm test:e2e` 흐름에서는 E2E Database의 Schema 반영과 Seed가 함께 수행됩니다.

어떤 변경에 Unit, Component, Integration, E2E Test가 필요한지는 `12_테스트_전략.md`를 따릅니다.

## 6. Database 명령어

주요 Database Command:

```txt
pnpm db:generate
  Prisma Client 생성

pnpm db:push
  현재 Prisma Schema를 개발 Database에 반영

pnpm db:migrate
  Migration 생성 및 적용

pnpm db:seed
  개발용 초기 데이터 삽입

pnpm db:studio
  Prisma Studio 실행
```

새로운 로컬 개발 환경을 준비하거나 Schema를 변경한 경우 일반적으로:

```bash
pnpm db:generate
pnpm db:push
```

를 사용합니다.

필요한 초기 데이터가 있다면:

```bash
pnpm db:seed
```

를 추가합니다.

Migration을 사용해야 하는 시점과 `db:push`의 구분은 `07_데이터베이스.md`를 따릅니다.

## 8. 코드 생성기

반복적인 Scaffold 생성에는 기존 Generator를 사용합니다.

```bash
pnpm generate
```

현재 Generator:

```txt
domain
component
entity
feature
view
```

예:

```bash
pnpm generate domain order
pnpm generate domain order --repository

pnpm generate entity order-status-badge \
  --app admin \
  --domain order

pnpm generate feature update-profile \
  --app web \
  --domain user \
  --ui update-profile-form

pnpm generate view order-detail-view \
  --app admin \
  --domain order
```

Generator는 필요한 구조를 빠르게 만드는 도구입니다.

생성 결과는 완성 코드가 아닙니다.

```txt
Generator 실행
  ↓
실제 요구사항에 맞게 구현
  ↓
불필요한 Scaffold 제거
  ↓
Test / Story 보완
```

모든 Generator Option과 생성 구조는 `14_코드_생성기.md`를 따릅니다.

## 9. 기능 구현 전 영향 범위 판단

새 기능을 구현하기 전에 다음 질문으로 변경 범위를 판단합니다.

```txt
새로운 Persistence가 필요한가?

새로운 Business Rule이 필요한가?

새로운 조회 Use Case가 필요한가?

새로운 Mutation이 필요한가?

새로운 Domain 표현 UI가 필요한가?

새로운 사용자 Interaction이 필요한가?

새로운 화면 조립이 필요한가?

새로운 Route가 필요한가?

같은 Mutation이 동시에 또는 중복 실행될 수 있는가?

외부 Side Effect와 Partial Failure가 존재하는가?

Retry나 Timeout 이후 결과가 불명확할 수 있는가?
```

이 판단에 따라 실제 필요한 계층만 구현합니다.

Concurrency, Idempotency, Partial Failure 같은 Runtime 위험이 있는 작업은 보호 수단을 구현하기 전에 Business Invariant와 실패 시나리오를 확인합니다. 상세한 구현 전 Checklist는 `22_구현_안전성.md`를 따릅니다.

예:

```txt
기존 상태를 보여주는 Badge
  → Entity

사용자 입력과 Mutation
  → Feature + Server Action + Domain

새로운 Page
  → View + App Router

새로운 영속 상태와 Business Rule
  → Prisma + Repository + Domain
```

## 10. 조회와 Mutation

일반적인 Server-side 조회는 다음 흐름을 따릅니다.

```txt
Repository
  ↓
Domain Service
  ↓
Server Component / View
  ↓
Entity
```

일반 조회를 위해 Server Action을 만들지 않습니다.

Mutation은 일반적으로 다음 흐름을 가집니다.

```txt
Repository
  ↓
Domain Permission / Rule
  ↓
Domain Service
  ↓
Server Action
  ↓
Feature
  ↓
View
```

Business Rule을 Server Action이나 UI에서 다시 구현하지 않습니다.

상세 책임은 `08_도메인_레이어.md`, `09_서버_액션.md`, `10_앱_구조.md`를 따릅니다.

## 11. Persistence가 포함된 기능

새로운 Database 상태까지 필요한 기능에서는 일반적으로 다음 순서를 사용합니다.

```txt
1. 요구사항과 Business Rule 확인

2. Prisma Schema 변경

3. pnpm db:generate

4. Repository 구현

5. Domain Rule / Permission / Service 구현

6. Mutation이라면 Server Action 구현

7. Entity / Feature / View 구현

8. App Router 연결

9. 관련 Unit / Component / Integration Test

10. 필요한 Story

11. 전체 검증
```

Database Schema를 개발 환경에 반영해야 한다면:

```bash
pnpm db:push
```

를 사용합니다.

Migration이 필요한 경우에는 `07_데이터베이스.md`의 정책을 따릅니다.

Domain과 Repository Scaffold가 동시에 필요하다면:

```bash
pnpm generate domain <domain-name> --repository
```

를 사용할 수 있습니다.

## 12. 구현 중 검증

모든 구현을 끝낸 뒤 한꺼번에 오류를 찾기보다 변경 지점 가까이에서 검증합니다.

예:

```txt
Prisma 변경
  → pnpm db:generate

Repository
  → 관련 Integration Test

Domain
  → 관련 Unit Test

UI
  → 관련 Component Test / Storybook

전체 구현
  → pnpm check
  → pnpm test
```

현재 작업과 관계없는 Test Suite를 매번 기계적으로 전부 실행할 필요는 없습니다.

## 13. 작업 유형별 기본 흐름

### Feature

```txt
요구사항 확인
  ↓
필요한 계층 판단
  ↓
구현
  ↓
관련 Test
  ↓
pnpm check
  ↓
실제 Application 확인
```

### Bug Fix

```txt
Bug 재현
  ↓
문제가 발생하는 책임 확인
  ↓
가능하면 실패 Test 작성
  ↓
수정
  ↓
관련 Test
  ↓
전체 검증
```

### Refactoring

```txt
현재 Behavior 확인
  ↓
Refactoring
  ↓
기존 Test
  ↓
pnpm check
```

Architecture나 Dependency 구조가 변경된다면 관련 문서와 Boundary도 함께 확인합니다.

### Documentation

문서만 변경했다면 Application Test 전체를 반드시 실행할 필요는 없습니다.

다만 다음과 같은 실제 구현을 함께 변경했다면 관련 검증을 수행합니다.

```txt
Generator

Package Script

Environment

Database Command

Config

Architecture Rule
```

## 14. 기능 완료 후 검증

기본적으로:

```bash
pnpm check
pnpm test
```

를 실행합니다.

변경 범위에 따라 다음 검증을 추가합니다.

```txt
실제 Persistence 변경
  → pnpm test:integration

Production Boundary 변경
  → pnpm build

주요 Browser User Flow 변경
  → pnpm test:e2e
```

예:

```bash
pnpm check
pnpm test
pnpm test:integration
pnpm build
pnpm test:e2e
```

위 명령을 모든 변경에서 전부 실행해야 한다는 의미는 아닙니다.

**변경 범위에 필요한 검증만 추가합니다.**

---

## 15. 완료 기준

기능 구현을 마치기 전에 다음을 확인합니다.

```txt
요구사항이 구현되었는가?

Business Rule이 올바른 계층에 있는가?

불필요한 계층이나 추상화를 만들지 않았는가?

Server / Client Boundary가 올바른가?

Package Dependency Boundary가 올바른가?

필요한 Test가 작성되었는가?

필요한 Story가 작성되었는가?

pnpm check가 통과하는가?

관련 Test가 통과하는가?

실제 Application에서 필요한 동작을 확인했는가?

동시 실행, 중복 요청, Partial Failure에서 Business Invariant가 유지되는가?
```

Database 변경이 있다면 추가로 확인합니다.

```txt
Prisma Client가 최신인가?

Schema가 필요한 환경에 반영되었는가?

실제 Persistence Behavior가 필요한 수준에서 검증되었는가?
```

Commit Naming은 `18_컨벤션.md`를 따릅니다.

---

## 16. 기타 명령

Build Output이나 Cache를 정리해야 하는 경우:

```bash
pnpm clean
```

을 사용할 수 있습니다.

이 명령은 `node_modules` 등도 제거할 수 있으므로 일반적인 개발 과정에서 습관적으로 실행하지 않습니다.

Scripts Package의 정리만 필요한 경우:

```bash
pnpm scripts:clean
```

을 사용할 수 있습니다.

## 18. 핵심 원칙

```txt
현재 요구사항에 필요한 계층만 변경한다.

Issue는 해결할 문제와 완료 조건을 정의한다.

PR은 실제로 변경한 내용과 수행한 검증을 설명한다.

변경 지점과 가까운 Test를 먼저 실행한다.

기능 완료 후 pnpm check와 관련 Test를 기본 검증으로 사용한다.

모든 변경에서 모든 Test를 기계적으로 실행하지 않는다.

Database 변경 후 Prisma Client를 최신 상태로 유지한다.

실제 Persistence Behavior가 중요하면 Integration Test로 검증한다.

중요한 Browser User Flow는 필요한 경우 E2E로 검증한다.

Production Boundary 변경은 Build로 확인한다.

반복 Scaffold는 Generator를 활용한다.

Generator Output을 완성 코드로 간주하지 않는다.

일반 조회를 위해 Server Action을 만들지 않는다.

Business Rule을 Server Action이나 UI에 중복 구현하지 않는다.

Mutation 구현 전 Concurrency, Idempotency, Partial Failure 위험을 검토한다.

구현이 끝나면 실제 Application에서도 필요한 동작을 확인한다.

검증 범위는 현재 변경의 영향 범위에 맞게 결정한다.
```
