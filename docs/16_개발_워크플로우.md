# 개발 워크플로우

이 문서는 `boilerplate-turborepo`에서 일상적인 개발 작업을 진행할 때 사용하는 명령어와 기본 작업 순서를 설명합니다.

이 문서의 목적은 다음과 같습니다.

```txt
어떤 명령어를 언제 사용하는지 빠르게 확인한다.

기능 개발 전후의 기본 검증 순서를 통일한다.

Database 작업과 Application 작업의 순서를 명확히 한다.

Generator를 실제 개발 흐름에 자연스럽게 사용한다.

새로운 기능을 어느 계층부터 구현할지 기준을 제공한다.
```

Architecture 자체의 세부 책임은 이 문서에서 반복하지 않습니다.

```txt
08_도메인_레이어.md
09_Server_Actions.md
10_앱_구조.md
12_테스트_전략.md
14_코드_생성기.md
18_컨벤션.md
```

를 함께 참고합니다.

---

## 1. 기본 개발 흐름

일반적인 기능 개발은 다음 순서를 기본으로 합니다.

```txt
Issue / 요구사항 확인
  ↓
영향 범위 확인
  ↓
필요한 Domain / Database 변경
  ↓
Application Boundary 구현
  ↓
Entity / Feature / View 구현
  ↓
App Router 연결
  ↓
Unit / Integration / Component Test
  ↓
필요한 Story 작성
  ↓
Lint / Boundary / Type / Format 검증
  ↓
필요한 E2E 검증
  ↓
Commit / PR
```

모든 기능이 위의 모든 계층을 필요로 하는 것은 아닙니다.

예를 들어 단순 UI 수정이라면:

```txt
Design System 또는 App UI
  ↓
Component Test
  ↓
Story
  ↓
검증
```

정도로 끝날 수 있습니다.

반대로 새로운 Persistence가 필요한 Business Feature라면:

```txt
Prisma
  ↓
Repository
  ↓
Domain
  ↓
Server Action
  ↓
Feature
  ↓
View
  ↓
App Router
```

까지 이어질 수 있습니다.

핵심은 **실제 변경에 필요한 계층만 수정하는 것**입니다.

# 2. 주요 명령어

루트 `package.json`에서 일상적인 개발에 사용하는 주요 명령은 다음과 같습니다.

```txt
개발
  pnpm dev

Build
  pnpm build

Lint
  pnpm lint
  pnpm lint:fix

Type Check
  pnpm check-types

Format
  pnpm format
  pnpm format:check

전체 정적 검증
  pnpm check

Unit / Component Test
  pnpm test
  pnpm test:watch
  pnpm test:coverage

Integration Test
  pnpm test:integration
  pnpm test:integration:watch

E2E
  pnpm test:e2e
  pnpm test:e2e:ui
  pnpm test:e2e:headed

Database
  pnpm db:generate
  pnpm db:push
  pnpm db:migrate
  pnpm db:seed
  pnpm db:studio

Generator
  pnpm generate
```

# 3. 개발 서버

전체 Workspace의 개발 서버를 실행합니다.

```bash
pnpm dev
```

내부적으로 Turborepo의:

```txt
turbo run dev
```

를 실행합니다.

각 Workspace Package 또는 App에 정의된 `dev` Task가 실행됩니다.

일반적으로 다음과 같은 상황에서 사용합니다.

```txt
UI 구현 확인

Server Component 확인

Server Action 확인

Database 연동 확인

App Router 확인

실제 Browser Flow 확인
```

기능을 구현한 뒤에는 Test만 확인하지 말고 실제 Application에서도 필요한 동작을 확인합니다.

---

# 4. 특정 App만 실행

필요한 경우 pnpm Filter를 사용하여 특정 Workspace만 실행할 수 있습니다.

예:

```bash
pnpm --filter @repo/web dev
```

또는 프로젝트 Scope를 변경한 경우:

```bash
pnpm --filter @athena/web dev
```

처럼 현재 Workspace Package Name을 사용합니다.

실제 Package Name은 각 App의 `package.json`을 기준으로 합니다.

---

# 5. Build

전체 Workspace의 Production Build를 확인합니다.

```bash
pnpm build
```

내부:

```txt
turbo run build
```

Build는 다음과 같은 문제를 확인하는 데 중요합니다.

```txt
Next.js Production Build 오류

Server / Client Boundary 오류

환경변수 누락

잘못된 Dynamic / Static Rendering 설정

Package Export 오류

Build 시점 Type 또는 Module Resolution 문제
```

일상적인 작은 수정마다 반드시 실행할 필요는 없지만 다음 경우에는 실행하는 것을 권장합니다.

```txt
PR 완료 전

App Router 구조 변경

Package Export 변경

Environment 변경

Build Configuration 변경

Deployment 관련 변경

Server / Client Boundary 변경
```

---

# 6. Lint

전체 Workspace의 Lint를 실행합니다.

```bash
pnpm lint
```

내부:

```txt
turbo run lint
```

Lint Error를 자동 수정할 수 있는 경우:

```bash
pnpm lint:fix
```

을 사용합니다.

Lint는 단순 Formatting뿐 아니라 다음 규칙을 포함할 수 있습니다.

```txt
Import 정렬

Type-only Import

React Rule

Unused Code

Package별 ESLint Rule

프로젝트 Convention
```

자동 수정 후에는 변경 내용을 확인합니다.

---

# 7. Type Check

전체 Workspace의 TypeScript 검사를 수행합니다.

```bash
pnpm check-types
```

내부:

```txt
turbo run check-types
```

다음과 같은 변경 후에는 특히 확인합니다.

```txt
Domain DTO 변경

Schema Input Type 변경

Repository Return Type 변경

Server Action Response 변경

Component Props 변경

Package Export 변경

Prisma Client 변경
```

Type Error를 `as`나 불필요한 Type Assertion으로 숨기기 전에 실제 계약이 올바른지 확인합니다.

---

# 8. Format

전체 프로젝트의 지원 대상 파일을 Format합니다.

```bash
pnpm format
```

현재 대상에는 다음 확장자가 포함됩니다.

```txt
ts
tsx
js
jsx
mjs
cjs
json
jsonc
css
scss
yml
yaml
```

Formatting이 필요한지 확인만 하려면:

```bash
pnpm format:check
```

를 사용합니다.

Generator Template 역시 생성 후 Formatter가 대규모로 코드를 변경하지 않도록 현재 Format Convention을 따라야 합니다.

# 9. Dependency Boundary 검사

Package Dependency Boundary를 확인합니다.

```bash
pnpm check:boundaries
```

대표적으로 다음과 같은 문제를 탐지합니다.

```txt
허용되지 않은 Package Dependency

상위 계층에서 하위 책임 침범

Package 간 잘못된 Runtime Dependency
```

구체적인 Boundary는 `05_의존성_경계.md`를 따릅니다.

# 10. 전체 정적 검증

```bash
pnpm check
```

```txt
pnpm lint

  ↓
pnpm check-types

pnpm format:check
```

따라서 다음 네 항목을 한 번에 확인할 수 있습니다.

```txt

Dependency Boundary

TypeScript

Formatting
```

일반적인 기능 개발 완료 후에는:

```bash
pnpm check
```

를 기본 검증 명령으로 사용합니다.

# 13. Coverage

Coverage를 확인하려면:

```bash
pnpm test:coverage
```

를 사용합니다.

Coverage는 누락된 테스트 영역을 찾기 위한 보조 지표입니다.

Coverage 수치 자체를 목표로 삼아 의미 없는 테스트를 추가하지 않습니다.

세부 정책은 `12_테스트_전략.md`를 따릅니다.

# 14. Integration Test

Integration Test를 실행합니다.

```bash
pnpm test:integration
```

Watch Mode:

```bash
pnpm test:integration:watch
```

대표적인 대상:

```txt
Repository

Database Constraint

Transaction

실제 Persistence

외부 Infrastructure Adapter
```

Repository의 실제 Database 동작을 확인해야 한다면 Mock Test만으로 끝내지 않고 Integration Test를 사용합니다.

# 15. E2E Test

전체 E2E Test:

```bash
pnpm test:e2e
```

현재 실행 과정에는 E2E Database 준비가 포함됩니다.

```txt
pnpm db:e2e:push
  ↓
pnpm db:e2e:seed
  ↓
turbo run test:e2e
```

즉 일반적인 E2E 실행에서는 별도로 Seed를 먼저 실행할 필요가 없습니다.

Prisma Schema 변경 후:

```bash
pnpm db:generate
```

를 실행합니다.

대표적인 변경:

```txt
Model 추가

Field 추가

Enum 추가

Relation 변경

Index 변경
```

# 18. Database Schema 반영

개발 Database에 현재 Schema를 반영하려면:

```bash
pnpm db:push
```

를 사용합니다.

새로운 로컬 Database를 처음 준비할 때도 사용할 수 있습니다.

```txt
schema.prisma
  ↓
pnpm db:push
  ↓
Development Database
```

# 19. Migration

변경 사항을 Migration History로 남겨야 한다면:

```bash
pnpm db:migrate
```

를 사용합니다.

`db:push`와 Migration의 용도는 다릅니다.

```txt
db:push
  현재 Schema 빠른 동기화

db:migrate
  Schema 변경 이력 생성 및 관리
```

구체적인 Database 정책은 `07_데이터베이스.md`를 따릅니다.

# 20. Seed

# 23. E2E Database

E2E Database 관련 명령:

```bash
pnpm db:e2e:generate
pnpm db:e2e:push
pnpm db:e2e:migrate

```

이 명령들은 `E2E=true` 환경으로 Database 및 Seed Script를 실행합니다.

# 24. Database 변경 기본 흐름

새로운 Model이나 Persistence 변경이 있다면 다음 흐름을 기본으로 합니다.

```txt
Prisma Schema 수정
  ↓
pnpm db:generate
  ↓
Database 반영
  ↓
Repository 구현
  ↓
Repository Unit Test
  ↓
Repository Integration Test
```

개발 Database에 빠르게 반영한다면:

```bash
pnpm db:push
```

Migration이 필요한 변경이라면:

```bash
pnpm db:migrate
```

를 사용합니다.


# 26. Domain Generator

새 Domain:

```bash
pnpm generate domain order
```

Persistence까지 필요한 경우:

```bash
pnpm generate domain order --repository
```

`--repository`를 사용하면 Domain Scaffold와 함께 Database Repository 관련 Scaffold도 생성합니다.

생성된 코드는 완성된 Business Logic이 아니라 시작점입니다.

```txt
생성
  ↓
실제 Domain 요구사항 반영
  ↓
필요 없는 파일 제거
  ↓
필요한 Rule / Service / Query 추가
```

# 31. Generator 사용 시점

Generator는 **구조가 필요한 시점에 사용합니다.**

예를 들어 새로운 `order` 기능을 만든다고 해서 처음부터:

```txt
domain
entity
feature
view
```

를 전부 기계적으로 생성하지 않습니다.

필요한 구조만 생성합니다.

예:

```txt
Domain이 이미 있음
  → domain generator 사용 안 함

기존 Entity로 충분함
  → entity generator 사용 안 함

새로운 사용자 Action 필요
  → feature generator 사용

새 화면 필요
  → view generator 사용
```

Generator의 목적은 Architecture를 강제하기보다 반복 작업을 줄이는 것입니다.

# 33. 새로운 기능 구현 전 확인

구현을 시작하기 전에 요구사항을 다음 관점으로 나눕니다.

```txt
새로운 Database 상태가 필요한가?

새로운 Domain Rule이 필요한가?

새로운 조회 Use Case가 필요한가?

새로운 Mutation이 필요한가?

새로운 사용자 Interaction이 필요한가?

새로운 Domain 표현 UI가 필요한가?

새로운 화면 조립이 필요한가?

새로운 Route가 필요한가?
```

이 질문에 따라 필요한 계층을 결정합니다.

---

# 34. Persistence가 없는 기능

Database 변경이 필요 없는 기능은 Database부터 시작하지 않습니다.

예:

```txt
기존 User 상태를 보여주는 Badge 추가
```

필요한 흐름:

```txt
Entity
  ↓
Component Test
  ↓
Story
```

정도로 끝날 수 있습니다.

---

# 35. 새로운 Domain이 필요한 기능

새로운 Business Concept이 추가된다면 Domain부터 정의합니다.

예:

```txt
Order Claim
```

기본 흐름:

```txt
Domain Constant / Schema / DTO
  ↓
Permission / Rule
  ↓
Mapper
  ↓
Service
```

Persistence가 필요하다면 Database 흐름을 함께 추가합니다.

---

# 36. 새로운 Database Model이 필요한 기능

새로운 Persistence가 필요하다면 다음 순서를 권장합니다.

```txt
Prisma Model
  ↓
Prisma Client Generate
  ↓
Repository
  ↓
Repository Test
  ↓
Domain Service
```

예:

```bash
pnpm db:generate
```

이후 필요한 Repository를 구현합니다.

Domain과 Repository Scaffold를 함께 시작한다면:

```bash
pnpm generate domain order-claim --repository
```

를 사용할 수 있습니다.

생성된 Repository는 실제 Prisma Model에 맞게 수정합니다.

# 37. 조회 기능 구현 순서

일반 조회 Use Case는 다음 흐름을 따릅니다.

```txt
Repository
  ↓
Domain Service
  ↓
View 또는 Server Component
  ↓
Entity
  ↓
App Router
```

일반적인 조회를 위해 Server Action을 추가하지 않습니다.

예:

```txt
Page / View
  ↓
getOrdersService
  ↓
findOrdersRepository
```

조회 Boundary 기준은 `09_Server_Actions.md`를 따릅니다.

---

# 38. Mutation 기능 구현 순서

사용자가 데이터를 변경하는 기능은 일반적으로 다음 흐름을 가집니다.

```txt
Repository
  ↓
Domain Rule / Permission
  ↓
Domain Service
  ↓
Server Action
  ↓
Feature
  ↓
View
  ↓
App Router
```

예:

```txt
주문 취소

cancelOrderRepository 또는 필요한 Persistence
  ↓
canCancelOrder / Order Rule
  ↓
cancelOrderService
  ↓
cancelOrderAction
  ↓
CancelOrderDialog
  ↓
OrderDetailView
```

Business Rule을 Feature나 Server Action에 중복해서 구현하지 않습니다.

# 39. 새로운 기능의 권장 구현 순서

Persistence를 포함하는 일반적인 신규 기능에서는 다음 순서를 권장합니다.

### 1. 요구사항과 상태 정의

먼저 다음을 확정합니다.

```txt
누가 사용할 수 있는가?

어떤 상태에서 가능한가?

입력은 무엇인가?

결과는 무엇인가?

어떤 실패가 가능한가?

Database 변경이 필요한가?
```

---

### 2. Prisma 변경

필요한 경우:

```txt
Model
Enum
Relation
Constraint
Index
```

를 정의합니다.

그 후:

```bash
pnpm db:generate
```

를 실행합니다.

---

### 3. Repository 구현

필요한 Persistence Operation만 구현합니다.

```txt
create
find
update
delete
count
```

등을 실제 Use Case에 맞게 작성합니다.

CRUD를 미리 모두 만들지 않습니다.

---

### 4. Repository Test

필요에 따라:

```txt
Repository Unit Test
Repository Integration Test
```

를 작성합니다.

실제 Persistence Behavior가 중요하면 Integration Test로 검증합니다.

---

### 5. Domain 구현

필요한 역할을 구현합니다.

```txt
constant
schema
DTO
error
permission
rule
mapper
service
```

모든 파일이 항상 필요한 것은 아닙니다.

---

### 6. Domain Unit Test

다음과 같은 책임을 검증합니다.

```txt
Schema

Permission

Rule

Mapper

Service
```

Domain Unit Test는 Domain Slice의 `test/`에 둡니다.

---

### 7. Server Action

Mutation이 있다면 Server Action을 구현합니다.

주요 책임:

```txt
Auth

FormData / Input 해석

Structural Validation

Domain Service 호출

Result → ActionResult 변환

Cache Invalidation

필요한 Navigation
```

Business Rule을 다시 구현하지 않습니다.

---

### 8. Entity

새로운 Domain 표현 UI가 필요하다면 Entity를 구현합니다.

예:

```txt

Summary
Table
Detail
Card
```

---

### 9. Feature

사용자가 수행하는 행위를 구현합니다.

예:

```txt
Form
Dialog
Button
Client Validation
Server Action 연결
Toast
router.refresh()
```

---

### 10. View

화면 단위의 조립을 구현합니다.

```txt
조회 결과
Entity
Feature
Pagination
Filter
Empty State
Error State
```

등을 조립합니다.

---

### 11. App Router

마지막으로 Route와 실제 View를 연결합니다.

Page에서는 가능한 한 Routing Boundary와 조립에 집중합니다.

구체적인 App 구조는 `10_앱_구조.md`를 따릅니다.

---

### 12. Test와 Story 보완

구현 범위에 따라:

```txt
Unit Test
Component Test
Integration Test
Story
E2E
```

를 추가합니다.

모든 Component에 Story를 만들거나 모든 기능에 E2E를 추가하는 것이 목적은 아닙니다.

각 테스트와 Story의 기준은 전문 문서를 따릅니다.

# 56. 핵심 원칙

```txt
개발 중에는 변경 지점과 가까운 테스트를 먼저 실행한다.

기능 완료 후 pnpm check와 관련 Test를 기본 검증으로 사용한다.

모든 변경에서 모든 Test를 기계적으로 실행할 필요는 없다.

Database 변경이 있으면 Prisma Client를 최신 상태로 만든다.

실제 Persistence Behavior는 Integration Test로 검증한다.

주요 User Flow는 필요할 때 E2E로 검증한다.

Production Boundary 변경은 Build로 확인한다.

Generator는 필요한 구조만 생성한다.

Generator가 만든 Scaffold를 완성 코드로 간주하지 않는다.

새 기능은 필요한 가장 아래 책임부터 위쪽 조립 계층으로 구현한다.

조회는 일반적으로 Repository → Service → Server Component 흐름을 따른다.

Mutation은 Repository → Domain → Server Action → Feature 흐름을 따른다.

Business Rule을 Server Action이나 UI에 중복 구현하지 않는다.

App Router는 가능한 한 Routing과 최종 조립에 집중한다.

기능 개발이 끝난 뒤 실제 Application에서도 동작을 확인한다.

Commit과 PR 전에는 변경 범위에 맞는 검증을 수행한다.
```
